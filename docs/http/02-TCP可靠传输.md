# 第 02 章 · TCP 可靠传输：三次握手、四次挥手、序列号

> 第 01 章你"随手"就建起了一条 TCP 连接，还发了数据。但你有没有想过一个问题：**数据在网络上走，中间经过无数路由器，凭什么不丢、不乱、不重复？**
>
> 本章你需要记住的就一件事：**TCP 的"可靠"不是运气，是用"序列号 + 确认号 + 重传 + 校验"这四件套硬造出来的。建立连接要三次握手，断开连接要四次挥手。**
>
> 这一条想清楚了，后面你会反复遇到它：HTTP 为什么敢是纯文本、HTTPS 为什么"加一层"就行、HTTP/3 为什么要换掉 TCP——全都跟 TCP 的这些特性有关。

---

## 02.1 先问：凭什么可靠？网络本来是不可靠的

**先说结论**：TCP 下层是 IP，而 **IP 是"尽力而为"（best-effort）的**——它只负责"尽量把包送到"，**不保证**送到、不保证顺序、不保证不重复。

先把这个残酷的事实摆清楚。你发一个数据包，从北京到广州，中间可能经过十几个路由器。每一个环节都可能出问题：

| 可能发生的事 | 后果 |
|---|---|
| 路由器忙不过来，把包**丢了** | 数据缺失 |
| 两个包走了**不同的路**，后发的先到了 | 顺序错乱 |
| 网络拥堵，包**绕了远路**，超时才到 | 你以为丢了，其实只是慢 |
| 一个包被**重复转发** | 数据重复 |
| 数据在传输中**被电磁干扰改坏了** | 内容损坏 |

**IP 层对这些统统不管。** 它只做一件事：看目标 IP，把包往正确的方向转发。丢了就丢了，它不重发。

**那 TCP 凭什么能"可靠"？** 因为 TCP 在 IP 之上，**自己额外搭了一层机制**，把上面这些坑一个个填上。这层机制的核心，就是本章的主角：**序列号（sequence number）和确认号（acknowledgment number）**。

理解了这个前提，你就能明白：**TCP 的"可靠"是花钱买来的**（要多发很多控制报文、要等确认），这正是它比 UDP 慢的原因。第 07 章讲 HTTP/3 时会回到这个代价上。

> 一句话记住它：IP 层是"尽力而为"，会丢、会乱、会重；TCP 在它之上用"序列号 + 确认号"自己造出了可靠。

## 02.2 三次握手：建立连接的三次对话

**先说结论**：一条 TCP 连接建立之前，双方要先互相"确认三件事"——我能发、你能收、你也能发。这个过程就是三次握手（three-way handshake）。

**为什么要握手？** 因为连接建立的本质是：**双方各自确认"我的发送能力"和"你的接收能力"都是好的**，并且就"从哪里开始编序列号"达成一致。

三次握手的具体过程（`SYN` 和 `ACK` 是 TCP 头里的标志位）：

```text
客户端                                  服务器
  │                                        │
  │ ── ① SYN（"我想连你，我的起始序号是 x"）──→ │
  │                                        │
  │ ← ② SYN+ACK（"好，我同意。我的序号是 y，│
  │        我收到了你的 x"）── │
  │                                        │
  │ ── ③ ACK（"收到你的 y，咱们开始吧"）──→ │
  │                                        │
  │          （连接建立，开始传数据）          │
```

**每一步在干什么，拆开看：**

| 步 | 报文 | 客户端明白了什么 | 服务器明白了什么 |
|---|---|---|---|
| ① | SYN | —— | "有人要连我，他的起始序号是 x" |
| ② | SYN+ACK | "服务器同意了，且能收我的数据" | —— |
| ③ | ACK | "连接正式建立" | "客户端也收到我的序号 y 了" |

**为什么偏偏是三次，不是两次、不是四次？**

这是面试高频题。答案是：**三次恰好能让双方都确认"自己的发送 + 对方的接收"都正常，同时避免"失效的连接请求"造成浪费。**

- **为什么不是两次？** 如果客户端发 SYN、服务器回 SYN+ACK 就完事，那**服务器没法确认**"客户端真的收到了我的 SYN+ACK"。万一客户端的 ACK 丢了，服务器以为连上了、开始傻等，客户端却已经放弃——服务器资源就白白浪费。所以需要第 ③ 步让客户端回一个 ACK 确认。
- **为什么不是四次？** 因为第 ② 步里，服务器把"对客户端 SYN 的确认（ACK）"和"自己的 SYN"**合并到一个报文**里发出去了（SYN+ACK）。如果拆开，就变成四次了。合并是允许的，也是常见的。

**关键洞察**：三次握手的本质是**交换双方的初始序列号**。第 ① 步客户端告诉服务器"我从 x 开始编号"，第 ② 步服务器告诉客户端"我从 y 开始编号"，第 ③ 步双方都确认了对方的初始序号。有了共同的"起跑线"，后面才能谈"哪些字节到了、哪些没到"。

> 一句话记住它：三次握手 = 双方交换初始序列号 + 各自确认"我能发、你能收"；三次是"既能双向确认、又不浪费"的最小次数。

## 02.3 序列号与确认号：可靠性的地基

**先说结论**：TCP 把要发送的数据**按字节编号**。序列号（seq）是"我这个包从第几个字节开始"，确认号（ack）是"我已经收到第几个字节了，请从下一个开始发"。这一对数字，是"可靠"的全部秘密。

**为什么按字节编号，不按"包"编号？** 因为数据可能被任意切分。你 `write('你好服务器')`，TCP 可能把它切成 3 个包发，也可能切成 1 个。按"包"编号没有稳定意义，按**字节**编号才是唯一确定的。

想象你要发送 "HELLO" 这 5 个字节（假设起始序号是 100）：

```text
字节:     H  E  L  L  O
序号:   100 101 102 103 104
```

**发送方**：把这段数据切成若干段，每段报一个 seq（这段从哪个字节开始）。

**接收方**：每收到一段，回一个 ack，值是"**我期待的下一个字节序号**"。

举一个具体的对话例子：

```text
发送方                               接收方
  │  seq=100, 数据="HEL"  ──────────→ │  收到 100~102
  │                                    │
  │  ←────────── ack=103（"我收到 102 了，请从 103 开始发"）
  │                                    │
  │  seq=103, 数据="LO"  ───────────→  │  收到 103~104
  │                                    │
  │  ←────────── ack=105（"收到 104 了"）
```

**看明白了吗？ack 值永远等于"已收到的最大序号 + 1"**，意思是"下一个该发这个字节了"。

**这个机制怎么解决三大问题的？**

1. **丢包**：如果发送方发了 seq=103，很久没等到 ack=105，就知道"103 之后的丢了"，重发。
2. **乱序**：如果接收方先收到 seq=106、后收到 seq=103，它一看序号不对，就知道"103~105 还没到"，先把 106 暂存，等 103 到了再按顺序上交。
3. **重复**：如果同一个 seq=103 收到两次，接收方一看"这个序号我收过了"，直接丢掉。

**一个必须澄清的误区**：很多人以为 TCP 是"每发一个字节就等一个 ack"。**不是**。TCP 用**累积确认**——ack=105 表示"105 之前的所有字节我都收到了"，不是"我只收到了 104 这一个"。这样就不必每字节回一个 ack，效率高得多。

> 一句话记住它：序列号按字节编号，确认号是"期待的下一个字节序号"；丢包靠"没等到 ack"发现，乱序靠"序号不对"发现，重复靠"序号收过"发现。

## 02.4 重传：丢了怎么办

**先说结论**：发送方发出去一段数据，会启动一个计时器。如果在"超时时间"内没等到对应的 ack，就认为丢了，**重发一次**。这个超时叫 **RTO（Retransmission Timeout，重传超时）**。

**为什么必须靠"超时"判断丢包？** 因为网络上没有一个"你的包丢了"的通知。发送方只能靠"我等了这么久，你还没确认"，**推断**它丢了。

**这里有个微妙的点：超时时间设多长？**

- 设太短：网络稍微慢一点（没丢，只是堵车），你就以为丢了、疯狂重发，把网络堵得更死。
- 设太长：真的丢了，也要等很久才重发，卡顿明显。

所以 TCP 的 RTO 是**动态算出来的**：它会根据这段时间网络的往返时间（RTT）自动调整。网络快就设短，网络慢就设长。这套自适应算法（Jacobson/Karels 算法）是 TCP 可靠性的又一块基石。

**除了超时重传，还有一个更聪明的机制——快速重传（Fast Retransmit）：**

超时重传要等 RTO，比较慢。快速重传利用了"**重复 ack**"这个信号：

```text
发送方发了 seq=100、103、106、109 四个包
假设 seq=103 丢了，后面 106、109 反而到了

接收方每收到一个"乱序"的包，都会回一个 ack=103（因为 103 还没到，它一直期待 103）
于是发送方会连续收到 3 个 ack=103
```

**规则：发送方收到同一个 ack 三次，就认为那个字节真的丢了，立刻重发，不等超时。** 这比傻等 RTO 快得多。

**这些机制对你的意义**：你写 `socket.write(data)` 的时候，所有这些重传、超时、重复 ack 都在内核里**自动发生**，你一行都不用管。这也是第 01 章说的"站在巨人的肩膀上"——TCP 的可靠性，是内核里几万行 C 代码帮你扛的。

> 一句话记住它：丢包靠"超时没等到 ack"发现，超时重传；收到 3 个重复 ack 就快速重传——这些都在内核自动发生，你只需信任 `write`。

## 02.5 乱序与重复：序号怎么摆平它们

**先说结论**：乱序靠"序号排序"，重复靠"序号去重"。接收方手里维护一个"滑动窗口"，没到的字节先缺着，到了再按序上交。

**乱序是怎么发生的？** 因为数据包可能走不同的路由。你发了 1、2、3 三个包，网络可能让 2 号包走了一条堵车的路，结果 1 和 3 先到了。

**接收方怎么处理？** 它不会"来一个交一个"，而是维护一个**按序号排序的缓冲区**：

```text
接收方期待序号 100（下一个要交上去的是 100）

先收到 seq=106 → 不对，期待的是 100，先暂存 [106]
又收到 seq=100 → 对了！上交 100，接着看暂存区
再收到 seq=103 → 上交 100 后期待 103，正好！上交 103，期待 106
暂存区有 106 → 上交 106
```

**于是，不管网络怎么乱，上交到应用层的数据永远是按序号排好的。** 这就是为什么第 01 章的 echo 服务器里，你写 `write('第一句')`、`write('第二句')`，对方收到的字节顺序永远是对的。

**重复是怎么发生的？** 可能是路由器重复转发了，也可能是超时重传时"其实没丢，只是慢"，导致接收方收到两份。

**接收方怎么处理？** 很简单：**每个序号只收一次**。如果收到一个已经收过的序号，直接丢掉。因为"序号"本身就是唯一标识，重复的序号 = 重复的字节。

**把三节串起来，就是 TCP 可靠性的完整闭环：**

| 问题 | 靠什么解决 |
|---|---|
| 丢包 | 超时重传 + 快速重传（收到 3 个重复 ack） |
| 乱序 | 序号排序，接收缓冲区按序号上交 |
| 重复 | 序号去重，重复序号直接丢 |
| 损坏 | 校验和（checksum），对不上就丢，当成丢包重传 |

> 一句话记住它：TCP 用一个按序号排序的接收缓冲区，把"乱序"排正、把"重复"丢掉，交到你手里的永远是正确顺序的字节流。

## 02.6 四次挥手：优雅断开

**先说结论**：建立连接要三次握手，断开连接要**四次挥手**。因为 TCP 是**双向**的，两个方向要**各自独立关闭**，所以比握手多一次。

**为什么断开比建立多一次？** 建立时，第 ② 步能把 ACK 和 SYN 合并成一个包（SYN+ACK）。但断开时，**往往一方说"我不发了"，另一方却还有数据要发**，没法合并，只能分四步。

四次挥手的过程（`FIN` 是"我发完了"的标志）：

```text
客户端                                  服务器
  │                                        │
  │ ── ① FIN（"我说完了，不再发数据"）──→ │
  │                                        │
  │ ← ② ACK（"知道了"）─────── │
  │                                        │
  │        （服务器可能还有数据要发）          │
  │ ← ③ FIN（"我也说完了"）─────── │
  │                                        │
  │ ── ④ ACK（"知道了，再见"）──→ │
  │                                        │
  │              （连接彻底关闭）              │
```

**为什么第 ② 步和第 ③ 步不能合并？** 因为服务器收到"客户端不发了"之后，可能**自己还有数据没发完**（比如还有最后一点响应要发）。它要先回个 ACK（第 ② 步）告诉客户端"收到你的 FIN 了"，然后**继续发自己的数据**，等自己发完了，再发 FIN（第 ③ 步）。这两件事之间有"服务器继续发数据"的时间间隔，所以不能合并。

**回到第 01 章的 `end` 和 `close`，你现在能彻底理解它们了：**

| Node 事件/方法 | 对应 TCP 动作 |
|---|---|
| `socket.end()` | 发送 FIN（第 ① 或 ③ 步） |
| `socket.on('end')` | 收到对端的 FIN（第 ① 或 ③ 步） |
| `socket.on('close')` | 四次挥手全部完成，连接彻底关闭 |

**"半关闭"就是这个状态**：你发了 FIN（我不再发了），但还没收到对方的 FIN（对方可能还在发），此时连接处于"我能收、不能发"的半关闭状态。这正是 `end` 事件和 `close` 事件之间隔着的那段。

> 一句话记住它：建立是三次（ACK 和 SYN 能合并），断开是四次（两个方向各自关，中间对方可能还有数据要发）；`end()` 发 FIN，`close` 才是彻底断。

## 02.7 用 node:net 观察握手和挥手（能观察到的部分）

**先说结论**：SYN/ACK/FIN 这些报文发生在**内核层**，你的 Node 代码**看不到报文本身**，但能看到它们的"后果"——`connect` 成功（握手完成）、`end` 事件（收到 FIN）、`close` 事件（挥手完成）。

配套示例 `examples/http/02-三次握手与可靠传输.mjs` 就是干这个的。跑一遍，对照着看：

```text
[server] connect 事件 = 三次握手已完成
[client] connect 成功（在应用层看来，握手"瞬间"完成）
[client] 发送请求，然后立刻 end() —— 这叫"半关闭"
[server] 收到一段字节: "给我一段话"
[server] 收到客户端的 FIN（客户端说"我发完了"）
[server] 这是"半关闭"：客户端不再发，但还能收
[server] 服务端回敬一个 FIN（附上一句告别），完成挥手
[client] 收到服务端的 FIN，双向挥手完成
[client] 把收到的片段按顺序拼起来（可靠传输的体现）:
[client]   "第一段：你好，第二段：这是被 TCP 保证第三段：有序送达的字节流。（服务端的告别）"
```

**逐行对号入座：**

1. `connect 事件 = 三次握手已完成`——三次握手发生在 `connect` 回调**之前**，你看到 connect 成功，说明握手已经完成。
2. `end() 这叫半关闭`——客户端 `write` 完立刻 `end()`，发了一个 FIN，但客户端**还在收**数据（半关闭）。
3. `收到客户端的 FIN`——服务器的 `end` 事件，就是收到了客户端的 FIN（第 ① 步）。
4. `服务端回敬一个 FIN`——服务器 `end()` 发自己的 FIN（第 ③ 步）。
5. `收到服务端的 FIN`——客户端的 `end` 事件（第 ③ 步到达）。
6. `双向挥手完成`——四次挥手结束。

**注意输出里那个真实现象**：服务器分 3 次 `write`（"第一段…"、"第二段…"、"第三段…"），但客户端**只触发了一次 `data`**，三句连在一起收到了。这就是第 01 章强调的——**TCP 是字节流，没有消息边界**，3 次 `write` 不保证 3 次 `data`。

**为什么顺序没乱？** 因为即使被合并、被分片，TCP 保证字节的**顺序**。你收到的永远是"第一段…第二段…第三段…"这个顺序，不会变成"第三段…第一段…"。

> 一句话记住它：你看到的 `connect` 是"握手已完成"、`end` 是"收到 FIN"、`close` 是"挥手完成"；报文本身在内核里，你看不见，但看得到后果。

## 02.8 滑动窗口：可靠之外的"流量控制"

**先说结论**：光有序列号/确认号，只能保证"不丢不乱"，还解决不了另一个问题——**发送方发太快，接收方来不及处理**。滑动窗口（sliding window）就是用来控制节奏的：接收方告诉发送方"我还能收多少"，发送方别超过这个量。

**为什么需要流量控制？** 想象发送方是台超快服务器，接收方是台慢手机。如果发送方不管不顾地狂发，接收方的缓冲区会被撑爆，数据照样丢（只不过这次是"接收方丢的"，不是网络丢的）。所以得有个机制，让发送方"看接收方的脸色行事"。

**窗口是什么？** 接收方每次回 ack 时，都带上一个字段——**窗口大小（window size）**，意思是"我这边还能容纳多少字节"。发送方发出去但还没收到确认的字节数，**不能超过这个窗口**。

画个图，假设窗口大小是 4（能容纳 4 个字节没确认）：

```text
发送方已发未确认的字节，必须 ≤ 窗口大小

发送 seq=100..103（4 字节，窗口满了）
  ↓ 收到 ack=102（确认了 2 字节）
现在还能再发 2 字节
  ↓ 发 seq=104..105
  ↓ 收到 ack=104
现在又能再发 2 字节
  ...
```

**窗口是"滑动的"**：每收到一个 ack，就说明"有些字节被确认了"，窗口就往前滑一点，腾出新的空间。所以叫滑动窗口。

**这带来一个优雅的副作用：窗口越大，能"在途"的数据越多，吞吐量越高；窗口越小，越保守。** 接收方通过调窗口大小，就能控制发送方的速度——这就是**流量控制（flow control）**的本质：不是"快"，是"别把对方冲垮"。

> 一句话记住它：滑动窗口 = 发送方"没被确认的字节数"不能超过接收方告知的窗口大小；每确认一点，窗口就往前滑一点，这就是流量控制。

## 02.9 拥塞控制：别把网络自己搞垮

**先说结论**：流量控制是"照顾接收方"，拥塞控制是"照顾整个网络"。它解决的是——**如果全网每个人都拼命发包，网络（路由器）会瘫痪，最后谁都发不出去**。

**流量控制和拥塞控制的区别，一句话：**

| | 谁在"告急" | 控制什么 |
|---|---|---|
| 流量控制 | 接收方（"我收不过来了"） | 发送速度 ≤ 接收方窗口 |
| 拥塞控制 | 网络（"路由器堵了"） | 发送速度 ≤ 网络能承受的量 |

**拥塞控制的核心思想：慢启动（slow start）+ 拥塞避免 + 快速恢复。**

TCP 不知道网络现在堵不堵，它只能靠**猜测 + 试探**：

1. **慢启动**：刚建立连接时，先**慢慢发**（从很小的窗口开始），然后**指数增长**——每收到一个 ack，窗口就翻倍，快速试探"网络到底能扛多少"。
2. **遇到丢包**：说明"发太快了，网络扛不住了"，窗口立刻**砍半**（甚至砍到最小），转为**线性增长**，谨慎地慢慢加。
3. **反复调整**：一丢就砍，不丢就加，最终收敛到一个"网络刚好能承受"的速度。

**为什么叫"慢启动"却是指数增长？** 这是历史遗留的命名坑。它"起步慢"（初始窗口小），但增长快（翻倍）。名字里的"慢"指的是"起点低"，不是"增长慢"。

**这套机制对你的意义**：你可能听说过"TCP 刚开始下载慢，后来越来越快"，这就是慢启动——它不敢一上来就全速，先试探网络，确认扛得住再提速。反之，网络一拥堵，它就自觉减速。

**到这里，TCP 可靠性的完整图景就齐了：**

| 机制 | 解决什么 |
|---|---|
| 序列号 + 确认号 | 不丢、不乱、不重 |
| 超时重传 + 快速重传 | 丢了能发现、能补 |
| 滑动窗口 + 流量控制 | 别冲垮接收方 |
| 慢启动 + 拥塞避免 | 别冲垮网络 |

前两者保证"**正确**"，后两者保证"**不把大家搞死**"。合起来，才是完整的 TCP。

> 一句话记住它：流量控制照顾接收方，拥塞控制照顾整个网络；慢启动"先试探、再提速、一丢就砍"——这就是 TCP 下载"先慢后快"的原因。

## 02.10 可靠性的代价：不是免费的

**先说结论**：TCP 的可靠是有代价的——**延迟更高、额外开销更大**。理解这个代价，你才能理解后面 HTTP/2、HTTP/3 为什么折腾。

**代价一：握手要等一个来回。** 建立连接前，三次握手要先跑一个 RTT（往返时间）。哪怕你只想发一个字节，也得先握手。这就是为什么"短连接"很浪费——每次都要重新握手。

**代价二：确认有开销。** 每个方向都要发 ack，还要维护序列号、计时器、缓冲区。这些"控制开销"在数据量大时不明显，数据量小时占比很高。

**代价三：丢了要等重传。** 一旦丢包，必须等 RTO 或快速重传，这段时间数据是"停"的。**而且 TCP 有个著名的缺点：队头阻塞（Head-of-Line Blocking）**——如果前面一个包丢了，后面的包即使已经到了，也只能等着，因为要按序上交。

**队头阻塞是 TCP 最被诟病的缺点**，也是第 07 章 HTTP/2、HTTP/3 的主角：

```text
发送顺序: [1] [2] [3] [4]
           丢   到   到   到

接收方按序上交，必须等 [1] 重传回来，才能交 [1][2][3][4]
→ [2][3][4] 虽然早到了，也只能在缓冲区里干等着
```

**对比 UDP**（第 07 章详讲）：UDP 不握手、不确认、不重传、不排序——所以它快，但不可靠。**TCP 和 UDP 是"可靠"和"快"的两个极端**，你永远在它们之间做取舍。

**一个重要的认知**：TCP 的可靠性是"**给应用层一个幻觉**"——让你以为有一条"绝对不会出错"的管道。但实际上底下仍然会丢、会乱，只是 TCP 在你看不见的地方把它们修好了。**这个幻觉值多少钱，取决于你的场景**：传文件、发请求，可靠性无价；打实时游戏、视频通话，宁可丢一帧也要快，于是用 UDP。

> 一句话记住它：TCP 的可靠是用"握手延迟 + 确认开销 + 队头阻塞"换来的；理解了队头阻塞，你就懂了 HTTP/2 和 HTTP/3 存在的意义。

## 02.11 本章常见坑速查

| 坑 | 现象 | 原因 | 正确做法 |
|---|---|---|---|
| 以为 `connect` 成功前就能发数据 | 数据没发出去或报错 | 握手还没完成，连接不存在 | 在 `connect` 回调里再 `write` |
| 以为 `end` 事件后连接就关了 | 还能继续 `write` | `end` 只是"对端发完 FIN"，是半关闭 | 记牢 `end` ≠ `close` |
| 用 `destroy()` 代替 `end()` | 对端收到 `ECONNRESET` | `destroy` 发 RST 暴力断开 | 正常关闭用 `end()`，`destroy` 留给错误处理 |
| 以为 `write` 几次对方 `data` 几次 | 只收到一次 `data` | TCP 是字节流，无消息边界 | 自己按协议定界，别依赖 `data` 次数 |
| 以为 TCP 保证"不丢"就万事大吉 | 程序卡住 | TCP 只保证"不丢且有序"，不保证"快"，队头阻塞会让数据卡住 | 实时场景考虑 UDP/QUIC |
| 服务器收到 `end` 后没回 `end` | 连接一直挂着不关 | 四次挥手只走了一半，服务器没发自己的 FIN | 收到 `end` 后记得也 `socket.end()` |
| 忘了 `error` 监听 | 进程直接崩 | 网络错误（如 `ECONNRESET`）没被捕获 | 给 socket 挂 `on('error')` |
| 短连接频繁建立 | 性能差 | 每次都要三次握手 + 四次挥手 | 用长连接/连接池复用 |

## 02.12 本章小结

- **IP 是"尽力而为"**：会丢、会乱、会重；TCP 在它之上自己造可靠。
- **三次握手**：交换双方初始序列号 + 双向确认；三次是"双向确认 + 不浪费"的最小次数。
- **序列号按字节编号**，确认号是"期待的下一个字节序号"。
- **丢包**靠超时重传（RTO）+ 快速重传（3 个重复 ack）发现和修复。
- **乱序**靠接收缓冲区按序号排序，**重复**靠序号去重，**损坏**靠校验和。
- **四次挥手**：TCP 双向，两个方向各自关；`end()` 发 FIN，`close` 才是彻底断。
- **半关闭**：发完 FIN 还能收，`end` 事件和 `close` 事件之间就是半关闭。
- **可靠性有代价**：握手延迟、确认开销、**队头阻塞**——这是 HTTP/2、HTTP/3 的动机。
- **真实错误名**：`ECONNRESET`（对端 RST 重置）、`ECONNREFUSED`（连不上）、`ETIMEDOUT`（超时）。

## 02.13 动手练习

**1. 为什么建立连接是三次握手，断开却是四次挥手？用一句话说清。**

<details><summary>参考答案</summary>

因为建立时，服务器的"确认（ACK）"和"自己的同步（SYN）"可以**合并成一个报文**（SYN+ACK），所以三次就够。而断开时，一方发 FIN 后，另一方**往往还有数据要发**，不能立刻合并，只能先回 ACK、发完数据再回自己的 FIN，所以是四次。

</details>

**2. 发送方发了 seq=200 的数据（共 10 个字节），接收方收到后会回 ack=多少？**

<details><summary>参考答案</summary>

`ack=210`。因为 ack 是"期待的下一个字节序号"，收到 seq=200 的 10 个字节（200~209），下一个期待的就是 210。

</details>

**3. 客户端 `end()` 之后，还能收到服务器发来的数据吗？为什么？**

<details><summary>参考答案</summary>

能。`end()` 只发了 FIN，表示"我不再发了"，但连接**没有彻底关闭**（半关闭），客户端仍能接收服务器发来的数据。要等服务器也发 FIN、双方挥手完成（`close` 事件），连接才彻底断。

</details>

**4. 下面这段代码，为什么服务器收不到"客户端说完了"这行日志？**

```js
const server = net.createServer((socket) => {
  socket.on('data', (d) => console.log('收到:', d.toString()));
  socket.on('end', () => console.log('客户端说完了'));
});

// 客户端
const client = net.createConnection({ host: '127.0.0.1', port });
client.write('你好');   // 只 write，没 end
```

<details><summary>参考答案</summary>

因为客户端只 `write` 了数据，**没有调用 `client.end()`**，所以客户端没有发 FIN。服务器的 `end` 事件只有在"收到对端 FIN"时才触发。客户端一直不发 FIN，服务器就一直等，自然收不到"客户端说完了"。

修法：客户端 `write` 之后调用 `client.end()`。

</details>

**5. 解释"队头阻塞"：为什么前面一个包丢了，后面的包到了也没用？**

<details><summary>参考答案</summary>

因为 TCP 要**按序上交**。接收方收到后面的包（比如 seq=106、109），但 seq=100 还没到，它只能把 106、109 暂存在缓冲区里，等 100 重传回来，才能按 100→103→106→109 的顺序交给应用层。所以"队头"（前面的包）丢了，"后面"的包再快到也只能排队等——这就是队头阻塞。HTTP/2 的多路复用和 HTTP/3 换 UDP，都是为了缓解或根治它。

</details>
