# 第 01 章 · 环境与心智模型：亲手建一条 TCP 连接

> 第 00 章告诉你"网络是层层外包"。这一章把这句话**落到代码里**：用 `node:net` 亲手建一条真实的 TCP 连接，亲眼看到数据是怎么被"封装"成字节、又是怎么被"解封装"回来的。
>
> 本章你需要记住的就一件事：**一条 TCP 连接 = 由"端口"识别的、建立在两台机器之间的一条可靠字节流。应用层写的文本，到了传输层就是一堆字节（Buffer）。**
>
> 这一条想清楚了，端口、封装/解封装、以及后面 HTTP 为什么是文本，全都是它的推论。

---

## 01.1 先跑起来：一条真实的 TCP 连接

**先说结论**：你不装任何东西，只用 Node 内置的 `node:net`，就能在两分钟内让两个进程在网络上对话。这不是"模拟"，是**真的**操作系统内核帮你建了一条 TCP 连接。

把这段代码存成文件（配套示例 `examples/http/01-TCP连接与封装.mjs`），直接跑：

```js
import net from 'node:net';

// 创建服务器：每当有客户端连进来，就触发一次这个回调
const server = net.createServer((socket) => {
  console.log('[server] 收到一条 TCP 连接');
  console.log('[server]   远端地址 ' + socket.remoteAddress + ':' + socket.remotePort);
  console.log('[server]   本地地址 ' + socket.localAddress + ':' + socket.localPort);

  socket.on('data', (data) => {
    console.log('[server] 收到的字节:', data.toString('utf8'));
    socket.write('收到，你好！');
    socket.end();
  });
});

// listen(0) 让内核随便分配一个空闲端口
server.listen(0, '127.0.0.1', () => {
  const { port } = server.address();
  console.log('[server] 监听在 127.0.0.1:' + port);

  const client = net.createConnection({ host: '127.0.0.1', port }, () => {
    console.log('[client] 连上了，本地端口 ' + client.localPort);
    client.write('你好服务器');
  });

  client.on('data', (d) => console.log('[client] 收到:', d.toString('utf8')));
  client.on('close', () => server.close(() => console.log('进程退出')));
});
```

跑一遍（本机 Node 22.22.2 实测）：

```text
[server] 监听在 127.0.0.1:65471
[server] 收到一条 TCP 连接
[server]   远端地址 127.0.0.1:65472
[server]   本地地址 127.0.0.1:65471
[client] 连上了，本地端口 65472
[server] 收到的字节: 你好服务器
[client] 收到: 收到，你好！
进程退出
```

（端口号每次跑都不一样，因为 `listen(0)` 是"随便分一个"。）

**你现在已经完成了一次真实的网络通信。** 但别急着高兴——上面这段输出里，藏着这一章要讲的全部概念。往下看，每一行都是个知识点。

先拆三个最容易被忽略的细节：

1. `socket.remoteAddress` 和 `socket.localAddress` 都打印 `127.0.0.1`，**为什么一模一样？** 因为客户端和服务器跑在同一台机器上，都用回环地址自己连自己。
2. `socket.remotePort` 是 `65472`，**这个端口是谁给的？** 是内核在客户端 `createConnection` 时随手分配的临时端口，不是客户端代码写的。
3. `socket.write('你好服务器')` 写的是**字符串**，但服务器 `data` 里收到的是**字节**——这中间发生了一次"封装"。

> 一句话记住它：`node:net` 的 `createServer` + `createConnection` 就是一条真实 TCP 连接的两端，没有黑魔法，你写的就是 TCP。

## 01.2 端口：一台机器的"门牌号"

**先说结论**：端口是一个 **0 到 65535 的整数**，它回答的问题是——"这台机器上，这段数据是给哪个程序用的？"

**为什么需要端口？**

你想想，一台服务器上可能同时跑着：

- 一个 Web 服务（监听 80 端口）
- 一个数据库（监听 3306）
- 一个 SSH 服务（监听 22）

数据包到了这台机器的网卡，**只带着这台机器的 IP 地址**。内核把数据交上来的时候，总得知道"这份数据是给 Web 服务还是给数据库"。端口就是干这个的——它把"一条连接"精确到"某一个程序"。

**端口是"逻辑门牌"，不是"物理插孔"。** 你机器上没有一个叫"3306"的洞，端口号是操作系统在内核里维护的一个映射表上的编号。

**端口分三段，这是约定（不是硬性规定）：**

| 端口范围 | 名称 | 用途 |
|---|---|---|
| 0 ~ 1023 | 知名端口（well-known） | 给标准服务留的，如 HTTP 80、HTTPS 443、DNS 53、SSH 22 |
| 1024 ~ 49151 | 注册端口 | 给各种软件注册用 |
| 49152 ~ 65535 | 动态/临时端口 | 客户端发起连接时，内核临时分配给你的 |

**回到 01.1 的输出**，你现在能看懂这几行了：

```text
[server]   本地地址 127.0.0.1:65471   ← 服务器监听在 65471 端口
[server]   远端地址 127.0.0.1:65472   ← 客户端来自 65472 端口
[client] 连上了，本地端口 65472       ← 内核给客户端随机分配的临时端口
```

**一条连接由四个东西唯一确定**：`（源IP，源端口，目标IP，目标端口）`。这就是"四元组"。服务器监听的是 `65471`，但客户端不是——客户端的 `65472` 是内核在你发起连接时**随手分的临时端口**（就在 49152~65535 那段）。所以：

- **服务器**：要有个**固定、公开**的端口，好让全世界知道去哪找你。
- **客户端**：端口随便分，用完就还。

**为什么客户端也要有端口？** 因为服务器得知道"回复该发回哪"。想象同一台机器上开了两个浏览器标签，都连到同一个网站——如果没有客户端端口，服务器回的数据就不知道给哪个标签页。**四元组里的"源端口"就是用来区分"这条回复是给哪个连接的"。**

**一个会咬人的坑**：两个程序不能同时监听同一个端口。跑这段：

```js
import net from 'node:net';

const s1 = net.createServer().listen(3000);
const s2 = net.createServer();

s2.on('error', (e) => console.log('s2 报错:', e.code)); // 真实错误名，照抄
s2.listen(3000);
```

输出：

```text
s2 报错: EADDRINUSE
```

`EADDRINUSE` 是真实错误名，意思是"这个地址（端口）已经在被用了"。你平时在项目里看到的 `Error: listen EADDRINUSE: address already in use :::3000`，就是它。

> 一句话记住它：端口是"程序的门牌号"，一条连接靠 `（源IP，源端口，目标IP，目标端口）` 四元组唯一确定；服务器端口要公开固定，客户端端口内核随手分。

## 01.3 TCP/IP 四层，落到你的机器上

**先说结论**：第 00 章那张"层层外包"的图，不是哲学，是**真实发生在你系统里的分工**。你写的 `node:net` 代码只待在**传输层**，它下面还有两层在替你干活。

把四层和 `node:net` 的代码对应起来：

| 层 | 干什么 | 谁在干 | 你的代码管不管 |
|---|---|---|---|
| 应用层 | 表达意图（"我要 GET 一个网页"） | 你的业务代码（HTTP、DNS…） | **你在写** |
| 传输层 | 可靠送达（不丢、不乱序） | **操作系统内核的 TCP 实现** | `node:net` 替你调用了它 |
| 网络层 | 寻址路由（找到那一台机器） | 内核的 IP 实现 | 完全看不见 |
| 链路层 | 相邻设备间传比特 | 网卡驱动、交换机、路由器 | 完全看不见 |

**关键结论：`node:net` 的 `socket.write('你好')`，调用的是你操作系统内核里那个已经被打磨了几十年的 TCP 协议栈。** 你不是"自己实现了 TCP"，你是"站在巨人的肩膀上"。

**为什么 Node 不让你碰下面两层？** 因为没必要，而且危险：

1. 网络层（IP）的职责是"把包从这台机器路由到那台机器"，中间要经过无数路由器，这部分是**整个互联网的基础设施**在管。你的程序不该也没法插手。
2. 链路层更底，是"光缆里怎么编码 0 和 1"，离你的业务十万八千里。

**分层给你最大的好处，用一句话说：你写 `socket.write('你好')`，完全不用知道对方的网线是铜线还是 Wi-Fi。**

反过来，分层也意味着：**当网络出问题时，你得知道去哪一层找**（这一条到第 08 章会变成一门手艺）。

**这里补一个重要的"反面"认知：分层是"接口约定"，不是"物理隔离"。** 你写的"应用层"代码和内核里的"传输层"，物理上跑在**同一个进程、同一块内存**里，靠系统调用（syscall）通信。分层说的是**职责划分**，不是说它们在不同机器上。别把"层"想成"不同的箱子"，它是"同一栋楼里不同的部门"。

> 一句话记住它：`node:net` 站在传输层，下面两层（IP 路由、链路传输）由内核和整个互联网替你搞定——这就是分层让你"看不见"的东西。

## 01.4 封装与解封装：数据怎么"包起来又拆开"

**先说结论**：你发出的"你好"这两个字，在网络上走的时候，**不是光秃秃两个汉字**，而是一层一层包了壳的字节；到了对端，再一层一层剥壳。

**这是分层最直接的物理后果。** 想象你在传输层写下：

```text
你好服务器
```

这段文本要真正出发，得先经历"层层加信封"：

```text
应用层（你的程序）        你好服务器
                            │  往下走
传输层（TCP 内核）      +TCP 头（写上源端口/目标端口/序列号…）
                            │  往下走
网络层（IP 内核）       +IP 头（写上源 IP/目标 IP…）
                            │  往下走
链路层（网卡）          +以太网头 + 帧尾（写上 MAC 地址、校验…）
                            ↓
                    通过光/电/无线电真跑出去
```

到了接收方，过程**完全反过来**：链路层剥掉以太网头，网络层剥掉 IP 头，传输层剥掉 TCP 头，最后把**光秃秃的"你好服务器"**交给你对面的程序。

**每一层只看得懂自己的"头"。** 传输层加 TCP 头的时候，它根本不在乎你应用层写的是"你好"还是"GET / HTTP/1.1"——对它来说都是"一堆要可靠送达的字节"。

**为什么"加壳"这件事这么重要？** 因为它让每层可以**只处理自己关心的信息**，其余内容对它都是不透明的：

- 路由器（网络层）转发包时，只看 IP 头里的"目标 IP"，**根本不看** TCP 头和应用数据。
- TCP 内核（传输层）确认送达时，只看 TCP 头里的序列号，**根本不看**你的"你好"是什么。
- 你的程序（应用层）只关心"你好"三个字，**根本不看** IP 头里写了什么。

**这个"壳"长什么样？** 下一节我们亲手把它挖出来看。

> 一句话记住它：发送是"层层加信封"，接收是"层层拆信封"；每一层只认识自己那层信封，其余对它都是不透明货物。

## 01.5 用 node:net 亲眼看一次封装

**先说结论**：`socket.on('data')` 拿到的那个 `data`，**是一个 Buffer（字节串），不是字符串**。这就是"封装"在你眼前的样子。

配套示例 `examples/http/01-TCP连接与封装.mjs` 里，客户端发了这样一段文本：

```js
const message = 'GET / HTTP/1.1\r\nHost: example.com\r\n\r\n';
client.write(message);
```

服务端收到后，先打印它的**原始字节（hex）**，再打印**解码成文本**：

```js
socket.on('data', (data) => {
  console.log('[server] 收到原始字节:', data.toString('hex'));
  console.log('[server] 解封装成文本后:', JSON.stringify(data.toString('utf8')));
});
```

实测输出（就是这段，一个字没改）：

```text
[server] 收到原始字节: 474554202f20485454502f312e310d0a486f73743a206578616d706c652e636f6d0d0a0d0a
[server] 解封装成文本后: "GET / HTTP/1.1\r\nHost: example.com\r\n\r\n"
```

**看懂了这两行，封装/解封装就不再是抽象概念。**

那一长串 hex，就是"应用层文本"被丢进 TCP 之后，在传输层真正传输的样子：

| hex | 对应字符 |
|---|---|
| `47` | `G` |
| `45` | `E` |
| `54` | `T` |
| `20` | 空格 |
| `0d 0a` | `\r\n`（回车换行） |

你在浏览器地址栏敲 `example.com`，浏览器替你发出的"请求"，本质上就是这串字节里的一个变体——只是更长、带了更多头（第 04 章会看到完整报文）。

**这里有个必须提前知道的真相：TCP 是"字节流"，没有"消息边界"。**

你 `write('你好')` 三次，对方可能一次 `data` 就全收到；也可能分三次收到。TCP 只保证**字节的顺序和完整**，不保证"你 write 几次、对方 data 就触发几次"。这个坑在第 02 章会正式讲，现在先记住有这回事。

**为什么 Node 用 Buffer 而不是直接给你字符串？** 因为网络传的是**字节**，而字节不一定能解码成字符（比如图片、压缩包）。Node 把"原始字节"和"解码后的文本"分开，你才能既看到 `47 45 54`，也能看到 `GET`。

**顺带纠正一个直觉错误**：`socket.write('你好服务器')` 里的字符串，Node 会在背后帮你转成 Buffer 再发出去。所以"应用层写字符串"只是**语法糖**，底层永远是字节。

> 一句话记住它：`socket.on('data')` 拿到的是 Buffer（原始字节），`data.toString('utf8')` 才把它解封装成你认识的文本——这两步就是"解封装"的微观现场。

## 01.6 一个会咬人的心智坑：localhost 和 127.0.0.1

**先说结论**：`localhost` 是一个**域名**，`127.0.0.1` 是一个**IP 地址**。大多数时候它们指同一台机器（你本机），但它们走的路径不一样。

**差别在哪？**

- `127.0.0.1`：直接就是 IP，内核一看就知道是"回环地址"，数据不出网卡。
- `localhost`：是个名字，得先**查 hosts 文件 / DNS** 把它解析成 IP，才知道连哪。

用第 03 章要学的 `node:dns` 看一眼（配套示例 `examples/http/03-DNS与IP.mjs` 里也有）：

```js
import dns from 'node:dns/promises';

const r = await dns.lookup('localhost');
console.log(r); // { address: '::1', family: 6 }
```

**注意输出可能是 `::1` 而不是 `127.0.0.1`。** `::1` 是 IPv6 的环回地址。也就是说，`localhost` 在你这台机器上可能先解析成了 IPv6。

**这为什么重要？** 一个真实到每天都在发生的坑：

```js
// 服务器只监听了 IPv4 的 127.0.0.1
server.listen(3000, '127.0.0.1');

// 客户端却用 localhost 去连（可能解析成 ::1），连不上
net.createConnection({ host: 'localhost', port: 3000 });
```

如果你服务器只听 `127.0.0.1`（IPv4），而客户端解析 `localhost` 得到 `::1`（IPv6），**就连接不上了**。报错是真实的 `ECONNREFUSED`（第 10 章会正式见它）。

**避免这个坑的两招：**

1. 服务器和客户端都用同一个明确的地址（都写 `127.0.0.1`，或都用 `localhost`）。
2. 想同时监听 IPv4 和 IPv6，监听时**不指定 host**（`server.listen(3000)`），Node 默认监听所有网卡。

> 一句话记住它：`localhost` 是"要解析的名字"，`127.0.0.1` 是"写死的 IP"；它俩平时等价，但解析方向不同，混用可能踩 `ECONNREFUSED`。

## 01.7 socket 到底是什么：一个"双向的字节管道"

**先说结论**：`net.createServer` 回调里那个 `socket`，本质是一个 **Duplex（双向流）**——它既是一个可读流（对方发来的字节从这里读），又是一个可写流（你往这里写，字节就发到对面）。

**这个认知很重要**，因为 Node 里"流"这套东西你以后天天见。socket 上你能做的事，全来自"流"：

| 你想做的事 | socket 的方法 | 说明 |
|---|---|---|
| 发数据 | `socket.write(data)` | 把字节写进发送缓冲区 |
| 优雅关闭发送方向 | `socket.end(data?)` | 发完就发 FIN，表示"我不再发了" |
| 立刻关闭（不优雅） | `socket.destroy()` | 直接断开，不等缓冲发完 |
| 暂停读 | `socket.pause()` / `resume()` | 流控用 |
| 监听数据到达 | `socket.on('data', ...)` | 每次收到一段字节触发 |

**socket 的几个常用属性**，第一次见要记住：

| 属性 | 含义 |
|---|---|
| `socket.remoteAddress` | 对方的 IP |
| `socket.remotePort` | 对方的端口 |
| `socket.localAddress` | 本端的 IP |
| `socket.localPort` | 本端的端口 |
| `socket.bytesRead` | 这条连接一共收了多少字节 |
| `socket.bytesWritten` | 这条连接一共发了多少字节 |

**socket 的完整生命周期事件**，按发生顺序是：

```text
connect（客户端连上 / 服务器 accept）
   ↓
data（收到数据，可能触发 0 次或多次）
   ↓
end（对端发来 FIN，表示"我不再发了"，但你还可能发）
   ↓
close（连接彻底关闭，双向都断了）
```

**`end` 和 `close` 的区别**，是新手最容易混的：

- `end`：对方**优雅地**关掉了它的发送方向（发了 FIN）。此刻**你还能继续发**，这叫"半关闭"。
- `close`：连接**彻底没了**，双向都不能再收发。

第 02 章会用"四次挥手"把这个讲透。现在先记住：**`end` 是"对方说完了"，`close` 是"这条线断了"。**

> 一句话记住它：socket 是一个双向字节流；`end` 是"对端不再发"（半关闭，你还能发），`close` 是"连接彻底断开"。

## 01.8 双向通信：写一个 echo（回声）服务器

**先说结论**：TCP 是**双向**的，客户端和服务器随时可以互发。最简单的双向演示就是 echo——客户端发什么，服务器原样回什么。

```js
import net from 'node:net';

const server = net.createServer((socket) => {
  console.log('新连接');
  // 每收到一段字节，就原样发回去（echo）
  socket.on('data', (d) => {
    console.log('收到:', d.toString('utf8'));
    socket.write(d); // 原样回
  });
  socket.on('end', () => console.log('客户端说完了'));
});

server.listen(0, '127.0.0.1', () => {
  const client = net.createConnection({ host: '127.0.0.1', port: server.address().port }, () => {
    // 连发三条
    client.write('第一句');
    client.write('第二句');
    client.write('第三句');
    client.end(); // 发完就关发送方向
  });

  client.on('data', (d) => console.log('回显:', d.toString('utf8')));
  client.on('close', () => server.close(() => console.log('进程退出')));
});
```

实测输出：

```text
新连接
收到: 第一句第二句第三句
回显: 第一句第二句第三句
客户端说完了
进程退出
```

**注意输出里那个细节**：客户端写了三次 `write`，服务器**只触发了一次 `data`**，收到的是"第一句第二句第三句"拼在一起。

这就是 01.5 埋下的那个伏笔——**TCP 是字节流，没有消息边界**。三次 `write` 只是"往发送缓冲区写了三次"，接收端读到的时候，可能已经合成了一段。

**这带来一个真实世界的结论**：如果你要在 TCP 上发"一条条的消息"（比如聊天消息、JSON 对象），**必须自己定协议**——比如每条消息后面加个 `\n` 当分隔符，或者先发长度再发内容。TCP 不会帮你划边界，这是**应用层**的活。

> 一句话记住它：TCP 双向且是流——echo 服务器里三次 `write` 可能被对方一次 `data` 读走；想传"一条条消息"，你得自己在应用层定边界。

## 01.9 为什么一个 Node 进程能同时处理很多连接

**先说结论**：`node:net` 是**事件驱动**的——服务器不是"连一个、处理完、再连下一个"，而是把所有连接的"数据到达"都挂到事件循环上，谁有数据就先处理谁。这就是 Node 能扛高并发的底层原因。

**先看一个"串行思维"会写错的例子：**

```js
// ❌ 不要这样想：先等第一个客户端说完，再管第二个
// 实际上 net 服务器是"并发"接受所有连接的
```

**真相是**：每个 `createServer((socket) => {...})` 回调，都是**独立的连接**。10 个客户端同时连进来，`createServer` 的回调会被**调用 10 次**，每个 `socket` 各是各的，互不阻塞。

用代码验证——让服务器同时接受两个连接，每个连接的处理都"慢一点"，看它们是不是并行：

```js
import net from 'node:net';

const server = net.createServer((socket) => {
  // 每个连接各睡 500ms 再回，模拟"慢处理"
  const id = socket.remotePort;
  console.log('连接进来了:', id);
  setTimeout(() => {
    socket.write('处理完 ' + id);
    socket.end();
  }, 500);
});

server.listen(0, '127.0.0.1', () => {
  const port = server.address().port;
  const t0 = Date.now();

  let done = 0;
  function onClose() {
    done++;
    if (done === 2) {
      console.log('两个连接都在 ' + (Date.now() - t0) + 'ms 左右完成（是并发的，不是 1000ms 串行）');
      server.close(() => console.log('进程退出'));
    }
  }

  // 同时发起两个连接
  for (let i = 0; i < 2; i++) {
    const c = net.createConnection({ host: '127.0.0.1', port });
    c.on('data', (d) => console.log('收到:', d.toString('utf8')));
    c.on('close', onClose);
  }
});
```

实测输出：

```text
连接进来了: 50500
连接进来了: 50501
收到: 处理完 50500
收到: 处理完 50501
两个连接都在 500ms 左右完成（是并发的，不是 1000ms 串行）
进程退出
```

**关键：两个连接各自睡了 500ms，但总耗时还是 500ms 左右，不是 1000ms。** 如果 Node 是"串行处理"，第二个连接得等第一个的 500ms 睡完，总耗时就是 1000ms。结果是 500ms，说明它们**并行**了。

**为什么能并行？** 因为 `setTimeout` 不"阻塞"——它只是"登记一个 500ms 后要执行的函数"，然后立刻回来继续处理别的连接。这就是 Node 事件循环的核心：**单线程，但通过"不等待"实现并发**。

**这一节和第 08 章会深度关联**：你现在知道"服务器能并发处理连接"，但"一个慢请求会不会堵住后面"又是另一个问题（第 07 章讲队头阻塞）。先把"连接是并发接受的"这个基础认知立住。

> 一句话记住它：Node 服务器靠事件循环并发处理连接，一个连接的慢操作不会阻塞别的连接——这是"单线程高并发"的根基。

## 01.10 背压：写得太快会发生什么

**先说结论**：`socket.write()` 不是"发完才返回"，它只是"把数据塞进内核的发送缓冲区"。如果你塞得比对方收得快，缓冲区会满，Node 会**返回 `false` 提醒你"别写了，慢点"**。这就是背压（backpressure）。

**先做个实验**：让服务器狂发数据，客户端故意不读，看会发生什么。

```js
import net from 'node:net';

const server = net.createServer((socket) => {
  // 狂发 1MB 数据，但不关心 write 的返回值
  const chunk = Buffer.alloc(1024, 'x'); // 1KB 的 'x'
  for (let i = 0; i < 1024; i++) {
    socket.write(chunk); // 一共 1MB
  }
  socket.end();
});

server.listen(0, '127.0.0.1', () => {
  const client = net.createConnection({ host: '127.0.0.1', port: server.address().port });
  // 客户端故意"慢读"：每隔 10ms 才读一点
  let total = 0;
  client.on('data', () => {
    total++;
    client.pause(); // 每收到一段就暂停，模拟消费不过来
    setTimeout(() => client.resume(), 10);
  });
  client.on('end', () => {
    console.log('客户端读到的 data 次数:', total);
    server.close(() => console.log('进程退出'));
  });
});
```

**`write` 的返回值是什么意思？**

```js
const canContinue = socket.write(data);
// canContinue === false 表示：内核发送缓冲区快满了，建议你先停一停
```

**当 `write` 返回 `false`，什么时候能继续写？** 等 `drain` 事件——它表示"缓冲区又腾出地方了"：

```js
socket.on('drain', () => {
  // 现在可以继续 write 了
});
```

**完整的背压正确写法**（生产代码的骨架）：

```js
function writeAll(socket, data) {
  if (!socket.write(data)) {
    // 缓冲区满了，等 drain 再继续
    socket.once('drain', () => console.log('缓冲腾空了，可以继续发'));
  }
}
```

**为什么你要关心这个？** 因为如果你无视 `write` 的 `false` 返回值一直写，数据会无限堆积在内存里，轻则内存暴涨，重则进程 OOM 崩掉。Node 用"返回 `false` + `drain` 事件"这套机制，让你有机会**自己控制节奏**。

> 一句话记住它：`write` 返回 `false` 表示"发送缓冲区满了，先停"，等 `drain` 事件再继续——这是 Node 流控（背压）的核心，无视它会撑爆内存。

## 01.11 更多真实报错：连接被对端重置（ECONNRESET）

**先说结论**：除了 `EADDRINUSE`（端口被占）、`ECONNREFUSED`（连不上），还有一个你迟早会遇到的——`ECONNRESET`，意思是"对端把连接重置（RST）了"。

**它和 `ECONNREFUSED` 的区别，必须分清：**

| 错误名 | 真实含义 | 典型触发条件 |
|---|---|---|
| `ECONNREFUSED` | 连接**被拒绝** | 你连的端口没有进程在监听 |
| `ECONNRESET` | 连接**被重置** | 连接建立后，对端突然断掉/崩了/主动发 RST |
| `ETIMEDOUT` | 连接**超时** | 对端不响应，等到超时也没建立/收到数据 |

**怎么复现 `ECONNRESET`？** 一个简单场景：你连接一个服务器，正在收发数据时，服务器进程被 `kill` 了（或调了 `socket.destroy()`），客户端就会收到 `ECONNRESET`。

```js
import net from 'node:net';

const server = net.createServer((socket) => {
  // 连上来后，等 100ms 直接"暴力"销毁连接（不等缓冲发完，发 RST）
  setTimeout(() => socket.destroy(), 100);
});

server.listen(0, '127.0.0.1', () => {
  const client = net.createConnection({ host: '127.0.0.1', port: server.address().port });
  client.on('error', (e) => {
    console.log('客户端收到错误:', e.code); // ECONNRESET
    console.log('原文:', e.message);
    server.close(() => console.log('进程退出'));
  });
});
```

实测输出（取决于操作系统，可能是 `ECONNRESET` 或 `ECONNRESET` 相关的变体）：

```text
客户端收到错误: ECONNRESET
原文: read ECONNRESET
```

**注意 `destroy()` 和 `end()` 的区别，这里体现出来了：**

- `socket.end()`：优雅关闭，发 FIN，对端知道"你说完了"，正常收到 `end` 事件。
- `socket.destroy()`：暴力关闭，直接发 RST（或直接断），对端收到 `ECONNRESET` 错误。

**你写代码时，99% 应该用 `end()`，而不是 `destroy()`。** `destroy()` 是"来不及好好说再见了，直接挂电话"，只在错误处理、超时清理这些场景用。

> 一句话记住它：`ECONNREFUSED` 是"门都没开"，`ECONNRESET` 是"聊到一半对方摔了电话"；优雅关闭用 `end()`（FIN），暴力关闭用 `destroy()`（RST）。

## 01.12 综合：一个 mini 聊天服务器

**先说结论**：把这一章学的拼起来——双向流、事件循环、优雅关闭——你就能写一个能"多个客户端互相聊天"的最小服务器。这不难，因为 TCP 已经替你保证了"字节可靠送达"。

```js
import net from 'node:net';

// 所有连上来的客户端，都存在这里，方便广播
const clients = new Set();

const server = net.createServer((socket) => {
  clients.add(socket);
  const id = socket.remotePort;
  console.log(id, '进来了，当前', clients.size, '人');

  // 广播：把某人说的话转发给所有其他客户端
  socket.on('data', (d) => {
    const msg = d.toString('utf8').trim();
    for (const c of clients) {
      if (c !== socket) c.write(`${id} 说: ${msg}\n`);
    }
  });

  socket.on('close', () => {
    clients.delete(socket);
    console.log(id, '走了，剩', clients.size, '人');
  });
});

server.listen(0, '127.0.0.1', () => {
  const port = server.address().port;
  console.log('聊天室开在 127.0.0.1:' + port);

  // 模拟两个客户端，A 说一句，B 说一句，看它们互相收到
  const a = net.createConnection({ host: '127.0.0.1', port });
  const b = net.createConnection({ host: '127.0.0.1', port });

  a.on('connect', () => a.write('大家好，我是 A\n'));
  b.on('connect', () => b.write('大家好，我是 B\n'));

  a.on('data', (d) => console.log('[A 收到]', d.toString('utf8').trim()));
  b.on('data', (d) => console.log('[B 收到]', d.toString('utf8').trim()));

  // 等一秒钟，两个人都说完、收完，再关
  setTimeout(() => {
    a.end();
    b.end();
    server.close(() => console.log('进程退出'));
  }, 500);
});
```

实测输出（端口号会变，顺序可能略有不同）：

```text
聊天室开在 127.0.0.1:54321
54322 进来了，当前 1 人
54323 进来了，当前 2 人
[A 收到] 54323 说: 大家好，我是 B
[B 收到] 54322 说: 大家好，我是 A
54322 走了，剩 1 人
54323 走了，剩 0 人
进程退出
```

**这段代码里藏了三个你已经学会的东西：**

1. **`clients` 集合**：每个连接是一个独立的 `socket`，存起来才能广播——这就是"连接是独立对象"的用法。
2. **广播时 `if (c !== socket)`**：排除说话人自己，不然 A 会收到自己说的话。
3. **`socket.on('close')` 里清理集合**：断开的人要从 `clients` 里删掉，不然内存泄漏。

**你现在已经具备了看懂任何 TCP 程序的基础**。后面第 04 章学 HTTP 时你会发现——HTTP 服务器就是在这个"聊天服务器"的骨架上，把"消息"换成了标准的请求/响应格式。

> 一句话记住它：TCP 编程的核心模式就三个——`createServer` 存连接、`data` 里处理消息、`close` 里清理——聊天服务器和 HTTP 服务器是同一副骨架。

## 01.13 本章常见坑速查

| 坑 | 现象 | 原因 | 正确做法 |
|---|---|---|---|
| 两个程序监听同一端口 | `Error: listen EADDRINUSE: address already in use` | 端口已被占用，一个端口只能一个监听者 | 换端口，或先找到并关掉占用者 |
| 把 Buffer 直接当字符串用 | 打印出 `<Buffer 47 45 54>` 或乱码 | `data` 是字节，不是文本 | `data.toString('utf8')` 解码 |
| 以为 `write` 几次对方就 `data` 几次 | 对方可能一次收到、也可能分几次 | TCP 是字节流，没有消息边界 | 别依赖 `data` 的次数，自己拼接、按协议定界 |
| 服务器只听 `127.0.0.1`，客户端用 `localhost` 连 | 连不上，报 `ECONNREFUSED` | `localhost` 可能解析成 `::1`（IPv6） | 两端用同一地址，或服务器监听所有网卡 |
| `listen(0)` 却不知道端口是多少 | 客户端连不上 | 端口是随机分配的，得拿到它 | 在 `listen` 回调里读 `server.address().port` |
| 忘了关 `server` / `socket` | 进程不退出，一直挂着 | 有句柄还开着，事件循环不结束 | `socket.end()` / `server.close()` |
| 用 `127.0.0.1` 去连别的机器 | 连的是自己 | `127.0.0.1` 永远是本机回环 | 连别的机器要用它的真实 IP/域名 |
| 混淆 `end` 和 `close` | 以为收到 `end` 就不能再发了 | `end` 是"对端不再发"，你还可能发 | 记牢：`end` 半关闭，`close` 全断开 |
| 在 `data` 里按"条"解析消息 | 拿到半条消息就处理，出错 | 一段 `data` 可能是半条消息 | 自己用 `\n` 或长度前缀定界，攒够一条再处理 |
| 以为 `write` 是"发完才返回" | 数据可能还在缓冲区没走 | `write` 是异步的，返回只是"进了缓冲区" | 要确认发出，用回调 `write(data, cb)` 或 `drain` 事件 |

## 01.14 本章小结

- **一条 TCP 连接**由四元组 `（源IP，源端口，目标IP，目标端口）` 唯一确定。
- **端口**是"程序的门牌号"，0~65535；服务器端口公开固定，客户端端口内核随机分。
- **`node:net` 站在传输层**，下面两层（IP、链路）由内核和互联网基础设施替你搞定。
- **封装/解封装**：发送层层加壳、接收层层剥壳；每一层只认识自己的头。
- **`socket.on('data')` 拿到的是 Buffer**，`toString('utf8')` 才解出文本。
- **TCP 是字节流**，没有消息边界——不保证 `write` 次数等于 `data` 次数。
- **socket 是双向流**：`end` 是半关闭（对端不再发），`close` 是彻底断开。
- **Node 靠事件循环并发处理连接**，单线程也能"同时"服务很多客户端。
- **`localhost` 是域名，`127.0.0.1` 是 IP**，混用可能踩 `ECONNREFUSED`。
- **`EADDRINUSE`** 是端口被占用的真实错误名。

**1. 起一个 TCP 服务器，让客户端连上来后，服务器发一句"欢迎"，客户端打印出来后主动断开。要求进程自然退出。**

<details><summary>参考答案</summary>

```js
import net from 'node:net';

const server = net.createServer((socket) => {
  socket.write('欢迎');
  socket.end(); // 发完就优雅关闭
});

server.listen(0, '127.0.0.1', () => {
  const client = net.createConnection({ host: '127.0.0.1', port: server.address().port });
  client.on('data', (d) => console.log('收到:', d.toString('utf8')));
  client.on('close', () => server.close(() => console.log('进程退出')));
});
```

关键点：`socket.end()` 是"发完就发 FIN 关闭"；客户端收到 `close` 后关服务器，进程才退出。

</details>

**2. 下面这段代码哪里有问题？跑起来会看到什么？**

```js
import net from 'node:net';

net.createServer().listen(3000);
net.createServer().listen(3000);
```

<details><summary>参考答案</summary>

第二个 `listen(3000)` 会抛错，真实错误名是 `EADDRINUSE`：

```text
Error: listen EADDRINUSE: address already in use :::3000
```

原因：一个端口同一时刻只能有一个监听者。第二个服务器抢不到 3000 端口。

</details>

**3. 写一段代码，亲手打印出"客户端发送文本的原始 hex 和 UTF-8 文本"，验证封装/解封装。**

<details><summary>参考答案</summary>

看配套示例 `examples/http/01-TCP连接与封装.mjs` 的核心两行：

```js
socket.on('data', (data) => {
  console.log('原始字节(hex):', data.toString('hex'));
  console.log('解码文本    :', data.toString('utf8'));
});
```

发 `hello`，你会看到 hex 是 `68656c6c6f`（`68`=`h`、`65`=`e`、`6c`=`l`、`6f`=`o`）。

</details>

**4. 为什么说"换 Wi-Fi 不影响你浏览器里的 HTTP"？用本章的"分层"概念回答。**

<details><summary>参考答案</summary>

因为换 Wi-Fi 只是换了**链路层**（从网线换成了无线信号），而上层的 HTTP（应用层）只依赖传输层提供的接口（"可靠送达字节流"），根本不关心下面走的是铜线还是无线电。这就是分层"每层独立演进"的体现：链路层随便换，应用层代码一行不用改。

</details>

**5. 客户端连写了三次 `write`，服务器为什么可能只收到一次 `data`？如果要可靠地传"三条消息"，该怎么办？**

<details><summary>参考答案</summary>

因为 TCP 是**字节流**，没有消息边界。三次 `write` 只是往发送缓冲区写了三次，接收端读到的时候可能已经被合成一段（也可能分三次到，**不确定**）。

要可靠传"三条消息"，必须**在应用层自己定界**，两条常用方案：

1. **分隔符**：每条消息后加 `\n`，接收端按 `\n` 切分。
2. **长度前缀**：先发 4 字节表示长度，再发正文；接收端先读长度，再读足字节。

TCP 只保证"字节有序完整"，不保证"消息边界"——划边界是应用层的责任。

</details>
