# 第 08 章 · 工程化：REST 设计、抓包调试与报错码

> 前七章你学会了"网络怎么通""HTTP 是什么"。这一章从"能用"走向"工程化"——怎么把 HTTP 设计得规范（REST）、怎么调试（抓包）、怎么读懂报错。
>
> 本章你需要记住的就一件事：**REST 是一套"用 HTTP 动词 + URL 表示资源操作"的设计约定；调试靠"亲眼看报文 + 看日志 + 看错误码"，而不是靠猜。**
>
> 这一条想清楚了，你写出的接口就规范、好维护，出了问题也能自己定位。

## 08.1 从"能跑"到"工程化"

**先说结论**：用 `node:http` 起个服务、能响应请求，只是"能跑"。工程化意味着三件事：**接口设计有规范**（别人一看就懂）、**出了问题能定位**（有日志、能抓包）、**错误码认得全**（不靠猜）。

**先看一个"能跑但糟糕"的接口设计：**

```http
GET /getUser?id=1        ← 动词塞进了 URL
POST /addUser            ← 又换了个动词
GET /deleteUser?id=1     ← 用 GET 做删除（危险！）
POST /updateUserName     ← 每个操作一个 URL，无穷无尽
```

**再看一个规范的 REST 设计：**

```http
GET    /users        ← 查所有用户
GET    /users/1      ← 查 1 号用户
POST   /users        ← 新建用户
PUT    /users/1      ← 整体替换 1 号用户
PATCH  /users/1      ← 局部改 1 号用户
DELETE /users/1      ← 删 1 号用户
```

**差别一目了然**：糟糕的设计"动词满天飞、URL 混乱"；REST 设计"**统一用名词表示资源，用 HTTP 动词表示操作**"，URL 简洁、可预测。

**工程化的三个抓手：**

1. **REST 设计**：接口规范，别人一看 URL + 方法就知道干什么。
2. **抓包调试**：亲眼看请求/响应报文，别靠猜。
3. **报错码**：认得 `ECONNREFUSED`、`404`、`500` 这些，快速定位。

下面逐个展开。

> 一句话记住它：工程化 = 接口规范（REST）+ 能定位问题（抓包/日志）+ 认得错误码；三者合起来，你才是"能交付"的工程师。

## 08.2 REST 设计原则

**先说结论**：REST（Representational State Transfer）是一套**设计约定**，不是硬性标准。它的核心思想就一条：**把一切都看成"资源"，用 URL 定位资源，用 HTTP 动词操作资源。**

**REST 的几条核心原则：**

**原则一：URL 只表示资源（名词），不表示动作（动词）。**

```http
❌ GET /getUsers          ← 动词 getUsers 塞进 URL
✅ GET /users             ← URL 是名词"用户集合"

❌ POST /deleteUser       ← 动词 deleteUser
✅ DELETE /users/1        ← 用 DELETE 动词 + 资源
```

**原则二：用 HTTP 动词表示操作。**

| 动词 | 操作 | 例子 |
|---|---|---|
| GET | 读（查） | `GET /users/1` |
| POST | 建（增） | `POST /users` |
| PUT | 整体改 | `PUT /users/1` |
| PATCH | 局部改 | `PATCH /users/1` |
| DELETE | 删 | `DELETE /users/1` |

**原则三：资源用"集合/成员"的层级表示。**

```http
GET /users            ← 集合：所有用户
GET /users/1          ← 成员：1 号用户
GET /users/1/posts    ← 子资源：1 号用户的文章
```

**原则四：用状态码表示结果，不自己造一套。**

```http
✅ 成功创建 → 201 Created
✅ 删除成功 → 204 No Content
✅ 资源不存在 → 404 Not Found
❌ 返回 200 但 body 里写 { code: -1, msg: "失败" }  ← 这是老式做法，浪费了 HTTP 状态码
```

**原则五：无状态（stateless）。** 每个请求带上**所有必要信息**（比如认证 token），服务器不依赖"上一次请求记住了什么"。这样服务器才能水平扩展。

> 一句话记住它：REST = 名词定位资源 + 动词表示操作 + 状态码表示结果；URL 别塞动词，结果别自造状态码。

## 08.3 一个 REST 接口的完整设计

**先说结论**：设计一个"用户"资源，把 REST 的原则落到具体的接口上，你就有了可套用的模板。

**完整的 REST 接口表（以"用户"为例）：**

| 方法 | URL | 含义 | 成功状态码 | 失败状态码 |
|---|---|---|---|---|
| GET | `/users` | 查所有用户 | 200 | —— |
| GET | `/users/1` | 查 1 号用户 | 200 | 404 |
| POST | `/users` | 新建用户 | **201** | 400（数据非法） |
| PUT | `/users/1` | 整体替换 1 号 | 200 | 404 |
| PATCH | `/users/1` | 局部改 1 号 | 200 | 404 |
| DELETE | `/users/1` | 删 1 号 | **204** | 404 |

**几个设计细节值得注意：**

1. **POST 成功返回 201**，不是 200——因为"创建了资源"是更具体的成功。
2. **DELETE 成功返回 204**，不是 200——因为"删了就没东西可返回"。
3. **查不存在的资源返回 404**——不是 200 + `{ error: 'not found' }`。

**响应体约定**：出错时返回统一的错误结构，方便客户端处理：

```json
{ "error": "Not Found" }
```

**第 09 章的完整服务器，就是严格按这个表实现的**。你现在可以先记住模板，下一章动手写。

> 一句话记住它：REST 接口 = 方法 + URL + 状态码三者统一；POST 建成功 201、DELETE 成功 204、查不到 404。

## 08.4 抓包调试的思路：别靠猜

**先说结论**：遇到 HTTP 问题，第一反应不是"改代码试试"，而是**先亲眼看报文**。报文是唯一的真相，猜只会浪费时间。

**抓包调试的完整思路，五步：**

```text
1. 复现问题（知道"什么请求"出了问题）
2. 看请求报文（方法、URL、头、body 对不对？）
3. 看响应报文（状态码、头、body 是什么？）
4. 按状态码/错误码定位（4xx 查自己，5xx 查服务器）
5. 修复 + 验证
```

**怎么"看报文"？三个层次的手段：**

| 手段 | 场景 | 说明 |
|---|---|---|
| 自己打印（`console.log`） | 写代码调试 | 服务器里打印 `req.method`、`req.headers` |
| curl 命令行 | 快速验证一个接口 | `curl -v` 能看完整报文 |
| 抓包工具（Charles/Fiddler/Wireshark） | 看浏览器真实流量 | 看加密前的报文、看中间过程 |

**用 curl 看完整报文**（`-v` 显示详细信息）：

```bash
curl -v http://localhost:3000/api/users
```

输出会包括：

```text
> GET /api/users HTTP/1.1     ← 请求行（> 开头是发的）
> Host: localhost:3000
>
< HTTP/1.1 200 OK             ← 状态行（< 开头是收的）
< Content-Type: application/json
<
[{"id":1,"name":"小明"}]
```

**在 Node 服务器里自己打印报文**，就是第 08.5 节要写的"可调试服务器"。

**一个通用的排查口诀**（第 03 章埋过伏笔）：

```text
看到 4xx → 检查你自己的请求（URL 错没、方法错没、头错没、body 错没）
看到 5xx → 检查服务器（看日志、看异常栈）
看到 ECONNREFUSED → 服务没起 / 端口不对
看到 ENOTFOUND → 域名写错 / DNS 问题
```

> 一句话记住它：调试靠"亲眼看报文"，三步——看请求对不对、看响应是什么、按错误码定位；别一上来就改代码。

## 08.5 用 curl 亲手调试：一个完整演练

**先说结论**：`curl` 是命令行里最常用的 HTTP 客户端，调试接口时几乎离不开它。学会几个关键参数，你就能在终端里快速验证任何接口。

**curl 的常用参数：**

| 参数 | 作用 | 例子 |
|---|---|---|
| `-v` | 显示**完整报文**（含请求和响应） | `curl -v http://x.com` |
| `-X` | 指定方法 | `curl -X POST ...` |
| `-H` | 加请求头 | `curl -H "Content-Type: application/json" ...` |
| `-d` | 发 body | `curl -d '{"a":1}' ...` |
| `-i` | 只看响应头+体（不看请求） | `curl -i http://x.com` |
| `-o` | 保存到文件 | `curl -o out.html http://x.com` |

**一个完整的调试演练**（配合第 09 章的服务器）：

```bash
# 1. 先起一个服务器（第 09 章的完整服务器）
#    另开一个终端跑：node examples/http/09-完整HTTP服务器.mjs

# 2. 查所有用户（GET，看完整报文）
curl -v http://localhost:3000/api/users

# 3. 新建用户（POST + JSON body）
curl -X POST http://localhost:3000/api/users \
  -H "Content-Type: application/json" \
  -d '{"name":"小刚"}'

# 4. 删除用户（DELETE，观察 204）
curl -v -X DELETE http://localhost:3000/api/users/3
```

**看 `curl -v` 的输出长什么样：**

```text
> GET /api/users HTTP/1.1          ← > 开头是"发出的请求"
> Host: localhost:3000
> User-Agent: curl/8.0
>
< HTTP/1.1 200 OK                  ← < 开头是"收到的响应"
< Content-Type: application/json; charset=utf-8
<
[{"id":1,"name":"小明"}]
```

**为什么 curl 比浏览器好用？** 三个原因：

1. **能看到完整报文**（`-v`），浏览器开发者工具要点好几下。
2. **能精确控制请求**（方法、头、body 任意组合），浏览器做不到那么细。
3. **能写进脚本**，自动化测试接口。

**curl 和抓包工具的分工**：curl 是"我主动发一个请求，看它返回什么"；抓包工具（Charles/Fiddler/Wireshark）是"被动观察浏览器/应用的真实流量"。前者调试自己的接口，后者分析别人的/真实的流量。

> 一句话记住它：`curl -v` 看完整报文、`-X` 定方法、`-H` 加头、`-d` 发 body；curl 是"主动发请求"，抓包工具是"被动看流量"。

## 08.6 写一个"可调试"的服务器

**先说结论**：一个"好调试"的服务器，核心是**自动记录每个请求**——谁、什么方法、什么路径、花了多久、返回什么状态码、出错时错误是什么。这些日志，就是你排障的"黑匣子"。

配套示例 `examples/http/08-可调试服务器.mjs` 就是干这个的。核心技巧是**包一层 `res.end`，让日志自动发生**：

```js
const server = http.createServer((req, res) => {
  const start = Date.now();
  const ip = req.socket.remoteAddress;

  // 关键：包一层 res.end，无论哪个分支 return，都会打一条日志
  const originalEnd = res.end;
  res.end = function (...args) {
    console.log(`[${req.method}] ${req.url} -> ${res.statusCode}（${Date.now() - start} ms）来自 ${ip}`);
    originalEnd.apply(res, args);
  };

  try {
    if (req.url === '/404') {
      res.statusCode = 404;
      res.end('404 Not Found');
    } else if (req.url === '/500') {
      throw new Error('模拟：数据库连接挂了');
    } else {
      res.end('根路径');
    }
  } catch (err) {
    console.log('  出错啦:', err.message);
    res.statusCode = 500;
    res.end('500 Internal Server Error');
  }
});
```

**三个工程化要点：**

**① 日志要带关键信息**：方法、URL、状态码、耗时、来源 IP。这几样够了，你就能回答"谁在什么时候访问了什么、结果如何、慢不慢"。

**② 错误要捕获，别让进程崩。** `try/catch` 包住业务逻辑，出错时打日志 + 返回 500。生产环境还会配合进程守护（PM2 等），但"先别崩"是第一位的。

**③ 协议层错误也要处理。** `server.on('clientError')` 捕获客户端发的非法请求：

```js
server.on('clientError', (err, socket) => {
  console.log('客户端协议错误:', err.code);
  socket.end('HTTP/1.1 400 Bad Request\r\n\r\n');
});
```

实测输出（配套示例跑出来的）：

```text
== 客户端依次请求，观察服务器日志 ==

2026-10-12T15:03:37.308Z [GET] / -> 200（0 ms）来自 127.0.0.1
2026-10-12T15:03:37.312Z [GET] /404 -> 404（0 ms）来自 127.0.0.1
2026-10-12T15:03:37.313Z   ⚠ 处理出错: 模拟：数据库连接挂了
2026-10-12T15:03:37.313Z [GET] /500 -> 500（0 ms）来自 127.0.0.1
2026-10-12T15:03:37.623Z [GET] /slow -> 200（309 ms）来自 127.0.0.1
2026-10-12T15:03:37.625Z   客户端协议错误: HPE_INVALID_METHOD Parse Error: Invalid method encountered
```

**注意最后一行 `HPE_INVALID_METHOD`**——这是 Node 解析 HTTP 时遇到非法方法（我们发了段垃圾）的真实错误码。带时间戳、带耗时、带状态码，这张日志就是你的"抓包调试"落地。

> 一句话记住它：可调试服务器的核心是"自动日志"——包一层 `res.end` 记录每个请求的方法/URL/状态码/耗时，错误用 `try/catch` + `clientError` 兜住。

## 08.7 常见报错码：一张表认全

**先说结论**：把这一路遇到的真实错误码和状态码汇总成一张表。遇到它们，你能一眼说出"出在哪、怎么查"。

**网络层/TCP 层错误码（Node 里 `err.code`）：**

| 错误码 | 真实含义 | 触发条件 | 怎么查 |
|---|---|---|---|
| `ECONNREFUSED` | 连接被拒绝 | 端口没人监听 | 服务起了吗？端口对吗？ |
| `ENOTFOUND` | 域名查不到 | 域名不存在/DNS 不通 | 域名写对吗？DNS 通吗？ |
| `ETIMEDOUT` | 连接超时 | 对端不响应/网络不可达 | 目标可达吗？防火墙？ |
| `ECONNRESET` | 连接被重置 | 对端崩了/主动 RST | 对端进程还活着吗？ |
| `EADDRINUSE` | 端口被占用 | 两个程序监听同端口 | 谁占了端口？ |
| `ECONNABORTED` | 连接被中止 | 本地中止连接 | 客户端代码逻辑 |

**HTTP 状态码（协议层，`res.statusCode`）：**

| 状态码 | 短语 | 谁的问题 |
|---|---|---|
| 200 | OK | 无 |
| 201 | Created | 无（成功） |
| 204 | No Content | 无（成功） |
| 301 | Moved Permanently | 无（永久跳转） |
| 302 | Found | 无（临时跳转） |
| 304 | Not Modified | 无（缓存） |
| 400 | Bad Request | 客户端 |
| 401 | Unauthorized | 客户端（没登录） |
| 403 | Forbidden | 客户端（没权限） |
| 404 | Not Found | 客户端（资源不存在） |
| 500 | Internal Server Error | 服务器 |
| 502 | Bad Gateway | 服务器（上游挂了） |
| 503 | Service Unavailable | 服务器（过载/维护） |

**排障时的"分层思维"**（这是本章和前几章连起来的心法）：

```text
ECONNREFUSED → 传输层没通 → 查服务/端口
ENOTFOUND    → DNS 层失败 → 查域名/DNS
HTTP 4xx     → 应用层，你的请求错 → 查请求
HTTP 5xx     → 应用层，服务器错 → 查服务器日志
```

> 一句话记住它：错误码分两层——`err.code` 是传输层（网络没通），`statusCode` 是应用层（HTTP 语义）；先分清哪一层，再对症查。

## 08.8 本章常见坑速查

| 坑 | 现象 | 原因 | 正确做法 |
|---|---|---|---|
| URL 里塞动词 | `GET /getUser` 这类 | 不懂 REST 约定 | URL 用名词，动词用 HTTP 方法 |
| 用 GET 做删除/修改 | 数据被误删/篡改 | GET 应该"安全"（不改变状态） | 删除用 DELETE，修改用 PUT/PATCH |
| 错误全返回 200 | 客户端难判断结果 | 没利用状态码 | 用 201/204/404/500 等表达结果 |
| 服务器不记日志 | 出问题只能靠猜 | 没有"黑匣子" | 包一层 `res.end` 自动记日志 |
| 服务器不捕获异常 | 一个错误进程就崩 | 没 `try/catch` | 捕获异常，返回 500，别崩 |
| 收到 `ECONNREFUSED` 就改代码 | 查错方向 | 其实是服务没起 | 先确认服务/端口，再改代码 |
| 分不清 `err.code` 和 `statusCode` | 排查混乱 | 一个传输层、一个应用层 | 传输层看 code，应用层看 statusCode |

## 08.9 本章小结

- **工程化三抓手**：REST 规范、抓包调试、认报错码。
- **REST 核心**：URL 用名词（资源）、HTTP 动词表操作、状态码表结果、无状态。
- **POST 成功 201、DELETE 成功 204、查不到 404**。
- **调试靠亲眼看报文**：请求对不对 → 响应是什么 → 按错误码定位。
- **可调试服务器**：包一层 `res.end` 自动记日志（方法/URL/状态码/耗时）。
- **错误分两层**：`err.code`（传输层，如 `ECONNREFUSED`）、`statusCode`（应用层，如 404）。
- **`HPE_INVALID_METHOD`** 是 Node 解析非法 HTTP 方法的真实错误码。

## 08.10 动手练习

**1. 把下面这个糟糕的接口改写成 REST 风格：**

```http
GET  /getAllUsers
POST /createUser
GET  /removeUser?id=1
POST /changeUserEmail
```

<details><summary>参考答案</summary>

```http
GET    /users          ← 查所有用户
POST   /users          ← 新建用户
DELETE /users/1        ← 删除 1 号用户
PATCH  /users/1        ← 局部改 1 号用户（改邮箱）
```

要点：URL 用名词 `/users`，操作全用 HTTP 动词，资源成员用 `/users/1` 表示。

</details>

**2. 为什么说"用 GET 做删除是危险的"？**

<details><summary>参考答案</summary>

因为 GET 的语义是"安全、幂等"的读操作。如果删除用 GET，会带来两个问题：(1) 搜索引擎爬虫、预加载、链接预览都可能**无意触发**这个 GET，导致数据被删；(2) 浏览器可能缓存 GET 请求，重复访问造成重复删除。所以删除应该用 DELETE。

</details>

**3. 你调试时看到 `ECONNREFUSED`，第一反应应该是什么？**

<details><summary>参考答案</summary>

第一反应是"**服务没起 / 端口不对**"，而不是改代码。`ECONNREFUSED` 是传输层错误，表示"连接被拒绝"，通常是目标端口没有进程监听。先确认：服务启动了吗？端口号对吗？

</details>

**4. 一个可调试服务器，日志里至少要记哪几样东西？为什么？**

<details><summary>参考答案</summary>

至少要记：**方法、URL、状态码、耗时、来源 IP**。有了这几样，就能回答"谁在什么时候访问了什么、结果如何、慢不慢"——这覆盖了绝大多数排障场景。出错时还要记**错误信息/堆栈**。

</details>

**5. `err.code === 'ECONNREFUSED'` 和 `res.statusCode === 404`，分别表示什么问题？出在哪一层？**

<details><summary>参考答案</summary>

- `ECONNREFUSED`：**传输层**问题，TCP 连接没建立起来（端口没人监听）。
- `404 Not Found`：**应用层**问题，HTTP 连接是通的，但服务器说"资源不存在"。

一个是"电话没打通"，一个是"电话通了但对方说没这个人"。

</details>
