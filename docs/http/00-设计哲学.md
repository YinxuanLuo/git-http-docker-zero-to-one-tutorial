# 第 00 章 · 设计哲学：分层——每一层只跟邻居说话

> 本章**不写一行代码**。
> 但读完它，后面每一章"为什么这么设计"你都能自己想出来。
>
> 本章你需要记住的就一件事：**网络不是"一根管子"，而是"层层外包"——每一层只解决一个问题、只跟上下相邻的两层打交道，谁也不用懂别人的全部细节。**

---

## 0.1 先问你一个问题

你在浏览器地址栏敲下 `https://www.example.com`，回车。页面出来了。

现在问：**从你敲回车，到页面出来，这中间到底发生了什么？**

大多数有 JS 基础的人，答案会是："浏览器发了请求，服务器返回了 HTML，浏览器渲染出来了。"

对，但等于没说。往下追一层，问题就变多了：

- 浏览器"怎么知道" `www.example.com` 对应的服务器在哪？全世界几亿台机器，它怎么找到那一台的？
- 找到之后，数据是"怎么"过去的？是一条光缆直连吗？中间会不会有设备把数据搞丢、搞乱？
- 发出去的"请求"长什么样？是二进制还是文本？对方怎么知道你发完了、可以回复了？
- 为什么网址前面要加 `https`？多出来的那个 `s` 到底挡住了谁？

你会发现，**"发一个请求"这五个字里，藏着一整套精密的分工。**

而这一整套分工背后的核心思想，就一句话：

> **把"让两台机器能通信"这个超级复杂的问题，切成好几层，每一层只解决一个小问题，并且只跟上下相邻的两层打交道。**

这一章就讲这一句话。讲透了，TCP、IP、DNS、HTTP、TLS 这些名词，全都会被"归位"到某个层上，你学起来就是"往格子里放"，而不是"背一堆散装概念"。

---

## 0.2 快递的隐喻：为什么一定要分层

想象你要从上海给北京的朋友寄一个易碎的花瓶。这件事，你会拆成几步？

- 你自己：把花瓶**包好**（塞泡沫、装箱），在箱子上**写地址**，交给楼下的快递点。
- 快递点：把箱子装上**卡车**，卡车沿高速公路开过去。
- 高速公路：只负责"把车从 A 运到 B"，它**不在乎你箱子里装的是花瓶还是砖头**。
- 到北京后：卡车卸货，快递点按地址**送到你朋友手上**。

关键在这里：**每一层只干自己的活，并且完全不关心其他层的细节。**

- 高速公路不知道、也不想知道箱子里是花瓶——它只管运货。
- 寄件人（你）不知道卡车走的是京沪高速还是沪陕高速——你只关心"能不能安全送到"。

这就是**分层**：把"寄一个花瓶"这个复杂目标，拆成"打包 → 运输 → 投递"几个相对独立的环节，每一层对上/对下都有**清晰、固定、简单**的接口，中间随便哪一层换实现，都不影响别的层。

现在把这个隐喻原样套到网络上：

| 快递 | 网络 | 解决的问题 |
|---|---|---|
| 你打包、写地址 | **应用层**（HTTP、DNS…） | "我要表达什么"（请求一个网页、查一个域名） |
| 快递点分拣、装车 | **传输层**（TCP/UDP） | "怎么可靠/高效地送到"（不丢、不乱序、不重复） |
| 卡车 + 高速公路 | **网络层**（IP） | "怎么从这一台找到那一台"（寻址、路由） |
| 柏油路、光缆、路由器 | **链路层 / 物理层**（以太网、Wi-Fi） | "在相邻设备之间怎么传比特" |

> 一句话记住它：网络分层的本质是"层层外包"——每一层只向上层提供一种服务、只依赖下层的一种能力，谁也不越界。

---

## 0.3 官方答案：TCP/IP 四层模型

上面那个"快递隐喻"不是我的发明，它对应的是网络界公认的 **TCP/IP 参考模型**。绝大多数互联网都按它运作：

```
┌─────────────────────────────────────┐
│  应用层（Application）              │  HTTP / HTTPS / DNS / FTP / WebSocket
│  "我要表达什么业务"                  │
├─────────────────────────────────────┤
│  传输层（Transport）                │  TCP / UDP
│  "怎么可靠地送到"                    │
├─────────────────────────────────────┤
│  网络层（Internet）                 │  IP / ICMP / 路由协议
│  "怎么找到那一台机器"                │
├─────────────────────────────────────┤
│  链路层（Link / 物理层）             │  以太网 / Wi-Fi / ARP
│  "相邻设备之间怎么传比特"            │
└─────────────────────────────────────┘
```

（有些教材把它拆成更细的 OSI 七层模型，但七层是"理论家画出来的标准"，四层是"互联网真实在用的模型"。本系列用四层，因为 HTTP 这套东西就长在四层上。）

你可能会问：**分层到底解决了什么问题？为什么不能就一层搞定？**

三个实打实的好处：

1. **每一层可以独立演进。** 你家的网线从网线换成了 Wi-Fi、再换成 5G，**链路层换了，但你浏览器里的 HTTP 一点不用改**。因为应用层只依赖"传输层给的接口"，不关心链路层用什么介质。
2. **每一层可以独立调试。** 网页打不开，你可以一层层排查：先看应用层（HTTP 状态码对不对）→ 再看传输层（TCP 连没连上）→ 再看网络层（IP 通不通）→ 最后看链路层（网线插没插）。
3. **复杂问题被"封口"了。** 写一个 HTTP 服务器的人，**根本不用知道**数据包是怎么在光纤里编码的；他只需要信任"传输层会帮我可靠送达"。

## 0.4 数据是怎么"包起来又拆开"的：封装与解封装

分层带来的一个直接后果，是你发出去的数据会**一层层被"打包"**。

你（应用层）写了一个 HTTP 请求，原文可能是：

```text
GET /index.html HTTP/1.1
Host: www.example.com
```

这段文字往下走一层，**传输层**会给它前面加一个 TCP 头（写上"这是发给端口 80 的"）；再往下，**网络层**再加一个 IP 头（写上"目的地 IP 是 xxx"）；再往下，**链路层**再加一个以太网头 + 帧尾。

到对方机器，过程**完全反过来**：一层层"拆包"，每层读自己认识的头、干自己的活，然后把剩下的"内馅"往上传。

```
发送方（层层加壳）              接收方（层层剥壳）
┌──────────────┐              ┌──────────────┐
│ 应用层 HTTP   │  ← 数据       │ 应用层 HTTP   │  ← 读到真正的请求
├──────────────┤              ├──────────────┤
│ 传输层 TCP    │  ← +TCP 头    │ 传输层 TCP    │  ← 校验没丢、没乱序
├──────────────┤              ├──────────────┤
│ 网络层 IP     │  ← +IP 头     │ 网络层 IP     │  ← 确认是发给我这台
├──────────────┤              ├──────────────┤
│ 链路层 帧     │  ← +以太网头  │ 链路层 帧     │  ← 相邻一跳收到
└──────────────┘              └──────────────┘
        ↓ 通过真实物理介质（光/电/无线电）→
```

**每一层只看得懂自己的"头"（和可能有的"尾"），其余内容对它来说都是不透明的"货物"。**

这就是为什么后面你学 HTTP 的时候，完全不需要先懂光缆里的编码——**HTTP 只关心自己那一层。** 但也正因如此，当你真的遇到"网络问题"时，得知道去哪一层找原因。

> 一句话记住它：数据在网上走，是"一层层加信封、到了再一层层拆信封"。每一层只拆自己那一层的信封，所以各层互不干扰。

## 0.5 这一层哲学，直接决定了 HTTP 长什么样

你现在可能觉得"分层"是个抽象的架构理论，跟"写代码"关系不大。**错。** 它直接决定了你天天用的 HTTP 是长这样的：

**因为传输层（TCP）已经保证了"字节能可靠、有序地送达"，所以 HTTP 可以放心地是"纯文本"——**

```
GET /index.html HTTP/1.1
Host: www.example.com
User-Agent: Mozilla/5.0
```

你可以用肉眼直接读它、甚至手敲一条请求，**因为"可靠传输"这件苦活已经被 TCP 包了，HTTP 只管"表达意图"**。

**因为分层是"封装"，所以 HTTP 里可以有 `Host` 头**——它其实是在"一个 IP 上跑多个网站"这个现实需求出现后，HTTP 这一层自己加的一个字段，用来告诉服务器"你要的是哪个站点"。这就是"每层独立演进"的活例子。

**因为分层是"只跟邻居说话"，所以 HTTPS 可以"无痛升级"**——它其实是在应用层和传输层之间，又插了一层 **TLS（加密层）**。HTTP 还是那个 HTTP，只是在"往下送"之前多包了一层加密信封，你业务代码几乎不用改。

你会在后面每一章反复看到这个思想冒出来。所以：

> 一句话记住它：理解了"分层"，你就理解了 HTTP 为什么是文本、为什么有 `Host` 头、为什么 HTTPS 能平滑加上去——因为每一层都只负责一件事，也只影响一件事。

---

## 0.6 分层模型明确"不负责"什么

最后，说清楚分层模型**管不了**的事，免得你对它有不切实际的期待：

| 它不负责 | 原因 | 该在哪一层/用什么解决 |
|---|---|---|
| **保证数据一定送达** | 传输层的 UDP 就**不保证**送达（TCP 才保证）。网络拥塞时包照样可能丢 | 看你的应用能不能容忍丢包；要可靠就选 TCP |
| **保证安全** | 四层模型本身**不含加密**。明文 HTTP 在网络上是"裸奔"的 | 在应用层和传输层之间加 TLS（即 HTTPS） |
| **保证"发多快就收多快"** | 分层只管"分工"，不管"性能"。拥塞、延迟是物理世界的问题 | 应用层做缓存、CDN、HTTP/2 多路复用等 |
| **解释"内容是什么"** | 网络层以下根本不看你的数据内容，它只负责搬运 | 内容语义是应用层（HTTP、DNS）的事 |

**分层解决的是"复杂度"和"可演进性"，不是"可靠性"和"安全性"。** 后两样要你在正确的层上、用正确的机制去补。

## 0.7 思考题（不用写代码，想清楚就行）

1. 你在手机上看视频，画面卡顿。这可能出在哪一层？至少列出三层，并说出每层的典型症状。
2. 为什么说"换 Wi-Fi 不影响你浏览器里的 HTTP"？这体现了分层的哪个好处？
3. 明文 HTTP 和 HTTPS，在"分层"视角下，差别到底在哪一层？
4. 如果传输层不保证"可靠送达"，那 HTTP 为什么还能假设"我发出的每个字节对方都能按序收到"？（提示：想想 HTTP 依赖的是哪个传输层协议）

> 答案在读完 01、02、05 章之后自然清楚。现在想不通没关系，带着问题往下读。
