# 第 07 章 · HTTP/1.1 → HTTP/2 → HTTP/3：一路变快的 HTTP

> 前面几章你一直用 HTTP/1.1。这一章讲它的问题，以及 HTTP/2、HTTP/3 是怎么一代代改进的。
> 核心线索只有一个：**队头阻塞（Head-of-Line Blocking）**。
>
> 本章你需要记住的就一件事：**HTTP/1.1 的问题是"一条连接上请求排队"（队头阻塞）；HTTP/2 用"多路复用"解决了应用层的队头阻塞；HTTP/3 干脆把 TCP 换成基于 UDP 的 QUIC，连传输层的队头阻塞也解决了。**
>
> 这一条想清楚了，你就理解了整个 HTTP 演进史——它从头到尾都在跟"阻塞"作斗争。

---

## 07.1 HTTP/1.1 的问题：队头阻塞

**先说结论**：HTTP/1.1 有个著名的毛病——**队头阻塞**。一条 TCP 连接上，请求是一个接一个排队的，前面一个慢，后面所有都得等。

**回顾第 02 章的伏笔**：TCP 是**有序的字节流**，而且要**按序上交**。这意味着：如果前面一个请求的响应卡住了，后面的响应就算已经准备好了，也得排着队等——因为同一条连接上的字节必须按顺序传输。

**HTTP/1.1 的实际限制：**

1. **一条连接一次只能处理一个请求**。你发了请求 A，必须等 A 的响应回来，才能在这条连接上发请求 B。
2. 浏览器为了缓解这个，会开**多条并行连接**（比如对同一个域名开 6 条）。但连接有成本（每条都要三次握手、都要占资源），而且受限制（不能无限开）。

**队头阻塞的具体场景**：

```text
一条连接上：
  请求1（大图片，慢）→ 正在传输……
  请求2（小文本，快）→ 已经准备好了，但只能排队等请求1 传完
  请求3（小图标，快）→ 同上，排队
```

**结果就是**：一个大文件卡在前面，整条连接后面所有请求全堵住。这就是队头阻塞。

**配套示例 `examples/http/07-HTTP2与QUIC.mjs` 第 1 部分，实测了这个现象：**

```text
===== 1. HTTP/1.1 的队头阻塞 =====
同一条连接上：先发 /slow，紧接着发 /fast
  /slow 耗时 509 ms
  /fast 耗时 508 ms（被 /slow 堵住了，这就是队头阻塞）
  总耗时 510 ms，两条请求是"排队"而不是"并发"
```

**看明白了吗？** `/fast` 明明能瞬间完成，却硬是被 `/slow` 拖到 508ms——因为同一条连接，它只能排在 `/slow` 后面。

> 一句话记住它：HTTP/1.1 一条连接一次一个请求，前面的慢请求会堵住后面所有请求——这就是队头阻塞。

---

## 07.2 HTTP/2 的解法：多路复用

**先说结论**：HTTP/2 的核心改进是**多路复用（multiplexing）**——在**一条** TCP 连接上，同时并行传输**多个请求/响应**，彼此互不阻塞。

**怎么做到的？** HTTP/2 把"请求-响应"拆成一个个**独立的帧（frame）**，给每个请求一个**流 ID（stream id）**。同一条连接上，不同流的帧可以**交错**发送：

```text
HTTP/1.1（串行）：  [请求1 完整][响应1 完整][请求2 完整][响应2 完整]

HTTP/2（多路复用）：
  流1: [请求1] ...... [响应1]
  流2: [请求2] [响应2]
  流3: [请求3] ...... [响应3]
  都在同一条连接上，帧交错传输，互不阻塞
```

**这样，`/slow` 慢它的，`/fast` 快它的**——`/fast` 的响应帧可以先到，不用等 `/slow`。

**配套示例第 2 部分，实测对比：**

```text
===== 2. HTTP/2 的多路复用 =====
同一条连接上：并发发 /slow 和 /fast（HTTP/2 一个连接里有多条流）
  /slow 耗时 509 ms
  /fast 耗时 2 ms（没被堵，两条流互不干扰）
  总耗时 509 ms，慢的挡不住快的
```

**对比强烈**：同样是"慢请求 + 快请求"，HTTP/1.1 里 `/fast` 被拖到 508ms，HTTP/2 里 `/fast` 只要 2ms。

**多路复用带来的三大好处：**

| 好处 | 说明 |
|---|---|
| 一条连接就够 | 不用开 6 条并行连接 |
| 请求不排队 | 慢请求挡不住快请求 |
| 连接成本下降 | 少了 N 次三次握手、N 份资源 |

> 一句话记住它：HTTP/2 用"帧 + 流 ID"把请求拆成交错的帧，在一条连接上并行传输——这就是多路复用，解决了 HTTP/1.1 的队头阻塞。

---

## 07.3 HTTP/2 的其他改进：头部压缩、二进制、服务器推送

**先说结论**：多路复用是 HTTP/2 的头号改进，但还有三个重要改进：**头部压缩**、**二进制分帧**、**服务器推送**。

**改进一：头部压缩（HPACK）。** HTTP/1.1 里，每个请求都要把 `Cookie`、`User-Agent` 这些头**完整重发一遍**——这些头又长又重复。HTTP/2 用 HPACK 算法，**重复的头只发一次，之后发"引用"**，大大省流量。

```text
HTTP/1.1：每个请求都带完整的 Cookie、User-Agent（几百字节重复发）
HTTP/2  ：头用 HPACK 压缩，重复部分只发一次
```

**改进二：二进制分帧。** HTTP/1.1 是**文本**，HTTP/2 是**二进制**。二进制对机器来说更好解析、更紧凑、更不容易出错（第 04 章说了 HTTP/1.1 是文本，但文本解析慢、有歧义）。

**改进三：服务器推送（Server Push）。** 服务器可以**主动**把资源推给客户端，不等客户端请求。比如你请求 `index.html`，服务器主动把 `style.css`、`app.js` 一起推过来。

（顺带一提：服务器推送在实践中效果争议较大，Chrome 后来甚至移除了对它的支持，所以这条知道概念即可。）

**一句话总结 HTTP/2 的升级**：多路复用（头号）、头部压缩（省流量）、二进制（好解析）、服务器推送（主动）。

> 一句话记住它：HTTP/2 除了多路复用，还有头部压缩（HPACK，重复头只发一次）、二进制分帧、服务器推送——核心还是"更快"。

---

## 07.4 HTTP/2 没解决的问题：TCP 层的队头阻塞

**先说结论**：HTTP/2 解决了**应用层**的队头阻塞，但没解决**传输层（TCP）**的队头阻塞——因为所有流还是跑在**同一条 TCP 连接**上，而 TCP 要**按序上交**。

**问题出在哪？** 回到第 02 章：TCP 是有序的，前面一个包丢了，后面的包只能等重传。

```text
HTTP/2 的多条流都跑在同一条 TCP 连接上
TCP 按字节序号传输，前面丢了，后面都得等

流1: [包1] [包2] [包3] ...
流2: [包4] [包5] ...
       ↑ 如果包1 丢了，包2、3、4、5 全要等包1 重传
       即使包4、5 属于流2，跟包1 毫无关系，也得等
```

**所以**：HTTP/2 解决了"请求排队"（应用层队头阻塞），但"一个 TCP 包丢了，整个连接的所有流都卡"（传输层队头阻塞）**依然存在**。

**什么时候这个很致命？** 在网络不稳定（丢包多）的场景——比如移动网络、Wi-Fi 信号差。一个包丢了，整条连接所有流都停，多路复用的好处大打折扣。

**这就是 HTTP/3 要解决的问题**：既然 TCP 的"有序 + 按序上交"是队头阻塞的根源，那干脆**不用 TCP 了**。

> 一句话记住它：HTTP/2 解决了应用层队头阻塞，但传输层（TCP 一个包丢了卡所有流）的队头阻塞还在——所以有了 HTTP/3。

---

## 07.5 HTTP/3 与 QUIC：把 TCP 换成 UDP

**先说结论**：HTTP/3 做了一个大胆的决定——**不用 TCP 了，改用基于 UDP 的 QUIC 协议**。QUIC 在 UDP 之上**自己实现**可靠性和多路复用，从而根治了 TCP 的队头阻塞。

**为什么换掉 TCP 能解决队头阻塞？** 因为 TCP 的队头阻塞来自"整个连接按字节序号严格有序"。QUIC 改成了"**每个流独立**"——一个流丢包，只影响它自己，不影响别的流：

```text
TCP（HTTP/2）：一个包丢 → 整条连接所有流都停（严格有序）
QUIC（HTTP/3）：流1 丢包 → 只有流1 停，流2、流3 照常传输（流独立）
```

**QUIC 的三大特点：**

| 特点 | 说明 |
|---|---|
| 跑在 UDP 上 | 不依赖内核的 TCP，协议栈在**用户态**，升级更快 |
| 流独立 | 一个流丢包不影响别的流，根治队头阻塞 |
| 连接建立更快 | 握手更短，甚至 0-RTT |

**为什么选 UDP 而不是"改 TCP"？** 因为 TCP 协议栈在**操作系统内核**里，改它意味着全世界所有操作系统都得升级——几十年都推不动。而 UDP 简单，QUIC 可以**在应用层（用户态）自己实现**，不依赖内核，升级快得多。

**一个重要的对应关系：**

```text
HTTP/1.1 → 跑在 TCP 上
HTTP/2   → 跑在 TCP 上（加多路复用）
HTTP/3   → 跑在 QUIC 上（QUIC 又跑在 UDP 上）
```

**配套示例第 3 部分，演示了 UDP 的本质（QUIC 的"地基"）：**

```text
===== 3. UDP：HTTP/3（QUIC）为什么换掉 TCP =====
  客户端连"连接"都不用建立，直接扔 3 个独立数据报
  UDP 不保证顺序、不保证送达——QUIC 是在 UDP 之上自己实现"可靠 + 多路复用"
  好处：一条连接里某个流丢了，不会卡住其它流（这正是 HTTP/3 的目标）
```

> 一句话记住它：HTTP/3 换掉 TCP，用基于 UDP 的 QUIC；QUIC 在用户态自己实现可靠性和"流独立"，根治了 TCP 的队头阻塞。

## 07.6 深入：HTTP/2 的二进制帧

**先说结论**：HTTP/2 不再用 HTTP/1.1 的文本格式，而是把请求/响应切成一个个**二进制帧（frame）**。每个帧有一个 9 字节的帧头，标明"这是哪个流的、什么类型、多长"。

**为什么要换成二进制？** 因为文本有三大缺点：解析慢（要逐字节找换行符）、有歧义（大小写、空白）、不好扩展。二进制对机器来说解析快、无歧义、容易加新类型。

**一个 HTTP/2 帧的结构（简化）：**

```text
┌─────────────────────────┬──────────┬────────────┐
│  长度(3字节)  类型(1字节)│ 标志(1字节)│ 流ID(4字节) │   ← 9 字节帧头
├─────────────────────────┴──────────┴────────────┤
│                   帧负载（frame payload）          │
└──────────────────────────────────────────────────┘
```

**帧头里最关键的字段：**

| 字段 | 作用 |
|---|---|
| 长度 | 这个帧的负载有多长 |
| 类型 | 这个帧是干嘛的（HEADERS、DATA、SETTINGS…） |
| 流 ID | **这个帧属于哪个请求**（多路复用的关键） |

**流 ID 就是多路复用的核心**。同一条连接上，流 1 的帧、流 2 的帧、流 3 的帧交错发送，接收方靠流 ID 把帧重新归位到各自的请求：

```text
流1: [HEADERS] ... [DATA] ... [DATA]
流2: [HEADERS] [DATA]
流3: [HEADERS] ... [DATA]
     ↑ 帧交错传输，按流 ID 重组
```

**常见帧类型：**

| 帧类型 | 作用 |
|---|---|
| HEADERS | 请求/响应头 |
| DATA | 请求/响应体 |
| SETTINGS | 连接参数协商 |
| PING | 保活/测延迟 |
| RST_STREAM | 提前终止某个流 |

> 一句话记住它：HTTP/2 用"9 字节帧头 + 负载"的二进制帧取代文本，帧头的**流 ID** 就是多路复用的关键——按流 ID 把交错的帧重新归位。

## 07.7 深入：HPACK 头部压缩

**先说结论**：HTTP/1.1 的请求头又长又重复（`Cookie`、`User-Agent` 每个请求都完整重发），浪费大量带宽。HTTP/2 用 **HPACK** 算法压缩头部——**重复的头只发一次，之后发"索引号"**。

**问题的严重性**：看两个连续请求的头：

```http
请求1: User-Agent: Mozilla/5.0 (长串)  Cookie: sid=abc... (几百字节)
请求2: User-Agent: Mozilla/5.0 (一模一样)  Cookie: sid=abc... (一模一样)
```

`User-Agent` 和 `Cookie` 在请求 2 里**原样重复**，白传几百字节。

**HPACK 的做法**：维护一张**静态表 + 动态表**，把常见的头存进表里。发的时候，如果头在表里，就只发**索引号**（几个字节），而不是完整字符串。

```text
静态表（固定）：1 = ":method: GET"，2 = ":method: POST"，3 = ":path: /" ...
动态表（连接内累积）：第 62 项 = "cookie: sid=abc..."（第一次发完整，之后发 62）
```

**效果**：第二次请求，`Cookie` 直接发"索引 62"，几十字节变成 1~2 字节。请求越多，动态表越满，压缩效果越好。

**为什么 HTTP/1.1 不这么做？** 因为 HTTP/1.1 是文本的、每条连接短命（用完就断），没有"连接内累积的动态表"这个概念。HTTP/2 的长连接 + 多路复用，让"一条连接发很多请求"成为常态，头部压缩才大有用武之地。

> 一句话记住它：HPACK 用"静态表 + 动态表"把重复的头变成索引号，重复头只发一次；HTTP/2 长连接让这个优化威力巨大。

## 07.8 深入：HTTP/3 的更多特性

**先说结论**：HTTP/3 除了根治队头阻塞，还有两个"换 QUIC"带来的额外好处：**0-RTT 连接恢复**和**连接迁移**。

**特性一：0-RTT 连接恢复。** HTTP/1.1 和 HTTP/2 的 HTTPS，每次建立连接要"TCP 三次握手 + TLS 握手"，好几个往返。HTTP/3 的 QUIC 把握手合并简化，**重连时甚至能做到 0-RTT**——上次连过的服务器，这次直接带上加密数据，不用重新握手。

**特性二：连接迁移（connection migration）。** 这是 QUIC 最优雅的特性之一。TCP 的连接靠四元组 `（源IP，源端口，目标IP，目标端口）` 标识，**你从 Wi-Fi 切到手机流量，IP 变了，TCP 连接就断了**，所有请求重来。QUIC 的连接靠**连接 ID** 标识，不依赖 IP——你换网络，IP 变了，连接 ID 不变，**连接无缝继续**。

```text
TCP：Wi-Fi（IP A）→ 切 4G（IP B）→ 四元组变了 → 连接断，请求重来
QUIC：Wi-Fi（IP A）→ 切 4G（IP B）→ 连接 ID 没变 → 连接继续，无缝切换
```

**这就是为什么 HTTP/3 特别适合移动端**——手机频繁在 Wi-Fi 和蜂窝网络之间切换，TCP 每次切换都断线重连，QUIC 则几乎无感。

**一个诚实的现状**：HTTP/3 和 QUIC 还在普及中（Google、Cloudflare、YouTube 已支持），而且它在 Node 里目前没有内置支持（需要第三方库，超出了本教程"零依赖"的范围）。所以配套示例里用 UDP 演示了 QUIC 的"地基"，但没真的跑一个 HTTP/3 服务。

> 一句话记住它：HTTP/3 换 QUIC 还带来 0-RTT 恢复和连接迁移（换网络不断线）两个红利，尤其适合移动端；但普及中，Node 暂无内置支持。

## 07.9 三代 HTTP 一张表

**先说结论**：把三代 HTTP 的演进串成一张表，你就有了整个 HTTP 发展史的"地图"。

| | HTTP/1.1 | HTTP/2 | HTTP/3 |
|---|---|---|---|
| 传输层 | TCP | TCP | **UDP（QUIC）** |
| 格式 | 文本 | 二进制 | 二进制 |
| 队头阻塞 | 有（应用层：请求排队） | 有（传输层：一个包卡所有流） | **基本根治** |
| 多路复用 | 无 | 有 | 有（且流独立） |
| 头部压缩 | 无 | HPACK | QPACK |
| 连接建立 | 3 次握手 | 3 次握手 + TLS | 握手更短，可 0-RTT |

**演进的主线，一句话总结：**

```text
HTTP/1.1：能用，但慢（请求排队）
HTTP/2  ：解决了应用层排队（多路复用）
HTTP/3  ：解决了传输层阻塞（换 QUIC）
```

**你该用什么？** 现实是：**HTTP/2 已经是主流**（各大网站都用），HTTP/3 正在普及（Google、Cloudflare、YouTube 等已支持）。写代码时，这些对你大多是**透明的**——`fetch`、`node:http` 会自动协商用哪个版本，你通常不用管。

**唯一要动手的**：用 `node:http2` 起 HTTP/2 服务（配套示例已经演示了）。HTTP/3 在 Node 里目前没有内置支持（需要第三方库，超出了"零依赖"的范围）。

> 一句话记住它：HTTP 演进就是一路跟"阻塞"作斗争——1.1 请求排队、2 解决应用层排队、3 连传输层阻塞也解决。

## 07.10 本章常见坑速查

| 坑 | 现象 | 原因 | 正确做法 |
|---|---|---|---|
| 以为 HTTP/2 就彻底没有队头阻塞了 | 弱网下仍然卡 | HTTP/2 只解决应用层，TCP 层队头阻塞还在 | 弱网场景考虑 HTTP/3 |
| 用明文 http:// 访问 HTTP/2 服务 | 连不上或降级 | 主流浏览器只支持 HTTPS 下的 HTTP/2 | HTTP/2 配 HTTPS |
| 以为 HTTP/3 直接跑在 TCP 上 | 概念错误 | HTTP/3 跑在 QUIC（基于 UDP） | 记住 HTTP/3 → QUIC → UDP |
| 以为 UDP 不可靠所以 HTTP/3 不可靠 | 理解偏差 | QUIC 在 UDP 之上**自己实现**了可靠 | UDP 只是"地基"，可靠性由 QUIC 补 |
| 手动解析 HTTP/1.1 文本报文 | 解析复杂易错 | 文本格式有歧义、慢 | 用现成的 `node:http`，或 HTTP/2 二进制帧 |

## 07.11 本章小结

- **HTTP/1.1 的队头阻塞**：一条连接一次一个请求，慢请求堵住后面所有。
- **HTTP/2 多路复用**：帧 + 流 ID，一条连接并行传多个请求，慢的挡不住快的。
- **HTTP/2 其他改进**：HPACK 头部压缩、二进制分帧、服务器推送。
- **HTTP/2 的局限**：仍跑在 TCP 上，TCP 层队头阻塞（一个包丢卡所有流）没解决。
- **HTTP/3 换 QUIC**：基于 UDP，在用户态实现可靠性和"流独立"，根治队头阻塞。
- **演进主线**：1.1 请求排队 → 2 解决应用层排队 → 3 解决传输层阻塞。
- **实战**：HTTP/2 已是主流（配 HTTPS）；HTTP/3 正在普及；代码里大多透明，`node:http2` 可起 HTTP/2 服务。

## 07.12 动手练习

**1. HTTP/1.1 的队头阻塞和 HTTP/2 的队头阻塞有什么不同？**

<details><summary>参考答案</summary>

- HTTP/1.1 的队头阻塞是**应用层**的：一条连接一次只处理一个请求，请求排队，前面的慢请求堵住后面。
- HTTP/2 用多路复用解决了上面这个，但仍跑在 TCP 上，所以有**传输层**的队头阻塞：一个 TCP 包丢了，整条连接的所有流都得等重传（因为 TCP 按序上交）。

HTTP/3 换 QUIC，流独立，才把传输层的队头阻塞也解决掉。

</details>

**2. HTTP/2 怎么实现"一条连接上并行多个请求"？**

<details><summary>参考答案</summary>

把每个请求-响应拆成**独立的帧（frame）**，给每个请求一个**流 ID**。同一条连接上，不同流的帧可以**交错传输**，接收方按流 ID 把帧重新组装回各自的请求/响应。于是慢请求的帧挡不住快请求的帧。

</details>

**3. 为什么 HTTP/3 选 UDP 而不是"改造 TCP"？**

<details><summary>参考答案</summary>

因为 TCP 协议栈在**操作系统内核**里，改造 TCP 意味着全世界所有操作系统都要升级，几十年推不动。而 UDP 简单，QUIC 可以在**应用层（用户态）自己实现**可靠性、多路复用，不依赖内核，升级快得多。

</details>

**4. QUIC 跑在 UDP 上，UDP 又不可靠，那 HTTP/3 怎么保证可靠？**

<details><summary>参考答案</summary>

UDP 只是"地基"，不可靠。QUIC 在 UDP 之上**自己实现**了可靠传输——序号、确认、重传、拥塞控制，都搬到用户态来做。所以 HTTP/3 依然可靠，只是"可靠性"不是由 TCP 提供，而是由 QUIC 提供。

</details>

**5. 你现在写 `fetch()` 时，需要指定用 HTTP/1.1 还是 HTTP/2 吗？为什么？**

<details><summary>参考答案</summary>

不需要。HTTP 版本协商是**自动的**：客户端和服务器在 TLS 握手时通过 ALPN 协商用哪个版本，`fetch`、`node:http` 会自动处理。你只管发请求，版本选择是底层的事。

</details>
