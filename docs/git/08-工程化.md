## 08.1 `.gitignore`：让 Git 永远忽略某些文件

### 先给结论

`.gitignore` 是一个**放在仓库根目录**的文件，里面每一行是一条"忽略规则"。命中的文件，Git 会当它们不存在：不跟踪、不提交、`git status` 也不显示。

### 什么时候必须用它

- `node_modules/`：依赖目录，几十上百 MB，且能随时 `npm install` 还原；
- `*.log`：日志文件，每跑一次变一次；
- `.env`：环境变量，**含密钥，绝不能提交**；
- 编译产物：`dist/`、`build/`、`.cache/`。

**不 ignore 这些，你的仓库会迅速膨胀，还可能把密钥泄出去。**

### 规则语法

```text
# 注释用 # 开头

node_modules/        # 忽略整个目录（带 / 后缀表示目录）
*.log                # 忽略所有 .log 文件（* 是通配符）
build/               # 忽略 build 目录
!important.log       # 例外：不忽略 important.log（! 取反）
.DS_Store            # 忽略 macOS 的垃圾文件
```

几条关键规则：

| 规则 | 含义 |
|---|---|
| `file.txt` | 忽略所有叫 file.txt 的文件 |
| `/file.txt` | 只忽略**根目录**下的 file.txt（带 `/` 开头） |
| `dir/` | 忽略整个 dir 目录 |
| `*.log` | 忽略所有 .log 文件 |
| `!keep.log` | 取反：不忽略 keep.log（需放在忽略规则之后） |

### 一个最重要的坑：已跟踪的文件，加了忽略也没用

**`.gitignore` 只对"未跟踪"的文件生效。** 如果一个文件**已经被 `git add` / 提交过了**，你再把它写进 `.gitignore`，Git 依然会跟踪它、依然会显示它的改动。

验证：

```bash
echo secret > config.txt
git add config.txt && git commit -m "tracked"
echo "config.txt" >> .gitignore
git status -s
```

```text
 M .gitignore
```

你看不到 `config.txt` 被忽略——它已经在版本库里了。要让它真正被忽略，得先把它从版本库里"踢出去"（但**保留本地文件**）：

```bash
git rm --cached config.txt     # 从版本库移除，但保留本地文件
```

之后再 `git status`，它就会按 `.gitignore` 规则被忽略了。

### 验证某条规则

```bash
git check-ignore -v node_modules/xxx.js
```

如果命中了，会打印是哪条规则命中的；没输出就是没命中。**这是排查"为什么这个文件没被忽略"的利器。**

> 一句话记住它：`.gitignore` 只对"未跟踪"文件生效；已跟踪的文件要先 `git rm --cached` 踢出版本库，忽略规则才管用。

## 08.2 Git Hooks：提交前后的自动化关卡

### 先给结论

**Git Hooks 是放在 `.git/hooks/` 目录下的一堆脚本**，Git 会在特定时机自动执行它们。比如 `pre-commit` 钩子，会在你 `git commit` **之前**跑一次。

### 常见的钩子

| 钩子 | 触发时机 | 典型用途 |
|---|---|---|
| `pre-commit` | commit 之前 | 跑 lint、跑测试、检查提交信息格式 |
| `commit-msg` | 写提交信息时 | 校验提交信息是否符合规范 |
| `pre-push` | push 之前 | 跑完整测试、阻止推坏分支 |
| `post-commit` | commit 之后 | 通知、记录 |

**最常用的是 `pre-commit`**——它能在坏代码进入历史之前拦下来。

### 亲手写一个 pre-commit

`.git/hooks/` 里默认有一堆 `.sample` 文件（示例），去掉 `.sample` 后缀就生效。写一个最简单的：

```bash
cat > .git/hooks/pre-commit <<'EOF'
#!/bin/sh
echo ">>> pre-commit 钩子被触发了！"
EOF
chmod +x .git/hooks/pre-commit
```

然后随便提交一次：

```bash
git commit -m "test"
```

```text
>>> pre-commit 钩子被触发了！
```

### 钩子能拦人：返回非 0 就拒绝提交

钩子脚本如果**以非 0 退出**，Git 就会**取消这次提交**。这是它"把关"的原理：

```bash
cat > .git/hooks/pre-commit <<'EOF'
#!/bin/sh
# 如果提交里有 console.log，就拒绝
if git diff --cached | grep -q "console.log"; then
  echo "❌ 提交里还有 console.log，先删掉！"
  exit 1
fi
EOF
```

这个钩子会在你提交含 `console.log` 的代码时拦住你。

### 两个必须知道的坑

**坑一：hooks 不会被 `git clone` 带走。**

`.git/hooks/` 属于 `.git` 目录，**不在版本控制里**。你 clone 一个仓库，不会得到它配置的 hooks。所以团队要共享 hooks，得用专门方案（比如把 hooks 脚本放进仓库 + 一个 setup 脚本，或 Husky 这类工具，或 Git 2.9+ 的 `core.hooksPath` 指向仓库内目录）。

**坑二：hooks 只在你本地触发，拦不住别人直接 push。**

hooks 是**本地**的。别人如果没有同样的 hooks，照样能提交坏代码。所以 hooks 是"第一道防线"（个人自检），真正的"第二道防线"在服务端（GitHub Actions、CI 等）。

> 一句话记住它：hooks 是 `.git/hooks/` 下的脚本，在提交/推送等时机自动执行；返回非 0 就拦住操作；hooks 不会被 clone 带走，要共享得用专门方案。

## 08.3 `git stash`：把没做完的改动藏起来

### 先给结论

**`git stash` 把你工作区和暂存区里"没提交的改动"临时藏起来，让工作区恢复干净**，好让你去切分支、拉代码、或处理别的事。之后再用 `git stash pop` 把改动拿回来。

### 一个真实场景

你正在 `feature` 分支上改代码，改到一半，突然要修一个线上紧急 bug。但你的改动没做完、不想提交。这时：

```bash
git stash           # 藏起未提交的改动
git switch -c hotfix # 干净地切过去
# ... 修 bug、提交 ...
git switch feature
git stash pop       # 把之前藏起来的改动拿回来
```

### 常用命令

| 命令 | 作用 |
|---|---|
| `git stash` | 藏起改动（默认工作区 + 暂存区） |
| `git stash list` | 看藏了几份 |
| `git stash pop` | 取出最新一份，并**从 stash 列表删除** |
| `git stash apply` | 取出最新一份，但**保留在列表里**（可反复用） |
| `git stash drop` | 丢弃某一份 stash |
| `git stash push -m "说明"` | 藏起并加说明 |

### `pop` 和 `apply` 的区别

这是最常混的：

- `pop` = 取出 **+ 删除**（一次性）；
- `apply` = 取出 **不删除**（可多次应用到不同分支）。

想"把同一份改动同时应用到处"，用 `apply`；想"取回来就用掉"，用 `pop`。

### 一个真实的报错：pop 时冲突

如果 stash 藏起来之后，这个文件又被别人（或你自己在别处）改了，`git stash pop` 可能冲突：

```text
CONFLICT (content): Merge conflict in xxx
The stash entry is kept in case you need it again.
```

**注意最后一句**：冲突时 stash 条目**不会被删除**，它还在 `git stash list` 里，你可以解决冲突后继续，或 `git stash drop` 丢弃。

> 一句话记住它：stash 藏起未提交改动、恢复干净工作区；`pop` 取出并删除，`apply` 取出不删除；pop 冲突时 stash 条目会保留。

## 08.4 `git tag`：给里程碑钉个标签

### 先给结论

**`git tag` 给某个 commit 起一个稳定的、人类可读的名字**（通常是版本号）。和分支不同，标签一般**不动**——它就是为了"钉住"某个发布点。

### 两种标签

| 类型 | 命令 | 特点 |
|---|---|---|
| 轻量标签（lightweight） | `git tag v1.0.0` | 就是给 commit 起了个名字，没有额外信息 |
| 附注标签（annotated） | `git tag -a v1.0.0 -m "说明"` | 是独立对象，含打标签的人、时间、说明 |

**发布版本时用附注标签**（`-a`），因为它记录的信息更全，能被 `git describe`、`git show` 更好地处理。

### 常用命令

```bash
git tag                     # 列出所有标签
git tag v1.0.0              # 轻量标签
git tag -a v1.0.0 -m "首个版本"   # 附注标签
git tag -n                  # 列出标签 + 说明
git show v1.0.0             # 看标签指向的提交
git push origin v1.0.0      # 把标签推到远程
git push origin --tags      # 推所有标签
```

### 标签和分支的区别

| | 分支（branch） | 标签（tag） |
|---|---|---|
| 会移动吗 | 会，每次 commit 往前挪 | 不会，钉死在某个 commit |
| 用途 | 持续的开发线 | 里程碑/发布点 |
| 能提交吗 | 能 | 不能（标签只是指针） |

**一句话理解：分支是"进行中的线"，标签是"钉住的点"。**

> 一句话记住它：tag 给 commit 钉一个稳定名字（版本号）；轻量标签只是指针，附注标签（`-a`）是独立对象、信息更全；发布用附注标签。

## 08.5 子模块与大文件：两个"超纲"问题的概览

Git 有两个众所周知的短板，这里给结论，不做深入——真遇到了再查文档。

### 子模块（submodule）

**问题**：一个项目里想引用另一个独立的 Git 仓库（比如公共组件库）。直接 copy 进来？两个仓库的历史就乱了。

**Git 的解法**：`git submodule`，让一个仓库**嵌套引用**另一个仓库。但它是出了名的**难用**——切换、更新、删除子模块都容易踩坑。

```bash
git submodule add https://github.com/某/组件.git libs/组件
```

**结论**：能用 monorepo（把相关项目放一个仓库里）解决的，就别上 submodule。它只在"必须严格隔离两个独立仓库"时才值得用。

### 大文件（Large File Storage）

**问题**：Git 按"内容快照"存文件，塞几个 500MB 的视频、PSD 进去，仓库会飞快膨胀，且每个克隆的人都得下载全部历史。

**Git 的解法**：Git LFS（Large File Storage）。原理是**仓库里只存一个"指针"**（几 KB 的文本），真正的文件存在 LFS 服务器上。

```bash
git lfs track "*.psd"
```

**结论**：二进制大文件（视频、设计稿、数据集）该用 LFS 或对象存储，别硬塞进 Git。

> 一句话记住它：子模块解决"仓库嵌套引用"但难用，能用 monorepo 就用 monorepo；大文件用 Git LFS，仓库里只存指针。

## 08.6 `.gitignore` 进阶：全局忽略与优先级

### 先给结论

除了项目里的 `.gitignore`，Git 还支持**全局忽略**，并且忽略规则有**优先级**。

### 全局忽略：`~/.gitignore_global`

有些东西是**每台机器特有的**，不该写进项目（因为别人不需要、也不该替别人决定）：

- macOS 的 `.DS_Store`；
- 编辑器配置 `.vscode/`、`.idea/`；
- 系统临时文件。

这些放进**全局忽略文件**，对这台机器上所有仓库生效：

```bash
git config --global core.excludesfile ~/.gitignore_global
echo ".DS_Store" >> ~/.gitignore_global
echo ".vscode/" >> ~/.gitignore_global
```

**注意**：全局忽略是你**个人**的行为，不该塞进项目仓库（否则你在强迫所有同事忽略你的编辑器配置）。

### 忽略规则的优先级

一个文件可以被多个规则命中，优先级从高到低：

1. 命令行指定的（`git check-ignore` 或临时）；
2. `.gitignore` 里的规则（项目级）；
3. 全局忽略文件里的规则；
4. `.git/info/exclude`（仓库级，但不提交）。

**后面写的规则覆盖前面写的**（同一文件里），所以 `!keep.log` 这种取反要写在忽略规则**之后**才生效。

### 验证规则

```bash
git check-ignore -v node_modules/xxx.js
```

会打印命中了哪条规则、在哪个文件里。**排查"为什么没忽略/为什么被忽略"就靠它。**

> 一句话记住它：机器特有的忽略放全局（`core.excludesfile`），项目共有的放 `.gitignore`；`check-ignore -v` 查规则命中来源。

## 08.7 Git Hooks 进阶：`commit-msg` 校验提交信息

### 先给结论

第 08.2 节讲了 `pre-commit`。还有一个同样重要的钩子 **`commit-msg`**，它在**你写完提交信息后**触发，用来校验提交信息是否符合规范。

### 为什么要校验提交信息

第 02 章讲了 Conventional Commits 规范。但"规范"靠自觉是不靠谱的——总会有人提交 `update`、`fix bug`。`commit-msg` 钩子能在**提交前**把不合规的信息拦下来。

### 一个真实的 commit-msg 钩子

`.git/hooks/commit-msg`：

```bash
#!/bin/sh
# 校验提交信息必须符合 <type>: <subject> 格式
msg=$(cat "$1")                      # $1 是提交信息文件路径
if ! echo "$msg" | grep -Eq '^(feat|fix|docs|style|refactor|test|chore)(\(.+\))?: '; then
  echo "❌ 提交信息不符合规范！格式：feat(scope): 说明"
  exit 1                             # 返回非 0，拒绝提交
fi
```

之后你提交 `update` 这种信息，会被直接拦下：

```text
❌ 提交信息不符合规范！格式：feat(scope): 说明
```

### pre-commit 和 commit-msg 的分工

| 钩子 | 触发时机 | 校验什么 |
|---|---|---|
| `pre-commit` | 提交之前 | 代码内容（lint、测试、调试语句） |
| `commit-msg` | 提交信息写好之后 | 提交信息格式 |

**两者配合**，一个管"代码对不对"，一个管"信息规不规范"。

### 钩子的传递问题（再次强调）

这些钩子都在 `.git/hooks/` 下，**不会被 clone 带走**。团队要共享，推荐用 `core.hooksPath` 指向仓库内的一个目录：

```bash
# 把钩子放进仓库的 .githooks/ 目录，然后：
git config core.hooksPath .githooks
```

这样钩子脚本本身被版本控制，clone 的人 `git config core.hooksPath .githooks` 一条命令就能启用。

> 一句话记住它：`commit-msg` 校验提交信息格式（pre-commit 校验代码）；钩子要团队共享，用 `core.hooksPath` 指向仓库内目录。

## 08.8 tag 进阶：`git describe` 与标签推送

### 先给结论

`git tag` 你会在 08.4 节用。这一节补两个**团队里高频**的进阶用法：`git describe` 和标签的推送/删除。

### `git describe`：从标签推算当前版本

`git describe` 告诉你"当前 HEAD 距离最近的标签有多远"，用于生成版本号：

```bash
git describe
```

```text
v1.0.0-2-g52d26c8
```

拆解：

- `v1.0.0`：最近的标签；
- `2`：距离那个标签又往前走了 2 个提交；
- `g52d26c8`：当前 HEAD 的短哈希（`g` 是 "git" 的意思）。

**用途**：自动化构建时，用 `git describe` 生成一个"带距离信息"的版本号，方便追踪是哪个提交构建的。

### 标签要单独推送

```bash
git push origin v1.0.0       # 推单个标签
git push origin --tags       # 推所有标签
git push origin --follow-tags  # 推代码时顺带推"附注标签"
```

**`git push origin main` 不会自动推标签**，这是新手最容易忘的（第 08.4 节提过，这里再强调）。

### 删除标签

```bash
git tag -d v1.0.0                 # 删本地标签
git push origin --delete v1.0.0   # 删远程标签
```

### 一个真实场景：用 tag + describe 定位线上问题

线上出了 bug，你想知道"线上跑的是哪个版本"。如果部署时打好了标签，`git describe` 一查就知道：`v1.2.3-1-gabc1234` 表示"线上是 v1.2.3 之后第 1 个提交"。再 `git log` 定位到具体改动，几分钟锁定问题。

> 一句话记住它：`git describe` 从标签推版本号；标签要单独 push（`--tags`），删标签用 `tag -d` + `push --delete`。

## 08.9 本章常见坑速查

| 坑 | 现象 | 原因 | 正确做法 |
|---|---|---|---|
| 已跟踪文件加忽略无效 | `.gitignore` 写了还提交 | ignore 只对未跟踪文件生效 | `git rm --cached <file>` 踢出版本库 |
| 把 `.env` 提交了 | 密钥泄露 | 没在第一次提交前 ignore | 立即改密钥 + `git rm --cached .env` + ignore |
| clone 后 hooks 没了 | 别人仓库没你的 hooks | hooks 不在版本控制里 | 用 `core.hooksPath` 指向仓库内目录，或 Husky |
| 以为 hooks 能拦所有人 | 别人照样提交坏代码 | hooks 是本地第一道防线 | 服务端再上 CI 做第二道防线 |
| `stash pop` 后改动没了 | 以为丢代码 | pop 取出并删除，可能没意识到 | 想保留就用 `apply` |
| stash 后切分支忘了 pop | 改动"消失" | 藏起来没取回 | `git stash list` 看有没有，`pop` 取回 |
| 发布用轻量标签 | 标签信息不全 | 轻量标签没说明/作者 | 发布用 `git tag -a -m` |
| 标签忘了推远程 | 别人看不到 | tag 不会随 push 自动传 | `git push origin --tags` |

## 08.10 本章小结

**.gitignore**

- 用 glob 规则忽略垃圾文件、密钥、依赖目录。
- **只对未跟踪文件生效**；已跟踪的要 `git rm --cached`。

**Git Hooks**

- `.git/hooks/` 下的脚本，`pre-commit`/`commit-msg`/`pre-push` 等时机触发。
- 返回非 0 拦截操作；hooks 不被 clone 带走，是本地第一道防线。

**stash**

- 藏起未提交改动，`pop` 取出并删除，`apply` 取出不删除。

**tag**

- 给 commit 钉版本号；轻量标签 vs 附注标签（`-a`），发布用附注标签。

**子模块 / 大文件**

- submodule 嵌套引用仓库（难用，优先 monorepo）；大文件用 LFS。

## 08.11 动手练习

### 练习 1：写一个 `.gitignore`

为一个 Node.js 项目写 `.gitignore`，要求忽略：`node_modules/`、所有 `.log`、`.env`、`dist/`、macOS 的 `.DS_Store`。

<details><summary>参考答案</summary>

```text
node_modules/
*.log
.env
dist/
.DS_Store
```

</details>

### 练习 2：让一个已跟踪文件被忽略

`secret.key` 已经被提交过了，现在你想忽略它（但保留本地文件）。写出步骤。

<details><summary>参考答案</summary>

```bash
echo "secret.key" >> .gitignore
git rm --cached secret.key    # 从版本库移除，保留本地文件
git commit -m "chore: 停止跟踪 secret.key"
```

关键：只加 `.gitignore` 没用，必须 `git rm --cached` 把已跟踪的文件踢出版本库。

</details>

### 练习 3：判断对错

1. Git Hooks 会被 `git clone` 一起复制过去。
2. `git stash pop` 之后，stash 列表里就没有这一条了。
3. 标签会像分支一样，随着 commit 自动往前移动。
4. `.gitignore` 对已经提交过的文件也生效。
5. 发布版本时应该用附注标签（`-a`）。

<details><summary>参考答案</summary>

1. **错。** hooks 在 `.git/hooks/` 里，不属于版本控制，clone 不会带走。
2. **对。** pop 是"取出并删除"，之后 `git stash list` 里就没有了。
3. **错。** 标签钉死在某个 commit，不会移动；分支才会随 commit 前进。
4. **错。** `.gitignore` 只对未跟踪文件生效，已跟踪的要先 `rm --cached`。
5. **对。** 附注标签是独立对象，记录作者/时间/说明，更适合发布。

</details>

### 练习 4：临时代码怎么处理

你正在改代码，突然要切去修一个紧急 bug，但当前改动不想提交。写出操作序列。

<details><summary>参考答案</summary>

```bash
git stash                 # 藏起未提交改动
git switch -c hotfix      # 干净地切走
# ... 修 bug、提交、合并回 main ...
git switch 原分支
git stash pop             # 取回藏起来的改动，继续干活
```

</details>
