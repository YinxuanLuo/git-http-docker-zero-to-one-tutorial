# 第 06 章 · 远程协作

> 前面 1~5 章，你都是一个人在本地玩。这一章把你的仓库"连上网"，和另一个（或另一群）人共享代码。
> 你大概率用过 `git push` / `git pull`，但你可能说不清：`origin` 到底是什么？`fetch` 和 `pull` 差在哪？远程分支 `origin/master` 又是谁？
>
> 读完本章，你要能回答三个问题：
> 1. `origin` 是什么？它和"远程仓库的 URL"是什么关系？
> 2. `git fetch` 和 `git pull` 到底差在哪？为什么说"先 fetch 再 merge"比"直接 pull"更可控？
> 3. `origin/master` 这个"远程分支"是什么？它和本地的 `master` 是一回事吗？
>
> 本章你需要记住的就一件事：**"远程"在本地有一份影子——`origin` 是 URL 的别名，`origin/master` 是远程分支的本地快照；`fetch` 只更新影子，`pull` 更新影子并合并，`push` 把你的提交推上去。**

---

## 06.1 `origin`：它只是 URL 的一个别名

### 先给结论

**`origin` 不是一个特殊概念，它只是你给"远程仓库 URL"起的一个名字（默认第一个远程就叫 origin）。**

当你把本地仓库和 GitHub 上的一个仓库关联起来时：

```bash
git remote add origin https://github.com/你/项目.git
```

这句干的事，就是在 `.git/config` 里写了两行：

```text
[remote "origin"]
	url = https://github.com/你/项目.git
	fetch = +refs/heads/*:refs/remotes/origin/*
```

**`origin` 就是 `https://github.com/你/项目.git` 这个 URL 的别名。** 以后你写 `git push origin master`，Git 就自动展开成"往那个 URL 推 master 分支"。

### 为什么叫 origin

没有任何技术原因，纯粹是习惯：`git clone` 一个仓库时，Git 默认把来源命名为 `origin`（"源头"的意思）。你也可以叫别的：

```bash
git remote add upstream https://github.com/原作者/项目.git
```

很多开源协作里，你会同时有 `origin`（你自己的 fork）和 `upstream`（原作者的仓库），两个远程、两个名字。

### 为什么要有别名，不直接写 URL

两个好处：

1. **短。** `git push origin master` 比 `git push https://github.com/你/项目.git master` 好敲；
2. **可切换。** 仓库搬家了，你只需 `git remote set-url origin 新地址`，所有命令都不用改。

> 一句话记住它：`origin` 是"远程仓库 URL"的别名，默认第一个远程叫这个名字；一个仓库可以有多个远程（origin/upstream）。

## 06.2 `git remote`：管理你的远程

### 先给结论

`git remote` 是"管理远程"的命令。几个常用子命令：

| 命令 | 作用 |
|---|---|
| `git remote -v` | 列出所有远程及 URL（`-v` 显示 fetch/push 两个地址） |
| `git remote add <名> <url>` | 添加一个远程 |
| `git remote remove <名>` | 删除一个远程 |
| `git remote set-url <名> <新url>` | 改远程的 URL |
| `git remote show <名>` | 看某个远程的详细信息 |

### 亲手看

```bash
git remote -v
```

```text
origin	https://github.com/你/项目.git (fetch)
origin	https://github.com/你/项目.git (push)
```

两行是因为 fetch 和 push 理论上可以是**不同的地址**（大多数时候相同，所以显示两遍）。

### 一个真实的报错：远程不存在

```bash
git push nope master
```

```text
fatal: 'nope' does not appear to be a git repository
fatal: Could not read from remote repository.

Please make sure you have the correct access rights
and the repository exists.
```

**触发条件**：远程名字拼错、或者 URL 无效/没有权限。看到它先 `git remote -v` 检查名字和地址对不对。

> 一句话记住它：`git remote -v` 看远程清单，`add`/`remove`/`set-url` 增删改；远程名拼错会报 `fatal: 'xxx' does not appear to be a git repository`。

## 06.3 远程分支 `origin/master`：远程的本地影子

### 先给结论

**`origin/master` 不是"远程上的 master"，而是"远程 master 在本地的一份快照"。** 它是你**上一次** `fetch` 或 `push` 时，远程 master 的样子。

它的全名是 `remotes/origin/master`，存在 `.git/refs/remotes/origin/master` 里。

### 为什么需要这个影子

因为你的 Git **不能实时知道远程发生了什么**。它只能在你 `fetch`/`push` 时，把"远程现在的样子"下载下来存成 `origin/master`。

所以这里有一个**时间差**的概念：

```text
本地 master     = 你的最新提交
origin/master   = 你上次 fetch/push 时，远程的最新提交
远程真正的 master = 别人 push 之后可能又变了
```

**你 `git status` 看到的 `Your branch is ahead of 'origin/master' by 1 commit.`**，比的就是"本地 master"和"origin/master 这个影子"的差距，不是和真实远程的差距。

### 分支的三类

```bash
git branch -a
```

```text
* master                  ← 本地分支（你可以切换、提交）
  remotes/origin/HEAD     ← 远程默认分支的标记
  remotes/origin/master   ← 远程分支（本地影子，不能直接 checkout 改）
```

**远程分支不能直接切换、不能直接提交**。你想在 `origin/master` 基础上工作，得先 `git switch -c 新分支 origin/master` 或 `git pull` 到本地分支。

### 一个真实的报错：checkout 远程分支

```bash
git switch origin/master
```

```text
fatal: a branch is expected, got remote branch 'origin/master'
```

**触发条件**：想直接切到远程分支。正确做法是切到本地分支，或基于它新建：

```bash
git switch -c 本地名 origin/master
```

> 一句话记住它：`origin/master` 是远程 master 的本地快照，只在 fetch/push 时更新；它不能直接 checkout，要基于它建本地分支。

## 06.4 `git push`：把你的提交推上去

### 先给结论

`git push` 把**本地分支的提交**推到**远程对应的分支**上。

```bash
git push origin master        # 把本地 master 推到远程的 master
git push -u origin master     # 额外建立"跟踪关系"（见下）
```

### `-u` 是干什么的

`-u`（upstream 的缩写）建立**跟踪关系（tracking）**：让本地 `master` 记住"我的上游是 `origin/master`"。之后你只需要敲 `git push`（不带参数），Git 就知道往哪推、推哪个分支。

```bash
git push -u origin master
```

```text
branch 'master' set up to track 'origin/master'.
```

建立跟踪后，`git status` 会显示本地和上游的差距：

```text
Your branch is up to date with 'origin/master'.
```

### push 成功时输出什么

```text
Enumerating objects: 5, done.
Counting objects: 100% (5/5), done.
...
To https://github.com/你/项目.git
   cacdbd5..93db969  master -> master
```

关键在最后一行 `cacdbd5..93db969 master -> master`：左边是旧哈希，右边是新哈希，意思是"远程 master 从 cacdbd5 更新到了 93db969"。

> 一句话记住它：`push` 把本地提交推到远程；`-u` 建立跟踪关系，之后 `git push` 就不用带参数了。

## 06.5 `fetch` 和 `pull`：差在一个"合并"

### 先给结论

**`git fetch` 只下载、不合并；`git pull` = `git fetch` + `git merge`。**

```text
git fetch origin     → 下载远程最新，更新 origin/master 这个影子，但不碰你的工作区
git pull  origin     → 先 fetch，再把 origin/master 合并进你的本地分支
```

### 为什么"先 fetch 再 merge"更可控

`git pull` 是两步合一，方便但**不透明**：它下载完立刻合并，如果远程的改动和你的本地有冲突，你可能在**不知情的情况下进入了合并状态**。

而 `fetch` 只更新影子，你可以先：

```bash
git fetch origin
git log --oneline HEAD..origin/master   # 看看远程多了哪些提交
git diff HEAD origin/master             # 看看远程改了什么
```

**看清楚再决定**要不要合并、怎么合并。这就是"fetch 再 merge"比"直接 pull"更稳的原因。

### 一张表说清三个命令

| 命令 | 下载远程更新 | 更新 origin/master 影子 | 合并进本地分支 |
|---|---|---|---|
| `git fetch` | ✅ | ✅ | ❌ |
| `git pull` | ✅ | ✅ | ✅ |
| `git push` | ❌（是上传） | 顺带更新 | ❌ |

### `git pull` 其实是两个动作

严格说，`git pull` 是 `fetch` + `merge` 的组合（默认策略是 merge，也可以配成 rebase，第 07 章讲）。它等价于：

```bash
git pull origin master
# 相当于：
git fetch origin
git merge origin/master
```

> 一句话记住它：`fetch` 只下载更新影子，`pull` 下载并合并；想"看清楚再合"就先 fetch 再 merge。

## 06.6 push 被拒绝：`! [rejected]` 是什么

### 先给结论

**当远程有你本地没有的提交时，`git push` 会被拒绝。** 这是 Git 在保护你——它不允许你的 push 把远程的历史"倒回"。

### 真实的报错

```bash
git push
```

```text
To /path/to/remote.git
 ! [rejected]        master -> master (fetch first)
error: failed to push some refs to '/path/to/remote.git'
hint: Updates were rejected because the remote contains work that you do not
hint: have locally. This is usually caused by another repository pushing to
hint: the same ref. If you want to integrate the remote changes, use
hint: 'git pull' before pushing again.
hint: See the 'Note about fast-forwards' in 'git push --help' for details.
```

**关键词 `[rejected]` 和 `(fetch first)`**。hint 已经告诉你解法了：`git pull` 先把远程的改动拉下来合并，再 push。

### 为什么 Git 要拒绝

设想没有这个保护：你 `push` 时，远程已经是 `A → B → C`（同事推了 B、C）。你的本地是 `A → B → D`。如果强行 push，远程的历史就会被覆盖成 `A → B → D`，**C 这个提交就在远程"消失"了**——同事的活白干。

所以 Git 拒绝，逼你先 `git pull`，把 C 合并进来，变成 `A → B → C → D → (merge)`，再 push。

### 正确的处理流程

```bash
# 1. 先看看远程多了什么
git fetch origin
git log --oneline HEAD..origin/master

# 2. 合并（或用 pull 一步到位）
git pull origin master

# 3. 解决可能的冲突后，再 push
git push
```

### 一个新手常犯的错：用 `--force` 硬推

```bash
git push --force    # ❌ 危险！
```

`--force` 会**强制覆盖远程历史**，把同事的提交真的冲掉。**除非你非常清楚自己在干什么，否则永远别用 `--force`**（更温和的替代是 `--force-with-lease`，它会先检查远程有没有别人新推的提交，有就不推）。

> 一句话记住它：push 被拒（`! [rejected] ... (fetch first)`）是因为远程领先于你；先 `git pull` 再 push，别用 `--force` 硬推。

## 06.7 一个真实的坑：`git pull` 时分支分叉

当你 `git pull` 时，如果本地和远程**都各自有新提交**（分叉了），新版 Git 会停下来问你：

```text
hint: You have divergent branches and need to specify how to reconcile them.
hint: You can do so by running one of the following commands sometime before
hint: your next pull:
hint:
hint:   git config pull.rebase false  # merge
hint:   git config pull.rebase true   # rebase
hint:   git config pull.ff only       # fast-forward only
hint:
fatal: Need to specify how to reconcile divergent branches.
```

**触发条件**：本地和远程分叉，且你没有配置 `pull.rebase`。Git 不知道你想用 merge 还是 rebase 来合并，所以让你先选。

解法（三选一）：

```bash
# 想用 merge（生成 merge commit）：
git config pull.rebase false

# 想用 rebase（历史变直线，第 07 章）：
git config pull.rebase true

# 只想快进，分叉就报错（最严格）：
git config pull.ff only
```

配置一次后，以后 `git pull` 就知道怎么合并了。

> 一句话记住它：pull 时分叉会报 `fatal: Need to specify how to reconcile divergent branches.`，配置 `pull.rebase false/true/only` 三选一即可。

## 06.8 SSH 和 HTTPS：两种远程协议怎么选

### 先给结论

远程仓库的 URL 有两种常见协议：**HTTPS** 和 **SSH**。区别在**怎么认证你是谁**。

| | HTTPS | SSH |
|---|---|---|
| URL 样子 | `https://github.com/你/项目.git` | `git@github.com:你/项目.git` |
| 认证方式 | 用户名 + 密码/token | SSH 密钥对 |
| 首次配置 | 简单（输一次 token） | 要生成并上传公钥 |
| 用起来 | 每次可能要输 token（可缓存） | 配置一次，之后免密 |

### 各自的坑

**HTTPS 的坑**：GitHub 从 2021 年起**禁止用密码**推送，必须用 **Personal Access Token（PAT）**。如果你 `git push` 时一直输密码失败，多半是这个原因——去生成一个 token，当密码用。

```bash
git remote set-url origin https://github.com/你/项目.git
# push 时输入用户名 + token（不是你的登录密码）
```

**SSH 的坑**：要先生成密钥、上传公钥，多一步。但配好后最省心。

```bash
ssh-keygen -t ed25519 -C "you@example.com"   # 生成密钥
cat ~/.ssh/id_ed25519.pub                    # 复制公钥，贴到 GitHub 的 SSH keys 里
git remote set-url origin git@github.com:你/项目.git
```

### 怎么选

- 临时用一下、不想折腾密钥 → HTTPS；
- 长期开发、想免密 → SSH；
- 公司内网 → 可能两者都有，问同事。

> 一句话记住它：HTTPS 用 token 认证（GitHub 已禁密码）、SSH 用密钥认证；长期开发配 SSH 更省心。

## 06.9 远程的更多操作：`show`、`prune`、删远程分支

### 先给结论

`git remote` 除了 `add`/`remove`/`-v`，还有几个团队里常用的子命令。

### `git remote show <名>`：看远程详情

```bash
git remote show origin
```

```text
* remote origin
  Fetch URL: https://github.com/你/项目.git
  Push  URL: https://github.com/你/项目.git
  HEAD branch: main
  Remote branches:
    main   tracked
    dev    tracked
  Local branch configured for 'git pull':
    main merges with remote main
```

一眼看清：远程有哪些分支、本地 main 跟踪的是谁、pull 会怎么合并。

### `git remote prune`：清理失效的远程分支

**场景**：同事删了远程的 `feature/xxx`，但你本地还留着 `origin/feature/xxx` 这个"影子"（因为它是 fetch 时留下的快照）。`prune` 删掉这些**远程已经不存在**的影子分支：

```bash
git remote prune origin
```

```text
Pruning origin
URL: https://github.com/你/项目.git
 * [pruned] origin/feature/xxx
```

### 删除远程分支

```bash
git push origin --delete feature/xxx
# 或老的写法：
git push origin :feature/xxx
```

删远程分支用 `push --delete`，**不是 `git branch -d`**（那个只删本地分支）。

### 一张表：远程相关的操作

| 想做什么 | 命令 |
|---|---|
| 看远程详情 | `git remote show origin` |
| 清理失效影子 | `git remote prune origin` |
| 删远程分支 | `git push origin --delete <branch>` |
| 改远程 URL | `git remote set-url origin <新url>` |

> 一句话记住它：`remote show` 看详情、`remote prune` 清失效影子、`push --delete` 删远程分支。

## 06.10 本章常见坑速查

| 坑 | 现象 | 原因 | 正确做法 |
|---|---|---|---|
| 把 origin 当特殊概念 | 以为只能叫 origin | origin 只是默认别名 | 可以 `git remote add upstream ...` |
| checkout 远程分支 | `fatal: a branch is expected, got remote branch` | 远程分支不能直接切 | 基于它建本地分支 `switch -c x origin/master` |
| push 被拒就用 --force | 同事提交被冲掉 | --force 覆盖远程历史 | 先 pull 再 push；真要强推用 `--force-with-lease` |
| 分不清 fetch 和 pull | 以为 fetch 会合并 | fetch 只下载不合并 | 记住 fetch 更新影子，pull = fetch + merge |
| pull 时分支分叉报错 | `fatal: Need to specify how to reconcile divergent branches` | 没配 pull.rebase | `git config pull.rebase false` |
| 以为 origin/master 实时同步 | 判断错误 | origin/master 只在 fetch/push 时更新 | 要最新先 `git fetch` |
| 远程名拼错 | `fatal: 'nope' does not appear to be a git repository` | 名字/URL 错 | `git remote -v` 检查 |
| 第一次 push 忘了 -u | 之后 `git push` 报错 | 没建立跟踪关系 | `git push -u origin master` |

## 06.11 本章小结

**origin 与 remote**

- `origin` 是远程 URL 的别名，默认第一个远程叫这个，可改名、可加多个（upstream）。
- `git remote -v` 看清单，`add`/`remove`/`set-url` 增删改。

**远程分支**

- `origin/master` 是远程 master 的本地影子，只在 fetch/push 时更新。
- 它不能直接 checkout，要基于它建本地分支。

**push**

- `push` 把本地提交推到远程；`-u` 建立跟踪关系。

**fetch vs pull**

- `fetch` 只下载更新影子；`pull` = fetch + merge。
- 先 fetch 看清楚了再 merge，比直接 pull 更可控。

**push 被拒**

- `! [rejected] ... (fetch first)` 表示远程领先，先 pull 再 push。
- 别用 `--force` 硬推。

## 06.12 动手练习

### 练习 1：说清三个命令

用一句话说清 `git push`、`git fetch`、`git pull` 三者的区别，以及 `origin/master` 是什么。

<details><summary>参考答案</summary>

- `push`：把本地提交上传到远程；
- `fetch`：下载远程最新，更新 `origin/master` 影子，但不合并；
- `pull`：`fetch` + `merge`，下载并合并进本地分支；
- `origin/master`：远程 master 的本地快照，只在 fetch/push 时更新，不能直接 checkout。

</details>

### 练习 2：push 被拒怎么办

你 `git push` 时看到 `! [rejected] master -> master (fetch first)`。写出正确处理步骤，并说明为什么不能 `--force`。

<details><summary>参考答案</summary>

```bash
git fetch origin                      # 先看看远程多了什么
git log --oneline HEAD..origin/master # 远程领先的提交
git pull origin master                # 合并
git push                              # 再推
```

不能 `--force` 的原因：远程有你本地没有的提交（同事推的），`--force` 会覆盖远程历史，把同事的提交冲掉。

</details>

### 练习 3：判断对错

1. `origin` 是 Git 的特殊关键字，不能改成别的名字。
2. `git fetch` 会修改你的工作区文件。
3. `origin/master` 和本地 `master` 是同一个东西。
4. `git pull` 等价于 `git fetch` + `git merge`。
5. push 被拒绝是因为你的提交有问题。

<details><summary>参考答案</summary>

1. **错。** origin 只是默认别名，可以 `git remote rename` 或添加其他名字。
2. **错。** fetch 只更新远程分支影子，不碰工作区；pull 才会合并进而改工作区。
3. **错。** `origin/master` 是远程的本地影子，`master` 是你的本地分支，两者是不同东西。
4. **对。** pull 默认策略就是 fetch 之后 merge（也可配成 rebase）。
5. **错。** 被拒是因为远程有你没有的提交（远程领先），不是提交内容有问题。

</details>

### 练习 4：第一次推送的完整流程

```bash
git remote add origin https://github.com/你/项目.git
git push -u origin master     # -u 建立跟踪，之后 git push 即可
```

`git push -u origin master` 建立跟踪关系后，`git status` 会显示 `Your branch is up to date with 'origin/master'.`
