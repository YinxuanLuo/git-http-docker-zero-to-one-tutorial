## 一、高频面试题（Q1~Q50）

### 1. Git 数据模型（10 题）

**Q1: `git commit` 保存的是差异还是快照？**

**答：快照。每个 commit 记录的是整个仓库在那一刻的完整目录树（通过 tree/blob 对象的哈希引用），不是"这次改了哪些行"。**

- 关键区分：**快照**（存整个状态） ≠ **差异**（只存改动）
- 推论：没变的文件内容哈希不变，Git 不用重存；改一个文件只新增一个 blob，其余引用旧 blob

**Q2: Git 里的对象有哪几种？**

**答：四种。blob（文件内容）、tree（目录清单）、commit（提交）、tag（标签）。**

- blob 存一个文件的完整内容
- tree 存"文件名 → blob/tree 哈希"的映射
- commit 存 tree + 父 commit + 作者/提交者/说明
- 每个对象的名字是它内容的 SHA-1 哈希

**Q3: 什么是"内容寻址"？有什么好处？**

**答：对象的名字就是它内容的哈希。好处有三：相同内容自动去重（只存一份）；内容被篡改一字节哈希就对不上（天然校验）；commit 的哈希一变，说明它引用的东西一定被动过。**

**Q4: 为什么 Git 用快照而不是差异？**

**答：差异存储（SVN 思路）要还原某个版本，得从第一个版本一路打补丁，越到后面越慢。快照存储直接取那一张"照片"即可，还原是 O(1)。代价是空间略贵（但内容寻址 + 压缩弥补了）。**

- 这是 Linus 为 Linux 内核那种"几万文件、几十万提交"的项目做的取舍

**Q5: blob 哈希是怎么算出来的？**

**答：`sha1("blob " + 字节长度 + "\0" + 文件内容)`。头部是 `blob ` + 内容的字节数 + 一个空字符。**

- 注意是**字节数**，不是字符数（中文要按 UTF-8 字节算）

**Q6: 两个文件内容相同，Git 存几个 blob？**

**答：一个。内容寻址意味着同样的内容哈希一样，底层只存一份，两个文件名只是两个 tree 条目引用同一个 blob。**

**Q7: commit 的 `parent` 字段是干什么的？**

**答：指向父 commit 的哈希，把提交串成一条单向链表。普通提交一个 parent，merge 提交两个，第一个提交（root）零个。**

- 这个设计让 commit 不可变：改中间一个，后面所有哈希都变

**Q8: author 和 committer 有什么区别？**

**答：author 是"写这段代码的人"，committer 是"执行提交的人"。正常情况两者相同；`cherry-pick`/`rebase`/`amend` 时会不同——author 保留原作者，committer 变成操作者。**

**Q9: Git 是怎么保证历史几乎不可能"静默损坏"的？**

**答：因为 commit 的名字就是内容哈希。任何对象被篡改一字节，它的哈希就变了，上层引用它的 tree/commit 哈希也对不上，`git fsck` 一查就能发现哈希网"断了"。**

**Q10: `git cat-file -p <hash>` 和 `git hash-object <file>` 是干什么的？**

**答：`cat-file -p` 查看某个对象的"漂亮格式"内容（blob 显示文本、tree 显示清单、commit 显示元信息）；`hash-object` 计算某个文件对应的 blob 哈希（不加 `-w` 就只算不写）。**

### 2. 三棵树与日常命令（10 题）

**Q11: 工作区、暂存区、版本库分别在哪？**

**答：工作区 = 你的项目文件夹；暂存区 = `.git/index`（一个二进制文件）；版本库 = `.git/objects` + `.git/refs`。**

**Q12: 为什么要设计一个"暂存区"？**

**答：让你精确控制"这次提交什么"。工作区可能同时有 bug 修复、半成品功能、随手改的配置，暂存区让你只把想提交的挑进去，提交语义清晰。**

**Q13: `git add` 和 `git commit` 各自做了什么？**

**答：`add` 把文件当前内容拍快照进暂存区；`commit` 把暂存区固化成历史里的一个快照节点。commit 只认暂存区，不认工作区。**

**Q14: `git status -s` 里 `??`、`M `、` M`、`AM` 分别是什么意思？**

**答：`??` 未跟踪；`M `（第一列 M）已修改且已暂存；` M`（第二列 M）已修改未暂存；`AM` 已暂存后又改了（暂存区 A + 工作区 M）。两列分别对应暂存区和工作区。**

**Q15: `git diff`、`git diff --staged`、`git diff HEAD` 各比什么？**

**答：`git diff` 比工作区 vs 暂存区；`--staged` 比暂存区 vs 最新 commit；`HEAD` 比工作区 vs 最新 commit。**

**Q16: 未跟踪的新文件，`git diff` 能显示吗？**

**答：不能。`git diff` 只在"已跟踪"文件之间比较，未跟踪文件对 Git 来说还不存在。要 `git add` 之后才能 diff。**

**Q17: `git log --oneline`、`--graph`、`--author` 分别干什么？**

**答：`--oneline` 一行一条；`--graph` 画分支图；`--author="名字"` 过滤某人的提交。另有 `--since`、`--grep`、`-- 路径` 等过滤。**

**Q18: `HEAD~1` 和 `HEAD^` 有什么区别？**

**答：`~1` 沿"第一个 parent"往回走 1 步；`^` 也表示第一个 parent（`HEAD^1` 同义）。对 merge commit，`HEAD^2` 表示"第二个 parent"（被合并的那条线），而 `HEAD~2` 表示"往回两步"（`HEAD^1^1`）。**

**Q19: 提交信息为什么要有规范？**

**答：提交信息是给"未来的自己和同事"看的，机器可读的规范（Conventional Commits：`type(scope): subject`）能自动生成 changelog、自动定版本号、一键搜索某类改动。**

**Q20: `feat` 和 `fix` 有什么区别？**

**答：`feat` 是"加了新功能"，`fix` 是"修了坏的东西"。两者直接影响语义化版本号的升降（feat 升 minor，fix 升 patch）。**

### 3. 分支、合并与冲突（10 题）

**Q21: 分支是什么？为什么 Git 的分支特别便宜？**

**答：分支只是一个指向 commit 的指针（`.git/refs/heads/` 下的哈希文件）。创建 = 写一行字，耗时几乎为零，所以"为每个想法开分支"是划算的。**

**Q22: HEAD 是什么？detached HEAD 是什么？**

**答：HEAD 是"你站在哪"的指针，通常指向某个分支。detached HEAD 是 HEAD 直接指向某个 commit 而非分支——此时能看能改，但提交不挂靠任何分支，切走就"悬空"。**

**Q23: 快进合并（fast-forward）和三方合并的区别？**

**答：快进 = 分叉后当前分支没动，直接把指针平移，不产生新 commit；三方 = 两边都动了，以共同祖先为基准合成一个有两个 parent 的 merge commit。**

**Q24: `git merge --no-ff` 有什么用？**

**答：即使能快进，也强制生成一个 merge commit。用于想保留"这里合并过一条分支"的痕迹的团队规范。**

**Q25: 冲突是怎么产生的？**

**答：只有"两边改了同一个文件的同一块地方"才冲突——Git 无法自动裁决，把两个版本都写进文件、用冲突标记分隔，交给你拍板。**

**Q26: 冲突标记 `<<<<<<<`、`=======`、`>>>>>>>` 各代表什么？**

**答：`<<<<<<< HEAD` 到 `=======` 是当前分支（HEAD）的版本；`=======` 到 `>>>>>>> 分支名` 是被合并分支的版本。**

**Q27: 解决冲突有哪几种方式？**

**答：三种——手动编辑后 `git add`（最常用）、`--ours`/`--theirs` 整取一边、`--abort` 中止合并。解决完的标志是 `git add`（标记已解决）。**

**Q28: 冲突时报错原文是什么？**

**答：`CONFLICT (content): Merge conflict in <文件>` + `Automatic merge failed; fix conflicts and then commit the result.`**

**Q29: 冲突文件在 index 里有几个阶段？**

**答：三个。阶段 1 = 共同祖先（base），阶段 2 = 当前分支（ours），阶段 3 = 被合并分支（theirs）。解决后合并回阶段 0。**

**Q30: 为什么说"合并方向永远是功能分支 → main"？**

**答：让 main 保持可发布状态。功能开发都在分支上做，main 只接受"已完成、测试过"的合并，历史清晰、随时能发布。**

### 4. 撤销与回退（10 题）

**Q31: `git reset --soft / --mixed / --hard` 的区别？**

**答：`--soft` 只挪 HEAD；`--mixed`（默认）挪 HEAD + 清空暂存区；`--hard` 连工作区一起覆盖。记忆：soft 挪指针、mixed 清暂存、hard 砸工作区。**

**Q32: `--hard` 为什么危险？**

**答：它会覆盖工作区，把**所有未提交改动**一并抹掉，且无法通过普通方式找回（只能靠 reflog）。**

**Q33: `git reset` 和 `git revert` 的区别？**

**答：`reset` 把历史往后挪（改写历史），`revert` 追加一个"反向提交"（不改历史）。未推送的用 reset，已推送的用 revert。**

**Q34: 为什么已推送的提交不能用 `git reset`？**

**答：已推送的历史是共享的。reset 改写本地历史后，需要 `push --force` 覆盖远程，会破坏同事已经 pull 的历史，导致混乱甚至丢提交。**

**Q35: `git restore` 和 `git checkout --` 什么关系？**

**答：等价。`restore` 是 Git 2.23 起的新命令，专职"恢复文件"，取代了身兼两职的 `checkout --`。新代码用 `restore`。**

**Q36: `git restore --staged <file>` 是干什么的？**

**答：把已暂存（add）的改动退回工作区，即"取消 add"，但不删除内容。**

**Q37: `git reflog` 是干什么的？**

**答：记录 HEAD 的每次移动（commit/reset/rebase/checkout），是"后悔药的后悔药"——被 reset 掉的提交也能在 reflog 里找到哈希找回。**

**Q38: `git log` 和 `git reflog` 的区别？**

**答：`log` 沿 parent 链看项目历史（被 reset 掉的看不到）；`reflog` 看 HEAD 的移动轨迹（被 reset 掉的也看得到）。前者是"项目历史"，后者是"操作历史"。**

**Q39: reflog 会永久保存吗？**

**答：不会。默认保留 90 天（可配 `gc.reflogExpire`）。超过期限且对象被 GC 回收，就真的找不回了。**

**Q40: `git commit --amend` 是干什么的？有什么坑？**

**答：修改**上一次**提交（改说明、或补上漏掉的文件）。坑：它会改写最后一个 commit 的哈希，所以**只对"还没 push 的最后一个提交"用**。**

### 5. 远程协作与 rebase（10 题）

**Q41: `origin` 是什么？**

**答：是"远程仓库 URL"的别名，默认第一个远程叫这个名字。`git remote add origin <url>` 就是在 `.git/config` 里记下这个映射。一个仓库可以有多个远程（origin/upstream）。**

**Q42: `origin/master` 是什么？**

**答：远程 master 在本地的一份快照，存在 `refs/remotes/origin/master`，只在 `fetch`/`push` 时更新。它不是实时同步的。**

**Q43: `git fetch` 和 `git pull` 的区别？**

**答：`fetch` 只下载远程最新、更新 `origin/master` 影子，不碰工作区；`pull` = fetch + merge，下载并合并进本地分支。**

**Q44: 为什么说"先 fetch 再 merge"比"直接 pull"更可控？**

**答：fetch 只更新影子，你可以先 `git log HEAD..origin/master` 看远程多了什么、`git diff` 看改了什么，想清楚了再决定怎么合并。pull 一步到位但不透明。**

**Q45: push 被 rejected 是什么意思？**

**答：`! [rejected] ... (fetch first)` 表示远程有你本地没有的提交（远程领先）。先 `git pull` 合并再 push。**

**Q46: 为什么 push 被拒时不能 `--force`？**

**答：`--force` 会覆盖远程历史，把同事已经 push 的提交冲掉。更温和的替代是 `--force-with-lease`（先检查远程有没有新提交）。**

**Q47: `git pull` 时分叉报什么错？**

**答：`fatal: Need to specify how to reconcile divergent branches.` 表示本地和远程都各有新提交，Git 不知道用 merge 还是 rebase。解法是 `git config pull.rebase false/true/only` 三选一。**

**Q48: rebase 和 merge 怎么选？**

**答：merge 保留真实分叉历史、不改写，适合公共分支；rebase 让历史变直线、会改写 commit，只适合未推送的私有分支。黄金法则：绝不 rebase 共享分支。**

**Q49: 为什么 rebase 会改写 commit？**

**答：rebase 把"分叉后的提交"逐个重放到新基底上，parent 变了，而 parent 是 commit 内容的一部分，所以哈希必然变。**

**Q50: cherry-pick 是干什么的？和 merge 有什么区别？**

**答：cherry-pick 挑**一个**提交的改动复制到当前分支（保留原 author）；merge 整合**整条**分支的所有提交。**

## 二、白板手写题（Q51~Q60）

面试官说"来，现场写/操作一下"的时候，**先讲思路再动手**——这是第一分。命令写了 80% 也比卡住强。

### 1. 现场操作（3 题 · 读命令说结果）

**Q51: 读下面这段命令，说出每一步 `git status -s` 的输出。**

```bash
git init
echo hi > a.txt
git status -s
git add a.txt
git status -s
echo bye >> a.txt
git status -s
```

**答：** `?? a.txt` → `A  a.txt` → `AM a.txt`。

- 第一步：未跟踪（`??`）
- 第二步：已暂存（`A `）
- 第三步：暂存后又改（`A ` + ` M` = `AM`），说明 add 拍的是那一刻的快照

**Q52: 读下面这段，说合并后的历史形状（快进还是三方，画出图）。**

```bash
git init -b main
echo a > f && git add . && git commit -m C1
git switch -c feat
echo b >> f && git add . && git commit -m C2
git switch main
git merge feat
```

**答：** 快进合并。main 在分叉后没动，直接平移到 C2。历史一条直线：`C1 → C2`。

**Q53: 读下面这段，说出冲突标记的内容。**

```bash
git init -b main
echo v1 > f && git add . && git commit -m base
git switch -c feat
echo v2 > f && git add . && git commit -m feat
git switch main
echo v3 > f && git add . && git commit -m main
git merge feat   # 冲突
cat f
```

**答：**

```text
<<<<<<< HEAD
v3
=======
v2
>>>>>>> feat
```

### 2. 场景问答（4 题）

**Q54: 你 push 了 3 个提交，发现中间那个有 bug。怎么安全地撤销它？**

**答：** 用 `git revert <中间提交的哈希>`，然后 `git push`。因为已经推送，不能 reset（会改写共享历史）。revert 会新增一个"反向提交"，把 bug 提交的改动抵消掉。

**Q55: 你在 feature 分支上开发，main 已经往前走了很多。想合并前让历史保持直线，怎么做？**

**答：** 在 feature 上 `git rebase main`，把 feature 的提交重放到 main 顶端，再 `git switch main && git merge feature`（此时是快进合并，历史直线）。**前提：feature 没推送过。**

**Q56: 手滑执行了 `git reset --hard HEAD~3`，怎么找回丢掉的提交？**

**答：** `git reflog` 找到 reset 之前 HEAD 的位置（哈希），然后 `git reset --hard <那个哈希>` 或 `git switch -c recovered <哈希>` 建分支查看。

**Q57: 一个文件已经被提交过了，现在想忽略它但保留本地文件，怎么做？**

**答：**

```bash
echo "文件名" >> .gitignore
git rm --cached 文件名
git commit -m "chore: 停止跟踪 xxx"
```

`git rm --cached` 从版本库移除但保留本地文件，之后 `.gitignore` 才生效。

### 3. 手写脚本（3 题）

**Q58: 手写一个 `.mjs`：在临时目录 `git init` 并提交一次，打印 `git log --oneline`，最后清理临时目录。**

**答：**

```js
import { execFileSync } from 'node:child_process';
import { mkdtempSync, writeFileSync, rmSync } from 'node:fs';
import { tmpdir } from 'node:os';
import { join } from 'node:path';

const dir = mkdtempSync(join(tmpdir(), 'demo-'));
try {
  const git = (a, o = {}) => execFileSync('git', a, { cwd: dir, encoding: 'utf8', ...o }).trimEnd();
  git(['init', '-q']);
  git(['config', 'user.email', 't@t.com']);
  git(['config', 'user.name', 't']);
  writeFileSync(join(dir, 'a.txt'), 'hi\n');
  git(['add', 'a.txt']);
  git(['commit', '-q', '-m', 'first']);
  console.log(git(['log', '--oneline']));
} finally {
  rmSync(dir, { recursive: true, force: true });
}
```

- 讲清：`execFileSync` 三参数（命令、参数数组、选项）；`cwd` 指定目录；`try/finally` 保证清理

**Q59: 手写一段"制造冲突并解决"的命令序列。**

**答：**

```bash
git init -b main
echo v1 > f && git add . && git commit -m base
git switch -c feat
echo v2 > f && git add . && git commit -m feat
git switch main
echo v3 > f && git add . && git commit -m main
git merge feat          # CONFLICT (content): Merge conflict in f
# 手动改 f 为最终内容
git add f
git commit -m "merge: 解决冲突"
```

## 三、一页速查表

### 三棵树速查

| 区 | 位置 | 操作 |
|---|---|---|
| 工作区 | 项目文件夹 | 编辑器 |
| 暂存区 | `.git/index` | `git add` / `git restore --staged` |
| 版本库 | `.git/objects` + `.git/refs` | `git commit` / `git log` |

### 常用命令速查

| 我想做的事 | 命令 |
|---|---|
| 建仓库 | `git init`（`-b main` 指定默认分支） |
| 看状态 | `git status`（`-s` 短格式） |
| 暂存 | `git add <file>` / `git add -A` |
| 提交 | `git commit -m "feat: 说明"` |
| 看历史 | `git log --oneline --graph --all` |
| 看单次提交 | `git show <commit>` |
| 看差异 | `git diff` / `--staged` / `HEAD` |
| 建/切分支 | `git switch -c <name>` |
| 切分支 | `git switch <name>` |
| 合并 | `git merge <branch>` |
| 中止合并 | `git merge --abort` |
| 丢弃工作区改动 | `git restore <file>` |
| 取消 add | `git restore --staged <file>` |
| 回退（软/默认/硬） | `git reset --soft/--mixed/--hard HEAD~1` |
| 安全撤销 | `git revert <commit>` |
| 看后悔药 | `git reflog` |
| 藏改动 | `git stash` / `git stash pop` |
| 打标签 | `git tag -a v1.0.0 -m "说明"` |
| 加远程 | `git remote add origin <url>` |
| 推/拉/下载 | `git push` / `git pull` / `git fetch` |
| 摘一个提交 | `git cherry-pick <commit>` |
| 整理历史 | `git rebase -i HEAD~N` |

### 真实报错速查

| 报错（原文） | 触发原因 | 怎么修 |
|---|---|---|
| `fatal: not a git repository (or any of the parent directories): .git` | 不在仓库里跑 git | cd 进仓库或 `git init` |
| `fatal: pathspec 'xxx' did not match any files` | 路径拼错/不存在 | 检查文件名 |
| `CONFLICT (content): Merge conflict in <文件>` | 两边改了同一处 | 解决冲突后 add + commit |
| `error: The branch 'xxx' is not fully merged.` | 删未合并的分支 | 先合并，或 `-D` 强删 |
| `! [rejected] master -> master (fetch first)` | push 时远程领先 | 先 pull 再 push |
| `fatal: Need to specify how to reconcile divergent branches.` | pull 时分支分叉 | `git config pull.rebase false` |
| `fatal: a branch is expected, got remote branch 'origin/master'` | 直接切远程分支 | 基于它建本地分支 |
| `fatal: invalid reference: nope` | 分支名拼错 | `git branch` 看清楚 |
| `error: could not apply <hash>... <说明>` | rebase 重放时冲突 | `git rebase --continue/--skip/--abort` |
| `Author identity unknown` | 没配 user.name/email | `git config --global user.name/email` |

> 记一条通用排查顺序：**先看"是不是不在仓库/路径错了"，再看"是不是远程领先或分叉"，最后看"是不是冲突没解决"。**

## 四、面试技巧

### 4.1 不会的时候怎么救场

**核心原则：把"不知道"换成一个有价值的过程。**

- ❌ 别硬编命令。说错一个参数，比说"我不确定"伤害大得多。
- ✅ 可以说：**"这个命令的具体参数我记不太准，但我知道它要解决的是 X 问题。能让我说下思路吗？"**
- ✅ 把问题**降维到你会的那一层**：不会 `rebase --onto`，就说"我理解它属于 rebase 的高级用法，目标是给提交换基底；我实际用过的是 `rebase main` 加交互式整理，思路一致"。**用你掌握的等价方案接住问题。**
- ✅ 明说**边界**："这块我目前只到会用，没深入看过内部实现。"诚实 + 说明掌握程度，好过硬撑。
- ✅ **把追问变成加分**：被问住时反问"您是想确认底层原理，还是想看我能不能用对？"——既争取时间，也暴露你在意需求。

**三句万能救场句：**

1. "我先说结论，再说为什么，可以吗？"
2. "这个场景我没遇到过，我的推理是这样的……"
3. "这个点我回去会补，能说说你们实际是怎么处理的吗？"

### 4.2 可以反问什么

**想了解团队与工程成熟度：**

- 你们的分支模型是什么？Git Flow、GitHub Flow，还是自定义？
- 提交信息有没有统一规范（Conventional Commits）？怎么强制执行？
- 有没有 Git Hooks / CI 做提交前检查？
- 合并用 merge 还是 rebase？公共分支怎么管理？

**想了解技术挑战与成长：**

- 团队遇到过最头疼的一次 git 事故是什么？怎么解决的？
- 新人入职，通常会踩哪些 git 的坑？
- 你们怎么处理大文件/子模块这类特殊需求？

**反向加分项（显示你懂工程）：**

- "你们的 reflog / 撤销流程有文档吗？还是靠老人经验口口相传？"
- "`.gitignore` 和 hooks 是怎么在团队里共享的？"

**别问的：** 薪资细节（留给 HR）、能在官网查到的公开信息。

### 4.3 现场操作时的小习惯

1. **先复述任务 + 确认边界。** "你是想让我演示一个 feature 分支合并回 main 的完整流程，对吗？需要处理冲突吗？"
2. **先讲思路再敲命令。** "我先 init，然后建分支开发，切回 main merge，最后删分支。"
3. **主动说出取舍。** "这里我用 merge 而不是 rebase，因为假定 main 是公共分支。"
4. **写完主动自检。** "我检查一下 `git log --graph`，确认历史符合预期。"
5. **遇到报错别慌，读原文。** git 的报错都带 hint，现场读出来并给出解法，反而是加分项。

### 4.4 高频陷阱题识别

| 听到这个问法 | 真正考的是什么 |
|---|---|
| "commit 存的是差异还是快照？" | 你知不知道"快照 + 内容寻址"，而不是背概念 |
| "分支是什么？" | 你知不知道分支是**指针**而不是**代码拷贝** |
| "reset 和 revert 区别？" | 你知不知道"改写历史"的后果，以及"已推送"这个判断标准 |
| "fetch 和 pull 区别？" | 你知不知道 `origin/master` 是本地影子 |
| "能 rebase 公共分支吗？" | 你知不知道 rebase 会重写哈希、坑到同事 |
| "冲突了怎么办？" | 你会不会先"读冲突标记"再解决，而不是慌 |
| "push 被拒了怎么办？" | 你会不会拒绝 `--force`，知道先 pull |
| "这段命令会输出什么？"（给你一段 add/commit/status） | 你有没有"三棵树"的运行时直觉 |

**最后一条提醒：** 面试官真正想知道的只有两件事——**你知不知道 Git 底层在存什么（内容寻址 + 三棵树 + 历史链表）**，以及**出问题时你能不能自己读懂报错找到原因**。所有题目都是这两件事的变体。

> 一句话记住它：**面试考的不是"你知道多少命令"，而是"你能不能把为什么讲清楚"。**
