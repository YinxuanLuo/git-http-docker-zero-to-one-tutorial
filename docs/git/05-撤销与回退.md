# 第 05 章 · 撤销与回退

> 前面的章节都在"往前走"。这一章讲"往后退"——但 Git 的"撤销"不是一招鲜，而是针对不同"后悔程度"给不同工具。
> 你心里大概会想：我 `commit` 都提交了，东西还能丢吗？——能，而且丢了你都不知道，直到你学会 `reflog`。
>
> 读完本章，你要能回答三个问题：
> 1. `git reset --soft / --mixed / --hard` 三个到底差在哪？为什么说 `--hard` 最危险？
> 2. 什么时候用 `revert`，什么时候用 `reset`？
> 3. 东西"丢"了之后，`reflog` 怎么把它找回来？
>
> 本章你需要记住的就一件事：**撤销分两种——"改写历史"（reset，对本地未推送的提交）和"追加反向提交"（revert，对已推送的提交）；而 `reflog` 是所有误操作的后悔药。**

---

## 05.1 先给结论：四种"后悔"对应四种工具

别一上来背命令，先看清你要撤销的是**什么**：

| 你想撤销什么 | 用哪个命令 | 危险程度 |
|---|---|---|
| 工作区里没 add 的改动（手滑改错了文件） | `git restore <file>` | 低（丢的是没暂存的改动） |
| 已经 add、但还没 commit 的改动 | `git restore --staged <file>` | 低（退回工作区，不删内容） |
| 已经 commit、但**还没推送** | `git reset` | 中（改写本地历史） |
| 已经 commit、且**已经推送** | `git revert` | 低（追加反向提交，不改历史） |
| 上面任何一种，已经"弄丢"了 | `git reflog` | 无（只是查看和找回） |

**核心判断原则只有一条：这个提交推送到远程了吗？**

- **没推送** → 可以 `reset`，因为改写历史只影响你自己；
- **已推送** → 只能 `revert`，因为别人可能已经基于你的提交在干活了，改写历史会坑到他们（第 07 章细讲"改写历史的风险"）。

> 一句话记住它：先分清"要撤销的是什么"，再选工具；已推送用 revert，未推送用 reset，误操作找 reflog。

## 05.2 `git reset` 三兄弟：soft / mixed / hard

### 先给结论

`git reset` 做的事是**把当前分支的指针移动到某个 commit**。它有三个档位，差别只在于"移动指针的同时，顺带动哪几棵树"：

| 档位 | 动 HEAD/分支指针 | 动暂存区 | 动工作区 |
|---|---|---|---|
| `--soft` | ✅ 移动 | ❌ 不动 | ❌ 不动 |
| `--mixed`（默认） | ✅ 移动 | ✅ 清空 | ❌ 不动 |
| `--hard` | ✅ 移动 | ✅ 清空 | ✅ 覆盖 |

**记忆口诀：soft 只挪指针，mixed 挪指针 + 清暂存区，hard 连工作区一起砸。**

### 用一个实验看清三者区别

先造三个提交：

```bash
git init && git config user.name t && git config user.email t@example.com
echo 1 > f.txt && git add . && git commit -m C1
echo 2 >> f.txt && git add . && git commit -m C2
echo 3 >> f.txt && git add . && git commit -m C3
git log --oneline
```

```text
455ad5b C3
7f7ec32 C2
417e178 C1
```

### ① `--soft`：只挪 HEAD

```bash
git reset --soft HEAD~1
git status -s
```

```text
 M f.txt
```

- HEAD 退到 C2；
- `f.txt` 的改动**还在暂存区**（第一列 `M `）；
- 工作区内容**没变**（还是 C3 的样子）。

**用途**：提交完了发现"提交信息写错了、或者想把多个提交合并成一个"，用 `--soft` 退回来，改动还在暂存区，改完直接重新 commit。

### ② `--mixed`（默认）：挪 HEAD + 清暂存区

```bash
git reset HEAD~1       # 不写 --mixed 也是这个
git status -s
```

```text
 M f.txt
```

注意这次 `M` 跑到**第二列**了（` M`），说明改动从暂存区**退回了工作区**。工作区内容依然没变。

**用途**：提交后发现"漏了 add 某个文件"，用 `--mixed` 退回来，把所有改动放回工作区重新挑。

### ③ `--hard`：连工作区一起砸

```bash
git reset --hard HEAD~1
git status -s
```

```text
（干净）
```

```bash
cat f.txt
```

```text
1
2
```

- HEAD 退到 C2；
- 暂存区清空；
- **工作区也被改回 C2 的样子**——C3 加的 `3` 那一行**彻底消失了**。

**这就是 `--hard` 最危险的地方**：它会把工作区里**所有未提交的改动一并抹掉**（包括你没 add 的、甚至没 commit 的）。如果这时候你发现"我工作区里还有没提交的东西"，那就晚了。

> 一句话记住它：soft 只挪 HEAD，mixed 挪 HEAD + 清暂存区，hard 连工作区一起砸；`--hard` 会抹掉所有未提交改动，最危险。

## 05.3 `reset` 移动的是"当前分支"

### 先给结论

`git reset <commit>` 里的 `<commit>`，是把**当前分支的指针**移过去。注意是"分支指针"，不是"HEAD 单独动"——你 reset 完，当前分支就指向新位置了。

### `<commit>` 怎么写

| 写法 | 含义 |
|---|---|
| `HEAD~1` | 上一个提交 |
| `HEAD~3` | 往上 3 个提交 |
| `417e178` | 指定短哈希 |
| `feature` | 指定分支（把当前分支指到 feature 的位置） |

**最常用的是 `HEAD~N`**：回退 N 个提交。

### reset 之后，原来的提交去哪了

**没删，只是"悬空"了。** reset 只是移动指针，commit 对象还在 `.git/objects/` 里，只是暂时没有分支指向它。这就是为什么 `reflog` 能把它们找回来（05.6 节）。

（一段时间后，Git 的垃圾回收 GC 会清理这些"没有指针指向、也不在 reflog 里"的对象。但 reflog 默认保留 90 天，所以你有充足时间后悔。）

> 一句话记住它：`reset <commit>` 移动的是当前分支指针；被"退掉"的提交没删，只是悬空了，靠 reflog 能找回来。

## 05.4 `git revert`：安全的"反向提交"

### 先给结论

`git revert` 和 `reset` 完全不同：**它不改写历史，而是新增一个"反向 commit"**，把某个提交的改动**反着做一遍**。

```bash
git revert HEAD
```

它会生成一个新提交，内容是把 HEAD 的改动撤销掉。历史变成：

```text
之前：C1 ── C2 ── C3
之后：C1 ── C2 ── C3 ── C3'   （C3' 是"撤销 C3"的新提交）
```

**注意 C3 还在历史里**，没有被删。只是多了一个 C3' 把它抵消了。

### revert vs reset 的根本区别

| | `git reset` | `git revert` |
|---|---|---|
| 改历史吗 | **改**（把指针往后挪，历史变短） | **不改**（历史变长，追加反向提交） |
| 适合 | 未推送的提交 | 已推送的提交 |
| 结果 | 那几次提交"消失"了 | 那几次提交还在，只是被抵消 |

**为什么已推送的必须用 revert？** 因为你 `push` 之后，历史已经共享给团队了。如果你 `reset` 然后 `push --force`，会把别人的本地历史搞乱。而 `revert` 只是追加一个提交，别人 `pull` 一下就能同步，互不干扰。

### 一个真实的报错：revert 时又产生冲突

`git revert` 撤销某个提交时，如果这个提交之后又有别的提交**改了同一个地方**，revert 也会冲突：

```text
error: could not revert <哈希>... <说明>
hint: after resolving the conflicts, mark the corrected paths
hint: with 'git add <paths>' or 'git rm <paths>'
```

**触发条件**：要撤销的改动和后续提交的改动重叠。解决方式和第 04 章一样：手动改、`git add`、然后 `git revert --continue`（或 `git commit`）。

> 一句话记住它：`revert` 是"新增一个反向提交"，不改历史，适合已推送的提交；`reset` 是"把历史往后挪"，适合未推送的提交。

## 05.5 `git restore`：丢弃工作区和暂存区的改动

### 先给结论

`git restore` 是第 03 章提过的"专职恢复文件"的命令，取代了老的 `git checkout -- <file>`。它只管工作区和暂存区，**不碰历史**。

### 丢弃工作区的改动

```bash
# 手滑改错了文件，想丢掉改动，回到"暂存区/HEAD"的版本
git restore f.txt
```

如果文件已经被 add 过，`restore` 会把它恢复到**暂存区**的版本；如果没 add，恢复到**HEAD**（最新提交）的版本。

```bash
git restore --staged f.txt    # 把已暂存的改动"退回工作区"（取消 add，不删内容）
```

### 和 `checkout --` 的关系

这两个是等价的：

```bash
git restore f.txt
git checkout -- f.txt    # 老写法，同一个效果
```

**新代码用 `restore`**，语义更清晰。`checkout --` 只是历史兼容。

### 一个真实的报错：restore 一个不存在于 Git 的文件

```bash
git restore nope.txt
```

```text
error: pathspec 'nope.txt' did not match any file(s) known to git
```

**触发条件**：这个文件从没被 Git 跟踪过（连暂存区都没有它的记录）。`restore` 只能恢复"Git 认识"的文件，一个全新的未跟踪文件它管不着——要删就 `rm`。

> 一句话记住它：`restore` 只管工作区和暂存区，不碰历史；`restore <file>` 丢工作区改动，`restore --staged <file>` 取消 add。

## 05.6 `git reflog`：救命稻草

### 先给结论

**`git reflog` 记录了 HEAD 每一次移动的历史**——不管你是 commit、reset、rebase、还是 checkout，只要 HEAD 的位置变了，reflog 就记一笔。所以它是"后悔药的后悔药"：哪怕你 `reset --hard` 把东西"弄丢"了，reflog 里还留着那条记录，能找回。

### 亲手看 reflog

```bash
git reflog
```

```text
89eae10 HEAD@{0}: reset: moving to HEAD~1
4d1880d HEAD@{1}: revert: Revert "C3"
89eae10 HEAD@{2}: commit: C3
7f7ec32 HEAD@{3}: reset: moving to HEAD~1
92ca399 HEAD@{4}: commit: C3 again
```

每一行是：

- 左边的哈希：**那个时刻 HEAD 指向的 commit**；
- `HEAD@{N}`：从新到旧编号，`@{0}` 是当前；
- 右边的说明：是什么操作导致 HEAD 移动的。

### 用 reflog 找回"丢了"的提交

场景：你 `reset --hard` 回退了两个提交，突然发现"不对，我刚才那两个提交里还有有用的东西"。

```bash
# 1. 找到"回退之前"那条记录
git reflog
# 假设看到 HEAD@{1} 是回退前的位置，哈希是 4d1880d

# 2. 直接切过去（或 reset 过去）
git reset --hard 4d1880d
# 或临时看一眼：
git switch -c recovered 4d1880d
```

于是"丢了"的提交又回来了。**只要 reflog 里还有记录，就没有真正"丢失"的提交。**

### reflog 和 log 的区别

| | `git log` | `git reflog` |
|---|---|---|
| 记录什么 | 当前分支的历史（沿着 parent 链） | HEAD 的**移动轨迹**（包括所有分支切换、reset） |
| 被 reset 掉的提交 | **看不到** | **看得到** |
| 作用 | 看项目历史 | 看"我最近干了什么" |

**一句话理解：`git log` 是"这个项目的历史"，`git reflog` 是"你在这个仓库里的操作历史"。**

### reflog 的保存期限

reflog 不是永久的。默认保留 **90 天**（可配置 `gc.reflogExpire`）。90 天内你都可以找回，超过 90 天且对象被 GC 回收，就真的没了。所以"误删后找不回"通常发生在"过了很久才发现"。

> 一句话记住它：`git reflog` 记录 HEAD 的每一次移动，是找回"被 reset/误删的提交"的救命稻草；默认保留 90 天。

## 05.7 一个完整的"撤销决策树"

把整章串起来，遇到"我后悔了"时按这个顺序走：

```text
我想撤销……
├─ 工作区里没 add 的改动？
│    └─ git restore <file>
├─ 已经 add 但没 commit？
│    └─ git restore --staged <file>   （取消 add，改动回到工作区）
├─ 已经 commit 但没 push？
│    ├─ 只改提交信息/合并提交 → git reset --soft HEAD~1
│    ├─ 漏了文件想重新挑 → git reset --mixed HEAD~1（或 HEAD~N）
│    └─ 彻底不要了 → git reset --hard HEAD~1
├─ 已经 push 了？
│    └─ git revert <commit>
└─ 已经"弄丢"了 / 回退过头了？
     └─ git reflog 找回
```

> 一句话记住它：按"改动在哪一层"选工具——工作区用 restore，暂存区用 restore --staged，未推送用 reset，已推送用 revert，弄丢了找 reflog。

## 05.8 `git clean`：清理没被跟踪的文件

### 先给结论

前面所有撤销工具（restore/reset/revert）管的都是**已跟踪**文件。但**未跟踪**的文件（`??` 状态）它们都管不着——这时候用 `git clean`。

`git clean` 删除**工作区里所有未跟踪的文件**。

### 一个真实场景

你跑了 `npm run build`，生成了一堆 `dist/` 下的未跟踪文件，或者 `git merge --abort` 后留下了一些临时文件。`git status` 里一堆 `??`，你想一键清掉。

```bash
# 先干跑一遍，看看会删什么（不真删）
git clean -n
```

```text
Would remove dist/bundle.js
Would remove tmp/cache.tmp
```

`-n`（dry run）只**预览**，不真删。确认没问题再真删：

```bash
git clean -f          # -f 强制（真的删）
git clean -fd         # -d 连未跟踪的目录一起删
```

### 为什么必须 `-f`

`git clean` 默认**需要 `-f`（force）才真的删**，因为它删的是"未跟踪文件"——这些文件**没有进过 Git，删了就找不回来**（不像 reset 掉的 commit 还能 reflog）。这个强制确认是 Git 的保护。

### `clean` 和 `restore` 的分工

| | 清理什么 | 能找回吗 |
|---|---|---|
| `git restore` | 已跟踪文件的改动 | 能（改动只是被覆盖，未提交的看 reflog） |
| `git clean` | 未跟踪的文件 | **不能**（从未进过 Git） |

**所以 `git clean` 前一定要 `-n` 预览**，确认没有误删你想留的东西。

> 一句话记住它：`git clean -f` 删未跟踪文件（`restore`/`reset` 管不着的那部分），删了找不回；先 `-n` 预览再动手。

## 05.9 `git commit --amend`：改写"上一个提交"

### 先给结论

`--amend` 把新改动**合并进上一次提交**，而不是新建提交。它属于"改写历史"的一种，但范围最小——只改最后一个提交。

```bash
# 改提交说明
git commit --amend -m "新的说明"

# 补一个漏掉的文件
git add 漏掉的文件
git commit --amend
```

### 它改的是什么

`--amend` 本质是"用一个新的 commit 替换掉上一个 commit"。上一个 commit 的哈希会变（因为内容变了），历史里它被"换"掉了。

```text
之前：C1 ── C2
之后：C1 ── C2'   （C2 被替换成 C2'，哈希变了）
```

### 和 reset 的对比

| | `git reset --soft HEAD~1` | `git commit --amend` |
|---|---|---|
| 目的 | 回退后重新提交（改动还在暂存区） | 直接改上一个提交 |
| 结果 | 上一个提交"退"回暂存区 | 上一个提交被"替换" |
| 适用 | 回退多个、重新挑选 | 只改最后一个提交的说明/补文件 |

两者都能"改写历史"，但 `--amend` 更轻量，只针对最后一次提交。

### 同样的禁忌

**`--amend` 只能对"还没 push 的最后一个提交"用。** 已经 push 了再用 amend，你就改写了共享历史，需要 `push --force` 才能同步，会坑到同事（和第 05.4 节 revert 的禁忌是同一件事）。

> 一句话记住它：`--amend` 替换最后一个提交（改说明/补文件），哈希会变；同样只对未 push 的提交用。

## 05.10 `git reset HEAD <file>`：取消暂存（路径形式）

### 先给结论

**`git reset` 有两种完全不同的用法，这是新手最容易搞混的地方：**

| 用法 | 作用 | 例子 |
|---|---|---|
| `git reset <commit>` | 移动**分支指针**（回退历史） | `git reset HEAD~1` |
| `git reset <commit> <file>` | **取消某个文件的暂存**（不动分支） | `git reset HEAD f.txt` |

带**文件路径**的 `reset`，是"把暂存区里这个文件退回到指定 commit 的版本"，**它不移动分支、不改历史**——它只是"取消 add"。

### 亲手看

```bash
echo 1 > f.txt
git add f.txt && git commit -m C1
echo 2 >> f.txt
git add f.txt          # 现在 f.txt 的改动进了暂存区
git reset HEAD f.txt   # 取消暂存，退回工作区
```

```text
Unstaged changes after reset:
M	f.txt
```

之后 `git status -s`：

```text
 M f.txt
```

注意 `M` 从第一列（暂存区）跑到了第二列（工作区）——**这就是"取消 add"的效果**：改动还在，只是不再处于"准备提交"的状态了。

### 为什么路径形式容易让人害怕

很多人第一次看到 `git reset HEAD f.txt` 会吓一跳："reset 不是会回退历史吗？会不会把我的提交删了？"

**不会。** 关键区别就在**有没有文件参数**：

- 有文件参数（`git reset HEAD f.txt`）→ 只动**暂存区**，分支指针纹丝不动；
- 没文件参数（`git reset HEAD~1`）→ 才移动**分支指针**。

**日常"取消 add"推荐用 `git restore --staged f.txt`**（05.5 讲过，语义更清晰），但 `git reset HEAD f.txt` 是历史更久的写法，网上的教程、同事的脚本里到处都是，你必须认得。

> 一句话记住它：`git reset <commit> <file>` 是"取消暂存"，不动分支；`git reset <commit>` 才是"回退历史"。有文件参数和没文件参数，是两件完全不同的事。

## 05.11 `git revert -n` 和批量 revert

### 先给结论

05.4 的 `git revert` 每次只撤销**一个**提交，并且**自动提交**。加 `-n`（`--no-commit`）后：**只把反向改动放进暂存区，不自动提交**——于是你就能"一次撤销多个提交，最后只提交一次"。

### 单个 revert 不加 `-n` vs 加 `-n`

```bash
git revert HEAD        # 撤销 HEAD，并立刻生成一个反向提交
git revert -n HEAD     # 撤销 HEAD，但只暂存，不提交
```

```bash
git revert -n HEAD
git status -s
```

```text
D  c.txt
```

`D `（第一列）说明"删除 c.txt"已经进了暂存区，等你自己 `git commit`。

### 批量 revert：一次撤销多个提交

如果你想撤销**连续的好几个提交**（比如 C2、C3 都有问题，要一起撤），逐个 revert 会产生一堆反向提交，历史很乱。用 `-n` 批量处理：

```bash
git revert -n HEAD HEAD~1   # 撤销最近的 C3 和 C2 两个提交
```

```text
（安静，直接退出码 0）
```

```bash
git status -s
```

```text
D  b.txt
D  c.txt
```

两个文件的删除都进了暂存区。最后**一次 commit** 就完成了"撤销两个提交"：

```bash
git commit -m "revert: 撤销 C2 和 C3"
```

历史里只多了**一个**干净的反向提交，而不是两个。

### 什么时候用批量 revert

| 场景 | 做法 |
|---|---|
| 撤销单个已推送提交 | `git revert <commit>` |
| 撤销连续多个提交，想只留一个反向提交 | `git revert -n <最新> <次新> ...` + 一次 commit |
| 撤销中间某个提交（非连续） | 只能逐个 revert，或 `reset`（未推送时） |

**注意**：revert 多个提交时，Git 会按你给参数的顺序**从后往前**应用反向改动，中间也可能遇到冲突（和第 04 章一样解决）。

> 一句话记住它：`revert -n` 只暂存不提交；`git revert -n A B C` 一次撤销多个提交、最后只 commit 一次，历史更干净。

## 05.12 `git restore --source`：从历史里捞单个文件

### 先给结论

05.5 的 `git restore` 只能恢复到"暂存区"或"HEAD"。加 `--source`，你可以指定**任意一个 commit**，从里面把某个文件捞回来。

```bash
git restore --source=<commit> <file>
```

### 亲手看

```bash
# 当前 f.txt 被改坏了，想找回 HEAD 版本的 f.txt
printf "xxx" > f.txt      # 手滑把 f.txt 覆盖成了垃圾
git restore --source=HEAD f.txt
cat f.txt
```

```text
1
```

`f.txt` 恢复成了 HEAD 里那个版本的内容。

### 从"更早的提交"捞

`--source` 后面可以是任意引用：

```bash
git restore --source=HEAD~3 f.txt      # 从上上个提交捞
git restore --source=<某个哈希> f.txt  # 从指定提交捞
git restore --source=feature f.txt     # 从 feature 分支捞
```

**典型场景**：你发现某个文件"三天前还是对的，最近被改坏了"。不用回退整个仓库，直接：

```bash
git log --oneline -- f.txt      # 先看这个文件的历史
git restore --source=<还好的那个提交> f.txt   # 只捞回这个文件
```

### 和 `checkout <commit> -- <file>` 的关系

老写法是 `git checkout <commit> -- <file>`，新写法是 `git restore --source=<commit> <file>`，两者等价：

```bash
git restore --source=HEAD~1 f.txt
git checkout HEAD~1 -- f.txt    # 老写法，同一个效果
```

**新代码用 `restore --source`**，语义更清晰。

> 一句话记住它：`git restore --source=<commit> <file>` 从任意提交捞回单个文件，不用回退整个仓库；取代老的 `checkout <commit> -- <file>`。

## 05.13 reflog 进阶：找回被删掉的分支

### 先给结论

05.6 讲了用 reflog 找回"被 reset 掉的提交"。它还有一个**同样重要的用法**：找回**被 `git branch -D` 删掉的分支**。

### 分支被删，但提交还在

删分支只是删指针，commit 对象还在（第 03 章说过）。所以被删分支指向的提交，reflog 里一定有记录：

```bash
git branch delme
git branch -D delme
```

```text
Deleted branch delme (was 76ddcdd).
```

**注意这行输出**：`(was 76ddcdd)` 就是被删分支当时指向的提交哈希——这就是找回它的钥匙。

### 用 reflog 找回

```bash
git reflog
```

```text
76ddcdd HEAD@{0}: commit: C3
cf36c9b HEAD@{1}: commit: C2
a66cae2 HEAD@{2}: commit (initial): C1
```

找到"删分支之前"那个提交（比如 `76ddcdd`），重新建一个分支指向它：

```bash
git branch delme 76ddcdd   # 用哈希重建分支
```

于是 `delme` 分支又回来了，指向原来的提交，历史完好无损。

### 更稳的办法：找回任何一个"曾经存在过"的位置

reflog 的本质是"HEAD 的移动轨迹"，所以**所有你曾经 checkout 过、reset 到过、commit 过的位置，都在里面**。哪怕你记不清哈希，只要记得大概的时间或操作，就能从 reflog 里认出来：

```bash
git reflog --date=iso    # 带时间戳的 reflog，方便按时间定位
```

```text
76ddcdd HEAD@{0}: commit: C3
cf36c9b HEAD@{1}: commit: C2
```

看到某条可疑记录，直接 `git show <哈希>` 看看是不是你要找的，再决定要不要 `git branch` / `reset` 过去。

> 一句话记住它：`git branch -D` 删分支时输出 `Deleted branch xxx (was <哈希>)`，那个哈希就是找回钥匙；用 `git branch 分支名 <哈希>` 或 reflog 都能重建。

## 05.14 撤销操作的安全习惯：先备份，再动手

### 先给结论

撤销命令里有一批是**不可逆**的（`reset --hard`、`clean -f`、`restore` 覆盖改动）。真正的高手不是"撤销得快"，而是**动手前先给自己留好后路**。这一节给你三条低成本的安全习惯。

### 习惯一：动手前先 `git status`

这是最简单的，也是被跳过最多的。`reset --hard` 之所以危险，是因为它会抹掉**未提交的改动**。动手前瞄一眼：

```bash
git status
```

- 如果有 `modified` / `untracked` 文件没提交，先想清楚"这些我是不是要留"；
- 如果要留，先提交或 stash，再撤销。

**一句话：`--hard` 前必看 `git status`，有未提交的东西就三思。**

### 习惯二：给"当前状态"建一个备份分支

分支便宜到不要钱（第 03 章），所以撤销前花一秒建个备份，是最划算的保险：

```bash
git branch backup-before-reset
```

这一下，当前分支指向的 commit 就被 `backup-before-reset` 这个分支"钉"住了。之后你随便 `reset`、`rebase`，只要没删这个分支，随时能：

```bash
git switch backup-before-reset    # 回到撤销前的状态
```

**这比 reflog 还省心**——不用从一堆 `HEAD@{n}` 里猜哪个是对的，分支名自己说明一切。

### 习惯三：不确定就用 `git stash` 存起来

如果你有"半成品"改动既不想提交、又怕被撤销误伤，用 `git stash`（第 08 章细讲）先藏起来：

```bash
git stash          # 把未提交改动存进"工作现场堆栈"，工作区变干净
git reset --hard HEAD~1   # 现在放心撤销
git stash pop      # 再把改动取回来
```

stash 存的是"未提交的改动"，和 commit 不同——它不进历史，只是一个"临时抽屉"。适合"我还想继续做，但暂时要清场"的场景。

### 一张安全清单

| 要做的撤销 | 先做哪一步保险 |
|---|---|
| `reset --hard` | `git status` 看未提交改动 + `git branch backup` |
| `clean -f` | `git clean -n` 预览 |
| `restore <file>` | 先 `git diff` 确认丢的是不是想要的 |
| `rebase`（第 07 章） | 先 `git branch backup` 备份分支 |

**核心思想只有一条：撤销本身不危险，危险的是"没留后路就撤销"。** 备份分支 + reflog 双保险，你几乎不可能真的"丢东西"。

> 一句话记住它：撤销前先 `git status` 看未提交改动，再用 `git branch backup` 钉住当前位置，或用 `stash` 存半成品；有后路才敢下手。

## 05.15 本章常见坑速查

| 坑 | 现象 | 原因 | 正确做法 |
|---|---|---|---|
| `--hard` 误删未提交改动 | 工作区改动全没了 | `--hard` 会覆盖工作区 | 用前先 `git status` 确认没有未提交的东西 |
| 对已推送的提交用 reset | 同事的仓库被搞乱 | 改写了共享历史 | 已推送的用 `revert` |
| reset 后以为提交被物理删除 | 慌 | reset 只是挪指针，对象还在 | 用 `reflog` 找回 |
| 分不清 soft/mixed/hard | 误操作 | 没记住三者的"动哪几棵树" | soft 挪指针、mixed 清暂存区、hard 砸工作区 |
| `restore` 一个未跟踪文件 | `error: pathspec ... did not match` | restore 只认 Git 跟踪过的文件 | 未跟踪的新文件直接 `rm` |
| 想取消 add 却用 `restore` | 改动被丢了 | `restore <file>` 丢工作区改动，`--staged` 才取消 add | 取消 add 用 `restore --staged` |
| 以为 reflog 永久保存 | 90 天后找不到 | reflog 有保质期 | 误删尽早找回 |
| revert 冲突后不知道怎么办 | 卡在冲突里 | revert 也会冲突 | 解决冲突后 `git revert --continue` |
| 想回退多个提交却逐个 revert | 繁琐 | revert 要逐个反向 | 未推送的话直接 `reset --hard <commit>` |
| 把 `git reset HEAD 文件` 当"回退历史" | 以为分支被重置了 | 带文件参数只取消暂存 | 取消 add 用 `restore --staged`，回退历史用 `reset <commit>` |
| `revert -n` 后忘了提交 | 反向改动停在暂存区，以为撤销完了 | `-n` 不自动提交 | 确认后手动 `git commit` |
| `git branch -D` 误删分支 | 以为提交丢了 | 删分支只删指针 | 看删除时输出的 `(was <哈希>)`，用 `git branch 名 <哈希>` 重建 |

## 05.16 本章小结

**reset 三兄弟**

- `--soft` 只挪 HEAD；`--mixed`（默认）挪 HEAD + 清暂存区；`--hard` 连工作区一起砸。
- `--hard` 会抹掉所有未提交改动，最危险。
- reset 移动的是"当前分支指针"，被退掉的提交没删，靠 reflog 能找回。

**revert**

- `revert` 新增一个"反向提交"，不改历史，适合已推送的提交。
- 和 reset 的根本区别：reset 让历史变短，revert 让历史变长。

**restore**

- `restore <file>` 丢工作区改动；`restore --staged <file>` 取消 add。
- 取代老的 `checkout --`，只管工作区和暂存区。

**reflog**

- 记录 HEAD 的每次移动，是误操作后的后悔药。
- 默认保留 90 天；`git log` 看项目历史，`git reflog` 看操作历史。

**决策树**

- 工作区 → restore；暂存区 → restore --staged；未推送 → reset；已推送 → revert；弄丢 → reflog。

**进阶**

- `git reset <commit> <file>` 是"取消暂存"，不动分支；`git reset <commit>` 才是回退历史。
- `revert -n` 只暂存不提交，可一次撤销多个提交再 commit 一次。
- `restore --source=<commit> <file>` 从任意提交捞回单个文件。
- 删分支时输出 `Deleted branch xxx (was <哈希>)`，用该哈希能重建分支。

**安全习惯**

- 撤销前先 `git status` 看未提交改动，再用 `git branch backup` 钉住当前位置，或用 `stash` 存半成品。

## 05.17 动手练习

### 练习 1：说出三个 reset 的结果

当前有 C1、C2、C3 三个提交，`f.txt` 内容分别是 `1`、`12`、`123`。分别执行下面三条命令后，`git status -s` 和 `cat f.txt` 会是什么？

```bash
git reset --soft HEAD~1
git reset --mixed HEAD~1
git reset --hard HEAD~1
```

<details><summary>参考答案</summary>

- `--soft HEAD~1`：HEAD 退到 C2，`f.txt` 内容仍是 `123`（工作区没动），`status -s` 显示 `M f.txt`（改动在暂存区）。
- `--mixed HEAD~1`：HEAD 退到 C2，`f.txt` 仍是 `123`，`status -s` 显示 ` M f.txt`（改动退回工作区）。
- `--hard HEAD~1`：HEAD 退到 C2，`f.txt` 变回 `12`（C3 的 `3` 消失），`status -s` 干净。

</details>

### 练习 2：已推送的提交怎么撤销

你 push 了一个提交，发现里面有 bug。为什么不能用 `git reset`？应该怎么做？

<details><summary>参考答案</summary>

不能用 reset 的原因：这个提交已经共享到远程，reset 会改写历史，和同事的仓库产生分叉，需要 `push --force` 才能同步，会破坏别人的工作。

正确做法：

```bash
git revert <有bug的commit>
git push
```

revert 只是追加一个反向提交，历史保持不变，同事 `pull` 就能同步。

</details>

### 练习 3：找回"丢失"的提交

你执行了 `git reset --hard HEAD~3`，然后发现不该回退这么多。写出找回步骤。

<details><summary>参考答案</summary>

```bash
# 1. 看 reflog，找到回退前的位置
git reflog
# 假设看到 HEAD@{1} 是回退前的位置，哈希 abc1234

# 2. 两种找回方式
git reset --hard abc1234          # 直接把分支指回去
# 或临时建个分支看：
git switch -c recovered abc1234   # 建分支指向那个提交，慢慢看
```

</details>

### 练习 4：判断对错

1. `git reset --hard` 之后，被回退的提交立刻从磁盘上物理删除了。
2. `git revert` 会改写历史。
3. `git restore --staged f.txt` 会删除 f.txt 的内容。
4. `git reflog` 和 `git log` 看到的是同一份历史。
5. 对已推送的提交，`git revert` 是安全的撤销方式。

<details><summary>参考答案</summary>

1. **错。** commit 对象还在 `.git/objects/` 里，只是悬空了，reflog 能找回；只有等 GC 回收才真删。
2. **错。** revert 是追加反向提交，不改写历史；reset 才改写历史。
3. **错。** `--staged` 只是把改动从暂存区退回工作区，内容还在。
4. **错。** log 沿 parent 链看项目历史（被 reset 掉的看不到）；reflog 看 HEAD 移动轨迹（被 reset 掉的也能看到）。
5. **对。** revert 追加反向提交，不动已有历史，对共享分支最安全。

</details>

### 练习 5：`git reset HEAD 文件` 到底干了什么

执行 `git add f.txt` 之后，你又执行了 `git reset HEAD f.txt`。说出：① 分支指针有没有移动；② `f.txt` 的改动去哪了；③ 这条命令和 `git reset --hard HEAD~1` 的本质区别。

<details><summary>参考答案</summary>

1. **没移动。** 带文件参数的 `reset` 不碰分支指针。
2. 改动从**暂存区退回工作区**（`M ` 变成 ` M`），内容没删。
3. 本质区别：`git reset HEAD f.txt` 是"取消暂存"（带文件参数，只动暂存区）；`git reset --hard HEAD~1` 是"回退历史"（不带文件参数，移动分支指针还砸工作区）。

推荐用 `git restore --staged f.txt` 替代，语义更清楚。

</details>

### 练习 6：批量撤销两个已推送的提交

线上最近的 C3、C2 两个提交都有问题，你想撤销它们，但希望历史里**只多一个**反向提交。写出命令序列。

<details><summary>参考答案</summary>

```bash
git revert -n HEAD HEAD~1   # 撤销 C3 和 C2，只暂存不提交
git status -s               # 确认反向改动都进了暂存区
git commit -m "revert: 撤销 C3 和 C2"
git push
```

`-n` 让两个 revert 合并成一次提交，历史只多一个干净的反向提交。

</details>

### 练习 7：找回误删的分支

你执行了 `git branch -D feature`，删完后才想起 feature 上还有没合并的代码。写出找回步骤。

<details><summary>参考答案</summary>

```bash
# 方法一：看删除时的输出（如果有）
# Deleted branch feature (was 76ddcdd).  ← 76ddcdd 就是要找回的哈希
git branch feature 76ddcdd

# 方法二：用 reflog 找
git reflog              # 找到删分支前的提交哈希
git branch feature <哈希>
```

核心：删分支只删指针，commit 对象还在，用哈希重新建分支即可找回。

</details>

### 练习 8：撤销前的"三步保险"

你准备执行 `git reset --hard HEAD~3` 回退三个提交，但你手头还有一处没提交的改动，而且不确定回退是否过头。写出一个"先留后路"的安全操作序列。

<details><summary>参考答案</summary>

```bash
# ① 先看清有没有未提交的改动
git status

# ② 把当前分支位置"钉"住（保险）
git branch backup-before-reset

# ③ 未提交的改动先 stash 存起来（或直接提交）
git stash

# ④ 现在放心撤销
git reset --hard HEAD~3

# ⑤ 若发现过头了，随时回到撤销前
git switch backup-before-reset
```

核心思路：撤销本身不危险，危险的是"没留后路"。备份分支 + stash + reflog 三保险。

</details>

### 练习 9：判断对错

1. `git reset HEAD f.txt` 会把分支指针回退到上一个提交。
2. `git revert -n HEAD` 会自动生成一个反向提交。
3. `git restore --source=HEAD~2 f.txt` 会回退整个仓库到 HEAD~2。
4. `git branch -D feature` 之后，feature 上的提交就永久丢失了。
5. 撤销前先 `git branch backup` 是为了给"当前状态"留个可跳回的指针。

<details><summary>参考答案</summary>

1. **错。** 带文件参数的 `reset` 只取消暂存，不动分支指针。
2. **错。** `-n` 表示"只暂存不提交"，需要手动 `git commit`。
3. **错。** `--source=HEAD~2` 只恢复 `f.txt` 这一个文件，不影响其它文件和分支。
4. **错。** 删分支只删指针，commit 还在，用删除时输出的 `(was <哈希>)` 或 reflog 能重建。
5. **对。** 备份分支把当前位置钉住，撤销过头了随时 `git switch` 回来。

</details>
