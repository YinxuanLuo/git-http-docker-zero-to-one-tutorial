# 第 09 章 · 实战：从零走一遍规范协作流程

> 前 8 章你学会了所有零件。这一章把它们**组装起来**：从一个空目录开始，走完"初始化 → 功能分支 → 小步提交 → 合并 → 删分支 → 打标签"的完整流水线。
> 全程用 `node:child_process` 封装的 `.mjs` 脚本真实跑一遍，让你既能手动敲、也能看脚本怎么自动化。
>
> 读完本章，你要能回答三个问题：
> 1. 一个"需求 → 上线"的规范流程，标准动作有哪几步？
> 2. 每一步背后对应的是前几章的哪个命令、哪个道理？
> 3. 怎么用 Node 脚本（`execFileSync`）把这一串 git 命令自动化起来？
>
> 本章你需要记住的就一件事：**规范流程 = 分支命名讲语义 + 提交信息讲语义 + 合并方向单一 + 收尾干净；每一步都不是"高级技巧"，只是把第 1~8 章的命令按正确顺序串起来。**

## 09.1 流程全景图

先看一张总览，再逐段拆：

```text
① 初始化        git init -b main  +  配置身份
      │
② 基线提交      main 上建好项目骨架，提交第一个 commit
      │
③ 开功能分支    git switch -c feature/add-login
      │
④ 小步开发      每完成一个独立单元，提交一次（feat/test/chore 前缀）
      │
⑤ 同步主线      切回 main，拉取别人在此期间合入的改动
      │
⑥ 合并          git merge feature/add-login
      │
⑦ 清理          git branch -d feature/add-login
      │
⑧ 打标签        git tag -a v1.0.0 -m "首个版本"
```

**这条流水线的两个核心原则：**

1. **main 永远保持可发布。** 功能开发都在分支上做，main 只接受"已经完成、测试过"的合并。
2. **每个 commit 语义清晰。** 分支名和提交信息都讲"为什么/是什么"，三个月后任何同事都能看懂历史。

> 一句话记住它：规范协作 = 主线干净 + 分支开发 + 语义化提交 + 干净收尾；这张全景图就是本章的地图。

## 09.2 准备：初始化 + 配置身份

### 手动敲

```bash
mkdir my-app && cd my-app
git init -b main                      # 默认分支直接叫 main
git config user.name "你的名字"
git config user.email "you@example.com"
```

### 每一步为什么

- `git init -b main`：让默认分支叫 `main` 而不是 `master`（第 01 章讲过 `init.defaultBranch`）。团队统一用 `main`，协作时不用猜名字。
- `git config user.name/email`：**不带 `--global`**，只对这个仓库生效——避免公司/个人身份混用（第 01 章）。

### 用 Node 封装

本章的示例脚本用 `execFileSync` 封装 git 命令（零第三方依赖）：

```js
import { execFileSync } from 'node:child_process';

// 封装：在指定目录里跑一条 git 命令，返回去尾空白的 stdout
const git = (cwd) => (args, opts = {}) =>
  execFileSync('git', args, { cwd, encoding: 'utf8', ...opts }).trimEnd();

const g = git(projectDir);
g(['init', '-q', '-b', 'main']);
g(['config', 'user.email', 'dev@example.com']);
g(['config', 'user.name', 'Dev']);
```

**为什么要封装**：`execFileSync` 是同步执行外部命令的标准方式（`node:child_process` 模块）。`git` 本身是 CLI，脚本只是"替你把命令敲出去"，所以封装的价值在于**集中处理 cwd、编码、报错**，而不是重复写一长串 `execFileSync` 参数。

> 一句话记住它：初始化就是 `init -b main` + 配置身份；用 `execFileSync` 封装 git 命令，能集中处理 cwd/编码/错误。

## 09.3 开发：功能分支 + 小步提交

### 手动敲

```bash
# 建好项目骨架，先提交一个基线
echo "# 我的项目" > README.md
git add README.md
git commit -m "chore: 初始化项目骨架"

# 开功能分支
git switch -c feature/add-login

# 小步开发：每完成一个独立单元就提交一次
echo "function login(){}" > login.js
git add login.js
git commit -m "feat: 新增 login 模块骨架"

echo "function validate(u,p){...}" >> login.js
git add login.js
git commit -m "feat: 实现用户名密码校验"

echo "..." > test.js
git add test.js
git commit -m "test: 补充登录单测"
```

### 每一步为什么

- **分支名 `feature/add-login`**：`feature/` 前缀表明"这是一条功能分支"，`add-login` 说明主题。第 03 章说分支便宜，这里就"为一个需求开一条分支"。
- **小步提交**：不是写完整个功能才 commit 一次，而是"骨架""校验""测试"各提交一次。第 02 章的"一条提交一件事"在这里落地——将来回滚"校验"这个改动时，不会牵连"骨架"。
- **提交前缀**：`feat` / `test` / `chore` 是第 02 章的 Conventional Commits。机器可读，能自动生成 changelog。

### 用 Node 封装

```js
const commit = (cwd) => (msg) => {
  git(cwd)(['add', '-A']);
  git(cwd)(['commit', '-q', '-m', msg]);
};
const c = commit(projectDir);
c('feat: 新增 login 模块骨架');
```

**为什么要封装 `commit`**：因为"add 全部 + commit"这个组合会反复出现，抽成一个函数减少重复。这体现了第 08 章"工程化"的思路——把重复动作变成可复用的小函数。

> 一句话记住它：分支名带 `feature/` 前缀讲语义，提交用 `feat/test/chore` 前缀讲语义，一个小单元一条提交。

## 09.4 同步：切回主线，拉取最新

### 手动敲

```bash
git switch main
git pull origin main        # 拉取同事在此期间合入的改动
```

### 每一步为什么

**开发期间，主线可能已经变了**（同事合入了别的功能、修复了别的 bug）。所以在你把自己的功能合进 main 之前，先 `pull` 一下，确保你合并的是"最新"的 main，而不是"你开分支那一刻"的 main（第 06 章）。

### 分支分叉怎么办

如果 pull 时本地和远程分叉了，会看到第 06 章那个报错：

```text
fatal: Need to specify how to reconcile divergent branches.
```

解决：明确告诉 Git 用哪种合并策略：

```bash
git config pull.rebase false   # 用 merge 策略
git pull origin main
```

（演示环境里没有真实远程，示例脚本用"直接在 main 上提交一个 commit"来模拟"期间同事合入了改动"，效果一样。）

> 一句话记住它：合并前先 `pull` 同步主线，避免在过时的 main 上合并；分叉了就配 `pull.rebase`。

## 09.5 合并：feature → main

### 手动敲

```bash
git merge feature/add-login -m "merge: 合入登录功能"
```

### 每一步为什么

- **合并方向永远是"功能分支 → main"**，单向。这样 main 的历史清晰：主线是一条直线（或干净的分叉合并），功能开发的细节在分支上。
- **`-m` 写清楚合并意图**：默认的合并信息是 `Merge branch 'feature/add-login'`，没有信息量。写 `merge: 合入登录功能` 让历史更可读。

### 遇到冲突怎么办

如果功能分支和 main 都改了同一处，merge 会冲突（第 04 章）。处理流程：

```bash
git merge feature/add-login        # → CONFLICT (content): Merge conflict in xxx
# 打开冲突文件，删标记，留下最终内容
git add xxx
git commit -m "merge: 合入登录功能（解决冲突）"
```

### 合并后看历史

```bash
git log --oneline --graph
```

```text
*   118d864 merge: 合入登录功能
|\
| * 64d030f test: 补充登录单测占位
| * 951cd29 feat: 实现用户名密码校验
| * 92d8047 feat: 新增 login 模块骨架
* | c8e42cf fix: 补上缺失的 config 模块
|/
* 143d3c9 chore: 初始化项目骨架
```

**这张图就是整个流程的"成绩单"**：你能看到主线（左边）、功能分支（右边）、以及合并点。历史清清楚楚。

> 一句话记住它：合并方向固定为"功能分支 → main"，用 `-m` 写清合并意图；冲突就按第 04 章的流程解决。

## 09.6 收尾：删分支 + 打标签

### 手动敲

```bash
git branch -d feature/add-login    # 已合并，安全删除
git tag -a v1.0.0 -m "首个版本：含登录功能"
git push origin main
git push origin v1.0.0             # 标签也要单独推
```

### 每一步为什么

- **删分支**：合并完，功能分支的使命结束了。删掉它，`git branch` 保持清爽（第 03 章：删分支只是删指针，commit 都还在历史里）。
- **打标签**：给这个发布点钉一个版本号（第 08 章）。用 `-a`（附注标签）记录发布信息。
- **标签要单独推**：`git push origin main` **不会**自动把标签推上去，要 `git push origin v1.0.0` 或 `--tags`（第 08 章）。

### 用 Node 封装

```js
g(['branch', '-d', 'feature/add-login']);
g(['tag', '-a', 'v1.0.0', '-m', '首个版本：含登录功能']);
console.log(g(['tag', '-n']));   // 验证标签打好了
```

> 一句话记住它：合并后删分支保持清爽、打附注标签钉里程碑；标签要单独 push，不会随 main 自动传。

### 脚本的几个设计要点

看 `examples/git/09-实战流程.mjs` 的骨架，你会发现它有几个值得学的写法：

```js
import { execFileSync } from 'node:child_process';
import { mkdtempSync, writeFileSync, rmSync } from 'node:fs';
import { tmpdir } from 'node:os';
import { join } from 'node:path';

// 1. 在系统临时目录里建仓库，跑完清理——不污染你的项目
const dir = mkdtempSync(join(tmpdir(), 'git-flow-'));

// 2. 封装 git，集中处理 cwd / 编码 / 去尾空白
const git = (args, opts = {}) =>
  execFileSync('git', args, { cwd: dir, encoding: 'utf8', ...opts }).trimEnd();

// 3. 封装 commit，减少"add + commit"的重复
const commit = (msg) => {
  git(['add', '-A']);
  git(['commit', '-q', '-m', msg]);
};

// 4. 用 try/finally 保证临时目录一定被清理
try {
  /* ...完整流程... */
} finally {
  rmSync(dir, { recursive: true, force: true });
}
```

**这四个写法是"用 Node 驱动 CLI 工具"的标准套路**：临时目录隔离、命令封装、重复逻辑抽函数、异常时保证清理。你在第 10 章第五关的项目题里，也会用同样的套路。

> 一句话记住它：用 `mkdtempSync` 隔离临时仓库、`execFileSync` 封装命令、`try/finally` 保证清理——这是"脚本驱动 git"的标准骨架。

## 09.8 扩展到真实团队：PR 流程（GitHub Flow）

### 先给结论

本章前面演示的是"本地仓库里的完整流程"。真实团队（尤其用 GitHub/GitLab 的）还会在**合并前加一道"代码评审（Code Review）"**——这就是 **Pull Request（PR）** 流程，也叫 GitHub Flow。

### 流程图

```text
① fork/clone 仓库
      │
② 从 main 开 feature 分支
      │
③ 开发 + 小步提交 + push 到远程
      │
④ 发起 PR（Pull Request）
      │
⑤ 同事评审、CI 跑测试
      │
⑥ 通过后合并进 main
      │
⑦ 删远程分支 + 本地同步
```

### 每一步对应的命令

```bash
# ① 克隆
git clone https://github.com/团队/项目.git

# ② 开功能分支
git switch -c feature/add-login

# ③ 开发、提交、推送
git add -A && git commit -m "feat: 登录功能"
git push -u origin feature/add-login

# ④ 发起 PR：在 GitHub 网页上点 "Compare & pull request"
# ⑤ 评审、CI 自动跑（这里你在网页上等结果）
# ⑥ 合并：点 "Merge pull request"（或本地 merge 后 push）
# ⑦ 删远程分支 + 本地清理
git push origin --delete feature/add-login
git switch main && git pull
git branch -d feature/add-login
```

### PR 流程和"本地直接 merge"的关键区别

| | 本地直接 merge | PR 流程 |
|---|---|---|
| 有没有代码评审 | 无 | **有**（同事 review 后才合并） |
| 有没有 CI 把关 | 无 | **有**（自动跑测试/lint） |
| 合并入口 | 你本地 `git merge` | 网页点 "Merge" 或 CI 自动合并 |
| 适用 | 个人项目 | 团队协作 |

**PR 的价值不在 Git 本身，而在于"把合并变成一个有评审、有测试的仪式"。** 这也是第 08 章说的"hooks 是本地第一道防线，服务端（CI/PR）是第二道防线"的落地。

> 一句话记住它：PR 流程 = 分支开发 + push + 发起 PR + 评审 + CI + 合并；它在"合并"前加了一道代码评审和自动测试的闸门。

## 09.10 线上出事故了：怎么回滚发布

### 先给结论

发布后线上出 bug，第一要务是**快速回滚**，不是慢慢改代码。用 Git 的 tag + revert，能做到"几分钟回到上一个稳定版本"。

### 场景：刚发布的 v1.1.0 有严重 bug

```text
历史：... v1.0.0（稳定）── 若干提交 ── v1.1.0（有 bug，刚发布）
```

### 方案一：用 revert 回滚（推荐，安全）

如果 bug 集中在少数几个提交，逐个 revert：

```bash
git revert <有 bug 的提交>
git push
git tag -a v1.1.1 -m "回滚 v1.1.0 的 bug"
```

**优点**：历史完整、不破坏共享历史、同事 pull 一下即可同步。

### 方案二：直接回退到上一个 tag（快，但要小心）

如果 bug 太多、想整体回到 v1.0.0：

```bash
git reset --hard v1.0.0
git push --force        # ⚠️ 改写共享历史，要团队协调
```

**注意**：这里用了 `--force`，会改写远程历史，**必须和团队确认没人基于 v1.1.0 干活**。更温和的做法是"从 v1.0.0 开新提交"：

```bash
git revert --no-commit v1.1.0..HEAD
git commit -m "revert: 回滚到 v1.0.0 状态"
```

### 为什么 tag 在这里是救命的

因为 `git reset --hard v1.0.0` 里的 `v1.0.0` 是个**稳定的锚点**——你不需要记那串哈希，标签就是那个"稳定版本"的名字。这就是第 08 章说的"tag 钉里程碑"的价值。

### 一条黄金流程

```text
线上出 bug
  ├─ 能定位到具体提交 → git revert 那个提交
  └─ 无法快速定位 → 回退到上一个 tag（用 revert，别用 reset --hard --force）
然后打新 tag、push、通知团队
```

> 一句话记住它：回滚用 `git revert`（安全）而不是 `reset --hard --force`（危险）；tag 是"稳定版本"的锚点，让回滚变成一条命令。

## 09.11 本章常见坑速查

| 坑 | 现象 | 原因 | 正确做法 |
|---|---|---|---|
| 直接在 main 上开发 | main 乱成一锅粥 | 没走分支开发 | 每个需求一条 `feature/` 分支 |
| 一个功能一次 commit | 回滚牵连一片 | 没小步提交 | 一个独立单元一条提交 |
| 合并前不 pull | 在过时的 main 上合并 | 没同步主线 | 先 `git pull origin main` |
| 默认合并信息没信息量 | 历史一堆 `Merge branch` | 没带 `-m` | `git merge -m "merge: 说明"` |
| 标签没推远程 | 别人看不到版本 | 标签不随 push 自动传 | `git push origin --tags` |
| 合并后分支不删 | 分支越堆越多 | 忘了清理 | `git branch -d feature/xxx` |
| 脚本里用 cwd 出错 | 命令在错误目录执行 | 没集中管理 cwd | 封装 git 函数统一传 `cwd` |
| 临时仓库污染项目 | 项目目录多一堆垃圾 | 没隔离 | `mkdtempSync(tmpdir())` + finally 清理 |

## 09.12 本章小结

**流程八步**

1. 初始化 + 配置身份（`init -b main`、`config`）
2. 基线提交（`chore: 初始化`）
3. 开功能分支（`switch -c feature/xxx`）
4. 小步开发（`feat/test/chore` 前缀）
5. 同步主线（`switch main` + `pull`）
6. 合并（`merge -m "merge: 说明"`）
7. 删分支（`branch -d`）
8. 打标签（`tag -a`）

**两个核心原则**

- main 永远可发布，功能在分支上做。
- 分支名、提交信息、合并信息都讲语义。

**脚本驱动 git 的套路**

- `mkdtempSync` 临时目录 + `execFileSync` 封装 + `try/finally` 清理。

### 练习 2：用 Node 封装一条 git 命令

写一个最小可运行的 `.mjs`：在临时目录 `git init`，然后 `git status`，打印输出，最后清理临时目录。

<details><summary>参考答案</summary>

```js
import { execFileSync } from 'node:child_process';
import { mkdtempSync, rmSync } from 'node:fs';
import { tmpdir } from 'node:os';
import { join } from 'node:path';

const dir = mkdtempSync(join(tmpdir(), 'demo-'));
try {
  execFileSync('git', ['init', '-q', dir], { stdio: 'pipe' });
  const out = execFileSync('git', ['status'], { cwd: dir, encoding: 'utf8' });
  console.log(out);
} finally {
  rmSync(dir, { recursive: true, force: true });
}
```

关键点：`execFileSync` 的三个参数（命令、参数数组、选项对象）；`cwd` 指定在哪个目录执行；`finally` 保证清理。

</details>

### 练习 3：判断对错

1. 功能开发应该直接在 main 分支上做。
2. `git push origin main` 会同时把标签推上去。
3. 合并功能分支时，方向是"main → 功能分支"。
4. 一个功能写完只提交一次是最规范的做法。
5. 合并前应该先 pull 同步主线。

<details><summary>参考答案</summary>

1. **错。** 功能开发应在 feature 分支上做，main 保持可发布。
2. **错。** 标签要单独 push（`git push origin v1.0.0` 或 `--tags`）。
3. **错。** 合并方向是"功能分支 → main"。
4. **错。** 应该小步提交，一个独立单元一条提交，而不是憋一个大 commit。
5. **对。** 先 pull 同步主线，再在最新的 main 上合并。

</details>
