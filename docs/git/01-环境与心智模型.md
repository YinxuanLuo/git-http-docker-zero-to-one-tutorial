# 第 01 章 · 环境与心智模型

> 第 00 章说了一句总纲：**Git 不是保存你的文件，是保存一个内容寻址的对象数据库。**
> 这一章回答的是：这句话落到你每天敲的 `git init` / `git add` / `git commit` 上，到底发生了什么。
>
> 读完本章，你要能回答三个问题：
> 1. 工作区、暂存区、版本库这三棵树，分别在你硬盘的哪里？怎么用 `git status` 一眼看出它们的状态？
> 2. `git add` 和 `git commit` 各自做了什么？为什么中间非要夹一个"暂存区"？
> 3. `.git` 目录里那一堆东西，到底各是干什么的？
>
> 本章你需要记住的就一件事：**Git 把"你的文件"分成了三个可以独立移动的区——工作区、暂存区、版本库；`git add` 和 `git commit` 就是在它们之间搬东西。**

---

## 01.1 先给结论：三棵树到底在哪

第 00 章已经说过三棵树的**概念**。这一章把它们落到**磁盘上的具体位置**，因为概念悬空没用，你得知道"它存在哪"才敢操作它。

先看一张表，再逐个拆：

| 名字 | 磁盘上的位置 | 里面装什么 | 你操作的命令 |
|---|---|---|---|
| **工作区（working tree）** | 就是你的项目文件夹本身（`.git` 之外的其余文件） | 你正在编辑、能直接看到、能直接改的文件 | 编辑器、`cat`、`rm`…… |
| **暂存区（index / staging area）** | `.git/index` 这一个二进制文件 | 你"挑选"出来、准备提交的清单 | `git add`、`git restore --staged` |
| **版本库（repository）** | `.git/objects/` 里的一堆对象 + `.git/refs/` 里的指针 | 所有已经 `commit` 的历史快照 | `git commit`、`git log` |

**一句话记住这个对应关系：**

- 工作区 = 你**看得见**的文件夹；
- 暂存区 = `.git/index` 这一个**你看不懂的二进制文件**；
- 版本库 = `.git/objects/` 里那堆**用哈希命名的对象**。

> 一句话记住它：三棵树不是三个"概念上的比喻"，而是三处**真实存在**的存储——文件夹、`.git/index`、`.git/objects`。

## 01.2 准备工作：确认环境、配好身份

在动手之前，有两件事必须做，否则你会卡在最不该卡的地方。

### 确认 git 装好了

```bash
git --version
```

```text
git version 2.55.0.windows.3
```

版本号无所谓，只要有输出就说明 git 在你的 `PATH` 里。如果报 `command not found` 或 `'git' 不是内部或外部命令`，先装 git。

### 配好"你是谁"

每次 `commit`，Git 都要往提交里写"作者是谁、邮箱是什么"。没配过的话，第一次提交会被 git 拦住并给出提示：

```text
Author identity unknown

*** Please tell me who you are.

Run

  git config --global user.email "you@example.com"
  git config --global user.name "Your Name"
```

**为什么必须配？** 因为 commit 对象里存的是"人 + 时间 + 说明"（第 02 章会拆给你看），而 Git 本身不发明你的身份，它只负责记录。不配身份，就没法生成一个合法的 commit。

配置命令（`--global` 表示全局生效，对所有仓库都管用）：

```bash
git config --global user.name "你的名字"
git config --global user.email "you@example.com"
```

**注意 `--global` 的坑**：它会写进 `~/.gitconfig`（Windows 上是 `C:\Users\你\.gitconfig`）。如果你是公司机器、家里机器共用，或者想给某个项目单独用不同身份，就**去掉 `--global`**，改成在项目目录里配（写进当前仓库的 `.git/config`）。

```bash
# 只对当前项目生效（写进 .git/config，不进全局配置）
git config user.name "工作专用名"
git config user.email "work@company.com"
```

> 一句话记住它：先 `git --version` 确认能跑，再配 `user.name` / `user.email`——否则第一个 commit 就卡住。

## 01.3 `git init`：从一个空目录到"一个仓库"

### 先给结论

`git init` 只干一件事：**在你当前目录下创建一个 `.git` 子目录**。没了。它不改你的任何文件，也不要求目录里有什么东西。

```bash
mkdir my-project
cd my-project
git init
```

```text
Initialized empty Git repository in /path/to/my-project/.git/
```

### 它到底建了什么

```bash
ls -la .git
```

```text
drwxr-xr-x  1 you  staff   0 Oct 12 22:50 ./
drwxr-xr-x  1 you  staff   0 Oct 12 22:50 ../
-rw-r--r--  1 you  staff  23 Oct 12 22:50 HEAD
-rw-r--r--  1 you  staff 130 Oct 12 22:50 config
-rw-r--r--  1 you  staff  73 Oct 12 22:50 description
drwxr-xr-x  1 you  staff   0 Oct 12 22:50 hooks/
drwxr-xr-x  1 you  staff   0 Oct 12 22:50 info/
drwxr-xr-x  1 you  staff   0 Oct 12 22:50 objects/
drwxr-xr-x  1 you  staff   0 Oct 12 22:50 refs/
```

先别被这一串吓到，你只需要立刻记住四个：

| 目录/文件 | 干什么 | 什么时候会变 |
|---|---|---|
| `HEAD` | 记录"你现在站在哪个分支" | 切分支时变 |
| `config` | 这个仓库的配置（身份、远程地址等） | `git config` 时变 |
| `objects/` | **所有对象**（blob/tree/commit）都存这里 | `add`/`commit` 时变 |
| `refs/` | 分支、标签这些"指针" | 建分支、commit 时变 |

剩下的 `hooks/`（钩子，第 08 章）、`info/`（排除规则）、`description`（给 GitWeb 用的说明），现在都不用管。

### 一个真实的坑：默认分支名是 master 还是 main

`git init` 之后，你敲 `git branch` 会看到默认分支名。这个环境实测是 `master`，但很多教程写 `main`——**两者都对，取决于你的 git 全局配置**。

历史是这样的：Git 长期默认 `master`；2020 年社区推动把默认分支名改成更中性的 `main`，GitHub 率先改了，Git 2.28 起给了配置项让你自己定。

```bash
# 想以后新建仓库默认就叫 main：
git config --global init.defaultBranch main

# 或者单次 init 时直接指定：
git init -b main
```

**你在本书后面看到的 `main`，和你机器上的 `master` 是同一个角色**（"主分支"），别被名字卡住。

> 一句话记住它：`git init` 就是建一个 `.git` 目录；里面你只要先认识 `HEAD`、`config`、`objects`、`refs` 这四个。

## 01.4 第一个真实的 `git status`：看懂它说了什么

现在往空仓库里放一个文件，然后跑 `git status`。**这是你未来每天要敲几十次的命令**，必须能一眼读懂。

```bash
echo "hello git" > a.txt
git status
```

```text
On branch master

No commits yet

Untracked files:
  (use "git add <file>..." to include in what will be committed)
	a.txt

nothing added to commit but untracked files present (use "git add" to track)
```

逐行读，每一句都是**可执行的信息**：

1. `On branch master` —— 你在 `master` 分支上（分支的概念第 03 章讲，现在理解为"一条时间线"）。
2. `No commits yet` —— 这个仓库**还没有任何提交**，历史是空的。
3. `Untracked files:` 下面列着 `a.txt` —— 这个文件 Git **从没见过**，它叫"未跟踪文件"。
4. 括号里 `use "git add <file>..."` 是 Git 给你的**下一步建议**。

**关键区分：`Untracked`（未跟踪）和后面会出现的 `Modified`（已修改）是两回事。**

- 未跟踪：Git 压根不知道有这个文件存在；
- 已修改：Git 知道这个文件，但它的内容和你上次提交的不一样了。

`git status` 还支持一个短格式，更适合放进脚本和日常看结果：

```bash
git status -s
```

```text
?? a.txt
```

`??` 就是"未跟踪"的缩写。你只要记住这张速查表，`git status -s` 的输出就能全看懂：

| 第一列字符 | 含义 |
|---|---|
| `??` | 未跟踪（Untracked） |
| `M `（M 在第一列） | 已修改且已暂存（在暂存区） |
| ` M`（M 在第二列） | 已修改但未暂存（只在工作区） |
| `A ` | 新文件已暂存 |
| `D ` | 已删除并已暂存 |
| ` D` | 已删除但未暂存 |

两列分别对应**暂存区**和**工作区**：第一列是"暂存区相对于上次提交"的变化，第二列是"工作区相对于暂存区"的变化。这个双列设计，正是三棵树的直接体现。

### 一个真实的报错：在非仓库里跑 git

如果你在**没有 `.git` 的目录**里敲 `git status`，会看到：

```text
fatal: not a git repository (or any of the parent directories): .git
```

**触发条件**：当前目录（以及它的所有父目录）都不存在 `.git` 目录。注意那句 `or any of the parent directories`——Git 会**向上**找，所以你在仓库的子目录里跑 git 命令也能正常，因为 Git 找到了上层的 `.git`。

> 一句话记住它：`git status` 是"三棵树的仪表盘"；`??` 是未跟踪，两列 `M` 分别指暂存区和工作区；在没 `.git` 的地方跑会报 `fatal: not a git repository`。

## 01.5 `git add`：把文件从工作区搬进暂存区

### 先给结论

`git add` **不提交任何东西**，它只做一件事：把文件的当前内容**拍一张快照，塞进暂存区**。这张快照是"这一刻"的内容，之后你再改文件，暂存区里的不会跟着变。

```bash
git add a.txt
git status -s
```

```text
A  a.txt
```

`A `（A 在第一列）说明 `a.txt` 已经被"暂存"了——它现在在暂存区里，等着被 commit。

### 证明"add 拍的是那一刻的快照"

这是新手最容易误解的地方。做一个实验：

```bash
echo "line 1" > a.txt
git add a.txt          # 把 "line 1" 暂存

echo "line 2" >> a.txt # add 之后再追加一行
git status -s
```

```text
AM a.txt
```

**`AM` 出现了两列**：

- `A `（第一列）：暂存区里有 `a.txt` 的快照（内容是 `line 1`）；
- ` M`（第二列）：工作区里的 `a.txt` 比暂存区又多了一行（`line 2`）。

**这就是"add 拍快照"的铁证。** 如果你现在 `git commit`，提交的是暂存区里那个只有 `line 1` 的版本，`line 2` 还在工作区飘着，不会进这次提交。

### `git add` 的三种常见用法

```bash
git add a.txt           # 只暂存一个文件
git add .               # 暂存当前目录下所有改动（含新增、修改、删除）
git add -A              # 暂存整个仓库的所有改动（不管你在哪个子目录）
```

**注意 `git add .` 和 `git add -A` 的差别**：`.` 是相对当前目录，`-A` 是相对整个仓库。当你 `cd` 进某个子目录时，`. ` 只 add 那个子目录下的东西，`-A` 会 add 全仓库。

### 两个真实的报错

**报错一：`git add` 一个不存在的文件。**

```bash
git add nope.txt
```

```text
fatal: pathspec 'nope.txt' did not match any files
```

**触发条件**：你指定的路径在工作区里不存在（拼错名、或者根本还没创建）。`pathspec` 是 Git 对"路径参数"的叫法。

**报错二（其实不是报错，是"没反应"）：`git add` 一个被 `.gitignore` 忽略的文件。**

```bash
git add node_modules/whatever.js
```

```text
The following paths are ignored by one of your .gitignore files:
node_modules/whatever.js
hint: Use -f if you really want to add them.
```

**触发条件**：文件命中了 `.gitignore` 的规则（第 08 章细讲）。Git 默认**拒绝**跟踪被忽略的文件，除非你 `-f` 强制。

> 一句话记住它：`git add` 是把"这一刻的内容"拍快照进暂存区，不是"标记这个文件"；add 之后再改文件，改动还在工作区里没进去。

## 01.6 `git commit`：把暂存区固化成历史

### 先给结论

`git commit` 把**暂存区里的内容**整体照一张快照，存进版本库，成为历史里不可变（实际上可改但要付出代价，第 05 章讲）的一个节点。

```bash
git commit -m "first commit"
```

```text
[master (root-commit) 16344d6] first commit
 1 file changed, 1 insertion(+)
```

逐行读：

1. `[master (root-commit) 16344d6]` —— 在 `master` 分支上，生成了提交 `16344d6`；`root-commit` 说明这是**第一个**提交（没有父提交）。
2. `first commit` —— 你写的提交说明。
3. `1 file changed, 1 insertion(+)` —— 相比上一个提交，1 个文件变了，插入了 1 行。

commit 之后再 `git status`：

```bash
git status
```

```text
On branch master
nothing to commit, working tree clean
```

**`working tree clean` 就是三棵树对齐的状态**：工作区 = 暂存区 = 版本库，三者一致，没有需要提交的东西。

### `-m` 到底在给什么写东西

`-m "first commit"` 里的 `-m` 是 message（提交说明）。**提交说明是给"未来的你和别人"看的**——三个月后你 `git log`，唯一能理解"这个改动为什么存在"的线索，就是这句话。

所以提交说明有规范（第 02 章专门讲）。现在先记住：**别写 `update`、`fix`、`改了改` 这种废话**。

如果忘了写 `-m`，git 会打开一个编辑器让你写。第一次遇到的人经常卡在那：**那是 vim**。怎么退出来：

```text
在 vim 里：先按 i 进入编辑，写好说明，
按 Esc 退出编辑，输入 :wq 回车 = 保存并退出
```

（不想进 vim 就永远记得带 `-m`。）

### commit 之后，对象库发生了什么

commit 完成，`git log` 能看到历史：

```bash
git log
```

```text
commit 16344d6e30022e0a9c1115853846cd87437d4562
Author: t <t@example.com>
Date:   Mon Oct 12 22:57:33 2026 +0800

    first commit
```

这个 commit 就是第 00 章说的"对象"。你现在提交了一个文件，Git 实际往 `.git/objects/` 里写了**三个对象**：

| 对象 | 类型 | 内容 |
|---|---|---|
| 一个 blob | 文件内容 `"hello git\n"` | 你的文件 |
| 一个 tree | 目录清单（`a.txt` → 那个 blob 的哈希） | 根目录 |
| 一个 commit | 指向 tree、记录作者和时间、指向"空"（无父提交） | 这次提交 |

**这三个对象，就是你第一次 commit 真正"存"下的东西。** 这个内容寻址的模型，正是 `examples/git/01-数据模型.mjs` 演示的——它用 `node:crypto` 手算 blob 哈希，再和 `git hash-object` 的真实输出对拍，结果一模一样：

```bash
node examples/git/01-数据模型.mjs
```

```text
--- 1. 手算 blob 哈希（内容寻址） ---
内容 'hello
' 的 blob 哈希 = ce013625030ba8dba906f756967f9e9ca394464a
内容 'Hello
'（改一个大写）= e965047ad7c57865823c7d992b1d046ea66edf78 （改一字节 → 完全不同）

--- 5. 与真实 git 命令对拍 ---
git hash-object 算出的真实哈希 = 6848ac47d80e4741f6bed355b356c55fd79e6ff4
我们手算的 blob 哈希          = 6848ac47d80e4741f6bed355b356c55fd79e6ff4
两者一致吗？ true → 手算的就是 git 内部算法
```

> 一句话记住它：`git commit` 把暂存区固化成历史里的一棵完整快照；`-m` 是写给未来看的话；一次 commit 背后是 blob + tree + commit 三个对象。

## 01.7 把三棵树串起来：一次完整的走位

现在做一次"走完三棵树"的练习，把前面所有知识点连成一条线。

```bash
# ① 工作区：新建文件
echo "v1" > note.txt
git status -s          # ?? note.txt   ← 未跟踪，只存在于工作区

# ② 暂存区：add 拍快照
git add note.txt
git status -s          # A  note.txt   ← 进入暂存区

# ③ 版本库：commit 固化
git commit -m "add note"
git status -s          # （无输出）     ← 三棵树对齐，干净

# ④ 再改工作区，制造"分叉"
echo "v2" >> note.txt
git status -s          #  M note.txt   ← 工作区领先暂存区
```

用一张流程图记住这条线：

```text
工作区                暂存区                版本库
 note.txt  --git add-->  note.txt  --git commit-->  历史快照
   │                       ↑
   └── 改了又改，暂存区不动 ──┘
```

**`git add` 是"工作区 → 暂存区"，`git commit` 是"暂存区 → 版本库"。** 方向千万别记反——`git commit` **不会**直接把工作区的改动提交上去，它只认暂存区里的东西。这是新手最常踩的坑：改了文件忘了 add，直接 commit，结果提交的是上一次 add 的内容。

> 一句话记住它：改动要先 `add` 进暂存区、再 `commit` 进版本库；`commit` 只认暂存区，不认工作区。

## 01.8 `.git` 目录深入：里面到底有什么

01.3 你只认识了四个，现在把整个 `.git` 逛一遍，看一次真实提交之后它长什么样。

```text
.git/
├── HEAD              # 一个文本文件，内容是 "ref: refs/heads/master"
├── config            # 这个仓库的配置
├── description       # 给 GitWeb 的说明（没人看）
├── hooks/            # 钩子脚本（第 08 章）
├── index             # ★ 暂存区本体！一个二进制文件
├── info/
│   └── exclude       # 类似 .gitignore，但只对本地生效
├── logs/             # ★ 日志：HEAD 每次移动的记录（reflog 就在这）
├── objects/          # ★ 所有对象，按哈希前两位分子目录
│   ├── 16/
│   │   └── 344d6e30022e0a9c1115853846cd87437d4562   # 一个对象
│   └── ...
└── refs/
    ├── heads/        # ★ 分支：每个文件就是一个分支，内容是 commit 哈希
    │   └── master
    └── tags/         # 标签
```

**几个必须亲眼看一眼的东西：**

`HEAD` 的内容，就是一个引用：

```bash
cat .git/HEAD
```

```text
ref: refs/heads/master
```

意思是"HEAD 指向 `refs/heads/master` 这个分支"。分支文件里才是真正的哈希：

```bash
cat .git/refs/heads/master
```

```text
16344d6e30022e0a9c1115853846cd87437d4562
```

`objects/` 的命名规则：哈希前两位是目录名，后面 38 位是文件名。所以你看到 `objects/16/344d6e...` 这种结构——**这是 Git 为了不让一个目录里堆几十万个文件做的分片**。

`index`（暂存区）是二进制的，直接 `cat` 是乱码。但你可以用 `git ls-files --stage` 看到它里面的结构：

```bash
git ls-files --stage
```

```text
100644 16344d6e30022e0a9c1115853846cd87437d4562 0	a.txt
```

这一行拆开：`100644` 是文件权限，中间是 blob 哈希，`0` 是冲突阶段标记（第 04 章会用到），最后是文件名。**你 add 的文件，就在这张清单里排队等着被 commit。**

> 一句话记住它：`.git` 里最核心的五个是——`index`（暂存区）、`objects/`（对象库）、`refs/heads/`（分支）、`HEAD`（当前分支指针）、`logs/`（reflog 的历史）。

## 01.9 配置的三级：system / global / local

### 先给结论

Git 的配置有**三个层级**，同一个配置项（比如 `user.name`）可能在三个地方都有值。Git 读取时遵循**"就近优先"**：`local` 覆盖 `global`，`global` 覆盖 `system`。

| 层级 | 命令 | 存储位置 | 生效范围 |
|---|---|---|---|
| system | `git config --system` | 系统级（如 `/etc/gitconfig`） | 这台机器上所有用户 |
| global | `git config --global` | `~/.gitconfig` | 你这个用户的所有仓库 |
| local | `git config`（默认） | 当前仓库的 `.git/config` | 仅当前仓库 |

### 一个真实场景：公司项目用工作邮箱，个人项目用个人邮箱

```bash
# 全局默认：个人身份
git config --global user.name "张三"
git config --global user.email "zhangsan@personal.com"

# 进公司仓库后，用 local 覆盖
cd ~/work/company-project
git config user.name "张三（工作）"
git config user.email "zhangsan@company.com"
```

因为 `local` 优先于 `global`，公司仓库里的提交会用工作邮箱，其它地方用个人邮箱。

### 怎么查某个配置最终生效的值

```bash
git config user.name          # 当前仓库实际生效的名字（已经按优先级合并过）
git config --list             # 列出所有生效的配置
git config --show-origin user.email   # 显示这个值来自哪个文件
```

`--show-origin` 是最有用的排查命令——当你不确定"这个配置到底是哪来的"，它直接告诉你来源文件。

### 什么时候用哪个层级

| 想配置的东西 | 用哪个层级 |
|---|---|
| 你的身份（名字/邮箱） | global（或 local 覆盖） |
| 默认分支名 `init.defaultBranch` | global |
| 编辑器 `core.editor` | global |
| 换行符处理 `core.autocrlf` | local（不同项目可能不同） |
| 远程地址 `remote.origin.url` | local（自动写进 `.git/config`） |

> 一句话记住它：配置分 system / global / local 三级，local 最优先；搞不清某个配置哪来的，用 `git config --show-origin` 查来源。

## 01.10 亲手看对象：`cat-file` 与 `hash-object`

### 先给结论

第 01.6 节说"一次 commit 背后是三个对象"，这一节让你**亲手把它们挖出来看**。两个命令就够了：

- `git hash-object <file>`：算一个文件的 blob 哈希（不加 `-w` 只算不写）；
- `git cat-file -p <hash>`：以"漂亮格式"查看任意对象的内容。

### 从哈希到对象，走一遍

```bash
# 1. 建一个仓库并提交
git init && echo "hello" > a.txt
git add a.txt && git commit -m "first"

# 2. 找到这次 commit 的哈希
git log --oneline
# 16344d6 first commit

# 3. 拆开这个 commit 对象
git cat-file -p HEAD
```

```text
tree 0d8a474fc67971fb3dd7616e26323d3066442555
author t <t@example.com> 1791817053 +0800
committer t <t@example.com> 1791817053 +0800

first
```

看到第一行 `tree 0d8a47...` 了吗？这就是 commit 指向"目录树"的哈希。继续拆：

```bash
# 4. 拆开那个 tree 对象
git cat-file -p 0d8a474
```

```text
100644 blob 6848ac47d80e4741f6bed355b356c55fd79e6ff4	a.txt
```

这一行就是 tree 的内容：`100644`（权限）`blob`（类型）`6848ac...`（a.txt 的 blob 哈希）`a.txt`（文件名）。再拆：

```bash
# 5. 拆开那个 blob 对象，就是文件内容
git cat-file -p 6848ac4
```

```text
hello
```

**一路拆下来：commit → tree → blob → "hello"。** 这就是第 00 章说的"对象数据库"，你现在亲眼看到了它的三层结构。

### 验证"对象名 = 内容哈希"

```bash
# 用 hash-object 算 a.txt 的 blob 哈希，和上面 tree 里引用的一致吗？
git hash-object a.txt
```

```text
6848ac47d80e4741f6bed355b356c55fd79e6ff4
```

一致。**这就证明了 Git 的对象名不是随机给的，而是内容的哈希。**

### 顺带知道：`git cat-file -t` 看类型

```bash
git cat-file -t HEAD      # commit
git cat-file -t 0d8a474   # tree
git cat-file -t 6848ac4   # blob
```

`-t` 只看类型，不展开内容。

> 一句话记住它：`cat-file -p` 一路拆 commit → tree → blob，`hash-object` 验证"对象名 = 内容哈希"；这就是 Git 底层的数据结构。

## 01.11 三个高频进阶用法：`add -p` / `commit -a` / `commit --amend`

第 01.5、01.6 节讲的 `add` 和 `commit` 是"标准用法"。这一节补三个真实项目里天天用的进阶用法。

### `git add -p`：一块一块地暂存

**先给结论**：`git add -p`（p = patch，补丁）让你**按"块"**决定要不要暂存，而不是整个文件一锅端。

场景：你在一个文件里同时改了"bug 修复"和"半成品功能"，想只提交 bug 修复。普通 `git add` 会把整个文件都暂存，但 `add -p` 能让你一块一块地选。

```bash
git add -p a.txt
```

Git 会把文件的改动切成若干"块（hunk）"，逐块问你：

```text
@@ -1,3 +1,5 @@
  line 1
+修复 bug 的那一行
+半成品功能的那一行

(1/1) Stage this hunk [y,n,q,a,d,e,?]?
```

按 `y` 暂存这一块、`n` 跳过、`q` 退出。**这是"精确控制提交内容"的终极武器**——第 00 章说暂存区让你"想清楚再提交"，`add -p` 把这件事做到了极致。

### `git commit -a`：跳过 add

**先给结论**：`git commit -a` 会**自动把"已跟踪文件"的改动先 add 再 commit**，省掉一次 `git add`。

```bash
# 这两条等价（前提：a.txt 已经被跟踪过）
git add a.txt && git commit -m "fix"
git commit -a -m "fix"
```

**注意坑**：`-a` **只对"已经跟踪过"的文件生效**。新建的未跟踪文件，`-a` 不会自动加进来（还是要先 `git add`）。这就是为什么新手"用了 `-a` 结果新文件没提交"。

### `git commit --amend`：修改上一次提交

**先给结论**：`--amend` 把"新的改动"合并进**上一次**提交，而不是新建一个提交。常用于"提交信息写错了"或"漏 add 了一个文件"。

```bash
# 场景一：提交信息写错了，改一下
git commit --amend -m "新的提交说明"

# 场景二：漏 add 了一个文件，补进去
git add 漏掉的文件
git commit --amend
```

**一个必须记住的坑**：`--amend` 会**改写上一个 commit 的哈希**（因为它改了 commit 的内容）。所以它**只能对"还没 push 的最后一个提交"用**。已经 push 了再用 amend，你就改写了共享历史（第 05、07 章会反复强调这个禁忌）。

> 一句话记住它：`add -p` 按块暂存，`commit -a` 跳过 add（只对已跟踪文件），`commit --amend` 修改上次提交（只能对未 push 的用）。

## 01.12 提交前瞄一眼：`git diff` 快速看"改了什么"

### 先给结论

`git status` 告诉你**哪些文件**变了，`git diff` 告诉你**具体改了哪几行**。提交前用 `git diff` 瞄一眼，是避免"把不该提交的东西提交上去"的最后一道防线。

`git diff` 有三个变体，对应三棵树里不同两棵的比较：

| 命令 | 比较的两棵树 | 回答的问题 |
|---|---|---|
| `git diff` | 工作区 vs 暂存区 | 我改了但还没 `add` 的是什么？ |
| `git diff --cached` | 暂存区 vs HEAD | 我 `add` 了但还没 `commit` 的是什么？ |
| `git diff HEAD` | 工作区 vs HEAD | 这次提交**总的**改动（已 add + 未 add 都算） |

（`--cached` 和 `--staged` 是同一个意思，两个写法都行。）

### 亲手看

```bash
echo "hello" > a.txt
git add a.txt && git commit -m "first"

# 提交之后又改了一行
echo "world" >> a.txt
git diff
```

```text
diff --git a/a.txt b/a.txt
index ce01362..94954ab 100644
--- a/a.txt
+++ b/a.txt
@@ -1 +1,2 @@
 hello
+world
```

先粗读，细节留给 02 章：

- `--- a/a.txt` 是"旧版本"（这里是暂存区），`+++ b/a.txt` 是"新版本"（这里是工作区）；
- `@@ -1 +1,2 @@` 是"改动位置"：旧文件从第 1 行起共 1 行，新文件从第 1 行起共 2 行；
- 行首 `+world` 的 `+` 表示"新增了这一行"。没有 `+` 的行（` hello`）是上下文，没变。

### 一个必须记住的坑：`git diff` 不显示未跟踪的新文件

一个全新的 `new.txt`（`git status -s` 里是 `??`）**不会被 `git diff` 显示**——因为 Git 手里根本没有它的"旧版本"可比。想看它，得先 `git add` 让它进入暂存区。

```bash
echo "我是新文件" > new.txt
git diff          # 什么都不输出，new.txt 没被显示
git add new.txt
git diff --cached # 现在能看到 new.txt 的完整内容了
```

```text
diff --git a/new.txt b/new.txt
new file mode 100644
index 0000000..7f84e6c
--- /dev/null
+++ b/new.txt
@@ -0,0 +1 @@
+我是新文件
```

注意 `new file mode 100644` 和 `--- /dev/null`：旧版本是"空"，所以整个文件都是新增的 `+`。

### 为什么是三个变体而不是一个

因为三棵树有两道"门"：工作区 → 暂存区、暂存区 → 版本库。`git diff` 的每个变体，就是**站在其中一道门前，比较门两边**。你只要记得"diff 不带参数看工作区→暂存区，带 `--cached` 看暂存区→HEAD"，就不会搞混。

> 一句话记住它：`git diff` 看"改了还没 add 的"，`git diff --cached` 看"add 了还没 commit 的"；全新未跟踪的文件两个都不显示，得先 add。

## 01.13 重命名和删除：`git mv` 与 `git rm`

### 先给结论

你当然可以直接用 `mv` / `rm` 命令操作文件——但那样只是改了**工作区**，暂存区并不知道。`git mv` 和 `git rm` 就是"系统命令 + 自动 `git add`"的合体，帮你一步到位。

| 命令 | 等价于 | 作用 |
|---|---|---|
| `git mv 旧名 新名` | `mv 旧名 新名 && git add 新名` | 重命名 + 暂存 |
| `git rm 文件` | `rm 文件 && git add 文件` | 删除 + 暂存 |

### `git mv` 重命名

```bash
git mv a.txt b.txt
git status -s
```

```text
R  a.txt -> b.txt
```

第一列的 `R` 表示"重命名已暂存"。**如果你直接 `mv a.txt b.txt` 而不 `git add`，`git status` 会把它拆成两件事**——删除 `a.txt`（未暂存）+ 新增 `b.txt`（未跟踪）。虽然 Git 事后能用"相似度"把两者识别回"其实是重命名"，但那是 commit 之后的事，不如 `git mv` 干净。

### `git rm` 删除

```bash
git rm d.txt
```

```text
rm 'd.txt'
```

然后 `git status -s` 会显示：

```text
D  d.txt
```

第一列的 `D` 表示"删除已暂存"。这里 `rm 'd.txt'` 那行是 `git rm` 自己的回显，告诉你它删了哪个文件。

### 一个真实的报错：删一个"有暂存改动"的文件

如果你改了文件、还 `git add` 了（暂存区里有它的新快照），这时 `git rm` 会拒绝：

```bash
git rm a.txt
```

```text
error: the following file has changes staged in the index:
    a.txt
(use --cached to keep the file, or -f to force removal)
```

**触发条件**：暂存区里该文件的内容和 HEAD 不一样。Git 怕你误删了"已经准备好要提交"的改动，所以拦一下。两个解法：

- `git rm --cached a.txt`：只从暂存区移除，**保留工作区的文件**（比如你想"反悔，不再跟踪这个文件"）；
- `git rm -f a.txt`：强制连工作区一起删。

### 一个容易踩的坑：删了文件忘了 `git rm`

```bash
rm d.txt        # 只删了工作区的文件
git status -s
```

```text
 D d.txt
```

注意这里是 ` D`（D 在**第二列**）：删除发生在工作区，暂存区还留着旧快照。如果你现在 `git commit`，提交里**仍然包含 d.txt**（因为暂存区没删）。想真的把它从版本库里删掉，必须 `git rm d.txt`（或 `git add d.txt` 把"删除"这个动作也暂存）。

> 一句话记住它：`git mv` / `git rm` = 系统命令 + 自动 add；只 `mv`/`rm` 不动暂存区，删除/重命名不会进下次提交。

## 01.14 两个高频配置：换行符与命令别名

### 先给结论

有两个配置，不配也能用，但配了能省掉大量"玄学问题"和"重复敲字"：`core.autocrlf`（换行符）和 `alias`（命令别名）。

### `core.autocrlf`：Windows 上最大的"玄学坑"

Windows 和 Linux 的换行符不一样：Windows 用 `\r\n`（CRLF，两个字符），Linux/macOS 用 `\n`（LF，一个字符）。同一个仓库，如果在 Windows 和 Linux 之间来回 clone / 提交，文件末尾的换行会"自己变来变去"，于是 `git diff` 经常整片整片地报"没改也显示改了"。

Git 用 `core.autocrlf` 在"提交时"和"检出时"统一换行符：

| 取值 | 提交时（写进仓库） | 检出时（落到工作区） |
|---|---|---|
| `true` | CRLF → LF | LF → CRLF |
| `input` | CRLF → LF | 不动 |
| `false` | 不动 | 不动 |

**这个环境实测默认是 `true`**（Windows 上 Git 安装器默认帮你开的）。于是你提交一个 LF 结尾的文件时，会看到这样的警告：

```text
warning: in the working copy of 'a.txt', LF will be replaced by CRLF the next time Git touches it
```

**别慌，这不是错**，它只是在告诉你"提交时我会把它转成 LF 存仓库里，下次检出再变回 CRLF"。仓库里存的一直是 LF，你的工作区看到的一直是 CRLF，两边都爽。

**什么时候该自己配**：如果你是纯 Linux 团队（服务器、CI 都跑 Linux），建议统一成：

```bash
git config --global core.autocrlf input
```

意思是"提交时统一成 LF，检出不转"，避免 Windows 同事把 CRLF 带进仓库。

### `alias`：给常用命令起短名

`git status` 天天敲，`git log --oneline --graph --all` 敲一次手都酸。别名就是"自定义命令缩写"：

```bash
git config --global alias.st status
git config --global alias.co checkout
git config --global alias.br branch
git config --global alias.lg "log --oneline --graph --all"
```

之后：

```bash
git st    # 等价 git status
git lg    # 等价 git log --oneline --graph --all
```

**注意**：带空格和参数的别名要加引号（如 `"log --oneline --graph --all"`）。别名只是"帮你展开命令"，不会改变 Git 行为。

> 一句话记住它：`core.autocrlf` 解决 Windows/Linux 换行符打架，`alias` 把高频命令缩成短名；两个都写进 `--global` 一次性配好。

## 01.15 本章常见坑速查

| 坑 | 现象 | 原因 | 正确做法 |
|---|---|---|---|
| 在非仓库目录跑 git | `fatal: not a git repository (or any of the parent directories): .git` | 当前及所有父目录都没有 `.git` | 先 `git init`，或 `cd` 进有 `.git` 的目录 |
| 忘了配 user.name/user.email | `Author identity unknown` | commit 需要作者信息，Git 不会替你发明 | `git config --global user.name/email` |
| 改了文件直接 commit | 提交里没有刚改的内容 | `git commit` 只认暂存区，你忘了 `add` | 先 `git add` 再 `git commit` |
| add 之后又改了文件 | `git status -s` 显示 `AM` | add 拍的是那一刻的快照，之后改动还在工作区 | 再 `git add` 一次，或接受"暂存的是旧版本" |
| `git add` 拼错文件名 | `fatal: pathspec 'xxx' did not match any files` | 路径在工作区不存在 | 检查文件名/路径 |
| `git add` 被忽略的文件 | `The following paths are ignored...` | 命中了 `.gitignore` 规则 | 确实要跟踪就 `git add -f` |
| `git commit` 没带 `-m` | 打开一个奇怪的编辑器 | git 默认打开编辑器让你写说明 | 带上 `-m`；已经进去了按 Esc 再 `:wq` |
| 默认分支名和教程不一致 | `git branch` 显示 master 而教程是 main | 你的 git 全局没配 `init.defaultBranch` | 两者同角色；想统一就 `git config --global init.defaultBranch main` |
| 把 `git add .` 当成"全仓库" | 子目录里只 add 了子目录 | `.` 相对当前目录 | 要全仓库用 `git add -A` |
| 用 `cat .git/index` 想看暂存区 | 一堆乱码 | index 是二进制文件 | 用 `git ls-files --stage` 看 |
| `git diff` 看不到新文件 | 输出为空，以为没改动 | 未跟踪文件没有"旧版本"可比 | 先 `git add`，或用 `git diff --cached` 看 |
| 直接 `rm` 文件后 commit | 提交里文件还在 | 只删了工作区，暂存区没删 | 用 `git rm`，或 `git add 文件` 把删除也暂存 |
| `git rm` 被拒绝 | `error: the following file has changes staged in the index` | 暂存区有该文件的新快照 | `git rm --cached`（留文件）或 `-f`（强删） |
| Windows 提交报换行符警告 | `warning: LF will be replaced by CRLF` | `core.autocrlf=true` 自动转 | 正常现象；纯 Linux 团队可设 `core.autocrlf input` |

## 01.16 本章小结

**三棵树**

- 工作区 = 你的项目文件夹；暂存区 = `.git/index`；版本库 = `.git/objects` + `.git/refs`。
- `git status` 是它们的仪表盘：`??` 未跟踪，第一列 `M` 是暂存区，第二列 `M` 是工作区。
- 数据流动方向：工作区 `--git add-->` 暂存区 `--git commit-->` 版本库。

**git init**

- `git init` 就是建一个 `.git` 目录，不改任何文件。
- 核心四件套：`HEAD`、`config`、`objects/`、`refs/`。

**git add**

- `add` 拍的是"那一刻"的快照，之后改动不会自动跟进去（`AM` 就是证据）。
- `add .` 相对当前目录，`add -A` 全仓库。

**git commit**

- `commit` 把暂存区固化成历史快照，一次提交 = blob + tree + commit 三个对象。
- `-m` 是写给未来看的话，别写废话。

**.git 目录**

- `objects/` 用哈希前两位分片；`refs/heads/` 一个文件一个分支；`logs/` 是 reflog 的来源。
- `HEAD` 存"指向哪个分支"，分支文件才存真正的 commit 哈希。

**git diff**

- `git diff` 看工作区 vs 暂存区；`git diff --cached` 看暂存区 vs HEAD；`git diff HEAD` 看工作区 vs HEAD。
- 未跟踪的新文件不会被 `git diff` 显示，得先 add。

**git mv / git rm**

- `git mv` = `mv + add`，`git rm` = `rm + add`，一步到位。
- 只 `mv`/`rm` 不动暂存区，删除/重命名不会进下次提交。

**配置**

- 配置分 system / global / local 三级，local 最优先；`--show-origin` 查来源。
- `core.autocrlf` 解决换行符打架，`alias` 把高频命令缩成短名。

### 练习 1：走一遍三棵树

从零建一个仓库，创建一个文件，依次执行 `git status`、`git add`、`git commit`，并记录每一步 `git status -s` 的输出。说出每一步"文件在哪个区"。

```bash
mkdir demo && cd demo && git init

git add a.txt
git status -s    # A  a.txt   → 已进暂存区
git commit -m "init"
git status -s    # （无输出） → 三棵树对齐
```

### 练习 2：解释 `AM` 和 `M `

下面的操作会让 `git status -s` 显示什么？为什么？

```bash
echo "1" > a.txt
git add a.txt
echo "2" >> a.txt
git status -s
```

<details><summary>参考答案</summary>

```text
AM a.txt
```

- 第一列 `A `：暂存区里有 `a.txt` 的快照（内容 `"1"`），是 add 时拍的；
- 第二列 ` M`：工作区的 `a.txt` 比暂存区多了一行 `"2"`。

`AM` 说明这个文件"暂存区和工作区内容不一致"。

</details>

### 练习 3：判断对错，并说理由

1. `git commit` 会把工作区所有改动都提交上去。
2. `git add` 之后继续改文件，再 commit，两次改动都会进这次提交。
3. `git init` 会清空当前目录里已有的文件。
4. 暂存区就是 `.git/index` 文件。
5. `HEAD` 文件里直接存着一个 commit 的完整哈希。

<details><summary>参考答案</summary>

1. **错。** `git commit` 只认暂存区。没 add 的改动留在工作区，不进入这次提交。
2. **错。** `git add` 拍的是那一刻的快照，之后改的内容还在工作区，除非再 add 一次。
3. **错。** `git init` 只是新建 `.git` 目录，对你已有的文件什么都不做。
4. **对。** 暂存区就是 `.git/index`，一个二进制文件，可用 `git ls-files --stage` 查看。
5. **错。** `HEAD` 通常存的是 `ref: refs/heads/master`（指向分支的引用），真正的哈希在 `refs/heads/master` 里。

</details>

### 练习 4：亲手看 `.git` 里的关键文件

在一个刚 `git init` 并 commit 过一次的仓库里，分别 `cat` 下面三个文件，说出每个文件的用途：

```bash
cat .git/HEAD
cat .git/refs/heads/master
git ls-files --stage
```

<details><summary>参考答案</summary>

- `.git/HEAD`：`ref: refs/heads/master`，表示当前在 master 分支上。
- `.git/refs/heads/master`：一串哈希，master 分支指向的 commit。
- `git ls-files --stage`：暂存区的清单，每行是 `权限 哈希 阶段号 文件名`。

</details>

### 练习 5：制造一次"忘了 add"的事故

写出操作步骤，让下面这件事发生：你改了文件、执行了 `git commit`，但提交里**没有**这次改动。然后说清楚为什么。

<details><summary>参考答案</summary>

```bash
echo "旧内容" > a.txt
git add a.txt
git commit -m "第一次"

echo "新内容" > a.txt   # 改文件，但没 add
git commit -m "第二次"  # ← 提交的是暂存区里的"旧内容"
```

第二次 commit 提交的是暂存区（还停留在"旧内容"的快照），工作区的"新内容"没被 add，所以没进提交。`git status -s` 会显示 ` M a.txt`（工作区领先暂存区）。

</details>
