# 第 04 章 · 冲突

> 第 03 章你合并分支，一路顺风顺水——那是因为两边改的是不同的文件或不同的行。
> 这一章让你亲手撞上一次 `CONFLICT`，看冲突标记长什么样、为什么会有，以及三种解决方式。
>
> 读完本章，你要能回答三个问题：
> 1. 冲突是怎么产生的？为什么有时 `git merge` 自动成功，有时却甩给你一堆 `<<<<<<<`？
> 2. 冲突标记 `<<<<<<< HEAD` / `=======` / `>>>>>>> 分支名` 各代表什么？
> 3. 解决冲突有哪几种方式？什么时候用"手动改"，什么时候直接"中止"？
>
> 本章你需要记住的就一件事：**冲突不是 bug，是 Git 在说"这件事我替你做不了主，你得自己拍板"——解决它 = 手动挑出你想要的内容，然后 `git add` 告诉 Git"解决完了"。**

---

## 04.1 先给结论：冲突到底是什么

### 一个反直觉的事实

**`git merge` 大多数时候是自动成功的，不需要你干预。** 只有当两边改的是**同一个文件里的同一块地方**时，Git 才无法决定"该留哪个"，于是停下来，把决定权交给你——这就是冲突。

### 什么情况下会冲突 vs 不会

| 情况 | 会冲突吗 | 为什么 |
|---|---|---|
| 两边改**不同的文件** | 不会 | 井水不犯河水，各自合并 |
| 两边改**同一个文件的不同行** | 不会 | 行与行之间不重叠，Git 能自动拼 |
| 两边改**同一个文件的同一行** | **会** | 同一行有两个版本，Git 不知道留哪个 |
| 一边改了某行，另一边删了这行 | **会** | 删除 vs 修改，也是二选一 |

**判断的核心就是"是否重叠"**：改动区域不重叠，Git 自动合并；重叠了，就必须人来裁决。

### 一个必须先破除的恐惧

新手一看到冲突就慌，觉得"是不是我把仓库搞坏了"。**不是。** 冲突时：

- 你的仓库**没有损坏**，历史完整；
- 你的工作区文件里被插入了冲突标记，但**没丢任何东西**——两边的版本都在标记里摆着呢；
- 冲突是可以**随时中止**的（`git merge --abort`），一键回到冲突前的状态。

**冲突是一个"待办事项"，不是一个"事故"。**

> 一句话记住它：只有"两边改了同一块地方"才会冲突；冲突时仓库没坏、东西没丢，它只是在等你拍板。

## 04.2 亲手制造一次冲突

### 先给结论

用最少的命令复现一次冲突，看真实的报错原文。

### 完整步骤

```bash
mkdir conflict-demo && cd conflict-demo
git init
git config user.name t && git config user.email t@example.com

# ① 建一个 base：a.txt 里有一行
echo "版本号：1" > a.txt
git add . && git commit -m "base"

# ② 开 feature 分支，把这一行改了
git switch -c feature
echo "版本号：feature 改的" > a.txt
git add . && git commit -m "feature 改版本号"

# ③ 切回 master，也把同一行改了
git switch master
echo "版本号：master 改的" > a.txt
git add . && git commit -m "master 改版本号"

# ④ 合并，触发冲突
git merge feature
```

### 你看到的真实报错

```text
Auto-merging a.txt
CONFLICT (content): Merge conflict in a.txt
Automatic merge failed; fix conflicts and then commit the result.
```

逐行读：

1. `Auto-merging a.txt` —— Git 尝试自动合并这个文件；
2. `CONFLICT (content): Merge conflict in a.txt` —— **冲突报错原文**。`(content)` 表示这是"内容冲突"（还有别的类型的冲突，后面讲）；
3. `Automatic merge failed` —— 自动合并失败，`fix conflicts and then commit the result` 是给你的下一步指示。

**注意 exit code**：冲突时 `git merge` 以**非 0** 退出。这一点在写脚本时要记住——你不能用"命令成功与否"判断"有没有冲突"，要看输出里的 `CONFLICT` 字样。

### 冲突时的 `git status`

```bash
git status
```

```text
On branch master
You have unmerged paths.
  (fix conflicts and run "git commit")
  (use "git merge --abort" to abort the merge)

Unmerged paths:
  (use "git add <file>..." to mark resolution)
	both modified:   a.txt

no changes added to commit (use "git add" and/or "git commit -a")
```

关键词 **`unmerged paths`（未合并的路径）** 和 **`both modified`（双方都改了）**。Git 给了你两条路：

- `fix conflicts and run "git commit"` —— 解决后提交；
- `use "git merge --abort"` —— 不想合并了，中止。

> 一句话记住它：冲突报错原文是 `CONFLICT (content): Merge conflict in <文件>`，同时 `git merge` 以非 0 退出；`git status` 会显示 `both modified`。

## 04.3 冲突标记：那三行符号是什么

### 先给结论

冲突发生后，打开冲突文件，你会看到 Git 把**两个版本都写进了文件**，用三行特殊标记分隔。这三行标记是**纯文本**，你必须看懂。

```bash
cat a.txt
```

```text
<<<<<<< HEAD
版本号：master 改的
=======
版本号：feature 改的
>>>>>>> feature
```

### 三段各是什么

```text
<<<<<<< HEAD          ← 标记开始："HEAD" 这一段是【当前分支】的内容
版本号：master 改的    ← 你（当前分支）的版本
=======               ← 分界线：上面是当前分支，下面是被合并分支
版本号：feature 改的   ← 对方（被合并分支）的版本
>>>>>>> feature       ← 标记结束："feature" 是【被合并分支】的名字
```

记住口诀：**`<<<<<<<` 到 `=======` 是"你的"（HEAD/当前分支），`=======` 到 `>>>>>>>` 是"对方的"（被合并的分支）。**

### 为什么 HEAD 有时是别的样子

`<<<<<<< HEAD` 里的 `HEAD` 是"当前分支"的代号。如果你在 rebase 中遇到冲突（第 07 章），标记会不一样，可能是 `<<<<<<< 某个 commit 标题`。但原理一致：**标记上方是"正在应用的一边"，下方是"被应用的一边"**。

### 冲突标记必须全部删掉

解决冲突的核心动作，就是**把文件里的冲突标记（`<<<<<<<`、`=======`、`>>>>>>>` 三行）以及你不需要的那个版本删掉，只留下你想要的内容**。

**新手最常犯的错：删了冲突内容，却忘了删那三行标记线**，结果把 `<<<<<<< HEAD` 这种鬼东西提交进了仓库。

> 一句话记住它：`<<<<<<<` 到 `=======` 是当前分支，`=======` 到 `>>>>>>>` 是被合并分支；解决 = 挑出想要的 + 删掉三行标记。

## 04.4 三种解决方式

### 方式一：手动编辑（最常用，也最该先学会）

打开文件，删掉标记，写下一个**你真正想要的最终内容**：

```text
版本号：双方协商后的 4
```

然后：

```bash
git add a.txt        # 关键一步：告诉 Git"这个文件解决完了"
git commit           # 提交（不带 -m 会用默认的合并信息）
```

`git add` 在这里的作用**不是"暂存"，而是"标记为已解决"**。冲突文件必须先 add，Git 才认为你处理完了。

提交后：

```bash
git log --oneline --graph
```

```text
*   52d26c8 merge feature: 手动解决冲突
|\
| * 71c1574 feature 改版本号
* | 0e0f3d4 master 改版本号
|/
* 82ef030 base
```

冲突解决了，历史里留下了一个 merge commit。

### 方式二：直接选一边 —— `--ours` / `--theirs`

如果你根本不想协商，就是要"整个文件都取我的"或"整个文件都取对方的"，用：

```bash
git checkout --ours a.txt     # 整个文件取"当前分支"版本
git checkout --theirs a.txt   # 整个文件取"被合并分支"版本
git add a.txt
git commit
```

`--ours` = 我们的（HEAD/当前分支），`--theirs` = 对方的（被合并分支）。

**注意这里的语义坑**：`--ours` 和 `--theirs` 在 `merge` 和 `rebase` 里的含义**是反的**。merge 时 `--ours` 是"当前分支"；rebase 时因为"当前分支"被临时倒转，`--ours` 反而指"被 rebase 的目标分支"。第 07 章会再强调，现在先记住"merge 时 ours=当前分支"。

### 方式三：中止 —— `--abort`

如果你合并到一半发现"方向不对，不想合了"，一键回到冲突前：

```bash
git merge --abort
```

它会**撤销这次合并**，把工作区和分支都恢复到 `git merge` 之前的状态。冲突文件里的标记也会被清掉，文件回到"当前分支"的版本。

**什么时候用 `--abort`**：合并方向错了、冲突太多不想现在处理、或者只是想先看看会不会冲突。它的好处是**零风险**——反正能回到原点。

### 一张表总结三种方式

| 方式 | 命令 | 适用场景 |
|---|---|---|
| 手动编辑 | 改文件 → `git add` → `git commit` | 两边内容各取一部分，协商出最终版 |
| 选一边 | `--ours` / `--theirs` → add → commit | 整个文件只要某一方的版本 |
| 中止 | `git merge --abort` | 不想合并了，回到冲突前 |

> 一句话记住它：解决冲突三条路——手动挑（最常用）、`--ours/--theirs` 整取一边（快速）、`--abort` 退回（放弃）；解决完的标志是 `git add`。

## 04.5 冲突标记之外：`git status -s` 的冲突符号

第 01 章学过 `git status -s` 的双列缩写。冲突时，缩写会变成**你没见过的三列**：

```bash
git status -s
```

```text
UU a.txt
```

`UU` 是 `both modified`（双方都改了）的缩写。完整的冲突状态缩写还有：

| 缩写 | 含义 |
|---|---|
| `UU` | 双方都修改了（最常见的内容冲突） |
| `AA` | 双方都添加了（`git add` 了同名文件） |
| `DU` | 一边删除、一边修改 |
| `UD` | 一边修改、一边删除 |
| `DD` | 双方都删除 |

**`git ls-files --stage` 也能看到冲突**——冲突文件会有多个"阶段"：

```bash
git ls-files --stage
```

```text
100644 <哈希1> 1	a.txt   ← 阶段 1：共同祖先版本
100644 <哈希2> 2	a.txt   ← 阶段 2：当前分支版本
100644 <哈希3> 3	a.txt   ← 阶段 3：被合并分支版本
```

一个文件出现**三个阶段**，就是冲突的铁证。阶段 1 是 base，阶段 2 是 ours，阶段 3 是 theirs。等你 `git add` 解决后，这三个阶段会合并回一个（阶段 0）。

> 一句话记住它：`git status -s` 里看到 `UU`/`AA`/`DU` 这类双字母，就是冲突；`git ls-files --stage` 里一个文件有三个阶段，也是冲突的底层证据。

## 04.6 冲突不止"内容冲突"：其它几种类型

### 先给结论

第 04.2 节制造的是最常见的 **content conflict（内容冲突）**。但 Git 里还有几种**别的类型**的冲突，报错原文不一样，要能认出来。

### 类型一：修改/删除冲突（modify/delete）

**一边改了文件，另一边删了这个文件。**

```text
CONFLICT (modify/delete): a.txt deleted in feature and modified in HEAD.
```

**触发条件**：你（HEAD）改了 `a.txt`，对方（feature）删了 `a.txt`。Git 无法判断"是保留修改后的文件，还是接受删除"。

**解决**：二选一——

```bash
# 保留文件（取你的修改版）
git add a.txt

# 接受删除
git rm a.txt
```

### 类型二：添加/添加冲突（add/add）

**两边各自 `git add` 了一个同名文件，但内容不同。**

```text
CONFLICT (add/add): Merge conflict in a.txt
```

**触发条件**：feature 分支建了 `a.txt`，main 分支也建了 `a.txt`，两边内容不一样。Git 不知道留哪个。

**解决**：和内容冲突一样，打开文件删标记、留想要的版本、`git add`。

### 类型三：重命名/重命名冲突（rename/rename）

**两边都把同一个文件改名成了不同的名字。**

```text
CONFLICT (rename/rename): a.txt renamed to b.txt in HEAD and to c.txt in feature.
```

**解决**：选一个名字，`git add` 保留的那个、`git rm` 删掉另一个。

### 一张表记住所有冲突类型

| 报错里的关键词 | 冲突类型 | 含义 |
|---|---|---|
| `(content)` | 内容冲突 | 两边改了同一行的内容 |
| `(modify/delete)` | 改/删冲突 | 一边改、一边删 |
| `(add/add)` | 添加冲突 | 两边各加了一个同名文件 |
| `(rename/rename)` | 改名冲突 | 两边各改成了不同名字 |

**所有类型的解法本质都一样**：`git status` 看哪些文件冲突 → 决定留什么 → `git add`/`git rm` 标记解决 → `git commit`。

> 一句话记住它：冲突不只有 `content`，还有 `modify/delete`、`add/add`、`rename/rename`；报错关键词不同，但解法统一——决定留什么 → add/rm → commit。

## 04.7 可视化解决冲突：`git mergetool`

### 先给结论

**`git mergetool` 打开一个图形化工具**，让你在界面上左右对比两个版本、点选合并，而不是手动编辑冲突标记。

```bash
git mergetool
```

### 默认用什么工具

第一次运行会列出你系统里检测到的合并工具，让你选一个：

```text
This message is displayed because 'merge.tool' is not configured.
See 'git mergetool --tool-help' or 'git help config' for more details.
'git mergetool' will now attempt to use one of the following tools:
meld opendiff kdiff3 ...
```

常见的图形合并工具：VS Code（内置 merge editor）、Beyond Compare、Meld、kdiff3。

### 怎么配成 VS Code

```bash
git config --global merge.tool vscode
git config --global mergetool.vscode.cmd 'code --wait $MERGED'
```

之后 `git mergetool` 会用 VS Code 打开冲突文件，左侧"当前分支"、右侧"对方"、中间"合并结果"，你点几下就解决完。

### 手动 vs 图形化怎么选

| 方式 | 优点 | 缺点 |
|---|---|---|
| 手动编辑 | 不依赖工具、随时能用 | 冲突一多容易眼花 |
| `mergetool` | 直观、快、不易漏 | 要装工具、要配置 |

**建议**：先学会手动编辑（这是基础功，任何环境都能用），再在团队里配好 `mergetool` 提高效率。

> 一句话记住它：`git mergetool` 用图形界面解决冲突，比手动编辑直观；手动编辑是基本功，图形化是提效手段。

## 04.8 冲突时的"调查命令"：`git diff` 和 `git log --merge`

### 先给结论

冲突之后别急着改文件。先用两个命令**把冲突的全貌看清楚**：`git diff`（看冲突文件到底差在哪）和 `git log --merge`（看冲突涉及了哪些提交）。

### 冲突时 `git diff` 的输出不一样了

平时 `git diff` 输出的是 `diff --git`（普通两文件对比）。**冲突时，它会变成 `diff --cc`（combined diff，组合差异）**：

```bash
git diff
```

```text
diff --cc f.txt
index 71f46f2,ce3eb01..0000000
--- a/f.txt
+++ b/f.txt
@@@ -1,3 -1,3 +1,7 @@@
  line1
++<<<<<<< HEAD
 +MAIN2
++=======
+ FEAT2
++>>>>>>> feat
  line3
```

注意几个和平时不同的地方：

| 特征 | 平时 | 冲突时 |
|---|---|---|
| 开头 | `diff --git` | `diff --cc`（两个 c） |
| 位置标记 | `@@ -1 +1 @@` | `@@@ -1,3 -1,3 +1,7 @@@`（三个 @） |
| index 行 | 两个哈希 | **三个**哈希：两个父版本 + `0000000` |

`diff --cc` 的本质是"**同时拿两个父版本和合并结果对比**"，所以位置标记里有两组数字（分别对应两个父版本）。

### `git log --merge`：冲突涉及了哪些提交

```bash
git log --merge --oneline
```

```text
27a38b7 main
9c80f7c feat
```

`--merge` 只显示**参与这次冲突合并的提交**（就是两个分支上"分叉之后"的提交），忽略无关的历史。**冲突一多，先用它把范围缩小到"到底哪几个提交在打架"**，再逐个 `git show` 看它们各改了什么。

### 一个实用的排查顺序

冲突后的建议动作顺序：

```bash
git status            # ① 先看哪些文件冲突了
git diff              # ② 看冲突文件的具体差异（combined diff）
git log --merge --oneline   # ③ 看冲突涉及哪些提交
git show <某个哈希>   # ④ 必要时看某个提交当时的完整改动
```

先把这几步走完，你脑子里就有了完整的"战场地图"，再动手改文件，不会瞎蒙。

> 一句话记住它：冲突时 `git diff` 变成 `diff --cc`（组合差异），`git log --merge` 只看冲突相关的提交；先用它们看清全貌再动手。

## 04.9 三个版本都能单独读出来：`git show :N:文件`

### 先给结论

04.5 说过冲突文件在暂存区里有**三个阶段**（1=base、2=ours、3=theirs）。你不只能"看"到它们存在，还能用 `git show :N:文件` **单独读出每一个版本的完整内容**。

### 语法：`git show :阶段号:文件`

```bash
git show :1:f.txt   # 阶段 1：共同祖先（base）的版本
git show :2:f.txt   # 阶段 2：当前分支（ours）的版本
git show :3:f.txt   # 阶段 3：被合并分支（theirs）的版本
```

```text
base
```

```text
main
```

```text
feat
```

### 这有什么用

冲突文件里的标记只显示**两段**（`<<<<<<<` 到 `=======` 是 ours，`=======` 到 `>>>>>>>` 是 theirs），**看不到 base**。但很多冲突的真正难点是："两边各自基于 base 改了什么？"

用 `git show :1:f.txt` 读出 base，你就能判断：

- ours 相对 base 改了什么；
- theirs 相对 base 改了什么；
- 谁改的是"有意的"，谁改的是"误伤"。

**这是解决复杂冲突的底层能力**——标记只给你"两个结果"，三版本给你"两个结果 + 一个起点"，判断力完全不一样。

### 和 `ls-files --stage` / `ls-files -u` 的关系

```bash
git ls-files -u
```

```text
100644 df967b96a579e45a18b8251732d16804b2e56a55 1	f.txt
100644 ba2906d0666cf726c7eaadd2cd3db615dedfdf3a 2	f.txt
100644 c7747099cf9e073babc68f52cdfb4d280ba5689f 3	f.txt
```

`ls-files -u`（unmerged）列出**未合并文件**的三阶段，每行的"阶段号"（第 3 列）就是 `:N:` 里的 N。看到 `1`，你就知道这是 base，可以用 `git show :1:f.txt` 读它。

> 一句话记住它：`git show :1/:2/:3:文件` 分别读出 base/ours/theirs 三个完整版本；`ls-files -u` 列出未合并文件的三个阶段。

## 04.10 diff3 冲突样式：把"共同祖先"显示出来

### 先给结论

默认的冲突标记只显示**两边**（ours 和 theirs）。开启 **diff3 样式**后，标记里会**多出 base（共同祖先）一段**，你能直接看到"改动前长什么样"。

### 默认样式 vs diff3 样式

默认（merge 样式）长这样：

```text
<<<<<<< HEAD
MAIN2
=======
FEAT2
>>>>>>> feature
```

只有两段。开启 diff3 后：

```text
<<<<<<< ours
MAIN2
||||||| base
line2
=======
FEAT2
>>>>>>> theirs
```

多了一段 `||||||| base`（共同祖先的内容），而且标记词从 `HEAD`/分支名 变成了更明确的 `ours`/`theirs`。

### 怎么开启

```bash
git config --global merge.conflictStyle diff3
```

配置后，**以后所有新产生的冲突**都会用 diff3 样式。已经存在的冲突，可以重新生成：

```bash
git checkout --conflict=diff3 f.txt
```

```text
Recreated 1 merge conflict
```

### 为什么 diff3 更好

**核心价值：`||||||| base` 那段让你一眼看出"原来是什么"。**

举个真实场景：base 是 `line2`，ours 改成了 `MAIN2`，theirs 改成了 `FEAT2`。默认样式里你只知道"两个人都动了这一行"；diff3 样式里你还能看到"原本是 `line2`"，于是立刻能判断——**是不是有一方的改动其实是误删了原内容**。

判断"该留谁"的关键，往往不是"谁的字面值对"，而是"谁相对 base 做了正确的改动"。diff3 把这个判断所需的全部信息都摆在了眼前。

> 一句话记住它：`merge.conflictStyle diff3` 让冲突标记多出 `||||||| base` 一段，显示共同祖先；判断"谁改得对"时它比默认样式有用得多。

## 04.11 `git rerere`：让 Git 记住冲突的解法

### 先给结论

**`rerere`（reuse recorded resolution）让 Git 记住你解决过的冲突**。同一个冲突第二次出现时，Git 自动应用你上次的解法，不用再手动解决一遍。

### 一个高频场景：rebase 时反复遇到同一个冲突

想象你在一个很长的 feature 分支上 rebase（第 07 章），期间要重放几十个提交。如果主线改了某个文件，你这个分支也改了同一个文件，那么**每一个提交重放时都可能触发同一个冲突**。

不开 rerere，你要手动解决几十次一模一样的冲突，痛不欲生。开了 rerere，**第一次解决后，后面几十次自动解决**。

### 怎么开启

```bash
git config --global rerere.enabled true
```

一句话就开好了。之后它的工作方式：

1. 遇到冲突，Git 会记录"冲突前的状态"；
2. 你手动解决并 `git commit`，Git 记录"解决后的状态"；
3. 之后遇到**完全相同的冲突**（base、ours、theirs 组合一致），Git 自动应用上次的解法，并在输出里提示：

```text
Resolved 'f.txt' using previous resolution.
```

### 几个管理命令

```bash
git rerere status    # 看当前记录了哪些冲突的解法
git rerere diff      # 看某个冲突的解法具体是什么
git rerere forget f.txt   # 忘掉某个文件的解法（下次重新手动解决）
```

### rerere 的代价与边界

- **它只对"完全相同的冲突"生效**。base/ours/theirs 只要有一个字节不一样，就是"新冲突"，不会误用旧解法；
- 它记录的是**结果**，不是"意图"。如果上次你选错了版本，下次它会"忠实地"重复这个错误——所以 `rerere forget` 是留给"记错了"时的后悔药。

> 一句话记住它：`rerere.enabled true` 让 Git 记住冲突解法，rebase 长分支时能救你几十次重复劳动；记错了用 `rerere forget` 清除。

## 04.12 一个多文件冲突的完整实战演练

### 先给结论

前面都是"一个文件冲突"的例子。真实项目里，一次 merge 经常**同时撞上好几个文件的冲突**。这一节用一个两文件冲突的例子，把"调查 → 逐个解决 → 提交"的完整流程走一遍。

### 制造：两个文件同时冲突

```bash
# 假设已有 base 提交，a.txt 和 b.txt 各有一行
git switch -c feat
echo "a-feat" > a.txt
echo "b-feat" > b.txt
git add . && git commit -m "feat: 改 a 和 b"

git switch main
echo "a-main" > a.txt
echo "b-main" > b.txt
git add . && git commit -m "main: 也改 a 和 b"

git merge feat
```

```text
Auto-merging a.txt
CONFLICT (content): Merge conflict in a.txt
Auto-merging b.txt
CONFLICT (content): Merge conflict in b.txt
Automatic merge failed; fix conflicts and then commit the result.
```

注意：**每个冲突文件都会单独报一行 `CONFLICT`**，最后才是一句总括的 `Automatic merge failed`。看第一眼就要数清"到底几个文件冲突了"。

```bash
git status -s
```

```text
UU a.txt
UU b.txt
```

两个 `UU`，两个文件都要解决。

### 逐个解决

**关键原则：一次只处理一个文件，解决完立刻 `git add`。** 不要把所有文件都改完才想起来 add——万一中途想 `--abort` 就来不及了。

```bash
# 解决 a.txt：假设协商后取 feature 的版本
vim a.txt              # 删标记，留下 "a-feat"
git add a.txt

# 解决 b.txt：假设这次取 main 的版本
vim b.txt              # 删标记，留下 "b-main"
git add b.txt
```

解决完再确认一次：

```bash
git status -s
```

```text
M  a.txt
M  b.txt
```

注意 `UU` 变成了 `M `（第一列，已暂存）——**这就是"冲突已解决"的信号**。如果还有文件是 `UU`，说明还没处理完。

### 提交完成合并

```bash
git commit -m "merge feat: 解决 a.txt 和 b.txt 的冲突"
```

提交完成，这次合并才算真正结束。全程没有魔法，就是"看报错 → 数清冲突文件 → 逐个解决并 add → 提交"。

### 流程图

```text
git merge feat
   │
   ├─ 报错：CONFLICT (content): Merge conflict in xxx（可能多行）
   │
   ├─ git status -s  → 找出所有 UU/AA/DU 文件
   │
   ├─ 对每个冲突文件：打开 → 删标记留内容 → git add
   │
   ├─ 确认 status -s 里没有 UU 了
   │
   └─ git commit -m "merge: ..."
```

> 一句话记住它：多文件冲突就是"单文件冲突的循环"——每个冲突文件一行 `CONFLICT`，逐个"解决 → add"，全部 `UU` 消失后再 commit。

## 04.13 解决冲突的判断心法：什么时候取谁的

### 先给结论

解决冲突最难的**不是删标记**（那是体力活），而是**决定留谁**（这是判断力）。这一节给你一套可复用的决策清单。

### 五种典型情况与建议

| 情况 | 建议 | 理由 |
|---|---|---|
| 对方的改动是**修 bug**，你的只是顺手的格式调整 | 取对方 | bug 修复优先级高于格式 |
| 你的改动是**新功能核心逻辑**，对方是误改 | 取自己 | 别把误伤合并进来 |
| 两边改的是**不同关注点**（你改逻辑、他改注释） | 两边都留 | 手动拼出"逻辑 + 注释"的最终版 |
| 两边改的**语义冲突**（一个加锁、一个删锁） | 停下来协商 | 这种冲突不是文本能裁的，得当面说清 |
| 你**不确定**该留谁 | 先 `--abort`，搞清楚再来 | 带着疑问合并，等于埋雷 |

### 判断的核心依据：base 说了算

**永远先问一句："base（共同祖先）长什么样？"** 然后看两边各自相对 base 做了什么：

```bash
git show :1:文件    # base 版本
git show :2:文件    # ours 版本
git show :3:文件    # theirs 版本
```

- 如果 ours 相对 base **没变**（ours == base），说明"改动全来自对方"——大概率直接取 theirs 就对；
- 如果 theirs 相对 base **没变**，说明"改动全来自你"——取 ours；
- 如果两边都变了，才需要认真判断。

**很多冲突根本不用纠结**，就是因为其中一边其实"没真改"，只是 base 的搬运。看清 base，一半以上的冲突秒解。

### 一个必须警惕的信号：语义冲突

文本冲突好办（删删选选）。真正危险的是**语义冲突**——文本上没冲突，但逻辑上打架了：

```text
# 你删了这个函数
function validate() { ... }   ← 你删了

# 对方在另一个文件里调用了它
validate(input)               ← 对方在调用
```

Git **检测不到**这种冲突（因为不在同一行），合并能成功，但程序一跑就崩。**这就是为什么合并后必须跑测试**——测试是语义冲突的最后一道防线。这个点第 09 章会再次强调。

### 一条黄金原则

**冲突的解决结果，必须是你"想清楚"的，不是"随手选"的。** 如果某次合并你连续三次都"整取对方版本"，就该停下来想想：是不是你对自己的改动理解不够，或者和同事的沟通出了问题。

> 一句话记住它：判断冲突先看 base（`git show :1:文件`），一边没真改就直接取另一边；真正的危险是测试才能发现的语义冲突。

## 04.14 本章常见坑速查

| 坑 | 现象 | 原因 | 正确做法 |
|---|---|---|---|
| 忘了删冲突标记 | 提交里出现 `<<<<<<< HEAD` | 只删了内容没删标记线 | 解决时把三行标记一起删干净 |
| 解决完不 `git add` | `git commit` 说"未解决" | add 才是"标记已解决"的信号 | 解决后必须 `git add` |
| 分不清 ours/theirs | 选错了版本 | merge 里 ours=当前分支，rebase 里反过来 | merge：ours=我，theirs=对方 |
| 一冲突就 panic | 以为仓库坏了 | 冲突只是待办，不是事故 | 用 `--abort` 随时能退回 |
| 冲突时用 `git status` 不会读 | 看不懂 `both modified` | 不认识 unmerged paths | 记住 `UU`、`both modified`、`unmerged paths` |
| 想放弃合并却手动回滚 | 操作一堆还出错 | 有现成的 `--abort` | 直接 `git merge --abort` |
| 用退出码判断冲突 | 脚本逻辑写错 | merge 冲突时非 0 退出 | 判断输出里有没有 `CONFLICT` |
| 解决冲突后提交信息是默认的 | 历史里一堆 `Merge branch` | 没写清楚合并意图 | 带 `-m "merge: 说明"` |
| 看不懂冲突时的 `git diff` | 看到 `diff --cc` 和 `@@@` 发懵 | 冲突时是 combined diff | `diff --cc` 是"两父版本 vs 结果"，正常现象 |
| 解决冲突只能靠"两边二选一" | 纠结留谁的版本 | 看不到 base（共同祖先） | 开 `merge.conflictStyle diff3`，或 `git show :1:文件` |
| rebase 反复遇到同一冲突 | 手动解决几十次 | 没开 rerere | `git config --global rerere.enabled true` |
| 合并成功但程序一跑就崩 | 文本没冲突，逻辑打架了 | 语义冲突，Git 检测不到 | 合并后必须跑测试，测试兜底 |
| 多文件冲突手忙脚乱 | 一起改完才想起 add | 没按"解决一个 add 一个" | 逐个文件解决 → add，`UU` 全消失再 commit |

## 04.15 本章小结

**冲突的本质**

- 冲突 = 两边改了同一块地方，Git 无法自动裁决，停下来交给你。
- 冲突不是 bug，仓库没坏，内容没丢，可随时 `--abort` 退回。

**制造与识别**

- 报错原文：`CONFLICT (content): Merge conflict in <文件>` + `Automatic merge failed`。
- `git status` 显示 `unmerged paths` / `both modified`；`status -s` 是 `UU`。

**冲突标记**

- `<<<<<<< HEAD`（当前分支）→ `=======` → `>>>>>>> 分支名`（对方）。
- 解决 = 挑出想要的 + 删掉三行标记线。

**三种解法**

- 手动编辑 → `git add` → `git commit`。
- `--ours` / `--theirs` 整取一边。
- `--abort` 中止。

**底层**

- 冲突文件在 `ls-files --stage` 里有三个阶段：1=base、2=ours、3=theirs。

**调查与进阶**

- 冲突时 `git diff` 变 `diff --cc`（组合差异），`git log --merge` 只看冲突相关提交。
- `git show :1/:2/:3:文件` 单独读出 base/ours/theirs 三个版本。
- `merge.conflictStyle diff3` 让标记多出 `||||||| base` 段；`rerere` 让 Git 记住解法、rebase 时省重复劳动。

**实战与心法**

- 多文件冲突 = 单文件冲突的循环：每个文件一行 `CONFLICT`，逐个"解决 → add"，`UU` 消失后 commit。
- 判断留谁先看 base：一边没真改（`ours == base`）就直接取另一边；语义冲突要靠测试兜底。


### 练习 2：读懂冲突标记

假设合并冲突后文件内容如下，说出"当前分支"的版本和"被合并分支"的版本分别是什么？

```text
<<<<<<< HEAD
const port = 3000;
=======
const port = 8080;
>>>>>>> feature
```

<details><summary>参考答案</summary>

- 当前分支（HEAD）的版本：`const port = 3000;`
- 被合并分支（feature）的版本：`const port = 8080;`

解决时删掉三行标记，留下你想要的最终值（比如 `const port = 8080;`）。

</details>

### 练习 3：判断对错

1. 只要两个分支都改了文件，merge 就一定会冲突。
2. 冲突时，工作区的文件里会丢失其中一方的改动。
3. `git add` 解决冲突后，必须用 `git commit` 完成合并。
4. `git merge --abort` 会让历史里多出一个"中止"的 commit。
5. `--ours` 在 merge 中表示"被合并分支"的版本。

<details><summary>参考答案</summary>

1. **错。** 只有"两边改了同一文件的同一块地方"才冲突；改不同文件、不同行都能自动合并。
2. **错。** 两边版本都完整保留在冲突标记里，什么都没丢。
3. **对。** add 只是"标记已解决"，还需要 commit 才完成合并。
4. **错。** `--abort` 撤销合并，回到冲突前，不产生任何新 commit。
5. **错。** merge 中 `--ours` 是"当前分支"（HEAD），`--theirs` 才是被合并分支。

</details>

### 练习 4：三种解法分别怎么写

冲突后，分别写出"手动解决""整取对方版本""放弃合并"三种操作的命令序列。
