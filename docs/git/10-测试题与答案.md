## 第一关 · 概念快问快答（20 题）

判断下面每句话是**对**还是**错**。不要猜，想清楚理由。

1. 工作区、暂存区、版本库是三个物理上真实存在的存储位置。
2. `git add` 会把文件的当前内容拍一张快照放进暂存区。
3. `git commit` 会把工作区里所有改动（包括没 `add` 的）一起提交。
4. 暂存区的物理实体就是 `.git/index` 文件。
5. `HEAD` 文件里直接存着一个 commit 的完整 40 位哈希。
6. 分支是一个指向某个 commit 的指针（一个写着哈希的小文件）。
7. 删除一个分支，会同时删除它上面独有的 commit。
8. commit 对象里保存着这次提交的 diff（改动清单）。
9. 一个 merge 提交可以有两个 parent。
10. 快进合并（fast-forward）会生成一个新的 merge commit。
11. 冲突时，Git 会丢弃其中一方的改动。
12. `git merge --abort` 可以撤销一次已经触发了冲突的合并。
13. `git reset --hard` 会把工作区里未提交的改动一并抹掉。
14. `git revert` 会改写历史。
15. `git reflog` 记录的是 HEAD 的移动轨迹。
16. `origin` 是 Git 的特殊关键字，不能改成别的名字。
17. `git fetch` 会把远程的改动合并进你的本地分支。
18. `origin/master` 是远程 master 分支在你本地的一份快照。
19. `git rebase` 会重写提交（导致哈希变化）。
20. 可以对一个已经推送到公共仓库的分支安全地执行 rebase。

## 第三关 · 改错（10 题）

每题给你一段**能跑出问题**的命令或操作。先别看修正，自己找。

### 3.1 改了文件直接 commit，改动没进去

**问题操作：**

```bash
echo "新内容" > a.txt
git commit -m "update a.txt"
```

**症状：** 提交成功了，但 `git show HEAD` 里没有"新内容"。

**为什么：** `git commit` 只认暂存区。你没 `git add`，改动还留在工作区。

**修正：**

```bash
echo "新内容" > a.txt
git add a.txt
git commit -m "update a.txt"
```

### 3.2 用 `git branch` 创建分支后还在原分支提交

**问题操作：**

```bash
git branch feature
# 继续改文件、提交……结果全提交到 master 上了
```

**症状：** 以为在 feature 上开发，实际提交都在 master 上。

**为什么：** `git branch feature` 只创建不切换。要"创建并切换"。

**修正：**

```bash
git switch -c feature
```

### 3.3 合并时冲突了，但把冲突标记提交了进去

**问题操作：**

```bash
git merge feature
# 出现冲突，打开文件，只删了"对方的内容"，忘了删标记线
git add a.txt
git commit -m "merge"
```

**症状：** 提交后的文件里还残留 `<<<<<<< HEAD` 和 `=======`。

**为什么：** 解决冲突要**连同三行标记一起删干净**，只留最终内容。

**修正：**

```text
# 文件里只能留最终内容，比如：
最终的一行内容
```

然后 `git add a.txt && git commit -m "merge: 解决冲突"`。

### 3.4 已推送的提交用 reset 撤销

**问题操作：**

```bash
git push origin main
git reset --hard HEAD~1
git push --force
```

**症状：** 同事 pull 时历史乱了，甚至丢提交。

**为什么：** 已推送的提交属于共享历史，`reset` 会改写它，`--force` 会覆盖远程。

**修正：**

```bash
git revert HEAD
git push
```

### 3.5 在非仓库目录跑 git

**问题操作：**

```bash
cd ~
git status
```

**症状：**

```text
fatal: not a git repository (or any of the parent directories): .git
```

**为什么：** 当前及所有父目录都没有 `.git`。

**修正：** 先 `cd` 进有 `.git` 的目录，或 `git init` 新建仓库。

### 3.6 `git add` 一个不存在的文件

**问题操作：**

```bash
git add readme.md
```

**症状：**

```text
fatal: pathspec 'readme.md' did not match any files
```

**为什么：** 文件名拼错（真实文件是 `README.md`），路径不存在。

**修正：**

```bash
git add README.md
```

### 3.7 想取消 add 却丢了改动

**问题操作：**

```bash
git add a.txt
# 想撤销 add，结果用了：
git restore a.txt
```

**症状：** `a.txt` 的工作区改动也没了。

**为什么：** `restore <file>` 丢的是"工作区改动"；想"取消 add、保留改动"应该用 `--staged`。

**修正：**

```bash
git restore --staged a.txt   # 取消 add，改动回到工作区
```

### 3.8 checkout 远程分支

**问题操作：**

```bash
git switch origin/master
```

**症状：**

```text
fatal: a branch is expected, got remote branch 'origin/master'
```

**为什么：** 远程分支是"影子"，不能直接切换。

**修正：**

```bash
git switch -c local-master origin/master
```

### 3.9 pull 时分支分叉报错

**问题操作：**

```bash
git pull
```

**症状：**

```text
fatal: Need to specify how to reconcile divergent branches.
```

**为什么：** 本地和远程都各有新提交（分叉），Git 不知道用 merge 还是 rebase。

**修正：**

```bash
git config pull.rebase false   # 用 merge 策略
git pull
```

### 3.10 已跟踪文件加了 .gitignore 也没用

**问题操作：**

```bash
echo "secret.key" >> .gitignore
git status
# secret.key 还在被跟踪、还显示改动
```

**症状：** 忽略规则对 `secret.key` 无效。

**为什么：** `.gitignore` 只对"未跟踪"文件生效，`secret.key` 已经进版本库了。

**修正：**

```bash
git rm --cached secret.key     # 从版本库移除，保留本地文件
git commit -m "chore: 停止跟踪 secret.key"
```

## 第三关答案

自测时可盖住上面的修正，先用下面这张表对答案。

| # | 症状 | 根因 | 改法 |
|---|---|---|---|
| 1 | commit 后改动没进去 | 忘了 `git add` | 先 `git add` 再 `git commit` |
| 2 | 提交跑到 master 上 | `git branch` 只创建不切换 | 用 `git switch -c feature` |
| 3 | 冲突标记被提交 | 只删内容没删标记线 | 连 `<<<<<<<`/`=======`/`>>>>>>>` 一起删 |
| 4 | 同事历史混乱 | 已推送提交被 reset 改写 | 用 `git revert` 撤销 |
| 5 | `fatal: not a git repository` | 不在仓库目录 | cd 进仓库或 `git init` |
| 6 | `fatal: pathspec did not match` | 文件名拼错 | 检查文件路径/名字 |
| 7 | 改动一起丢了 | `restore` 丢工作区改动 | 取消 add 用 `restore --staged` |
| 8 | `fatal: a branch is expected` | 想直接切远程分支 | 基于它建本地分支 |
| 9 | `fatal: Need to specify how to reconcile` | 分支分叉未配策略 | `git config pull.rebase false` |
| 10 | 忽略规则无效 | 文件已跟踪 | `git rm --cached` 踢出版本库 |

**一句话总结这 10 个坑：** 前 3 个是"三棵树"没吃透，中间 4 个是"撤销/远程"没吃透，最后 3 个是"工程化细节"没记住。

### 第 1 题

**Q：用一句话说清 Git 的核心心智模型。**

**A：** Git 不是保存你的文件，是保存一个**内容寻址的对象数据库**——文件内容、目录结构、提交历史都是对象，靠 SHA-1 哈希串成一张网；commit 存的是"整个项目的快照"，不是"差异"。

> **面试官想听到的要点：** 提到"快照不是差异""内容寻址"，能顺口说出 blob/tree/commit 三种对象。

### 第 2 题

**Q：工作区、暂存区、版本库是什么？为什么要夹一个暂存区？**

**A：** 工作区是你正在改的文件，暂存区（`.git/index`）是你挑选出来准备提交的内容，版本库是 commit 之后的历史。暂存区的意义是**让你精确控制"这次提交什么"**——你可以把混乱的工作区整理成语义清晰的提交。

> **面试官想听到的要点：** 说清三棵树，并讲出暂存区的价值是"精确控制提交内容"，而不是"多此一举"。

### 第 3 题

**Q：`git add` 和 `git commit` 的区别？**

**A：** `add` 把文件当前内容拍快照进暂存区，`commit` 把暂存区固化成历史里的一个快照节点。**`commit` 只认暂存区，不认工作区**——没 add 的改动不会进提交。

> **面试官想听到的要点：** 说清"add 拍快照、commit 固化"，并能指出"改了文件忘了 add 直接 commit 会提交旧内容"。

### 第 4 题

**Q：一个 commit 对象里存了什么？**

**A：** 五样东西：`tree`（指向目录树的哈希）、`parent`（指向父 commit）、`author`（作者）、`committer`（提交者）、提交说明。**没有 diff**。

> **面试官想听到的要点：** 说出"没有 diff，存的是快照 + 父指针"，能区分 author 和 committer 是加分项。

### 第 5 题

**Q：分支是什么？为什么 Git 的分支特别便宜？**

**A：** 分支只是一个指向某个 commit 的指针（`.git/refs/heads/` 下的一个哈希文件）。创建分支就是写一行字，耗时几乎为零，所以"为每个想法开一个分支"是划算的。

> **面试官想听到的要点：** 说出"分支 = 指针/纸条"，而不是"代码拷贝"。

### 第 6 题

**Q：HEAD 是什么？和"当前分支"什么关系？**

**A：** HEAD 是"你站在哪"的指针，通常指向某个分支（`ref: refs/heads/xxx`），分支再指向 commit。两跳设计的代价几乎为零，让切分支和提交都只是改一个小文件。

> **面试官想听到的要点：** 说出"HEAD → 分支 → commit"的两跳结构，知道 detached HEAD 是 HEAD 直接指向 commit。

### 第 7 题

**Q：快进合并和三方合并有什么区别？**

**A：** 快进合并是"当前分支在分叉后没动"，直接把指针平移，不产生新 commit；三方合并是"两边都动了"，以共同祖先为基准合成一个有两个 parent 的 merge commit。

> **面试官想听到的要点：** 能说出判断依据（"分叉后当前分支动没动"），以及三方合并的"三方"是 base/ours/theirs。

### 第 8 题

**Q：冲突是怎么产生的？怎么解决？**

**A：** 只有"两边改了同一个文件的同一块地方"才会冲突——Git 无法自动裁决，把两个版本都写进文件、用 `<<<<<<<`/`=======`/`>>>>>>>` 标记，交给你拍板。解决方式：手动编辑后 `git add`、`--ours/--theirs` 整取一边、或 `--abort` 中止。

> **面试官想听到的要点：** 说清"冲突不是 bug，是 Git 在等你裁决"，并知道 `add` 是"标记已解决"的信号。

### 第 9 题

**Q：`git reset --soft / --mixed / --hard` 的区别？**

**A：** `--soft` 只挪 HEAD；`--mixed`（默认）挪 HEAD + 清空暂存区；`--hard` 连工作区一起覆盖。`--hard` 会抹掉所有未提交改动，最危险。

> **面试官想听到的要点：** 精确说出三者"动哪几棵树"，并能指出 `--hard` 的风险。

### 第 10 题

**Q：`git revert` 和 `git reset` 的区别？什么时候用哪个？**

**A：** `revert` 追加一个"反向提交"，不改历史，适合**已推送**的提交；`reset` 把历史往后挪，改写历史，适合**未推送**的提交。已推送的用 reset 会坑到同事。

> **面试官想听到的要点：** 抓住"是否改写历史"和"是否已推送"这两条判断标准。

### 第 11 题

**Q：`git reflog` 是干什么的？**

**A：** 记录 HEAD 的每次移动（commit/reset/rebase/checkout），是"后悔药的后悔药"——即使 `reset --hard` 把提交"弄丢"，也能在 reflog 里找到哈希找回。默认保留 90 天。

> **面试官想听到的要点：** 区分 `log`（项目历史）和 `reflog`（操作历史），知道它能找回被 reset 的提交。

### 第 12 题

**Q：`git fetch` 和 `git pull` 的区别？**

**A：** `fetch` 只下载远程最新、更新 `origin/master` 影子，不碰工作区；`pull` = fetch + merge，下载并合并进本地分支。"先 fetch 再 merge"更可控，因为能先看清远程改了什么。

> **面试官想听到的要点：** 说清"fetch 只更新影子"，并知道 `origin/master` 是远程的本地快照。

### 第 13 题

**Q：push 被 rejected 是什么意思？怎么办？**

**A：** `! [rejected] ... (fetch first)` 表示远程有你本地没有的提交（远程领先）。先 `git pull` 合并远程改动，再 push。**别用 `--force` 硬推**，会覆盖同事的提交。

> **面试官想听到的要点：** 知道被拒是"远程领先"而不是"提交有问题"，并拒绝 `--force`。

### 第 14 题

**Q：rebase 和 merge 的区别？rebase 有什么风险？**

**A：** merge 保留分叉历史、生成 merge commit、不改写；rebase 把提交重放到目标顶端、历史变直线、**改写 commit（哈希变）**。风险是：改写共享历史会坑到已经 pull 过的人，所以**公共分支只能用 merge，rebase 只用于未推送的私有分支**。

> **面试官想听到的要点：** 说出"rebase 会重写哈希"，并讲清"绝不 rebase 公共分支"这条黄金法则。

### 第 15 题

**Q：cherry-pick 和 merge 的区别？**

**A：** `cherry-pick` 只挑**一个**提交的改动复制到当前分支，生成新提交但保留原 author；`merge` 整合**整条**分支的所有提交。

> **面试官想听到的要点：** 说清"单提交 vs 整条分支"，知道 cherry-pick 保留原 author。

## 第五关 · 项目实战（5 题）
