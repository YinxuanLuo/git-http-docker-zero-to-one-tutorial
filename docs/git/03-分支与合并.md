# 第 03 章 · 分支与合并

> 第 00 章埋过一个钩子：**"分支太便宜了，所以你应该为每一个想法开一个分支。"**
> 这一章把这个钩子收回来——讲清楚分支到底是什么、HEAD 又是什么、以及两种合并（快进 vs 三方）的本质区别。
>
> 读完本章，你要能回答三个问题：
> 1. 分支是一个"复制出来的目录"吗？如果不是，它到底是什么？
> 2. HEAD 和"当前分支"是什么关系？切分支的时候到底发生了什么？
> 3. `git merge` 有时打印 `Fast-forward`，有时生成一个新的 merge commit，为什么？
>
> 本章你需要记住的就一件事：**分支只是一个指向某个 commit 的指针（一张写着哈希的小纸条），HEAD 是"你现在站在哪"的指针；合并的本质，是让指针指向合适的位置或生成一个新节点。**

---

## 03.1 HEAD：你现在站在哪

### 先给结论

**HEAD 是一个指针，指向你"当前所在"的位置。** 绝大多数时候，它指向的是"某个分支"；极少数时候（第 05 章会讲），它直接指向某个 commit（叫 detached HEAD，游离状态）。

第 01 章已经看过它的真实内容：

```bash
cat .git/HEAD
```

```text
ref: refs/heads/master
```

这一行的意思是：**HEAD 不直接存 commit 哈希，它存的是"我指向 refs/heads/master 这个分支"**。真正的哈希在分支文件里：

```bash
cat .git/refs/heads/master
```

```text
16344d6e30022e0a9c1115853846cd87437d4562
```

### 为什么设计成"两跳"

你可能会问：为什么 HEAD 不直接存哈希，非要"HEAD → 分支 → commit"两跳？

**答案：因为这样"切分支"就只是一次文件内容的修改，代价几乎为零。**

想象 HEAD 直接存哈希，那么：

- 你在 `master` 上提交了一个新 commit，HEAD 得更新成新哈希；
- 切到 `feature` 分支，HEAD 又得改；
- 切回 `master`，HEAD 又得改回。

而"两跳"设计让事情变成：**HEAD 始终指向"分支名"，分支名指向 commit**。你 commit 时，Git 更新的是"分支文件里的哈希"（`refs/heads/master`），HEAD 文件根本不用动。

### 一个真实的比喻

把整个仓库想成一个"路牌系统"：

```text
HEAD        = 你这个人现在站在哪条路上
分支（refs/heads/master） = 路尽头的一个路标，写着"这条路的最新提交是 xxx"
commit      = 路上一块一块的里程碑
```

你 `git commit`，就是在这条路的尽头再放一块新里程碑，然后把路标往前挪一格。你 `git switch`，就是"换到另一条路去站"。

> 一句话记住它：HEAD 是"我站在哪"，分支是"这条路的最新提交在哪"，两者靠 `ref: refs/heads/xxx` 这一行文字连起来。

## 03.2 分支：一张写着哈希的小纸条

### 先给结论

**分支不是"复制一份代码"，它是一个指向某个 commit 的指针。** 在磁盘上，就是一个文件，内容是一行哈希。

```bash
ls .git/refs/heads/
cat .git/refs/heads/master
```

```text
master
16344d6e30022e0a9c1115853846cd87437d4562
```

一个分支 = `.git/refs/heads/` 下的一个文件 = 里面一行哈希。**就这么多。**

### 这个设计带来的三个推论

**推论一：创建分支是瞬间的事。**

`git branch feature` 就是往 `refs/heads/` 里写一个文件，耗时微秒级。这就是第 00 章说的"分支便宜到像不要钱"。

**推论二：分支可以被删除，但 commit 还在。**

你删一个分支，只是删掉那张"纸条"，commit 本身在 `.git/objects/` 里一动不动（除非它成了"不可达对象"被 GC 回收，第 05 章 reflog 会讲）。

**推论三：多个分支可以指向同一个 commit。**

刚 `git branch feature` 完（还没提交新东西），`master` 和 `feature` 指向的是**同一个** commit。这不是 bug，是常态。

> 一句话记住它：分支 = `refs/heads/` 里的一个哈希文件；建分支是写一行字，删分支是删一行字，commit 本体从不因此丢失。

## 03.3 `git branch`：创建、列出、删除

### 先给结论

`git branch` 有三种核心用法：不带参数是"列出"，加名字是"创建"，加 `-d` 是"删除"。

### 列出所有分支

```bash
git branch
```

```text
* master
```

`*` 表示**当前所在的分支**（也就是 HEAD 指向的那个）。想看分支指向的 commit，加 `-v`：

```bash
git branch -v
```

```text
* master 16344d6 first commit
```

### 创建分支

```bash
git branch feature
```

**注意：`git branch feature` 只是"创建"，不会切过去。** 你现在还在 `master` 上。创建后 `master` 和 `feature` 都指向同一个 commit。

### 创建并切换（更常用）

```bash
git switch -c feature      # 现代写法（推荐）
# 等价于老的：
git checkout -b feature    # 老写法
```

`-c`（create）或 `-b`（branch）表示"创建并切换过去"。日常开发 99% 用的是这种。

### 删除分支

```bash
git branch -d feature      # 安全删除：只删"已经合并过"的分支
git branch -D feature      # 强制删除：就算没合并也删
```

`-d` 和 `-D` 的区别很重要：

```bash
git branch -d 一个没合并的分支
```

```text
error: The branch 'xxx' is not fully merged.
If you are sure you want to delete it, run 'git branch -D xxx'.
```

**触发条件**：这个分支上有"别的分支还没有"的提交。Git 怕你误删导致这些提交"悬空"，所以拦你一下。`-D` 就是"我确定，删"。

> 一句话记住它：`git branch` 列出（`*` 是当前）、加名字创建、`-d` 安全删除、`-D` 强制删除；创建不会自动切过去。

## 03.4 `git switch` / `git checkout`：切换分支

### 先给结论

切分支 = 把 HEAD 指向新分支 + 把工作区和暂存区的内容**换成**那个分支对应的快照。**切换会真实地改你工作区的文件。**

```bash
git switch feature     # 现代写法（推荐）
git checkout feature   # 老写法（仍能用）
```

### 切过去时，磁盘上发生了什么

假设两个分支的 `a.txt` 内容不同：

```text
master 分支：a.txt 内容是 "master 版本"
feature 分支：a.txt 内容是 "feature 版本"
```

你 `git switch feature`，Git 会把工作区的 `a.txt` **真的替换成** "feature 版本"。这就是为什么切分支前最好先提交或 stash（第 08 章）——否则没提交的改动可能被带过去或冲突。

### `switch` 和 `checkout` 的区别

这是 Git 2.23 起的一个改进。历史包袱在于：`git checkout` 一个人干了**两件不相干的事**：

1. 切换分支（`git checkout feature`）；
2. 丢弃工作区改动（`git checkout -- file`，第 05 章讲）。

一个人干两件事，就导致新手混乱："`checkout` 到底是切分支还是丢文件？"。于是 Git 把功能拆开了：

| 命令 | 专职干什么 | 取代了 |
|---|---|---|
| `git switch` | 只切换分支 | `git checkout <branch>` |
| `git restore` | 只恢复文件/丢弃改动 | `git checkout -- <file>` |

**结论：新代码一律用 `switch`（切分支）和 `restore`（丢改动），`checkout` 作为老命令依然兼容，但新写代码别用了。**

### 一个真实的报错：切到不存在的分支

```bash
git switch nope
```

```text
fatal: invalid reference: nope
```

**触发条件**：分支名拼错或不存在。想看有哪些分支，先 `git branch`。

> 一句话记住它：切分支会真实替换工作区文件；`switch` 专职切分支、`restore` 专职恢复文件，别再混用 `checkout` 了。

## 03.5 `git merge`：合并的两种结局

### 先给结论

`git merge` 把另一个分支的提交**并进当前分支**。结局只有两种：

1. **快进合并（Fast-forward）**：当前分支在分叉点之后**没动过**，Git 直接把指针往前挪，不产生新 commit。
2. **三方合并（3-way merge）**：两边在分叉点之后**都动了**，Git 生成一个全新的 merge commit，有两个 parent。

用图表达：

```text
快进合并（fast-forward）：
        feature
  C1 ── C2 ── C3
  master（没动） ──→ 直接把 master 挪到 C3

三方合并（3-way merge）：
        C2 ── C3（feature）
       /
  C1 ── C4（master）
  两边都动了 → 生成 M，M 的 parent 是 C3 和 C4
```

### 怎么判断自己会遇到哪种

判断依据只有一条：**分叉之后，当前分支有没有新的提交？**

- 当前分支**没有**新提交 → 快进；
- 当前分支**有**新提交 → 三方合并。

> 一句话记住它：merge 只有两种结局——快进（一方没动）和三方（两边都动）；判断就看"分叉后当前分支动没动"。

## 03.6 快进合并：指针平移

### 先给结论

快进合并是**最简单也最理想**的合并：没有冲突、没有新节点，只是指针平移。

### 亲手走一遍

```bash
git init
echo v1 > a.txt && git add . && git commit -m "C1"

git switch -c feature
echo v2 >> a.txt && git add . && git commit -m "C2"

git switch master
git merge feature
```

```text
Updating 9687769..1d9e461
Fast-forward
 a.txt | 1 +
 1 file changed, 1 insertion(+)
```

`Fast-forward` 这个词就是信号。它告诉你：**master 直接挪到了 feature 的位置，历史依然是一条直线**，没有分叉。

合并后两个分支指向同一个 commit：

```bash
git rev-parse master feature
```

```text
1d9e461f965ebe64d5ea4f49f98e1d8b3fdd1986
1d9e461f965ebe64d5ea4f49f98e1d8b3fdd1986
```

### 快进合并的好处和"坏处"

**好处**：历史干净，一条直线，没有多余的 merge commit。

**坏处**（对某些团队来说是）：你看不出"这里曾经有个 feature 分支被合并了"。有些人更喜欢保留合并痕迹，会用 `--no-ff` 强制生成 merge commit：

```bash
git merge --no-ff feature
```

```text
Merge made by the 'ort' strategy.
```

`--no-ff` 的意思是"即使能快进，也给我造一个 merge commit"。这样历史里会留下"这里合过一条分支"的明确标记。**团队规范不同，选择不同**——大团队、需要审计时常用 `--no-ff`。

> 一句话记住它：快进 = 指针平移，历史一条直线；想保留"合并过分支"的痕迹就用 `--no-ff` 强制生成 merge commit。

## 03.7 三方合并：生成 merge commit

### 先给结论

两边都动了，Git 就会做**三方合并**：找到"共同祖先"，把祖先、你这边、对方那边三方比对，合成一个新的 merge commit。

### 为什么叫"三方"

三方 = 三个 commit 同时参与计算：

1. **共同祖先（base）**：分叉点，两边共同的起点；
2. **你这边（ours）**：当前分支的顶端；
3. **对方（theirs）**：被合并分支的顶端。

Git 的逻辑是：拿 base 当参照，看 ours 改了哪些、theirs 改了哪些，然后合并。**两边改的是不同文件（或不同行），Git 就能自动合成**；改的是同一行，就冲突（第 04 章）。

### 亲手走一遍

```bash
# 接着 03.6 的仓库，或者重新造一个分叉
git switch -c feat2
echo feat2 > b.txt && git add . && git commit -m "C3"

git switch master
echo master > c.txt && git add . && git commit -m "C4"

git merge feat2 -m "merge feat2"
```

```text
Merge made by the 'ort' strategy.
 b.txt | 1 +
 1 file changed, 1 insertion(+)
 create mode 100644 b.txt
```

注意输出里的 **`Merge made by the 'ort' strategy.`**——`ort` 是 Git 2.34 起的默认合并算法（更早的版本是 `recursive`）。这句在告诉你：这次不是快进，Git 用了三方合并算法，生成了一个 merge commit。

合并后的历史出现了分叉和汇合：

```bash
git log --oneline --graph
```

```text
*   21a9174 merge feat2
|\
| * cf2f847 C3
* | 39c790d C4
|/
* 1d9e461 C2
```

**看懂这张图**：`*` 是 commit，`|\` 是分叉，`|/` 是汇合，最下面的 `1d9e461` 是共同祖先。

### merge commit 的两个 parent

三方合并生成的 `21a9174` 有两个 parent：

```bash
git show -s --pretty=format:%P 21a9174
```

```text
39c790d0e4fa6ca7ce6abaa83e24755f84c76fed cf2f847cb307308ab3ea58f4c858fb79d414ff60
```

第一个 parent 是"你这边"（C4），第二个是"对方"（C3）。

> 一句话记住它：三方合并 = 共同祖先 + 两边，各比各的改动再合成；输出里的 `ort` 就是三方合并算法，merge commit 有两个 parent。

## 03.8 一个常被问的：`checkout` 还能切 commit

前面说 `switch` 专职切分支。但有个能力目前只有 `checkout` 好使（或者说 `switch` 有对应但少人用）：

```bash
git checkout 16344d6    # 切到某个具体的 commit（不是分支）
```

这时你会看到：

```text
Note: switching to '16344d6'.

You are in 'detached HEAD' state. ...
```

**这就是 detached HEAD（游离状态）**——HEAD 不再指向任何分支，而是直接指向一个 commit。

在这个状态下你也能提交，但这些提交**不属于任何分支**。一旦你切走，这些提交就成了"无主之物"，只能靠 reflog（第 05 章）或哈希找回。

**什么时候需要 detached HEAD？** 临时回去看一眼旧代码、调试某个历史版本。**看完了记得切回分支**，别在游离状态里干活。

> 一句话记住它：`checkout <commit>` 会进入 detached HEAD（游离状态），能看能改但不挂靠在任何分支上，看完赶紧切回。

## 03.9 分支命名规范：让分支名自己说话

### 先给结论

**分支名应该一眼看出"这是干什么的"**。团队统一命名规范后，`git branch` 一列出来，谁在做什么一目了然。

### 最常用的三种前缀

| 前缀 | 用途 | 例子 |
|---|---|---|
| `feature/` | 新功能 | `feature/add-login`、`feature/user-profile` |
| `fix/` | 修 bug | `fix/password-validation` |
| `hotfix/` | 紧急线上修复 | `hotfix/2026-10-12-crash` |

（有的团队还有 `chore/`（杂项）、`refactor/`（重构）、`docs/`（文档）等前缀，核心原则一致：**前缀 + 主题，讲清楚意图**。）

### 为什么这很重要

因为分支名会**出现在历史里**（merge commit 的说明里、`git branch` 的列表里）。三个月后你看到一堆 `dev1`、`test2`、`branch-a`，根本不知道它们是干嘛的。而看到 `feature/add-login`，一秒就懂。

### 一个常见坑：分支名带斜杠

`feature/add-login` 里的 `/` 是允许的（Git 会把分支存在 `refs/heads/feature/add-login`，形成子目录）。但注意：

- **不要**用 `/` 结尾（`feature/` 这种）；
- **不要**一个分支名是另一个的前缀（比如同时有 `feature` 和 `feature/login`），会引发引用歧义。

> 一句话记住它：分支名 = `前缀 + 主题`（feature/fix/hotfix），让它自己说话；历史里看到名字就知道意图。

## 03.10 两种"非标准"合并：`--no-ff` 和 `--squash`

第 03.6、03.7 讲了快进和三方两种标准结局。还有两种"带参数"的合并，团队规范里常见。

### `--no-ff`：强制生成 merge commit

快进合并虽然干净，但**看不出"这里曾有过一条分支"**。`--no-ff` 强制即使能快进也生成 merge commit：

```bash
git merge --no-ff feature -m "merge: feature"
```

合并后的历史：

```text
*   M  merge: feature          ← 多了一个 merge commit
|\
| * C3 (feature)
|/
* C2
```

**适用团队**：需要审计"谁、在什么时候合了什么分支"的大团队。代价是历史里多了很多 merge commit，线形图会"绕"一点。

### `--squash`：把整条分支压成"一个未提交的改动"

```bash
git merge --squash feature
```

它把 feature 分支的**所有改动合并成一个"待提交的改动"**放进你的暂存区，但**不自动提交、也不生成 merge commit**：

```bash
git merge --squash feature
git status -s          # 改动都在暂存区，等你自己 commit
git commit -m "feat: 登录功能"   # 你手动提交，历史里只有这一个 commit
```

**适用场景**：feature 分支上有一堆 `wip` 碎提交，你想合进 main 时**只留一个干净的提交**，不保留那些碎历史。

### 三种"合并"方式的对比

| 方式 | 历史效果 | 适用 |
|---|---|---|
| `git merge`（快进） | 一条直线，无痕迹 | 个人小项目 |
| `git merge --no-ff` | 保留 merge commit | 需要审计的大团队 |
| `git merge --squash` | 压成单提交，不保留分支历史 | 想清理碎提交时 |

**注意**：`--squash` 和 `--no-ff` 的取舍本质是"要不要保留分支的历史痕迹"。这和 `rebase`（第 07 章）的取舍是同一类问题——**历史要"真实"还是要"干净"**。

> 一句话记住它：`--no-ff` 强制留 merge commit（要审计），`--squash` 把分支压成单提交（要干净）；都是"历史真实 vs 历史干净"的取舍。

## 03.11 `git branch` 进阶：看分支指向哪、合没合并

### 先给结论

03.3 的 `git branch` 只能"列出"和"创建/删除"。这一节补三个进阶参数，解决两个真实问题：**"这个分支现在指向哪个提交？"** 和 **"哪些分支可以安全删除了？"**

### ① `git branch -v`：每个分支指向哪个提交

```bash
git branch -v
```

```text
  feat 2d30140 C2
* main 3b96c6f C3
```

`-v`（verbose）在分支名后面多显示一列：该分支指向的**短哈希 + 提交说明**。一眼看出"每个分支的最新提交是什么"。

再加一个 `-v` 变成 `-vv`，会多出一列**上游追踪分支**（用 `[origin/main]` 这种形式标出来）：

```bash
git branch -vv
```

```text
* main 3b96c6f [origin/main] C3
  feat 2d30140 C2
```

`[origin/main]` 表示"本地 main 在追踪远程的 origin/main，且两者进度一致"。这个上游追踪的概念属于远程协作（第 06 章细讲），这里先知道 `-vv` 能看它就行——**没配远程的仓库，这一列是空的**。

### ② `git branch --merged`：哪些分支已经合进来了

```bash
git branch --merged
```

```text
* main
```

**含义：列出"已经合并进当前分支"的分支。** 这些分支的所有提交都已经被当前分支包含，所以**可以放心删除**。

合并完 feature 后，最该做的清理动作就是先跑一遍 `--merged`，确认 feature 在里面，再 `git branch -d feature`。

### ③ `git branch --no-merged`：哪些分支还没合进来

```bash
git branch --no-merged
```

```text
  feat
```

**含义：列出"还没合并进当前分支"的分支。** 这些分支上有当前分支**没有**的提交，直接 `-d` 删会被拒绝（就是 03.3 那个 `not fully merged` 报错）。

### 一张表总结

| 命令 | 显示什么 | 典型用途 |
|---|---|---|
| `git branch` | 所有分支（`*` 是当前） | 看有哪些分支 |
| `git branch -v` | 每个分支指向的提交 | 看每个分支进展到哪 |
| `git branch -vv` | 再加一列上游追踪 | 看本地和远程的关系 |
| `git branch --merged` | 已合并的分支 | 找出能安全删除的 |
| `git branch --no-merged` | 未合并的分支 | 找出删了会丢提交的 |

> 一句话记住它：`-v` 看分支指向哪个提交，`--merged` 看哪些能安全删，`--no-merged` 看哪些还带着独有提交。

## 03.12 detached HEAD 详解：游离状态能干嘛、怎么转正

### 先给结论

03.8 用一句话带过了 detached HEAD。这一节把它讲透：**它是什么、能干嘛、什么时候该用、以及最危险的一个坑**。

**detached HEAD = HEAD 直接指向一个 commit，而不是通过分支指向。** 换句话说，你站在了一个"不属于任何分支"的位置上。

### 亲手看完整的提示

```bash
git checkout HEAD~1
```

```text
Note: switching to 'HEAD~1'.

You are in 'detached HEAD' state. You can look around, make experimental
changes and commit them, and you can discard any commits you make in this
state without impacting any branches by switching back to a branch.

If you want to create a new branch to retain commits you create, you may
do so (now or later) by using -c with the switch command. Example:

  git switch -c <new-branch-name>

Or undo this operation with:

  git switch -

Turn off this advice by setting config variable advice.detachedHead to false

HEAD is now at cc545b7 C1
```

这段提示其实是**一份完整的使用说明书**，翻译成人话：

1. 你现在处于 detached HEAD，可以四处看看、做实验、甚至提交；
2. 在这里提交的东西，**切回分支后可以当没发生过**（不影响任何分支）；
3. 想**保留**这里的提交，就用 `git switch -c <新分支名>` 给它建个分支；
4. 想**撤销**这次游离，用 `git switch -` 切回之前的位置。

### 怎么确认自己是不是游离了

游离状态下，`git status` 的第一行和平时不一样：

```bash
git status -sb
```

```text
## HEAD (no branch)
```

平时这里是 `## main`（或你的分支名），游离时会变成 **`HEAD (no branch)`**——"HEAD 没有指向任何分支"。看到这行，就知道自己在游离状态。

### 什么时候该用 detached HEAD

| 场景 | 做法 |
|---|---|
| 临时看一眼旧版本代码 | `git checkout <哈希>`，看完 `git switch -` 切回 |
| 复现一个历史 bug | 切到 bug 引入前的提交，验证 |
| 做"实验性"改动（不想污染分支） | 游离状态下随便改，切走即弃 |

### 最危险的一个坑：在游离状态提交，然后切走

这是新手最容易"丢提交"的地方：

```bash
git checkout HEAD~1      # 游离
echo fix >> a.txt
git add a.txt && git commit -m "临时修复"   # 在游离状态下提交了！
git switch main          # 切走，忘了给这个提交建分支
```

这个"临时修复"提交现在**不属于任何分支**。它没有丢（还在 `.git/objects` 里），但**没有任何分支指向它**，`git log` 在 main 上也看不到它。找回它只能靠 `git reflog`（第 05 章）。

**正确做法**：游离状态下如果真要做提交，先给它建个分支：

```bash
git switch -c fix-temp    # 把游离状态"转正"成一个分支
```

之后的所有提交就都挂在这个新分支上了，再也不会"无主"。

> 一句话记住它：detached HEAD 是"站在一个不属于任何分支的提交上"；`git status -sb` 显示 `HEAD (no branch)` 就是它；想在这里提交，先 `git switch -c` 建分支。

## 03.13 merge 的更多细节：`--no-commit`、`--abort` 与合并策略

### 先给结论

`git merge` 除了 `--no-ff` 和 `--squash`（03.10），还有两个实用参数和一条值得知道的背景知识：`--no-commit`（合并但不自动提交）、`--abort`（冲突时反悔），以及它背后的"合并策略"。

### ① `--no-commit`：合并了，但先别提交

```bash
git merge --no-commit feat
```

```text
Automatic merge went well; stopped before committing as requested
```

它把 feat 的改动**合并进工作区和暂存区，但不生成 commit**：

```bash
git status -s
```

```text
A  b.txt
```

改动已经进了暂存区（`A ` 在第一列），等你自己 `git commit`。

**什么时候用**：你想在提交前**先检查合并结果**，或者想**自定义 merge commit 的提交说明**（而不是用 Git 默认的 `Merge branch 'feat'`）。确认没问题后手动 `git commit -m "..."` 即可。

### ② `--abort`：合并到一半，反悔了

当你 `git merge` 遇到冲突（第 04 章细讲），合并会停在"冲突待解决"状态。如果你**不想解决了，想直接撤销这次合并**：

```bash
git merge --abort
```

它会回到合并前的干净状态，就像什么都没发生过。这是冲突时最常用的"后悔药"之一，第 04 章会再次用到。

### ③ 合并策略：为什么输出里总有 `ort`

你在 03.6、03.7 见过 `Merge made by the 'ort' strategy.`。这里的 `ort` 是 **Git 默认的合并策略**：

| 策略 | 说明 |
|---|---|
| `ort` | Git 2.34 起的默认策略，`recursive` 的改进版，更快、更少冲突 |
| `recursive` | 旧版本（2.34 之前）的默认，处理两个分支的合并 |
| `octopus` | 一次合并**多个**分支（3 个以上）时用的策略 |
| `resolve` | 最基础的策略，很少用 |

普通的两分支合并你不需要关心策略，Git 会自动选 `ort`。只有一种情况你会"看见"策略切换：**一次合并多个分支**时，Git 会自动用 `octopus`：

```bash
git merge feat-a feat-b feat-c   # 同时合并三个分支，会用 octopus 策略
```

不过 octopus 有个限制：**任何一个分支有冲突，整个合并就失败**（它不处理冲突）。所以日常合并还是老老实实一次合一个分支，冲突了也好定位。

> 一句话记住它：`--no-commit` 合并但先不提交（方便检查），`--abort` 冲突时反悔；默认策略 `ort` 你不用管，除非一次合并多分支才碰 `octopus`。

## 03.14 分支的日常杂项：重命名、切回上一个、从历史建分支

### 先给结论

前面讲的分支操作都是"创建/切换/删除/合并"。这一节补三个真实项目里高频用到、但教程常漏的小操作：**重命名分支**、**切回上一个分支**、**从历史某个点建分支**。

### ① `git branch -m`：重命名分支

分支名起错了、或者想改成更规范的 `feature/xxx`，用 `-m`（move）：

```bash
git branch -m master      # 把"当前分支"重命名为 master（只给一个参数）
git branch -m 旧名 新名   # 把指定分支重命名（给两个参数）
```

```bash
git branch -m main master
git branch
```

```text
* master
```

**注意两种写法的区别**：给一个参数是"重命名当前分支"，给两个参数是"重命名任意分支"。这个和 `mv` 命令的语义一致，容易记混，敲之前想清楚。

### ② `git switch -`：切回上一个分支

就像 shell 里的 `cd -`（切回上一个目录），Git 也有 `git switch -`（切回上一个分支）：

```bash
git switch -
```

```text
Switched to branch 'master'
```

这个 `-` 表示"上一个所在的分支"。**在两个分支之间来回切时，这个命令能省掉记分支名**——你切过去改完，`git switch -` 就回来了。

### ③ 从历史某个点建分支

通常 `git switch -c 新分支` 是从"当前提交"建分支。但你也可以指定**从历史任意一个提交**建：

```bash
git switch -c oldpoint HEAD~1
```

```text
Switched to a new branch 'oldpoint'
```

之后 `git branch -v`：

```text
  master   bdd7ca6 C3
* oldpoint d090547 C2
```

注意 `oldpoint` 指向的是 **C2**，不是最新的 C3——因为你在 `HEAD~1`（C2）这个点建的分支。

**典型场景**：线上最新版出了 bug，你想回到"上一个稳定版本"上打补丁。就从那个稳定提交建一个 hotfix 分支：

```bash
git switch -c hotfix <稳定版本的哈希>
# 或
git branch hotfix <稳定版本的哈希>
```

（`git branch 分支名 起点` 是"建分支但不切过去"，`git switch -c 分支名 起点` 是"建并切过去"，区别同 03.3。）

### 一张表收尾

| 操作 | 命令 | 说明 |
|---|---|---|
| 重命名当前分支 | `git branch -m 新名` | 一个参数 = 当前分支 |
| 重命名任意分支 | `git branch -m 旧名 新名` | 两个参数 |
| 切回上一个分支 | `git switch -` | 像 `cd -` |
| 从历史某点建分支 | `git switch -c 新名 起点` | 起点可以是哈希/`HEAD~n` |

> 一句话记住它：`git branch -m` 重命名分支（一个参数改当前，两个参数改任意），`git switch -` 切回上一个分支，`git switch -c 新名 起点` 从历史任意点建分支。

## 03.15 本章常见坑速查

| 坑 | 现象 | 原因 | 正确做法 |
|---|---|---|---|
| `git branch feature` 后仍在原分支 | 提交都跑到 master 上去了 | `git branch` 只创建不切换 | 用 `git switch -c feature` |
| 切分支带着未提交改动 | 改动被带到新分支/报错 | 未提交改动跟着工作区走 | 先 commit 或 stash 再切 |
| 分不清 `-d` 和 `-D` | 删分支被拦 | 分支没合并，`-d` 拒绝 | 确认不要了就 `-D`，否则先合并 |
| 把 `checkout` 当万能命令 | 不知道何时切分支何时丢文件 | checkout 身兼两职 | `switch` 切分支、`restore` 丢文件 |
| 在 detached HEAD 里提交 | 提交"丢了" | 游离状态提交不挂分支 | 用 reflog 找回，或先 `switch -c` 建分支 |
| 期望 merge 总是自动成功 | 报冲突 | 两边改了同一行 | 第 04 章：手动解决冲突 |
| 不知道 merge 是快进还是三方 | 历史忽直线忽分叉 | 没判断"当前分支动没动" | 分叉后当前分支没动 → 快进；动了 → 三方 |
| 合并后分支还在 | `git branch` 还能看到 feature | merge 不会自动删分支 | 确认合并完 `git branch -d feature` |
| `switch` 到不存在的分支 | `fatal: invalid reference: nope` | 名字拼错 | 先 `git branch` 看清楚 |
| 游离状态提交后切走 | 提交"丢了"，`git log` 看不到 | detached HEAD 提交不挂分支 | 游离时先 `git switch -c` 建分支；丢了用 reflog 找回 |
| 乱删分支删错了 | `-d` 删不掉/误删独有提交 | 没先看合并状态 | 删前先 `git branch --merged` / `--no-merged` 确认 |
| `merge --no-commit` 后忘了提交 | 合并改动停在暂存区，以为合并完了 | `--no-commit` 不自动提交 | 检查后手动 `git commit`，或下次别加 `--no-commit` |
| `git branch -m` 只给一个参数 | 想改指定分支却把当前分支改了 | 一个参数 = 重命名当前分支 | 改指定分支用 `git branch -m 旧名 新名` |

## 03.16 本章小结

**HEAD**

- HEAD 是"你站在哪"的指针；`cat .git/HEAD` 是 `ref: refs/heads/xxx`。
- "两跳"设计（HEAD → 分支 → commit）让切分支和提交都只是改一个小文件。

**分支**

- 分支 = `refs/heads/` 里的一个哈希文件，创建/删除都只是读写一行字。
- `git branch` 列出（`*` 当前）、加名创建、`-d`/`-D` 删除。
- 创建不会自动切，`git switch -c` 才会创建并切。

**切换**

- `git switch` 切分支会真实替换工作区文件；`restore` 专职恢复文件，取代 `checkout --`。
- `checkout <commit>` 进入 detached HEAD，提交不挂分支。

**合并**

- `git merge` 两种结局：快进（一方没动，指针平移）和三方（两边都动，生成 merge commit）。
- 三方 = base + ours + theirs；merge commit 有两个 parent。
- `--no-ff` 强制生成 merge commit，保留合并痕迹。

**分支进阶与游离状态**

- `git branch -v` 看每个分支指向的提交，`-vv` 多看一列上游追踪，`--merged/--no-merged` 看合没合并。
- detached HEAD：`git status -sb` 显示 `HEAD (no branch)`；想提交先 `git switch -c` 建分支。
- `merge --no-commit` 合并但不自动提交，`--abort` 冲突时反悔；默认策略 `ort`。

**分支杂项**

- `git branch -m` 重命名分支（一个参数改当前、两个参数改任意），`git switch -` 切回上一个分支。
- `git switch -c 新名 起点` 从历史任意提交建分支，常用于 hotfix。

## 03.17 动手练习

### 练习 1：画出 HEAD 和分支的关系

执行下面命令后，`HEAD`、`master`、`feature` 三者分别指向哪个 commit？画出图。

```bash
git init
echo a > a.txt && git add . && git commit -m C1
git branch feature
git switch -c dev
echo b > b.txt && git add . && git commit -m C2
```

<details><summary>参考答案</summary>

```text
HEAD → dev → C2
master → C1
feature → C1
```

- `git branch feature` 创建了 feature，但没切换，所以 feature 指向 C1；
- `git switch -c dev` 创建并切到 dev，HEAD 指向 dev；
- 在 dev 上提交 C2，dev 前进到 C2，master 和 feature 还停在 C1。

</details>

### 练习 2：预测快进还是三方

```text
C1 ── C2（master）
       \
        C3（feature）
```

在 master 上执行 `git merge feature`，是快进还是三方？为什么？

<details><summary>参考答案</summary>

**快进。** 分叉点（C2 之前的 C1）之后，master 没有新提交（它就在 C2 上），feature 在 C3。master 直接把指针挪到 C3 即可，历史保持直线。

（如果 master 在分叉后又提交了 C4，才是三方合并。）

</details>

### 练习 3：判断对错

1. 分支就是一份独立的代码拷贝。
2. 删除分支会同时删除它上面的 commit。
3. `git merge` 快进合并会生成一个 merge commit。
4. `git switch` 切换分支不会改动工作区的文件。
5. detached HEAD 状态下可以正常提交，且提交会挂在某个分支上。

<details><summary>参考答案</summary>

1. **错。** 分支只是一个指向 commit 的指针（哈希文件），不是拷贝。
2. **错。** 删分支只删指针，commit 还在对象库里（除非之后被 GC 回收）。
3. **错。** 快进合并不生成新 commit，只是指针平移；三方合并才生成 merge commit。
4. **错。** 切换分支会真实地把工作区文件换成目标分支的快照。
5. **错。** detached HEAD 下的提交不挂靠任何分支，切走后就"悬空"，需要 reflog 或哈希找回。

</details>

### 练习 4：合并后清理分支

完成一次 feature → master 的合并后，怎么安全地删掉 feature 分支？如果 `git branch -d` 报错了，说明什么？

<details><summary>参考答案</summary>

```bash
git switch master
git merge feature
git branch -d feature   # 已合并，安全删除
```

如果 `-d` 报 `error: The branch 'feature' is not fully merged.`，说明 feature 上有 master 还没有的提交（可能你 merge 的不是这个分支，或合并失败了）。确认这些提交不要了，用 `-D` 强删；否则先合并再删。

</details>

### 练习 5：游离状态怎么"转正"

你执行了 `git checkout HEAD~2` 想看看旧代码，结果在游离状态下改了文件并提交了一次。现在你不想丢这个提交，该怎么做？写出完整命令。

<details><summary>参考答案</summary>

游离状态下提交的 commit 不属于任何分支。用 `git switch -c` 给它建一个分支，把"当前游离位置"变成一个新分支的顶端：

```bash
git switch -c my-fix    # 以当前游离位置为起点，建并切到 my-fix
```

这样刚才那个"悬空"的提交就挂到 `my-fix` 分支上了。之后再正常合并回主线即可。

如果已经切走、找不到那个提交了，用 `git reflog`（第 05 章）找回它的哈希，再 `git branch my-fix <哈希>`。

</details>

### 练习 6：合并前快速摸清分支状态

你负责合入同事的 `feature/payment` 分支。合并前你想确认两件事：① 这个分支最新提交是什么；② 它有没有已经包含主线的最新代码。写出你用的命令，并说明如何根据输出判断。

<details><summary>参考答案</summary>

```bash
git branch -v                     # ① 看 feature/payment 指向哪个提交
git branch --merged               # ② 看它是否已经合并进当前分支
git branch --no-merged            #    看它是否还带着主线没有的提交
```

- `git branch -v` 输出里 `feature/payment <哈希> <说明>` 就是它的最新提交；
- `--merged` 里出现 `feature/payment`，说明它已完全并入当前分支，可直接删；
- `--no-merged` 里出现它，说明还有独有提交，合并前要 `git diff main feature/payment` 先看差异。

</details>
