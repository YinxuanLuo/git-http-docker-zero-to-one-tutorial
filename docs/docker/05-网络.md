# 第 05 章 · 网络：容器怎么"上网"、怎么"互相找到"

> 第 04 章你做出了自己的镜像，这一章解决两个问题：**外面怎么访问容器**（端口映射）、**容器之间怎么通信**（自定义网络 + DNS）。
>
> 本章你需要记住的就一件事：**`-p 宿主端口:容器端口` 决定"外面怎么进来"，网络（network）决定"容器之间怎么互通"。默认 bridge 网络里容器名不能互访，自定义网络里可以。**

---

## 05.1 容器的网络：默认就有三种

**先说结论**：Docker 每个容器都必须属于某个网络，默认情况下 Docker 帮你建好了三种网络：`bridge`、`host`、`none`。

```bash
docker network ls
```

```text
NETWORK ID     NAME      DRIVER    SCOPE
a1b2c3d4e5f6   bridge    bridge    local
b2c3d4e5f6a1   host      host      local
c3d4e5f6a1b2   none      null      local
```

**三种默认网络的定位：**

| 网络 | 隔离程度 | 什么时候用 |
|---|---|---|
| `bridge` | 独立网络，靠端口映射和外面通信 | **默认**，绝大多数场景 |
| `host` | 直接用宿主的网络栈，无隔离 | 追求极致性能、端口不想映射时 |
| `none` | 完全没网络 | 高度安全隔离、纯计算任务 |

**你 `docker run` 不指定网络时，容器默认进 `bridge`。** 所以前面所有章节的容器，都在默认 bridge 网络里。

**为什么要懂网络？** 因为两个最实际的问题都靠它解决：

1. **外面访问容器**：`-p` 端口映射（05.5）。
2. **容器 A 访问容器 B**：网络 + 容器名（05.7）。

> 一句话记住它：**容器默认进 bridge 网络；Docker 内置 bridge/host/none 三种默认网络。`-p` 管"外面进来"，网络管"容器互通"。**

---

## 05.2 bridge：默认的"桥接"网络

**先说结论**：`bridge` 是默认网络。每个容器在 bridge 里拿到一个**私有 IP**（如 `172.17.0.2`），通过**端口映射**才能被宿主机和外界访问。

**bridge 网络的模型：**

```text
外界（你的浏览器、宿主机）
        ▲
        │ 只有映射的端口能进来
        ▼
   宿主机（172.17.0.1 是网桥网关）
        │
   ┌────┴─────────────┐
   │  docker0 网桥      │
   └────┬──────┬──────┘
        │      │
   容器A       容器B
  (172.17.0.2) (172.17.0.3)
```

**三个关键认知：**

**认知一：容器有独立 IP，但这个 IP 是"私有"的。** 宿主机外面的人（你的同事、公网）访问不到 `172.17.0.2`——这是 Docker 内部的私有网段。所以**必须端口映射**才能从外面访问。

**认知二：默认 bridge 里，容器之间**可以**用 IP 互访，但**不能**用容器名互访。** 这个限制是历史上"link"被发明的原因（05.9 讲）。而**自定义网络**解决了这个问题（05.7）。

**认知三：bridge 自带 NAT。** 容器访问外网（如 `apt-get`）时，通过 NAT 把容器的私有 IP 翻译成宿主的 IP 出去。所以容器能上网，但外面的人看不到容器的真实 IP。

**看一个容器的网络详情：**

```bash
docker run -d --name web nginx
docker inspect web --format '{{.NetworkSettings.IPAddress}}'
```

```text
172.17.0.2
```

> 一句话记住它：**bridge 是默认网络，容器拿私有 IP，靠 NAT 上网、靠端口映射对外。默认 bridge 里容器名不能互访（只能用 IP），这是它的历史短板。**

## 05.3 host：直接共享宿主的网络栈

**先说结论**：`host` 模式让容器**直接用宿主机的网络**，没有独立 IP，没有端口映射这回事——容器监听什么端口，宿主机就监听什么端口。

```bash
docker run --network host nginx
```

**host 模式的行为：**

| 特性 | bridge 模式 | host 模式 |
|---|---|---|
| 独立 IP | 有（172.17.x.x） | 无，用宿主的 IP |
| 端口映射 | 需要 `-p` | **不需要**，端口直接就是宿主的 |
| 隔离性 | 有 | 无 |
| 性能 | 有轻微 NAT 开销 | 更高（无 NAT） |

**什么时候用 host？**

1. **追求极致性能**：网络密集型应用（如高频交易、代理服务），省掉 NAT 的一层开销。
2. **端口很麻烦的场景**：程序要监听很多端口，一个个 `-p` 太啰嗦，直接 host 全共享。

**host 的代价：**

1. **端口冲突**：容器的端口和宿主的端口**共用一套**，容器占了 80，宿主的 80 就被占了。
2. **无隔离**：容器网络完全暴露在宿主网络里，安全边界弱。

**一个重要的坑**：`host` 模式下，你**不能再写 `-p`**（端口映射），会报错：

```bash
docker run --network host -p 8080:80 nginx
```

```text
WARNING: Published ports are discarded when using host network mode
```

它不是报错，是警告——`-p` 被直接忽略了（因为 host 模式端口本来就共享，无需映射）。

> 一句话记住它：**host 模式共享宿主网络栈：无独立 IP、无需端口映射、性能高，但端口冲突、无隔离。适合性能敏感或端口多的场景。**

## 05.4 none：完全没网络

**先说结论**：`none` 模式给容器一个**完全空白的网络**——没有网卡、没有 IP、没有网络连接。适合"纯计算、不需要任何网络"的隔离任务。

```bash
docker run --network none alpine ifconfig
```

```text
lo        Link encap:Local Loopback   ← 只有回环接口 lo，连 eth0 都没有
          inet addr:127.0.0.1
```

**为什么要有 none？** 安全。一个处理敏感数据、根本不需要网络的容器，直接 `none` 断网，从物理上杜绝了"数据往外传"的可能。

**典型场景：**

- 离线批处理任务（算哈希、转码、数据处理）。
- 高安全隔离（不允许任何网络通信）。

**验证它真的没网：**

```bash
docker run --network none alpine ping -c 1 8.8.8.8
```

```text
ping: bad address '8.8.8.8'   ← 根本解析不了外网
```

> 一句话记住它：**none 模式 = 彻底断网，只有 lo 回环。适合不需要网络的纯计算或高安全隔离场景。**

## 05.5 端口映射 -p 详解

**先说结论**：`-p 宿主端口:容器端口` 把宿主机的端口"转发"到容器的端口。这是外面访问容器的唯一入口。

```bash
docker run -d -p 8080:80 nginx
```

含义：宿主机 8080 → 容器 80。现在 `curl localhost:8080` 就能访问 nginx（它在容器里监听 80）。

**完整的 `-p` 语法：**

```text
-p [宿主IP:]宿主端口:容器端口[/协议]
```

几种写法：

| 写法 | 含义 |
|---|---|
| `-p 8080:80` | 宿主机所有网卡的 8080 → 容器 80 |
| `-p 127.0.0.1:8080:80` | 只绑定宿主的 127.0.0.1 的 8080（**只本机可访问**） |
| `-p 8080:80/tcp` | 指定协议（默认 tcp） |
| `-p 8080:80/udp` | UDP 协议 |

**最容易踩的坑：左右顺序写反。**

```bash
docker run -p 80:8080 nginx     # 宿主 80 → 容器 8080
```

如果 nginx 在容器里其实监听的是 **80**（默认），你却映射成 `-p 80:8080`，那么外面访问宿主 80，转发到容器 8080——而容器根本没有进程监听 8080，连接失败。

**口诀：`-p` 左边是"你从外面敲的端口"，右边是"容器里应用真正监听的端口"。**

**怎么知道容器监听哪个端口？** 看镜像文档（nginx 默认 80、node 默认 3000 看你自己代码），或 `docker inspect` 的 `ExposedPorts`（第 04 章 EXPOSE）。

**查看端口映射：**

```bash
docker ps
```

```text
CONTAINER ID   IMAGE    ...   PORTS                  NAMES
a1b2c3d4e5f6   nginx    ...   0.0.0.0:8080->80/tcp   web
```

`PORTS` 列 `0.0.0.0:8080->80/tcp`：宿主所有网卡的 8080 转发到容器 80。

> 一句话记住它：**`-p 宿主:容器`，左宿主机右容器，别写反。`127.0.0.1:8080:80` 只绑本机（更安全）。看映射用 `docker ps` 的 PORTS 列。**

## 05.6 端口占用：一个高频报错

**触发条件**：宿主机上某个端口已经被占了（被另一个容器、或宿主自己的进程），你再 `-p` 映射同一个端口。

**现象**（真实报错原文）：

```bash
docker run -d -p 8080:80 nginx   # 假设 8080 已被占用
```

```text
docker: Error response from daemon: driver failed programming external connectivity on endpoint web (a1b2c3d4e5f6): Bind for 0.0.0.0:8080 failed: port is already allocated.
See 'docker run --help'.
```

**关键句**：`Bind for 0.0.0.0:8080 failed: port is already allocated`——端口已被分配。

**排查和解决：**

```bash
# 1. 看谁占了 8080（Linux）
ss -tulpn | grep 8080
# 或
lsof -i:8080

# 2. 看是不是某个 docker 容器占了
docker ps --format '{{.Names}} {{.Ports}}' | grep 8080

# 3. 解决：换个宿主端口
docker run -d -p 8081:80 nginx
```

**注意**：这个报错发生时，**容器可能已经被创建了**（只是网络配置失败）。你会看到一个 `Created` 状态、起不来的容器残留，记得清理：

```bash
docker ps -a        # 找到那个 Created 的容器
docker rm <id>      # 删掉它
```

> 一句话记住它：**`Bind for 0.0.0.0:8080 failed: port is already allocated` = 宿主端口被占。换端口，或先找出占用者；报错后可能有 Created 残留容器，记得 rm。**

## 05.7 自定义网络：容器名互访

**先说结论**：在**自定义网络**里，容器之间可以直接用**容器名**当主机名互相访问，不用记 IP。这是现代 Docker 多容器通信的标准做法。

```bash
# 创建一个自定义网络
docker network create my-net

# 两个容器都加入这个网络
docker run -d --name db --network my-net postgres:16
docker run -d --name web --network my-net myapp
```

现在 `web` 容器里，可以直接用 `db` 这个主机名访问数据库：

```text
连接字符串：postgres://db:5432/mydb
#                ↑ 直接用容器名，不用 IP
```

**为什么自定义网络能做到，默认 bridge 做不到？** 因为自定义网络内置了 **DNS 解析**：容器名会自动注册到网络的内置 DNS，容器之间靠名字就能找到对方（05.8 详讲）。而默认 bridge 是 Docker 最古老的实现，没带这个 DNS。

**自定义网络 vs 默认 bridge：**

| 特性 | 默认 bridge | 自定义网络 |
|---|---|---|
| 容器名互访 | ❌ 不行（只能 IP） | ✅ 可以 |
| DNS 解析 | 无 | 内置 |
| 网络隔离 | 所有容器挤一个网 | 每个网络独立，可隔离 |
| 推荐度 | 别用（除非单容器） | **多容器标配** |

**为什么要"自定义网络"而不是都在默认 bridge 里？** 除了 DNS，还有一个好处：**网络隔离**。你可以让"前端网络"和"数据库网络"分开，数据库只对后端容器可见，前端摸不到——这就是微服务里的网络分段。

> 一句话记住它：**自定义网络里容器名可以直接互访（内置 DNS），这是多容器通信的标准做法；默认 bridge 只支持 IP 互访，别用它做多容器互联。**

## 05.8 DNS：容器名是怎么解析的

**先说结论**：Docker 给每个自定义网络内置了一个 DNS 服务器（地址通常是 `127.0.0.11`）。容器里访问别的容器名时，请求发给这个 DNS，它把容器名解析成那个容器的 IP。

**解析过程：**

```text
web 容器里访问 db:5432
        │
        ▼
   容器名 "db" 是主机名，去问 DNS（127.0.0.11）
        │
        ▼
   Docker 内置 DNS 查到 db 容器在 my-net 网络的 IP（172.18.0.2）
        │
        ▼
   web 用 172.18.0.2 连接 db
```

**几个重要细节：**

**细节一：容器名是"网络内"的主机名，跨网络不解析。** `db` 在 `my-net` 里能解析，但另一个网络的容器访问 `db` 就不行——因为 DNS 是按网络隔离的。

**细节二：容器重启后 IP 可能变，但容器名不变。** 这就是"用容器名而不是 IP"的核心价值：容器重建、重启，IP 会变（DHCP 分配），但名字永远叫 `db`，连接字符串不用改。

**细节三：`--network-alias` 可以给容器加"别名"。** 一个容器可以有多个名字：

```bash
docker run -d --name db --network my-net --network-alias database postgres:16
```

这样别的容器用 `db` 或 `database` 都能访问到它。

**细节四：容器里看 DNS 配置：**

```bash
docker exec web cat /etc/resolv.conf
```

```text
nameserver 127.0.0.11    ← Docker 内置 DNS
options ndots:0
```

> 一句话记住它：**容器名解析靠内置 DNS（127.0.0.11）；容器名按网络隔离，跨网络不解析；IP 会变但名字不变，所以连接用容器名。**

## 05.9 link 的兴衰：为什么被 network 取代

**先说结论**：`--link` 是 Docker **早年**用来"让容器 A 能访问容器 B"的机制，后来被**自定义网络 + DNS**取代。你现在几乎不应该再用它，但要知道它存在（很多老教程、老项目里还有）。

**link 解决什么问题？** 当年默认 bridge 网络不支持容器名解析，你想让 web 访问 db，只能：

1. 硬编码 db 的 IP（但 IP 会变，不可靠）；
2. 用 `--link` 手动声明依赖关系。

```bash
# 老式写法：--link db 让 web 能解析 "db" 这个名字
docker run -d --name db postgres:16
docker run -d --name web --link db:db myapp
```

`--link db:db` 会在 web 容器的 `/etc/hosts` 里加一条 `db → db的IP`，于是 web 能用 `db` 访问。

**link 的三大毛病（所以被取代）：**

1. **单向**：`--link db` 只让 web 能访问 db，db 不能反过来访问 web。
2. **静态**：link 建立时把 IP 写死进 `/etc/hosts`，db 重启换了 IP，web 里的记录就失效了（要重启 web）。
3. **有依赖顺序**：必须先起 db 再起 web，否则 link 失败。

**自定义网络 + DNS 全解决了**：双向、动态（DNS 实时解析，IP 变了自动更新）、无启动顺序要求。

**结论**：**看到 `--link`，把它翻译成"过时的老写法"，换成自定义网络。**

```text
老：docker run --link db:db ...
新：先 docker network create my-net，两个容器都 --network my-net，直接容器名互访
```

> 一句话记住它：**`--link` 是自定义网络出现前的老机制（单向、静态、有顺序要求），已被"自定义网络 + 内置 DNS"取代。看到 link 就换成 network。**

## 05.10 网络命令速查

**先说结论**：网络相关的命令就那么几个，一次记全。

```bash
# 看所有网络
docker network ls

# 创建网络
docker network create my-net

# 看网络详情（含它连接了哪些容器）
docker network inspect my-net

# 删除网络（必须没有容器连接）
docker network rm my-net

# 把容器连接到网络（运行中也能连）
docker network connect my-net web

# 把容器从网络断开
docker network disconnect my-net web

# 清理未使用的网络
docker network prune
```

**一个真实报错**：删除一个还有容器连接的网络：

```bash
docker network rm my-net    # 假设还有容器连着
```

```text
Error response from daemon: error while removing network: network my-net id a1b2c3d4e5f6 has active endpoints
```

意思是"有活跃端点（容器还连着）"。先把容器断开/删除，再删网络。

**一个常用组合**：`docker run` 时直接指定网络：

```bash
docker run -d --network my-net --name web nginx
```

如果网络不存在，会报错（真实原文）：

```text
Error response from daemon: network my-net not found
```

> 一句话记住它：**网络命令：ls/create/inspect/rm/connect/disconnect/prune。删有容器的网络报 `has active endpoints`；用不存在的网络报 `network xxx not found`。**

## 05.12 本章常见坑速查

| 坑 | 现象 | 原因 | 正确做法 |
|---|---|---|---|
| `-p` 左右写反 | 外面访问不到服务 | `-p` 左边是宿主、右边是容器 | 记住"左宿主右容器" |
| 端口被占 | `Bind for 0.0.0.0:8080 failed: port is already allocated` | 宿主端口已被占用 | 换端口，或先找出占用者 |
| 以为默认 bridge 能用容器名 | 容器间 `getaddrinfo` 失败 | 默认 bridge 没有 DNS，只能 IP | 用自定义网络 |
| 用 `--link` | 单向、静态、顺序要求 | link 是过时机制 | 换自定义网络 |
| 容器 IP 写死进配置 | 容器重建后连不上 | IP 会变 | 用容器名（DNS 动态解析） |
| 删网络报错 | `has active endpoints` | 还有容器连着这个网络 | 先断开/删容器，再删网络 |
| 用不存在的网络 | `network xxx not found` | 网络没创建 | 先 `docker network create` |
| host 模式还写 `-p` | 警告 `Published ports are discarded` | host 模式无需端口映射 | 去掉 `-p` |
| 容器间用 localhost 互访 | 连不上 | localhost 指向容器自己，不是对方 | 用容器名，或宿主视角用端口映射 |

---

## 05.13 本章小结

- **三种默认网络**：`bridge`（默认，私有 IP + NAT）、`host`（共享宿主网络）、`none`（彻底断网）。
- **bridge**：容器拿私有 IP，靠 NAT 上网、靠端口映射对外；默认 bridge 里容器名不能互访。
- **host**：无独立 IP、无需端口映射、性能高，但端口冲突、无隔离。
- **none**：只有 lo 回环，适合不需要网络的纯计算/高安全隔离。
- **端口映射**：`-p 宿主:容器`，左宿主机右容器；`127.0.0.1:8080:80` 只绑本机。
- **端口占用报错**：`Bind for 0.0.0.0:8080 failed: port is already allocated`。
- **自定义网络**：容器名可直接互访（内置 DNS），多容器通信标配。
- **DNS**：内置 DNS（127.0.0.11）解析容器名；IP 会变名字不变，连接用容器名。
- **link**：过时机制（单向、静态、有顺序），已被自定义网络取代。
- **网络命令**：`ls/create/inspect/rm/connect/disconnect/prune`。

## 05.14 动手练习

**1. `docker run -p 80:8080 myapp` 里，`80` 和 `8080` 分别是什么？哪个是宿主的？**

<details><summary>参考答案</summary>

- `80`：**宿主机**端口（外面访问的）。
- `8080`：**容器**端口（应用真正监听的）。

格式是 `-p 宿主:容器`。所以这条命令是"宿主 80 → 容器 8080"。

</details>

---

**2. 两个容器要互相通信（比如 web 连 db），现代推荐怎么做？默认 bridge 网络里能不能直接用容器名？**

<details><summary>参考答案</summary>

现代推荐：创建自定义网络，两个容器都加入：

```bash
docker network create my-net
docker run -d --name db --network my-net postgres:16
docker run -d --name web --network my-net myapp
```

然后 web 里直接用 `db` 访问。

默认 bridge 网络里**不能用容器名**互访（只能 IP），因为它是老实现，没有内置 DNS。

</details>

---

**3. `docker run -d -p 8080:80 nginx` 报错 `Bind for 0.0.0.0:8080 failed: port is already allocated`，什么意思？怎么处理？**

<details><summary>参考答案</summary>

意思是宿主机 8080 端口已经被占用了。

处理：换个宿主端口（如 `-p 8081:80`），或先找出占用者（`ss -tulpn | grep 8080`、`lsof -i:8080`）再决定。

注意：这个报错后可能残留一个 `Created` 状态的容器，记得 `docker rm` 清理。

</details>

---

**4. `--network host` 和默认 bridge 有什么区别？什么时候用 host？**

<details><summary>参考答案</summary>

- bridge：容器有独立私有 IP，需要 `-p` 端口映射对外，有 NAT 开销。
- host：容器共享宿主的网络栈，无独立 IP、无需端口映射、性能更高，但端口冲突、无隔离。

host 适合：性能敏感的代理/网关、需要监听大量端口的程序。代价是端口与宿主冲突、失去网络隔离。

</details>

---

**5. 为什么容器间通信要"用容器名"而不是"写死 IP"？**

<details><summary>参考答案</summary>

因为容器的 IP 是动态分配的，容器重启/重建后 IP 可能变。而容器名是稳定的。自定义网络的内置 DNS 会把容器名动态解析成当前 IP，所以用容器名，连接字符串永远不用改。

</details>

---

**6. `docker network rm my-net` 报错 `has active endpoints`，说明什么？怎么解决？**

<details><summary>参考答案</summary>

说明还有容器连接着 `my-net`（有"活跃端点"）。

解决：先把那些容器断开（`docker network disconnect my-net 容器`）或删除，再 `docker network rm my-net`。

</details>
