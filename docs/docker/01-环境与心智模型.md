# 第 01 章 · 环境与心智模型：镜像、容器、仓库

> 第 00 章讲了 Docker 为什么存在，这一章把它落地成三个词：**镜像、容器、仓库**。
> 以及一个绕不开的细节：**容器到底是不是虚拟机**。
>
> 本章你需要记住的就一件事：**镜像是"类"，容器是"实例"，仓库是"放类的远端"。其余所有命令，都是围绕这三者的增删改查。**

---

## 01.1 三个词先分清：镜像、容器、仓库

**先说结论**：Docker 的世界里只有三个"实体"，其它一切（网络、卷、compose）都是为它们服务的。

| 名词 | 一句话 | 类比（你有 JS 背景） | 生命周期 |
|---|---|---|---|
| **镜像 image** | 只读的、固化的"代码 + 环境"打包产物 | 一个**类**，或 `npm run build` 后的 dist | 构建一次，永久不变 |
| **容器 container** | 镜像"运行起来"的一个实例 | 一个 **new 出来的实例**，或正在跑的进程 | 创建、运行、停止、删除 |
| **仓库 registry** | 存放镜像的远端服务 | **npm registry**（`npm install` 从哪来，`docker pull` 从哪来） | 一直在远端 |

用你最熟的 npm 来类比，立刻就能对上号：

```text
npm 世界                          Docker 世界
─────────────────────────────     ─────────────────────────────
npm install react               ↔  docker pull nginx
（从 registry 拉一个包）            （从 registry 拉一个镜像）

node_modules/react（装好的包）   ↔  本地镜像（拉下来/构建出来的）
（只读，你一般不改它）              （只读，你从不改它）

你写的代码 import react 并运行    ↔  docker run nginx
（把包"用起来"）                    （把镜像"跑起来"）

npm publish                     ↔  docker push
（把包推到 registry）              （把镜像推到 registry）
```

**这三者怎么串起来，看一条命令就够了：**

```bash
# 从仓库(registry) 拉镜像(image)
docker pull nginx

# 用镜像(image) 启动一个容器(container)
docker run nginx

# 把本地镜像(image) 推回仓库(registry)
docker push 你的用户名/nginx
```

**为什么要分三个词，而不是一个"包"？** 因为它们有本质不同的生命周期：

- 镜像**不可变**，构建一次，到处分发；
- 容器**可变可弃**，跑坏了删掉重来，一点不心疼；
- 仓库**永远在远端**，是分发的中转站。

把这三者分开，才谈得上"秒级回滚"（回到旧镜像）、"秒级扩容"（多起几个容器）、"秒级分发"（拉同一个镜像）。

> 一句话记住它：**镜像=类、容器=实例、仓库=远端。`pull`/`run`/`push` 就是在这三者之间搬运镜像。**

## 01.2 镜像 = 类，容器 = 实例

第 00 章已经给了这个类比，这里再往深处推一步——**因为它能解释你后面遇到的一半困惑**。

在 JS 里：

```js
class Nginx {
  constructor() {
    this.port = 80;
    this.version = '1.27';
  }
}

const a = new Nginx();   // 实例 a
const b = new Nginx();   // 实例 b

a.port = 8080;           // 改 a，不影响 b
console.log(b.port);     // 还是 80
```

Docker 里完全一样：

```text
镜像 nginx:latest（一个"类"）
   │
   ├── docker run ──▶ 容器 web-1（实例 1，监听 80）
   │
   └── docker run ──▶ 容器 web-2（实例 2，监听 80）
```

**这个类比带来的三个推论，每条都很重要：**

**推论一：一个镜像能跑出无数个容器，互不影响。** 你 `docker run nginx` 跑三次，得到三个独立容器，改一个不影响另外两个。就像 `new` 三次得到三个独立对象。

```bash
docker run -d --name web-1 nginx
docker run -d --name web-2 nginx
docker run -d --name web-3 nginx
docker ps
```

```text
CONTAINER ID   IMAGE    ...   NAMES
a1b2c3d4e5f6   nginx    ...   web-1
b2c3d4e5f6a1   nginx    ...   web-2
c3d4e5f6a1b2   nginx    ...   web-3
```

**推论二：容器挂了，镜像还在。** 你把容器 `rm` 掉，镜像 `nginx` 一分不少地躺在本地。类删不掉，删的是实例。所以"删容器"永远是安全的，不会伤到镜像。

**推论三：改容器不改镜像。** 你在容器里 `apt install` 装了个东西，容器一删就没了——**镜像没有被改动**。这一点是新手最容易误解的：以为"我在容器里装了个软件，下次 `docker run` 还在"。不，不在。镜像只读，容器里的改动是临时的（第 06 章会讲怎么把改动固化或持久化）。

```text
容器里的"改动"去哪了？
  docker run nginx           → 基于镜像，容器诞生
  在容器里 apt install curl   → 改动写在容器的"可写层"
  docker rm 容器             → 可写层随容器一起销毁
  再 docker run nginx        → 又是一个全新的容器，curl 没了
```

> 一句话记住它：**镜像是类、只读；容器是实例、可销毁。改容器从来不影响镜像，删容器从来不丢镜像。**

## 01.3 容器 vs 虚拟机：到底差在哪

**先说结论**：容器**不是**虚拟机，也不是"轻量级虚拟机"。它是**进程级别的隔离**，用的是宿主机的内核。

这是第 00 章那张图的细节展开。先记住一个最直观的区别：

```text
虚拟机：每个虚机 = 一整台假电脑（含一个完整操作系统）
  启动时间：几十秒
  内存占用：每个几个 GB
  隔离层级：硬件级（Hypervisor 模拟 CPU/内存/硬盘）

容器：每个容器 = 一个被"圈起来"的进程
  启动时间：毫秒~秒级
  内存占用：每个几 MB~几百 MB
  隔离层级：进程级（复用宿主内核，只隔离用户空间）
```

**为什么会有这么大的差距？** 因为虚拟机要"模拟一台电脑"，所以每个虚机都得装一整个操作系统（Guest OS），跑在 Hypervisor 之上。容器不模拟任何硬件，它只是让进程"以为"自己独占一台机器——实际上进程跑在宿主机的内核上，只是被 Linux 的 **namespace**（命名空间）和 **cgroup**（控制组）划了块独立的空间。

用一句话说清技术本质：

> **虚拟机虚拟的是"硬件"，容器虚拟的是"操作系统"（更准确说，是操作系统的"视图"）。**

**这带来两个直接后果：**

**后果一：容器必须和宿主同内核。** Linux 容器只能跑在 Linux 宿主上。你不能在 Windows 上直接跑 Linux 容器——所以 Windows/Mac 上装 Docker，其实是在你机器里跑了一个**轻量 Linux 虚拟机**，容器跑在那个虚拟机里。这解释了为什么 Windows 上 Docker 占的内存比 Linux 上大：那台隐形虚拟机在吃内存。

**后果二：容器的隔离性弱于虚拟机。** 因为共享内核，理论上一个容器的内核漏洞可能影响到宿主。所以：

| 需求 | 用谁 |
|---|---|
| 跑自己的服务、微服务、CI | 容器（轻、快） |
| 跑不受信任的第三方代码、要强隔离 | 虚拟机 |
| 要跑 Windows 内核、要跑不同 Linux 内核版本 | 虚拟机 |

**别把容器当虚拟机用**——这是第 00 章"反面清单"里写过的。容器最擅长的是"跑一个服务"，不是"当一台电脑玩"。

> 一句话记住它：**虚拟机虚拟硬件（每个一个 OS），容器虚拟操作系统视图（共享宿主内核）。所以容器快、轻，但隔离弱、且必须同内核。**

## 01.4 容器靠什么隔离：namespace 和 cgroup

上一节说"容器是进程级隔离"，这一节回答：**到底靠什么机制，让一个普通进程"以为自己独占一台机器"？**

**答案是两个 Linux 内核特性，Docker 只是它们的"包装工"：**

| 技术 | 解决的问题 | 类比 |
|---|---|---|
| **namespace** | 隔离"**看什么**"——每个容器看到独立的进程表、网络、文件系统、主机名 | 给每个进程一个"单间"，它只看得见自己房间的东西 |
| **cgroup** | 限制"**用多少**"——每个容器能用多少 CPU、内存、IO | 给每个进程设"配额"，防止一个吃光所有资源 |

**namespace 有七种，最常用的几个：**

| namespace | 隔离什么 | 例子 |
|---|---|---|
| PID | 进程编号 | 容器里 `ps` 只看到自己的进程，且自己常常是 PID 1 |
| NET | 网络 | 容器有独立的网卡、IP、端口（第 05 章） |
| MNT | 文件系统挂载 | 容器只看到自己的根目录（第 02/06 章） |
| UTS | 主机名 | 容器可以有独立 hostname |
| USER | 用户/组 | 容器里可以是 root，宿主上其实是普通用户 |

**这些机制不是 Docker 发明的**。Docker 2013 年做的事，本质是把 Linux 早就有的 namespace + cgroup + 联合文件系统（UnionFS）**包装成一个好用的工具**。这也是为什么说"Docker 是容器技术的普及者，不是发明者"——底层技术早在 Linux 内核里躺了十年。

**为什么知道这些有用？** 两个实际意义：

1. **你能解释"容器为什么快"**：不是黑魔法，是"启动一个被 namespace 圈起来的进程"，比"启动一整个 OS"轻了无数倍。
2. **你能理解"为什么容器里 `ps` 看到的和宿主不一样"**：因为 PID namespace 把进程表隔开了。

**一个能让你信服的实验**（需要在 Linux 宿主上，装了 Docker 的话）：

```bash
# 宿主机上看进程，能看到 nginx 的进程（因为共享内核）
docker run -d --name web nginx
ps aux | grep nginx
```

你会发现宿主的 `ps` 里**能看到** nginx 进程——这就是"容器不是虚拟机"的铁证：虚拟机的进程宿主机根本看不见，而容器的进程就是宿主内核上的普通进程，只是被 namespace 藏进了一个"单间"。

> 一句话记住它：**容器 = namespace（隔离"看什么"）+ cgroup（限制"用多少"）+ UnionFS（文件系统分层）。Docker 是包装工，不是这些技术的发明者。**

## 01.5 装 Docker：怎么确认装好了

本教程**不要求你装 Docker**——没有 Docker 也能看懂全部概念（配套的 `.mjs` 演示脚本会自动检测：没装就跳过）。但如果你想亲手跑，这里给你一个"装没装好"的自检清单。

**第一步：看 client 在不在。**

```bash
docker --version
```

装好了会看到类似（版本号会随你安装的版本变化）：

```text
Docker version 27.3.1, build ce12230
```

**第二步：看 daemon 在不在跑。** client 装好了不代表 daemon 起来了，这是新手第一道坎：

```bash
docker version
```

`docker version` 和 `docker --version` 不一样——前者会打印**两段**：Client 和 Server。Server 就是 daemon。正常时：

```text
Client: Docker Engine - Community
 Version:           27.3.1
 ...

Server: Docker Engine - Community
 Engine:
  Version:          27.3.1
  ...
```

如果 daemon 没启动，Server 段会变成错误（这是真实报错，照抄）：

```text
Client: Docker Engine - Community
 Version:           27.3.1
 ...

Server:
ERROR: Cannot connect to the Docker daemon at unix:///var/run/docker.sock. Is the docker daemon running?
```

**第三步：跑通 hello-world。** 这是官方给的最小验证镜像，能拉下来并跑出结果，说明整条链路（client → daemon → registry）都通了：

```bash
docker run hello-world
```

成功输出（节选）：

```text
Unable to find image 'hello-world:latest' locally
latest: Pulling from library/hello-world
...
Hello from Docker!
This message shows that your installation appears to be working correctly.
```

> 注意第一行 `Unable to find image 'hello-world:latest' locally`——**它不是报错**，是 Docker 告诉你"本地没这个镜像，我去仓库拉"。新手常把这一行当成错误惊慌，其实它后面紧接着就是拉取。

**平台差异一句话总结：**

| 平台 | 跑容器的地方 | 备注 |
|---|---|---|
| Linux | 本机内核直接跑 | 最"原汁原味"，无额外开销 |
| macOS | 一个轻量 Linux 虚拟机里 | Docker Desktop 自动管理 |
| Windows | WSL2 或 Hyper-V 虚拟机里 | Docker Desktop 自动管理 |

**Linux 上原生装 Docker（生产常用）的几句话：**

```bash
# 用官方脚本（curl 官网 get.docker.com）
curl -fsSL https://get.docker.com | sh

# 启动并设置开机自启
sudo systemctl start docker
sudo systemctl enable docker

# 让自己不用 sudo（加入 docker 组）
sudo usermod -aG docker $USER
# 之后要重新登录才生效
```

> 一句话记住它：**`docker --version` 看 client，`docker version` 看 daemon，`docker run hello-world` 看整条链路。看到 `Cannot connect to the Docker daemon` 就是 daemon 没起。**

## 01.6 docker CLI 的结构

**先说结论**：docker 命令行有一个非常规律的结构，记住它，90% 的命令你都能"猜"出来：

```text
docker <对象> <动作> [选项]
```

**"对象"** 是你要操作的东西：`image`（镜像）、`container`（容器）、`network`（网络）、`volume`（卷）、`buildx`（构建）等。

**"动作"** 是你对它做什么：`ls`（列出）、`rm`（删除）、`inspect`（查看详情）等。

组合起来：

```bash
docker image ls          # 列出所有镜像
docker image rm nginx    # 删除镜像 nginx
docker container ls      # 列出运行中的容器
docker container rm web  # 删除容器 web
docker network ls        # 列出网络
docker volume ls         # 列出卷
```

**为什么 `docker ps` 和 `docker container ls` 是一个东西？** 因为 Docker 早年命令只有 `docker ps`、`docker images` 这种"短命"写法，后来统一成 `docker <对象> <动作>` 的格式，但为了兼容老用户，把旧命令保留成了别名：

| 新写法（规范） | 旧写法（别名） | 都是干什么 |
|---|---|---|
| `docker container ls` | `docker ps` | 列出运行中的容器 |
| `docker container rm` | `docker rm` | 删除容器 |
| `docker image ls` | `docker images` | 列出镜像 |
| `docker image rm` | `docker rmi` | 删除镜像 |

**新手建议：先记新写法**（`docker container ...` / `docker image ...`），因为它逻辑清晰。等你看到别人用 `docker ps`，知道是同义词就行。

**一个高频的坑**：`docker rm` 删的是**容器**，`docker rmi` 删的是**镜像**（rm + image）。两个字母之差，一个删实例、一个删类。删错对象是新手最常干的事。

**看帮助的正确姿势**：任何命令不知道参数，就 `--help`：

```bash
docker run --help
```

```text
Usage:  docker run [OPTIONS] IMAGE [COMMAND] [ARG...]

Create and run a new container from an image

Options:
  -d, --detach                         Run container in background and print container ID
      --name string                    Assign a name to the container
  -e, --env list                       Set environment variables
  -p, --publish list                   Publish a container's port(s) to the host
  -v, --volume list                    Bind mount a volume
  ...
```

`--help` 输出的第一行 `Usage: docker run [OPTIONS] IMAGE [COMMAND] [ARG...]` 是这个命令的**完整语法骨架**，读懂了它，参数就都在这里。

> 一句话记住它：**`docker <对象> <动作>` 是万能结构；`ps`=`container ls`、`rmi`=`image rm`。删容器用 rm，删镜像用 rmi。**

## 01.7 Docker 架构：client / daemon / registry

**先说结论**：你敲的 `docker` 命令只是一个"传话筒"（client），真正干活的是后台常驻的 **daemon**，镜像来自远端的 **registry**。

```text
  ┌─────────┐    REST API(over unix socket/tcp)    ┌──────────┐      https       ┌──────────┐
  │ docker  │ ───────────────────────────────────▶ │  daemon  │ ───────────────▶ │ registry │
  │ (client)│ ◀─────────────────────────────────── │ (后台)   │ ◀─────────────── │ (Docker  │
  └─────────┘                                      └──────────┘                  │  Hub)    │
      你敲命令          "翻译"成 REST 请求           真正干活的进程                 放镜像的地方
```

**三个角色各干什么：**

| 角色 | 是什么 | 类比 |
|---|---|---|
| **client** | 命令行工具 `docker`，把你敲的命令翻译成 REST 请求发给 daemon | 浏览器 |
| **daemon** | 后台常驻进程 `dockerd`，管理镜像、容器、网络、卷 | 服务器 |
| **registry** | 存放镜像的远端服务（默认 Docker Hub） | 静态资源服务器 / npm registry |

**这个架构有三个你可能不知道的关键点：**

**关键点一：client 和 daemon 可以不在同一台机器。** 你本地敲 `docker`，实际操作的是远端的 daemon。这让"远程管理 Docker"成为可能：

```bash
# 把命令发给远程机器的 daemon
docker -H tcp://192.168.1.100:2375 ps
```

（生产里 2375 这个明文端口很危险，一般用 SSH 隧道或 TLS，第 08 章讲安全会提。）

**关键点二：daemon 是"单点"。** 所有容器都归这一个后台进程管。它挂了，所有 `docker` 命令都报错——这就是 01.5 里 `Cannot connect to the Docker daemon` 的来源：不是 client 坏了，是**后台那个进程没起来**。

**关键点三：registry 默认是 Docker Hub。** 你没写仓库地址时，`docker pull nginx` 实际拉的是 `docker.io/library/nginx`。这点在 02 章讲镜像名时会展开，这里先留个印象：**`nginx` 是个缩写，全称很长。**

**完整的一次 `docker run nginx` 背后发生了什么：**

```text
1. 你敲 docker run nginx
2. client 把它翻译成 REST 请求，发给 daemon
3. daemon 检查本地有没有 nginx 镜像 → 没有
4. daemon 去 registry（Docker Hub）拉 nginx 镜像
5. daemon 用镜像启动一个容器
6. daemon 把容器 id 返回给 client
7. client 把 id 打印到你的终端
```

> 一句话记住它：**client 传话、daemon 干活、registry 存镜像。daemon 是单点，挂了所有命令报 `Cannot connect to the Docker daemon`。**

## 01.8 第一个真实报错：daemon 没启动

**这是你第一个会亲手踩到的坑，值得单独一节。**

**触发条件**：装了 Docker，但 Docker Desktop（或 dockerd 服务）没启动，直接敲任意 docker 命令。

**现象**（真实报错原文）：

```text
docker: Cannot connect to the Docker daemon at unix:///var/run/docker.sock. Is the docker daemon running?
```

或者在某些环境里，前半部分稍有不同：

```text
error during connect: Get "http://%2F%2F.%2Fpipe%2Fdocker_engine/v1.45/containers/json": open //./pipe/docker_engine: The system cannot find the file specified.
```

（上面这条是 Windows 上 Docker Desktop 没起时的典型报错，`//./pipe/docker_engine` 是 Windows 命名管道路径。）

**为什么报这个错？** 回到 01.7：`docker` 命令只是 client，它要连 daemon 才能干活。daemon 没起，连接失败，于是报错。

**怎么修？**

| 平台 | 修法 |
|---|---|
| Windows / macOS | 打开 Docker Desktop 应用，等右下角图标变绿（或显示"Engine running"） |
| Linux | `sudo systemctl start docker` |

**一条排查心法**：以后你看到任何 docker 报错，先问自己一句——**"daemon 起来了没？"** 因为这是所有 docker 命令的共同前置条件，也是最低成本的排查点。

> 一句话记住它：**`Cannot connect to the Docker daemon` = 后台没起，不是命令写错。先开 Docker Desktop（或 `systemctl start docker`）再谈别的。**

---

## 01.9 拉镜像：docker pull 与镜像名

**先说结论**：`docker pull` 从 registry 把镜像下载到本地；镜像名分"仓库名"和"标签（tag）"两段，用冒号隔开。

```bash
docker pull nginx            # 等价于 docker pull nginx:latest
docker pull nginx:1.27       # 明确指定 tag 为 1.27
docker pull node:22-alpine   # tag 可以是多个单词
```

**镜像名的完整结构**（02 章会展开，这里先建立形状）：

```text
[registry/][用户名/]仓库名[:tag]
  ↑         ↑        ↑      ↑
  可省略    可省略    必填    可省略（默认 latest）
```

例如：

| 你写的 | 实际全称 | 说明 |
|---|---|---|
| `nginx` | `docker.io/library/nginx:latest` | 官方镜像，registry 和用户名都省略 |
| `nginx:1.27` | `docker.io/library/nginx:1.27` | 指定了 tag |
| `你的用户名/myapp` | `docker.io/你的用户名/myapp:latest` | 你的个人镜像 |
| `gcr.io/foo/bar` | `gcr.io/foo/bar:latest` | 指定了非默认 registry（谷歌的） |

**`latest` 是个坑，现在就要知道**：`latest` **不是"最新版本"**，它只是"没写 tag 时的默认值"。一个仓库的 `latest` 标签指向哪个镜像，完全取决于推送的人给哪个镜像打了 `latest` 这个标签。它可能不是最新，甚至可能是坏的。**生产里永远写明确 tag（`nginx:1.27`），别用 `latest`。**

**拉一个不存在的 tag 会怎样？** 真实报错：

```bash
docker pull nginx:not-exist
```

```text
docker: Error response from daemon: manifest for nginx:not-exist not found: manifest unknown: manifest unknown.
See 'docker run --help'.
```

`manifest unknown` 是 registry 的"我没这个 tag"的意思。

**看本地有哪些镜像：**

```bash
docker image ls
```

典型输出：

```text
REPOSITORY   TAG       IMAGE ID       CREATED        SIZE
nginx        latest    6139a7d6b26f   2 weeks ago    192MB
node         22-alpine 6b7f8d0c2e4b   3 weeks ago    132MB
```

三列要记住：`REPOSITORY`（仓库名）、`TAG`（标签）、`IMAGE ID`（镜像的唯一 id）。同一个镜像可能因为多个 tag 而出现多行，但 `IMAGE ID` 相同——因为内容一样（第 02 章的内容寻址）。

**删除镜像：**

```bash
docker image rm nginx
```

如果这个镜像正被容器使用（哪怕是已停止的容器），删除会失败，报错（真实原文）：

```text
Error response from daemon: conflict: unable to delete 6139a7d6b26f (must be forced) - image is being used by stopped container a1b2c3d4e5f6
```

**修法**：先删掉用它的容器，再删镜像；或者强行删（不推荐）：

```bash
docker container rm a1b2c3d4e5f6   # 先删容器
docker image rm nginx               # 再删镜像
```

> 一句话记住它：**`docker pull 名[:tag]` 从仓库拉镜像；`latest` 只是"默认 tag"，不代表最新；删镜像前先删掉用它（哪怕已停止）的容器。**

## 01.10 跑第一个容器：docker run 的魔法

**先说结论**：`docker run` 做了四件事——找镜像（没有就拉）、创建容器、启动容器、前台附着。它是 Docker 里最"重"的一个命令。

```bash
docker run nginx
```

第一次跑，你会看到它**先去拉镜像**：

```text
Unable to find image 'nginx:latest' locally
latest: Pulling from library/nginx
...
```

**注意**：`docker run` 找不到镜像时会**自动 pull**。所以你不必先 `docker pull` 再 `docker run`——一步到位。`Unable to find image ... locally` 这一行，和 01.5 一样，**不是报错**，是"本地没有，我去拉"的提示。

**nginx 是"前台阻塞"的**：`docker run nginx` 之后，终端会被 nginx 占住，一直刷日志，直到你按 `Ctrl+C`。这背后是容器默认"前台运行"——第 03 章会讲 `-d`（后台）和 `-it`（交互）。

**`docker run` 的完整语义，拆开是三步：**

```bash
docker run nginx
# 等价于
docker create nginx   # 1. 创建容器（还没跑）
docker start <容器id>  # 2. 启动容器
docker attach <容器id> # 3. 附着到容器（前台看日志）
```

第 03 章会把这几个命令逐个讲透，现在你只需要知道：**`run` = `create` + `start` + `attach`**。

**一个容易慌的场景**：`docker run nginx` 后按 `Ctrl+C`，然后 `docker ps` 一看，容器没了？

```bash
docker run nginx      # 跑起来，Ctrl+C 退出
docker ps             # 看不到 nginx
```

```text
CONTAINER ID   IMAGE     COMMAND   CREATED   STATUS    PORTS   NAMES
（空）
```

**不是容器"消失了"，是 `docker ps` 默认只显示"正在运行"的容器**。被 Ctrl+C 停掉的容器还在，只是状态变成了 `exited`。要看它：

```bash
docker ps -a          # -a = all，列出所有状态
```

```text
CONTAINER ID   IMAGE    COMMAND                  CREATED          STATUS                       PORTS   NAMES
a1b2c3d4e5f6   nginx    "/docker-entrypoint.…"   30 seconds ago   Exited (0) 3 seconds ago              boring_kowalevski
```

**看到 `NAMES` 那一列了吗**——`boring_kowalevski` 这种怪名字，是 Docker 在你没指定名字时**随机生成**的（形容词 + 科学家名）。想自己命名用 `--name`：

```bash
docker run --name web nginx
```

**`docker ps` 各列含义**：

| 列 | 含义 |
|---|---|
| `CONTAINER ID` | 容器唯一 id（其实是镜像层 id 的前 12 位） |
| `IMAGE` | 用的哪个镜像 |
| `COMMAND` | 容器启动时执行的命令 |
| `CREATED` | 创建了多久 |
| `STATUS` | 当前状态（Up = 运行中，Exited = 已停止） |
| `PORTS` | 端口映射（第 05 章） |
| `NAMES` | 容器名 |

> 一句话记住它：**`docker run` = 拉镜像 + 创建 + 启动 + 附着；`docker ps` 只看运行中的，要看全部加 `-a`；容器名不指定就随机生成。**

---

## 01.11 docker run 的核心选项

`docker run` 有一堆选项，但**新手阶段你只需要吃透四个**：`-d`、`--name`、`--rm`、`-e`。

**`-d`（detach，后台运行）**：让容器在后台跑，不占住终端：

```bash
docker run -d nginx
```

```text
a1b2c3d4e5f6   ← 打印出来的是容器 id，命令立刻返回
```

对比：不加 `-d` 时终端被占住；加了 `-d` 命令秒回，容器在后台默默跑。

**`--name`（命名）**：给容器起个名字，否则是随机怪名：

```bash
docker run -d --name web nginx
docker ps
```

```text
CONTAINER ID   IMAGE    ...   NAMES
a1b2c3d4e5f6   nginx    ...   web     ← 好认了
```

**`--rm`（用完即删）**：容器停止时自动删除。适合一次性任务，省得留下一堆 `exited` 垃圾容器：

```bash
docker run --rm alpine echo "跑完就删"
```

```text
跑完就删
```

这个容器跑完就没了，`docker ps -a` 里都找不到它。

**`-e`（环境变量）**：给容器传环境变量：

```bash
docker run -e MY_NAME=zhangsan alpine env
```

```text
PATH=/usr/local/sbin:...
HOSTNAME=...
MY_NAME=zhangsan     ← 你传的变量出现在容器环境里
```

**组合起来，一个"规范"的后台服务启动命令长这样：**

```bash
docker run -d --name web -e NODE_ENV=production nginx
```

（`-p` 端口映射和 `-v` 挂载是另外两个高频选项，分别在第 05、06 章专章讲，这里先不展开。）

> 一句话记住它：**`-d` 后台、`--name` 命名、`--rm` 用完即删、`-e` 传环境变量。这四个是 `docker run` 最常用的选项。**

## 01.12 docker info：daemon 的"自报家门"

**先说结论**：`docker info` 打印 daemon 的自我描述——存储驱动、镜像数、容器数、网络模式等。它是排查"环境对不对"的利器。

```bash
docker info
```

关键输出（节选，字段会随环境变化）：

```text
Client:
 Version:    27.3.1
 Context:    default
 ...

Server:
 Containers: 3                    ← 现在有几个容器
  Running: 1
  Paused: 0
  Stopped: 2
 Images: 10                       ← 本地有几个镜像
 Server Version: 27.3.1
 Storage Driver: overlay2         ← 存储驱动（第 02 章会讲 overlay2）
  Backing Filesystem: extfs
 Logging Driver: json-file
 ...
 Security Options:
  seccomp
  ...
 Kernel Version: 6.8.0-...        ← 宿主内核版本
 Operating System: Ubuntu 24.04   ← 宿主操作系统
 OSType: linux
 Architecture: x86_64
```

**几个值得注意的字段：**

| 字段 | 意义 |
|---|---|
| `Storage Driver: overlay2` | 镜像分层的存储驱动，现代 Docker 默认都是 overlay2 |
| `Server Version` | daemon 版本（区别于 client 版本） |
| `Kernel Version` / `Operating System` | 宿主内核和系统——再次印证"容器共享宿主内核" |
| `Containers` / `Images` | 当前环境有多少容器/镜像 |

**排查场景**：同事说他那边"Docker 行为不一样"，你先 `docker info` 对比一下 `Server Version` 和 `Storage Driver`——很多时候差异就是这两处。

> 一句话记住它：**`docker info` 看 daemon 自报家门；`Storage Driver`、`Server Version`、`Kernel Version` 是排查环境差异的三板斧。**

## 01.13 从零到跑通：完整流程演练

把前面所有小节串起来，走一遍"第一次用 Docker"的完整流程。每一步都能在你机器上复现。

**第 0 步：确认环境。**

```bash
docker --version
docker version   # 确认 daemon 也起来了
```

**第 1 步：拉一个镜像。**

```bash
docker pull nginx:1.27
```

**第 2 步：看它躺在哪了。**

```bash
docker image ls
```

```text
REPOSITORY   TAG       IMAGE ID       CREATED        SIZE
nginx        1.27      xxxxx         2 weeks ago    192MB
```

**第 3 步：跑起来（后台 + 命名 + 映射端口）。**

```bash
docker run -d --name web -p 8080:80 nginx:1.27
```

**第 4 步：确认它在跑。**

```bash
docker ps
```

```text
CONTAINER ID   IMAGE        ...   STATUS         PORTS                  NAMES
a1b2c3d4e5f6   nginx:1.27   ...   Up 5 seconds   0.0.0.0:8080->80/tcp   web
```

`PORTS` 列 `0.0.0.0:8080->80/tcp` 的意思是：宿主机 8080 端口 → 容器 80 端口（第 05 章详解）。

**第 5 步：访问它。**

```bash
curl http://localhost:8080
```

看到 nginx 的欢迎页 HTML 就对了。

**第 6 步：停掉、删掉，保持环境干净。**

```bash
docker stop web      # 停止
docker rm web        # 删除容器
docker image rm nginx:1.27   # （可选）删镜像
```

**这套流程的"肌肉记忆"顺序**，记住一个口诀：**拉（pull）→ 看（images）→ 跑（run）→ 查（ps）→ 停（stop）→ 删（rm）**。

以后你 80% 的日常操作，就是在这六步之间循环。剩下的 20%（Dockerfile 构建、网络、卷、compose）是后面几章的内容。

> 一句话记住它：**日常六步口诀：pull → images → run → ps → stop → rm。先把这套循环练熟，Docker 就算入门了。**

## 01.15 本章常见坑速查

| 坑 | 现象 | 原因 | 正确做法 |
|---|---|---|---|
| 把 `Unable to find image ... locally` 当报错 | 以为命令失败了 | 那是"本地没有，去拉"的提示，不是错 | 看它后面的 `Pulling from ...` |
| 装了 Docker 却所有命令报错 | `Cannot connect to the Docker daemon` | daemon（后台）没启动 | 开 Docker Desktop / `systemctl start docker` |
| 用 `latest` 部署 | 上线跑的是"不知道哪个版本" | `latest` 只是默认 tag，不等于最新 | 生产写死 `nginx:1.27` 这类明确 tag |
| `docker ps` 看不到刚跑的容器 | 以为容器丢了 | `ps` 只显示运行中的，被 Ctrl+C 停掉的在 exited | 用 `docker ps -a` 看全部 |
| `docker rm` 想删镜像 | 报 `No such container` | `rm` 删的是容器，镜像用 `rmi` | 删镜像用 `docker image rm` |
| 删镜像报 conflict | `conflict: unable to delete ... is being used by stopped container` | 有（已停止的）容器还在用它 | 先 `docker rm` 容器，再删镜像 |
| 以为容器是虚拟机 | 想在容器里"装个系统玩玩" | 容器是进程级隔离，不是完整电脑 | 容器跑服务；要完整系统用虚拟机 |
| 以为改容器能保存 | 容器删了改动没了 | 镜像只读，改动在容器可写层，随容器销毁 | 持久化用卷（第 06 章），改动固化用 commit（第 03 章） |
| 没写 `--name` 找不到容器 | 容器名是一堆随机词 | Docker 默认随机命名 | `docker run --name web nginx` |
| 后台跑却看不到日志 | `docker run -d` 后没输出 | `-d` 把输出藏到后台了 | `docker logs web` 看日志（第 03 章） |

## 01.16 本章小结

- **三个实体**：镜像（只读的类）、容器（可销毁的实例）、仓库（放镜像的远端）。
- **容器 ≠ 虚拟机**：容器虚拟的是"操作系统视图"，共享宿主内核；虚拟机虚拟的是"硬件"，每个带一个完整 OS。所以容器快、轻，但隔离弱、必须同内核。
- **隔离机制**：namespace（隔离"看什么"）+ cgroup（限制"用多少"）+ UnionFS（分层文件系统）。
- **CLI 结构**：`docker <对象> <动作>`；`ps` = `container ls`，`rmi` = `image rm`。
- **架构**：client（命令行）→ daemon（后台进程）→ registry（远端）。daemon 是单点。
- **第一个报错**：`Cannot connect to the Docker daemon` = daemon 没起。
- **镜像名**：`[registry/][用户/]仓库名[:tag]`；`latest` 是默认 tag 不是最新版。
- **`docker run`** = 拉镜像 + create + start + attach；`docker ps` 只看运行中，`-a` 看全部。
- **核心选项**：`-d` 后台、`--name` 命名、`--rm` 用完即删、`-e` 传环境变量。
- **删容器用 `rm`，删镜像用 `rmi`**，别搞混；删镜像前先删容器。

## 01.17 动手练习

**1. 下面这条命令，如果本地没有 nginx 镜像，会发生什么？第一行输出是什么？**

```bash
docker run nginx
```

<details><summary>参考答案</summary>

会先自动拉取镜像。第一行输出是：

```text
Unable to find image 'nginx:latest' locally
```

这一行**不是报错**，是"本地没有，去 registry 拉"的提示，紧接着是 `Pulling from library/nginx`。

</details>

---

**2. `docker ps` 看不到我刚 `docker run nginx` 又 `Ctrl+C` 退出的容器，为什么？怎么看到它？**

<details><summary>参考答案</summary>

`docker ps` 默认只显示**正在运行**的容器。Ctrl+C 把容器停掉了，状态变成 `exited`，所以不在列表里。

用 `docker ps -a`（`-a` = all）就能看到所有状态（含 exited）的容器。

</details>

---

**3. 删容器用哪个命令？删镜像用哪个命令？为什么容易混？**

<details><summary>参考答案</summary>

- 删容器：`docker rm 容器名`（或 `docker container rm 容器名`）
- 删镜像：`docker rmi 镜像名`（或 `docker image rm 镜像名`）

容易混是因为两个命令只差一个 `i`。记法：`rmi` 里的 `i` 是 image 的 `i`。

</details>

---

**4. 你在容器里 `apt install curl` 装了个工具，然后 `docker rm` 删掉容器，再 `docker run` 同一个镜像，curl 还在吗？为什么？**

<details><summary>参考答案</summary>

**不在。** 镜像只读，你在容器里的改动写在容器的"可写层"，随容器一起销毁。重新 `docker run` 出来的是基于镜像的全新容器，没有你之前装的 curl。

要长期保留，要么用卷（第 06 章），要么把安装步骤写进 Dockerfile 重新构建镜像（第 04 章）。

</details>

---

**5. 装了 Docker，敲 `docker version` 报 `Cannot connect to the Docker daemon`，这说明什么？怎么修？**

<details><summary>参考答案</summary>

说明 **client 装好了，但 daemon（后台进程）没启动**。

- Windows / macOS：打开 Docker Desktop，等图标变绿。
- Linux：`sudo systemctl start docker`。

这是所有 docker 命令的公共前置条件，先解决它再谈别的。

</details>

---

**6. 说清楚"容器为什么快"——它和虚拟机最本质的区别是什么？**

<details><summary>参考答案</summary>

最本质区别：**虚拟机虚拟的是硬件**（每个虚机跑一个完整 Guest OS，Hypervisor 模拟 CPU/内存/硬盘）；**容器虚拟的是操作系统视图**（复用宿主内核，用 namespace + cgroup 把进程"圈"进独立空间）。

所以容器启动 = 启动一个被圈起来的进程，毫秒级；虚拟机启动 = 启动一整个 OS，几十秒。代价是容器隔离性弱、且必须与宿主同内核。

</details>
