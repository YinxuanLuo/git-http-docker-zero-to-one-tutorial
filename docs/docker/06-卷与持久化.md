# 第 06 章 · 卷与持久化：数据比容器活得更久

> 前面几章你反复听到一句话："容器删了数据就没了"。这一章就解决它——怎么让数据**比容器活得更久**。
>
> 本章你需要记住的就一件事：**容器的可写层是"一次性"的，数据要持久化必须放进"卷"（volume）或"绑定挂载"（bind mount）。命名卷适合生产数据，bind mount 适合开发热更。**

---

## 06.1 容器的数据为什么"用完即丢"

**先说结论**：容器是**可随意销毁重建**的，它自己的文件系统（可写层）随容器一起销毁。这是特性，不是 bug——但前提是你要把"该留的数据"放到卷里。

**回到第 02 章的分层模型：**

```text
镜像（只读，永不丢）
  ├── 第 3 层：应用
  ├── 第 2 层：依赖
  └── 第 1 层：基础系统

容器启动时，最上面加一层：
  ├── 可写层（container layer）  ← 你所有写入都在这
  └── 镜像的只读层

容器删除时：
  可写层被销毁 ❌（里面的数据没了）
  镜像的只读层原封不动 ✓
```

**所以一个残酷但重要的事实：**

```bash
docker run -d --name db postgres:16      # 起个数据库
# 往里写数据……
docker rm db                              # 删掉容器
docker run -d --name db2 postgres:16      # 再起一个
# 数据没了！因为数据写在 db 的可写层，随 db 一起删了
```

**数据库、上传的文件、用户数据——这些都必须持久化。** 而"持久化"的本质就是：**把数据放到容器可写层之外的地方**。这个地方就是"卷"。

**什么该持久化、什么不该：**

| 数据 | 该放哪 |
|---|---|
| 数据库文件 | 卷（volume） |
| 用户上传的文件 | 卷或对象存储 |
| 应用日志（要保留的） | 卷或日志系统 |
| 应用的代码、配置 | 镜像里（构建时 COPY 进去） |
| 临时缓存、临时文件 | 容器可写层（丢了无所谓） |

> 一句话记住它：**容器可写层随容器销毁，是"一次性"的。要留的数据（数据库、上传文件）必须放卷；不该留的（缓存、临时文件）才留在可写层。**

---

## 06.2 两种持久化方式：bind mount 和 volume

**先说结论**：Docker 有两种把"外部存储"挂进容器的方式——**bind mount**（挂宿主的某个目录）和 **volume**（Docker 自己管理的存储）。它们都能持久化，但定位不同。

| 对比项 | bind mount | volume（卷） |
|---|---|---|
| 存哪 | 宿主的任意目录（你指定路径） | Docker 管理的目录（`/var/lib/docker/volumes/`） |
| 谁管理 | 你（像普通目录） | Docker |
| 可移植性 | 依赖宿主路径 | 好（脱离宿主路径） |
| 典型场景 | **开发时热更源码** | **生产存数据** |
| 性能 | 略低（依赖宿主文件系统） | 略高（Docker 优化） |

**一句话区分**：

> **bind mount = 把宿主的文件夹"借"给容器；volume = Docker 开一块地，专给容器存数据。**

**两者的命令对照：**

```bash
# bind mount：-v 宿主绝对路径:容器路径
docker run -v "$(pwd)/src:/app" myapp

# volume：-v 卷名:容器路径
docker run -v pgdata:/var/lib/postgresql/data postgres:16
```

看出区别了吗？`-v` 冒号左边：**是路径（带 `/`）就是 bind mount，是名字（不带 `/`）就是 volume**。

> 一句话记住它：**bind mount 挂宿主目录（开发热更），volume 是 Docker 管理的卷（生产存数据）。`-v` 冒号左边带 `/` 是 bind，不带 `/` 是卷。**

---

## 06.3 bind mount：把宿主的目录"借"给容器

**先说结论**：bind mount 把宿主机的一个**绝对路径**挂到容器里，两边**实时同步**。改宿主的文件，容器里立刻看到；改容器里的，宿主也立刻变。

```bash
docker run -v "$(pwd)/src:/app" myapp
# 把当前目录的 src 文件夹，挂到容器的 /app
```

**它解决的最经典场景：开发热更。** 你在本机写代码（`src/`），不用每次改完都重新 build 镜像，容器直接读你最新代码：

```text
本机 src/ 目录
     │  bind mount（实时同步）
     ▼
容器 /app ── 就是你的 src/，你改一行代码，容器里立刻生效
```

**三个关键点：**

**点一：必须用绝对路径。** 相对路径不行，会报错：

```bash
docker run -v ./src:/app myapp     # ❌ 相对路径
```

```text
docker: Error response from daemon: invalid mount config for type "bind": bind source path does not exist: /src.
```

（Windows 上 `$(pwd)` 展开的路径格式也可能有问题，建议用完整路径。）

**点二：宿主目录不存在时会怎样？** bind mount 下，Docker **不会**自动创建宿主目录（这点和 volume 相反），会报错：

```text
docker: Error response from daemon: invalid mount config for type "bind": bind source path does not exist: /path/that/does/not/exist.
```

**点三：权限问题。** bind mount 挂进去的文件，权限沿用宿主的。容器里的进程（可能以非 root 跑）读不到宿主目录，就会权限报错。这是 bind mount 在开发环境最烦人的坑。

**bind mount 适合什么？**

| 场景 | 说明 |
|---|---|
| 开发时挂源码 | 改代码立刻生效 |
| 挂配置文件 | 宿主改配置，容器重启读新配置 |
| 挂日志目录 | 让日志落到宿主方便查看 |

> 一句话记住它：**bind mount = 挂宿主绝对路径，两边实时同步，最适合开发热更。必须绝对路径；宿主目录不存在会报错；权限沿用宿主，容易踩权限坑。**

---

## 06.4 volume（命名卷）：Docker 管理的持久存储

**先说结论**：volume 是 Docker 自己管理的一块存储（存在 `/var/lib/docker/volumes/`），你只需要给它起个名字。这是**生产环境存数据的标准做法**。

```bash
# 创建命名卷
docker volume create pgdata

# 挂载
docker run -v pgdata:/var/lib/postgresql/data postgres:16
```

**volume 的三个优势（相对 bind mount）：**

**优势一：Docker 管理，不依赖宿主路径。** 你不用关心数据物理存在宿主哪里，只要记卷名 `pgdata`。换台机器、换宿主路径都不影响。

**优势二：自动创建。** 用 `-v pgdata:...` 时，如果 `pgdata` 卷不存在，Docker **自动创建**它（bind mount 不会自动建宿主目录）。

**优势三：性能好、可移植。** 卷可以被 `docker volume` 管理、备份、迁移（`docker volume` 命令族）。

**看卷列表和详情：**

```bash
docker volume ls
```

```text
DRIVER    VOLUME NAME
local     pgdata
```

```bash
docker volume inspect pgdata
```

```json
[
  {
    "Name": "pgdata",
    "Driver": "local",
    "Mountpoint": "/var/lib/docker/volumes/pgdata/_data"
  }
]
```

`Mountpoint` 就是数据真正存放的位置（宿主的这个路径），但**日常你不需要碰它**，用卷名就够了。

**什么时候用 volume？**

| 场景 | 说明 |
|---|---|
| 数据库数据 | postgres/mysql 的 data 目录 |
| 应用持久数据 | 上传文件、状态 |
| 需要备份/迁移的数据 | volume 有完整的管理命令 |

> 一句话记住它：**volume 是 Docker 管理的持久存储（`/var/lib/docker/volumes/`），生产存数据的标准做法。用 `-v 卷名:路径` 自动创建，`docker volume ls/inspect` 管理。**

## 06.5 匿名卷 vs 命名卷

**先说结论**：`-v 容器路径`（只写右边、不写卷名）会创建一个**匿名卷**；`-v 卷名:容器路径` 是**命名卷**。匿名卷能用，但管理起来一团糟。

```bash
# 命名卷：有名字，好管理
docker run -v pgdata:/data postgres:16

# 匿名卷：没名字，Docker 起个随机 ID
docker run -v /data postgres:16
```

**匿名卷的后果**：你 `docker volume ls` 会看到一堆乱码名字的卷：

```text
DRIVER    VOLUME NAME
local     8f3a2b1c9d4e...   ← 匿名卷，不知道是哪个容器的
local     2b1c9d4e8f3a...   ← 又一个匿名卷
local     pgdata             ← 命名卷，一眼认得
```

**匿名卷为什么会堆积？** 因为 `docker rm 容器` **默认不删卷**（包括匿名卷）。于是每次 `docker run -v /data` 都留一个匿名卷，越积越多，占满磁盘。

**清理孤儿卷：**

```bash
docker volume prune
```

```text
WARNING! This will remove anonymous local volumes not used by at least one container.
Are you sure you want to continue? [y/N] y
Deleted Volumes:
8f3a2b1c9d4e...
2b1c9d4e8f3a...
```

**什么时候会用到匿名卷？** 其实大多数情况下你**不想**用它。它主要用于"某些镜像的 Dockerfile 里声明了 `VOLUME /data`"，Docker 自动给那个路径挂匿名卷。日常你主动写 `-v /data`（不带卷名）的情况很少。

**结论**：**主动用命名卷，避免匿名卷堆积；定期 `docker volume prune` 清理。**

> 一句话记住它：**`-v 路径` 是匿名卷（随机名，难管理），`-v 卷名:路径` 是命名卷（好管理）。`docker rm` 不删卷，匿名卷会堆积，用 `docker volume prune` 清理。**

## 06.6 -v 和 --mount：两种写法

**先说结论**：`-v` 和 `--mount` 都能挂载，`-v` 是短写法（简洁但容易写错），`--mount` 是长写法（显式、清晰、不易错）。**新手建议用 `-v` 熟悉，生产脚本用 `--mount` 更严谨。**

**`-v` 写法（三个字段，用冒号分隔）：**

```bash
docker run -v 卷名或宿主路径:容器路径[:选项] 镜像
```

问题：字段靠位置和冒号区分，一旦路径里含冒号（少见）或写错就难排查。

**`--mount` 写法（键值对，显式）：**

```bash
docker run --mount type=bind,src=/host/path,dst=/app 镜像
docker run --mount type=volume,src=pgdata,dst=/data 镜像
docker run --mount type=volume,src=pgdata,dst=/data,readonly 镜像
```

**两者对比：**

| 对比 | `-v` | `--mount` |
|---|---|---|
| 简洁 | ✅ 短 | ❌ 长 |
| 显式 | ❌ 靠位置猜 | ✅ 键值对，一目了然 |
| 可读性 | 一般 | 好 |
| 是否推荐生产 | 可以 | **推荐**（尤其复杂挂载） |

**`--mount` 的 type 三选一：**

| type | 对应 |
|---|---|
| `bind` | bind mount（宿主路径） |
| `volume` | 命名卷 |
| `tmpfs` | 内存临时盘（重启即失，第 08 章提） |

**一个 `--mount` 独有的能力：`readonly` 只读挂载。** 让容器只能读、不能写这个挂载点（安全）：

```bash
docker run --mount type=volume,src=pgdata,dst=/data,readonly postgres:16
```

> 一句话记住它：**`-v` 短但靠位置猜，`--mount` 长但键值对清晰。复杂/生产挂载用 `--mount`（还能加 `readonly`）。**

## 06.7 数据生命周期：容器删了，数据还在吗

**先说结论**：这是本章最核心的一张表。答案取决于你的数据放在哪。

| 数据在哪 | 删容器（`docker rm`）后 | 删卷（`docker volume rm`）后 |
|---|---|---|
| 容器可写层 | ❌ 没了 | — |
| 匿名卷 | ✅ 还在（但变孤儿） | ❌ 没了 |
| 命名卷 | ✅ 还在 | ❌ 没了 |
| bind mount（宿主目录） | ✅ 还在（在宿主目录里） | —（宿主目录要手动删） |

**几个关键结论：**

**结论一：`docker rm` 默认不删卷。** 不管匿名卷还是命名卷，`docker rm 容器` 都不删它们。要连卷一起删，得显式加 `-v`：

```bash
docker rm -v 容器        # 删容器，同时删它挂的匿名卷
```

（注意：`-v` 只删**匿名卷**，命名卷不会被 `docker rm -v` 删掉。）

**结论二：命名卷删容器后数据还在，重新挂载就"回来了"。** 这是数据库容器的核心用法：

```bash
docker run -d --name db -v pgdata:/var/lib/postgresql/data postgres:16
# 写数据……
docker rm db                                    # 删容器
docker run -d --name db2 -v pgdata:/var/lib/postgresql/data postgres:16
# 数据还在！因为数据在卷 pgdata 里，不在容器里
```

配套脚本把这段跑得很清楚：

```bash
node examples/docker/06-卷与持久化.mjs
```

```text
==================== 2. 命名卷（volume） ====================
  docker volume create pgdata → 创建了一个独立于容器的存储
  容器 db-1 挂载卷 pgdata 到 /var/lib/postgresql/data
  db-1 写入了数据（实际写到卷 pgdata 里）
  docker rm db-1 之后，卷 pgdata 还在：
  卷 pgdata 里的数据: {"pg_data":"数据库文件…"}
  容器 db-2 挂载同一个卷 pgdata，数据"回来"了： {"pg_data":"数据库文件…"}
```

**结论三：`docker compose down -v` 会连卷一起删！** 这个 `-v` 很危险，第 07 章会专门警告。

> 一句话记住它：**`docker rm` 不删卷；数据在卷里，删容器后重挂载就"回来"；`docker rm -v` 只删匿名卷，命名卷要 `docker volume rm` 删。**

## 06.8 共享数据：多个容器挂同一个卷

**先说结论**：一个卷可以同时挂到多个容器，这是"容器间共享数据"的正规方式（比"容器间直接读写对方文件"可靠得多）。

```bash
# 两个容器挂同一个卷
docker run -d --name writer -v shared:/data alpine sleep 3600
docker run -d --name reader -v shared:/data alpine sleep 3600
```

writer 往 `/data` 写，reader 在 `/data` 能读到——因为它们挂的是**同一块存储**。

**典型场景：**

| 场景 | 说明 |
|---|---|
| 一个应用 + 一个日志收集器 | 应用写日志到卷，收集器读卷 |
| 主程序 + 备份进程 | 备份进程挂同一卷做备份 |

**注意一个并发坑**：多个容器同时**写**同一个文件，会有竞态（和多个进程写同一个文件一样的问题）。所以"共享卷"更适合"一个写、一个读"的模式，而不是"多个都写"。

> 一句话记住它：**一个卷可挂多个容器，实现数据共享；适合"一个写、多个读"的模式，多个都写会有竞态。**

## 06.9 卷命令速查

**先说结论**：卷的命令就这些，一次记全。

```bash
docker volume ls            # 列出所有卷
docker volume create 卷名    # 创建卷
docker volume inspect 卷名   # 看卷详情（含 Mountpoint）
docker volume rm 卷名        # 删除卷
docker volume prune          # 清理所有"没被容器使用"的卷
```

**一个真实报错**：删除一个还在被容器使用的卷：

```bash
docker volume rm pgdata    # 假设有容器还挂着它
```

```text
Error response from daemon: remove pgdata: volume is in use - [a1b2c3d4e5f6]
```

`volume is in use` = 有容器还挂着它。先删容器（或断开挂载），再删卷。

**备份一个卷的常用技巧**（用临时容器 + tar）：

```bash
# 备份：把 pgdata 卷的内容打包到宿主当前目录
docker run --rm -v pgdata:/data -v "$(pwd)":/backup alpine \
  tar czf /backup/pgdata-backup.tar.gz -C /data .

# 恢复：从备份文件解压回卷
docker run --rm -v pgdata:/data -v "$(pwd)":/backup alpine \
  tar xzf /backup/pgdata-backup.tar.gz -C /data
```

> 一句话记住它：**卷命令：ls/create/inspect/rm/prune。删在用卷报 `volume is in use`；备份用临时容器 + tar（`--rm` 用完即删）。**

## 06.10 本章常见坑速查

| 坑 | 现象 | 原因 | 正确做法 |
|---|---|---|---|
| 数据放容器里，删容器后没了 | 重启容器数据丢失 | 数据写在可写层，随容器销毁 | 数据放卷（volume） |
| bind mount 用相对路径 | `bind source path does not exist` | bind mount 要绝对路径 | 用 `$(pwd)/src` 或完整路径 |
| 宿主目录不存在直接挂 | `bind source path does not exist` | bind mount 不自动建宿主目录 | 先 `mkdir`，或用卷（自动建） |
| 匿名卷堆积 | `docker volume ls` 一堆乱码卷 | `-v /data` 创建匿名卷，且 rm 不删卷 | 用命名卷；定期 `docker volume prune` |
| 删在用卷报错 | `volume is in use - [容器id]` | 还有容器挂着这个卷 | 先删容器，再删卷 |
| 以为 `docker rm` 会删卷 | 卷还在，数据占着磁盘 | rm 默认不删卷 | 显式 `docker volume rm` / `prune` |
| 多个容器写同一文件 | 数据错乱 | 并发写竞态 | 改成"一写多读"，或加锁 |
| `compose down` 丢数据 | 数据没了 | `down -v` 连卷删了 | 谨慎用 `-v`（第 07 章） |

## 06.11 本章小结

- **容器可写层是"一次性"的**：随容器销毁，数据要持久化必须放卷。
- **两种持久化**：bind mount（挂宿主目录，开发热更）vs volume（Docker 管理，生产存数据）。
- **bind mount**：绝对路径、两边实时同步、不自动建宿主目录、权限沿用宿主。
- **volume**：Docker 管理、自动创建、可备份迁移，生产标准。
- **匿名卷 vs 命名卷**：`-v /data` 匿名（随机名难管理），`-v 卷名:/data` 命名（推荐）。
- **`-v` vs `--mount`**：`-v` 短，`--mount` 键值对清晰，还能 `readonly`。
- **数据生命周期**：`docker rm` 不删卷；命名卷删容器后数据还在；`rm -v` 只删匿名卷。
- **共享数据**：一个卷挂多个容器，适合"一写多读"。
- **卷命令**：`ls/create/inspect/rm/prune`；删在用卷报 `volume is in use`。

## 06.12 动手练习

**1. 你的数据库容器删掉重开，数据全没了，为什么？怎么避免？**

<details><summary>参考答案</summary>

因为数据写在了容器的**可写层**，容器删除时随容器一起销毁。

避免：把数据库数据目录挂到卷（volume）：

```bash
docker run -d -v pgdata:/var/lib/postgresql/data postgres:16
```

这样数据在卷 `pgdata` 里，删容器后数据还在，重开挂同一卷数据就"回来"了。

**2. `-v /data` 和 `-v pgdata:/data` 有什么区别？各自有什么问题？**

<details><summary>参考答案</summary>

- `-v /data`：创建**匿名卷**（Docker 起随机名），数据能持久但难管理，`docker rm` 后变成孤儿卷堆积。
- `-v pgdata:/data`：**命名卷**，有名字好管理。

日常推荐命名卷；匿名卷主要用于镜像 Dockerfile 里声明 `VOLUME` 的场景，且要定期 `docker volume prune` 清理。

**3. `-v $(pwd)/src:/app` 和 `-v pgdata:/app` 分别是什么挂载？怎么从写法上区分？**

<details><summary>参考答案</summary>

- `-v $(pwd)/src:/app`：**bind mount**（冒号左边是宿主路径，带 `/`）。
- `-v pgdata:/app`：**volume**（冒号左边是卷名，不带 `/`）。

区分规则：冒号左边带 `/` 是 bind mount，不带 `/` 是卷。

</details>

---

**4. `docker rm` 会删掉卷吗？`docker rm -v` 呢？**

<details><summary>参考答案</summary>

- `docker rm 容器`：**不删卷**（匿名卷和命名卷都不删）。
- `docker rm -v 容器`：删容器时，**只删它挂的匿名卷**，命名卷仍不删。

命名卷要删除，用 `docker volume rm 卷名`。

</details>

---

**5. `docker volume rm pgdata` 报 `volume is in use - [xxx]`，怎么处理？**

<details><summary>参考答案</summary>

说明还有容器挂着 `pgdata` 卷。先 `docker rm` 那些容器（或 `docker volume` 断开），再删卷。

</details>

---

**6. 开发时想"改代码立刻生效，不用重新 build 镜像"，用哪种挂载？写出来。**

<details><summary>参考答案</summary>

用 **bind mount**，把宿主的源码目录挂到容器里：

```bash
docker run -v "$(pwd)/src:/app" myapp
```

两边实时同步，改 `src/` 里的代码，容器里立刻生效。注意：bind mount 要绝对路径，且宿主目录要先存在。

</details>
