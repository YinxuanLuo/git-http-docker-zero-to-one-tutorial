# 第 09 章 · 实战：把一个 Node 应用完整容器化并编排

> 前面 8 章把 Docker 的零件都讲完了。这一章把它们**拼成一个完整可跑的项目**：一个 Node 应用，从"裸机能跑"到"Dockerfile 容器化"再到"compose 编排多服务"。
>
> 本章你需要记住的就一件事：**容器化的完整闭环是——写代码 → 写 Dockerfile → `docker build` 成镜像 → 多服务写 compose → `docker compose up` 一键起 → `down` 一键清。前面所有知识点，都在这个闭环里汇合。**

---

## 09.1 实战目标：一个完整的 Node 应用

**先说结论**：本章实战做的东西，是一个"带健康检查的 Node API + PostgreSQL 数据库"的小项目，完整走一遍容器化 + 编排。

**应用的功能**：一个极简的 HTTP API，提供：

| 路由 | 返回 | 用途 |
|---|---|---|
| `GET /` | `{"message":"hello from node app"}` | 主接口 |
| `GET /health` | `{"status":"ok", ...}` | 健康检查（供 Docker healthcheck 用） |

**为什么选这个应用？** 因为它麻雀虽小、五脏俱全——正好能演示：Dockerfile、多阶段构建、健康检查、compose 编排、卷持久化、服务间通信（连数据库）。而代码短到你能看懂每一行。

**本机的完整代码**（Node 内置模块，零依赖，`node server.js` 就能跑）：

```js
// server.js —— 一个零依赖的迷你 Node API
import { createServer } from 'node:http';

const server = createServer((req, res) => {
  if (req.url === '/health') {
    res.writeHead(200, { 'content-type': 'application/json' });
    res.end(JSON.stringify({ status: 'ok', time: new Date().toISOString() }));
    return;
  }
  res.writeHead(200, { 'content-type': 'application/json' });
  res.end(JSON.stringify({ message: 'hello from node app' }));
});

server.listen(3000, () => console.log('listening on 3000'));
```

**先在本机跑一遍，确认应用本身没问题**（这一步很重要——容器化之前，先保证裸机能跑）：

```bash
node server.js
curl http://localhost:3000/health
```

```text
{"status":"ok","time":"2026-10-12T14:58:53.911Z"}
```

**配套脚本把"应用本身能跑"这步演示出来了**：

```bash
node examples/docker/09-node-app容器化.mjs
```

```text
==================== 1. 要容器化的应用本身 ====================
  应用已在 127.0.0.1:49275 启动
  GET /health → {"status":"ok","time":"..."}
  GET /      → {"message":"hello from node app"}
  应用已关闭（这证明：本地裸机能跑）
  Docker 要解决的，就是"让这个应用在任何机器上都这样跑"，不用现装环境。
```

> 一句话记住它：**容器化的第一步，永远是"先让应用在裸机上能跑"。裸机都跑不通，容器化只会放大问题。这一步做了，才有下一步的 Dockerfile。**

## 09.2 写 Dockerfile

**先说结论**：给这个应用写 Dockerfile，综合运用第 04 章（指令）和第 08 章（工程化）的知识。

```dockerfile
# 09 章实战：一个会被 compose 编排的 Node 应用
FROM node:22-alpine
WORKDIR /app

# 先复制依赖清单 → 让 npm install 这一层可缓存
COPY package*.json ./
RUN npm install --omit=dev

# 再复制源码
COPY . .

ENV NODE_ENV=production
EXPOSE 3000
CMD ["node", "server.js"]
```

**逐条回顾，这是第 04 章 + 第 08 章知识的综合运用：**

| 指令 | 用到了哪章的知识 | 为什么这么写 |
|---|---|---|
| `FROM node:22-alpine` | 08.5 基础镜像 | alpine 小，生产省体积 |
| `WORKDIR /app` | 04.6 | 统一相对路径 |
| `COPY package*.json ./` 在 install 前 | 04.13 / 08.3 | 缓存依赖安装 |
| `RUN npm install --omit=dev` | 04.4 | 只装生产依赖 |
| `COPY . .` 放后面 | 04.13 | 源码常变，放后面 |
| `ENV NODE_ENV=production` | 04.7 | 生产模式 |
| `EXPOSE 3000` | 04.8 | 声明端口 |
| `CMD ["node", "server.js"]` | 04.9 | exec 形式，信号直达 |

**这个文件作为示例文件存在**：`examples/docker/09-app/Dockerfile`。

**一个值得注意的点**：这个应用**没有构建步骤**（没有 TypeScript、没有打包），所以这里**不需要多阶段构建**。多阶段构建是"有构建产物"时才需要（第 08 章）。如果你的应用是 TypeScript 或需要 `npm run build`，才用多阶段。**别为了用多阶段而多阶段——按需选择。**

> 一句话记住它：**Dockerfile 是第 04、08 章的实战落点：alpine + 依赖清单先 COPY + 只装生产依赖 + exec 形式 CMD。没有构建步骤就不需要多阶段，按需选择。**

## 09.3 写 .dockerignore

**先说结论**：构建之前，先写 `.dockerignore`，防止 node_modules、.git、日志等被塞进构建上下文。

```dockerignore
# .dockerignore：构建时忽略这些，别让它们进构建上下文
# 好处：构建上下文变小 → 上传快；node_modules 不会污染镜像里的依赖

node_modules
npm-debug.log
.git
.gitignore
.env
*.md
Dockerfile
docker-compose.yml
.dockerignore
```

**为什么这个文件不能省？**（第 08 章 08.4 讲过，这里落到实战）

1. 项目目录里有 `node_modules`（可能几百 MB），不 ignore 的话全被打包上传，build 卡在 `Sending build context`。
2. `Dockerfile` 和 `docker-compose.yml` 本身不需要进镜像（它们是"构建配方"，不是"运行时内容"）。
3. `.env` 可能含密码，绝不能进构建上下文。

**这个文件作为示例文件存在**：`examples/docker/09-app/.dockerignore`。

**怎么验证它生效了？** 构建时看上下文大小：

```bash
docker build -t myapp .
```

```text
Sending build context to Docker daemon  2.1MB    ← 小，说明 .dockerignore 生效
```

对比没写 `.dockerignore` 时，这行会是几百 MB。

> 一句话记住它：**`.dockerignore` 是构建前的"防火墙"，排除 node_modules/.git/.env，让上下文从几百 MB 降到几 MB。写 Dockerfile 的同时就写它。**

## 09.4 构建镜像

**先说结论**：把 Dockerfile 变成镜像，用 `docker build -t 名字:tag .`。然后 `docker image ls` 确认，`docker run` 验证。

```bash
# 构建（在包含 Dockerfile 的目录下）
docker build -t myapp:1.0 .
```

```text
[+] Building 3.1s (8/8) FINISHED
 => [1/5] FROM docker.io/library/node:22-alpine
 => [2/5] WORKDIR /app
 => [3/5] COPY package*.json ./
 => [4/5] RUN npm install --omit=dev
 => [5/5] COPY . .
 => exporting to image
 => => naming to docker.io/library/myapp:1.0
```

**确认镜像在：**

```bash
docker image ls
```

```text
REPOSITORY   TAG       IMAGE ID       CREATED         SIZE
myapp        1.0       6139a7d6b26f   1 minute ago    132MB
```

**跑起来验证：**

```bash
docker run -d --name app -p 3000:3000 myapp:1.0
curl http://localhost:3000/health
```

```text
{"status":"ok","time":"..."}
```

**验证没问题后，清理：**

```bash
docker stop app
docker rm app
```

**一个常见报错**（构建时 `COPY` 找不到文件，第 04 章 04.5 讲过）：

```text
COPY failed: file not found in build context or excluded by .dockerignore: stat package.json: file does not exist
```

触发条件：`docker build` 的上下文目录里没有 `package.json`（比如你 `cd` 错了目录），或它被 `.dockerignore` 排除了。

> 一句话记住它：**构建三连：`docker build -t 名:tag .` → `image ls` 确认 → `docker run` 验证。看到 `COPY failed: file not found` 先查上下文目录对不对、.dockerignore 有没有误排除。**

## 09.5 写 docker-compose.yml：编排多服务

**先说结论**：单容器跑通了，现在加入 PostgreSQL 数据库，用 compose 把"应用 + 数据库"编排起来。

```yaml
# 09 章实战：app + db 两个服务的编排
services:
  app:
    build: .              # 用当前目录的 Dockerfile 构建
    ports:
      - "3000:3000"       # 宿主机 3000 → 容器 3000
    environment:
      NODE_ENV: production
      DATABASE_URL: postgres://app:secret@db:5432/app   # 用容器名 db 访问
    depends_on:
      - db                # 先启动 db，再启动 app（但不保证 db 已就绪）

  db:
    image: postgres:16    # 用现成镜像，不用自己构建
    environment:
      POSTGRES_USER: app
      POSTGRES_PASSWORD: secret
      POSTGRES_DB: app
    volumes:
      - pgdata:/var/lib/postgresql/data   # 命名卷：数据独立于容器

volumes:
  pgdata:                 # 声明命名卷，由 compose 管理
```

**这份文件综合了哪些章节的知识：**

| 片段 | 章节 | 知识点 |
|---|---|---|
| `app.build: .` | 07.10 | 自己的应用本地构建 |
| `ports: "3000:3000"` | 05.5 | 端口映射 |
| `DATABASE_URL: ...@db:5432` | 05.7 / 07.4 | 用服务名 db 互访（DNS） |
| `depends_on: - db` | 07.8 | 启动顺序 |
| `db.image: postgres:16` | 07.10 | 第三方服务用现成镜像 |
| `volumes: pgdata:...` | 06.4 / 07.5 | 命名卷持久化 |
| `volumes.pgdata` | 07.5 | 声明卷 |

**这个文件作为示例文件存在**：`examples/docker/09-app/docker-compose.yml`。

> 一句话记住它：**compose 是第 05、06、07 章的实战落点：app 用 build + 端口映射，db 用现成镜像 + 命名卷，两者通过服务名 + 网络互访。**

## 09.6 启动、验证、清理

**先说结论**：compose 就三条命令的循环——`up` 起、`ps` 查、`down` 清。

**启动：**

```bash
docker compose up -d
```

```text

 ✔ Network 09-app_default  Created
 ✔ Container 09-app-db-1   Started
 ✔ Container 09-app-app-1  Started
```

**查看状态：**

```bash
docker compose ps
```

```text

09-app-app-1   09-app-app     Up 5 seconds   0.0.0.0:3000->3000/tcp
```

**验证：**

```bash
curl http://localhost:3000/health
```

```text

```

**看日志（哪个服务出问题看哪个）：**



> 一句话记住它：**compose 操作循环 = `up -d` 起、`ps` 查、`logs` 看、`down` 清。出问题先看对应服务的 `logs`，别瞎猜。**

## 09.7 完善：健康检查与就绪

**先说结论**：上一节的 compose 有个隐患（第 07 章 07.8 讲过）——`depends_on` 只保证顺序，不保证 db 就绪。app 可能起太早连不上 db。这一节补上健康检查。

**给 db 加 healthcheck，让 app 等它健康：**

```yaml
services:
  app:
    build: .
    ports:
      - "3000:3000"
    environment:
      DATABASE_URL: postgres://app:secret@db:5432/app
    depends_on:
      db:
        condition: service_healthy   # ← 关键：等 db 健康，不是等 db 起来
    restart: unless-stopped

  db:
    image: postgres:16
    environment:
      POSTGRES_USER: app
      POSTGRES_PASSWORD: secret
      POSTGRES_DB: app
    volumes:
      - pgdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app"]   # 用 postgres 自带的探针
      interval: 5s
      timeout: 5s
      retries: 5

volumes:
  pgdata:
```

**两个关键点：**

**点一：`condition: service_healthy`。** 让 `depends_on` 从"等启动"升级成"等健康"。这是生产里最正确的写法。

**点二：`healthcheck` 的四个字段。**

| 字段 | 含义 |
|---|---|
| `test` | 怎么探测健康（跑一条命令，退出码 0 算健康） |
| `interval` | 多久探测一次 |
| `timeout` | 单次探测超时时间 |
| `retries` | 连续失败几次算"不健康" |

**验证健康状态：**

```bash
docker inspect --format '{{.State.Health.Status}}' 09-app-db-1
```

```text
healthy
```

**顺带给 app 也加个 healthcheck**（用我们自己写的 `/health` 接口）：

```yaml
  app:
    build: .
    ports:
      - "3000:3000"
    healthcheck:
      test: ["CMD", "wget", "-qO-", "http://localhost:3000/health"]
      interval: 10s
      timeout: 5s
      retries: 3
```

（注意：alpine 镜像里可能没 `wget`，可以用 `wget` 的替代 `wget` 在 busybox 里有，或用 `node -e` 探测。这里演示概念。）

> 一句话记住它：**健康检查是 compose 编排的"保险丝"：db 用 `pg_isready` 探针，app 用 `/health` 接口，`depends_on` 用 `condition: service_healthy` 等真正就绪。这是从"能跑"到"可靠"的关键一步。**

## 09.9 本章常见坑速查

| 坑 | 现象 | 原因 | 正确做法 |
|---|---|---|---|
| 裸机没跑通就容器化 | 容器里报错一头雾水 | 应用本身有 bug | 先裸机 `node server.js` 跑通 |
| `COPY` 找不到文件 | `COPY failed: file not found` | build 目录不对 / .dockerignore 误排除 | 查上下文目录和 .dockerignore |
| 没写 .dockerignore | build 卡在 Sending context | node_modules 全打包了 | 写 .dockerignore 排除 |
| depends_on 不管用 | app 连不上 db | depends_on 不保证就绪 | healthcheck + `service_healthy` |
| 改了代码不生效 | 容器还是旧代码 | 没重新 build | `docker compose up -d --build` |
| 连不上数据库 | 一直报连接失败 | 用了 IP 或写错服务名 | 用服务名（compose DNS） |
| `down -v` 误删数据 | 数据库清空 | `-v` 连卷删 | 别用 `-v`，除非确定清库 |
| 健康检查命令不存在 | healthcheck 一直 unhealthy | alpine 里没那个命令 | 用镜像自带的探针（如 pg_isready） |

## 09.10 本章小结

- **容器化第一步**：先让应用在裸机能跑，再谈容器化。
- **Dockerfile**：alpine + 依赖清单先 COPY + 只装生产依赖 + exec 形式 CMD。
- **.dockerignore**：排除 node_modules/.git/.env，减小上下文、防泄漏。
- **构建验证**：`build` → `image ls` → `run` 三步；`COPY failed` 先查上下文。
- **compose 编排**：app 用 build，db 用现成镜像 + 命名卷，服务名互访。
- **健康检查**：db 用 `pg_isready`，app 用 `/health`，`depends_on` 用 `service_healthy`。
- **完整闭环**：写代码 → Dockerfile → build → run → compose → up → ps/logs → down。
- **操作循环**：`up -d` 起、`ps` 查、`logs` 看、`down` 清。
