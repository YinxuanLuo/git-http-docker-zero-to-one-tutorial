# 第 02 章 · 镜像与分层：一层层叠起来的只读文件系统

> 第 01 章说了镜像"像类、像安装包"，这一章把它拆开，看它到底**由什么组成**。
> 你会发现：镜像不是一个大文件，而是一串**只读层**叠起来的，而且层是靠**内容寻址**认亲的。
>
> 本章你需要记住的就一件事：**镜像是"一串只读层"叠出来的；层靠 sha256 内容寻址，内容一样的层会被复用。理解了这两点，`docker pull` 为什么一层层下载、`docker build` 为什么有缓存，就全都通了。**

---

## 02.1 镜像到底是什么：一层层叠起来的

**先说结论**：一个镜像，不是"一个打包好的文件"，而是**一串只读层（layer）从下往上叠起来**的。每一层记录的是"相对上一层，文件系统发生了什么变化"。

打个比方，镜像像一张**照片的图层**（PSD 文件）：

```text
镜像 nginx:latest 的结构
┌─────────────────────────────┐
│ 第 4 层：nginx 应用本体        │  ← 最顶层：你的应用/主程序
├─────────────────────────────┤
│ 第 3 层：安装 nginx 依赖库     │
├─────────────────────────────┤
│ 第 2 层：apt 更新 + 装基础工具  │
├─────────────────────────────┤
│ 第 1 层：Debian 基础系统       │  ← 最底层：基础镜像
└─────────────────────────────┘
```

**每一层都是只读的。** 你把四层"合起来看"，就是一个完整的、能跑 nginx 的系统。但物理上，它们是分开存、分开下载、分开复用的。

**为什么这个结构重要？** 因为它带来了三个你能直接感受到的好处：

1. **下载省**：多个镜像共享同一个底层，底层只下载一次。
2. **构建快**：改代码只需要重建最上面一两层，下面的层直接复用（层缓存）。
3. **存储省**：镜像之间共享的层，磁盘上只存一份。

这三点，本质都来自同一个词：**复用**。

> 一句话记住它：**镜像不是一个大文件，是一串只读层叠起来的。层与层之间是"谁在谁上面"的关系，而"复用"是分层的全部意义。**

---

## 02.2 为什么是"层"而不是"一个文件"

**先说结论**：因为"层"能表达"**增量**"，而"一个文件"只能表达"**全量**"。

想象你把一个 nginx 应用从 v1 升级到 v2。如果镜像是一个大文件：

```text
v1 镜像 = 整个系统的完整快照（假设 200MB）
v2 镜像 = 整个系统的完整快照（假设 200MB）
升级 = 重新下载整个 200MB
```

如果镜像是分层的：

```text
v1 镜像 = [基础层] + [依赖层] + [应用层 v1]
v2 镜像 = [基础层] + [依赖层] + [应用层 v2]   ← 只有应用层变了

升级 = 只下载变化的那一层（假设只有 5MB）
```

**这就是"差分"的思想**——和 Git 的"快照 + 内容寻址"是同一套思路（本教程 Git 篇讲过）：**只存"变化"，不存"重复"。**

用你有 JS 背景的话说：这就像**不可变对象**。每一层一旦生成就永不变，新的层是"基于旧层的一个新快照"。你要"改"某一层？做不到——你只能在上方再叠一层来"覆盖"它。

**这个设计的代价**：层多了会变"碎"。一个由几十层叠出来的镜像，管理起来比"一个大文件"复杂。所以第 08 章会讲"合并层、减少层数"的优化。但绝大多数情况下，"分层"带来的复用收益，远超它的小麻烦。

> 一句话记住它：**层 = 增量，大文件 = 全量。分层让"升级只传变化的部分"成为可能，代价是层会变碎，需要适时合并。**

## 02.3 UnionFS 与 OverlayFS：层怎么"叠"成一个文件系统

**先说结论**：把多个层"叠"成一个完整文件系统，靠的是**联合文件系统（UnionFS）**；现代 Docker 默认用的是它的一个实现叫 **OverlayFS**（`docker info` 里那个 `Storage Driver: overlay2` 就是它）。

**它解决的核心问题**：多个只读层 + 一个可写层，怎么让进程看到"一个统一的、完整的文件系统"？

答案是一个"**覆盖（overlay）**"的规则：

> **上层同名文件覆盖下层；被删的文件用"标记"遮住，而不是真删。**

想象四层里有这样几个文件：

```text
第 3 层（最上层）:  /app/server.js      = "console.log('hi')"
第 2 层:            /app/config.json    = "{"port": 3000}"
                    /app/node_modules/x = ...
第 1 层（最底层）:  /etc/os-release     = "debian:12"
                    /app/config.json    = "{"port": 8080}"
```

合起来之后，进程看到的是：

```text
/etc/os-release      = "debian:12"          ← 只有第 1 层有
/app/config.json     = "{"port": 3000}"     ← 第 2 层覆盖了第 1 层
/app/node_modules/x  = ...                  ← 只有第 2 层有
/app/server.js       = "console.log('hi')"  ← 只有第 3 层有
```

注意 `/app/config.json`：第 1 层和第 2 层**都有**这个文件，但进程只看到**上面那层**的版本。这就是"覆盖"语义。

**那"删除"文件是怎么回事？** 底层是只读的，物理上删不掉。OverlayFS 的做法是：在可写层里放一个"**白文件（whiteout）**"标记，告诉系统"这个文件在合并视图里不存在"。所以"删除"不是真的删，是"盖一个看不见的戳"。

**你不需要记住 OverlayFS 的内部实现**，但这一条要记住：

> **分层文件系统 = 只读的下层 + 只读的中间层 + 一个可写的顶层。读的时候从上往下找，找到第一个就算数；写的时候永远写在最上面的可写层。**

这解释了一个第 01 章埋下的疑问：为什么"容器里改文件，不影响镜像"？——因为容器启动时，OverlayFS 在最上面加了一个**容器的可写层**，你所有的写都进这一层，镜像的只读层一个字节都没动。容器一删，可写层没了，镜像原样。

> 一句话记住它：**OverlayFS 把"多只读层 + 一可写层"叠成一个视图；读自上而下找第一个，写永远进最上面的可写层。容器里的写都在可写层，删容器即丢。**

## 02.4 内容寻址：层靠 sha256 认亲

**先说结论**：每一层都有一个由**内容**算出来的 sha256 摘要（digest），作为它的唯一身份。**内容一样 → digest 一样 → 层可以被复用。**

这是理解"缓存"和"复用"的钥匙。回想第 01 章 `docker image ls` 输出里的 `IMAGE ID`：

```text
REPOSITORY   TAG       IMAGE ID       CREATED        SIZE
nginx        latest    6139a7d6b26f   2 weeks ago    192MB
```

那个 `6139a7d6b26f` 是什么？它不是"第 6139 个镜像"，而是**镜像内容算出来的 sha256 摘要的前 12 位**。完整版很长：

```text
sha256:6139a7d6b26f1b5e9a8c3d4e5f6a7b8c9d0e1f2a3b4c5d6e7f8a9b0c1d2e3f4a5b6
```

**"内容寻址"意味着三件事：**

**第一，同一个层，被多个镜像共享，只存一份。** 你 `docker pull nginx` 和 `docker pull` 另一个也用 Debian 基础的镜像，底层可能完全相同，Docker 只下载一次、磁盘只存一份。

**第二，内容被篡改立刻能被发现。** 层的内容一变，digest 全变，和记录的对不上号，Docker 就能发现"这层被改过了"。这是镜像完整性的基础。

**第三，"缓存命中"的判断标准就是 digest。** `docker build` 时，如果某条指令的"输入"（指令内容 + 上一层 digest）和上次一样，就直接复用上次的层，不重新执行。

用配套脚本跑一遍内容寻址，看得最清楚：

```bash
node examples/docker/02-镜像分层.mjs
```

```text
==================== 1. 内容寻址 ====================
layerA 内容: "echo hello"
layerA digest: 584a331fd6b02dcb…
layerB 内容: "echo hello"
layerB digest: 584a331fd6b02dcb…
layerA 与 layerB 相同吗? 是 → 层可复用
layerC 内容: "echo HELLO"
layerC digest: 1f648a0934316bff…
layerA 与 layerC 相同吗? 否 → 内容一变，digest 全变
```

看到没：layerA 和 layerB 内容一样，digest 就一样（可复用）；layerC 只改了一个字符大小写，digest 就完全不同了。这就是"内容寻址"的全部直觉。

> 一句话记住它：**层的身份 = sha256(内容)。内容一样则 digest 一样，可复用、可校验、可缓存。这就是镜像复用和构建缓存的地基。**

## 02.5 docker pull 为什么是一层层下载

**先说结论**：你 `docker pull` 一个镜像，输出里那一串 `Pull complete` / `Already exists`，就是**一层层在下载**。已经有的层会显示 `Already exists`，直接跳过。

```bash
docker pull nginx
```

```text
latest: Pulling from library/nginx
a1b2c3d4e5f6: Pull complete       ← 第 1 层（Debian 基础）
b2c3d4e5f6a1: Pull complete       ← 第 2 层
c3d4e5f6a1b2: Pull complete       ← 第 3 层
...
Digest: sha256:6139a7d6b26f...    ← 整个镜像的 digest
Status: Downloaded newer image for nginx:latest
```

**每一行前面那个十六进制串**，就是那一层的 digest。`Pull complete` 表示"这层下好了"。

**如果你之前已经拉过相关的镜像，某些层会显示 `Already exists`：**

```text
latest: Pulling from library/nginx
a1b2c3d4e5f6: Already exists      ← 这层本地有了，跳过
b2c3d4e5f6a1: Already exists
c3d4e5f6a1b2: Pull complete       ← 只有新的层才真下载
...
```

**这就是分层的直观收益**：你拉 nginx 时，如果它和 node 镜像共享某个 Debian 底层，那个底层你已经有了，就不会重复下载。**下载省、磁盘省，都体现在这些 `Already exists` 里。**

**`Digest:` 那一行**是整个镜像的 digest（不是某一层），它是镜像内容的"总指纹"。你可以用它精确引用某个镜像版本：

```bash
docker pull nginx@sha256:6139a7d6b26f1b5e9a8c3d4e5f6a7b8c9d0e1f2a3b4c5d6e7f8a9b0c1d2e3f4a5b6
```

用 digest 引用比用 tag 更精确——tag 是可以被移动的（`latest` 指到哪算哪），digest 是焊死的。

> 一句话记住它：**`docker pull` 的输出是一层层的下载记录；`Already exists` 表示该层本地已有、直接复用；`Digest:` 是整个镜像的内容指纹，比 tag 更精确。**

## 02.6 docker images 与 docker inspect：看透一个镜像

**先说结论**：`docker image ls` 看"列表"，`docker image inspect` 看"详情"。想看一个镜像到底由哪些层组成，得用 inspect。

**看列表：**

```bash
docker image ls
```

```text
REPOSITORY   TAG       IMAGE ID       CREATED        SIZE
nginx        latest    6139a7d6b26f   2 weeks ago    192MB
node         22-alpine 6b7f8d0c2e4b   3 weeks ago    132MB
```

**看详情（层、配置、入口、环境变量）：**

```bash
docker image inspect nginx
```

输出是一个巨大的 JSON，关键字段：

```json
[
  {
    "Id": "sha256:6139a7d6b26f...",
    "RepoTags": ["nginx:latest"],
    "Architecture": "amd64",
    "Os": "linux",
    "Size": 192000000,
    "RootFS": {
      "Type": "layers",
      "Layers": [
        "sha256:a1b2c3d4...",   ← 第 1 层
        "sha256:b2c3d4e5...",   ← 第 2 层
        "sha256:c3d4e5f6..."    ← 第 3 层
      ]
    },
    "Config": {
      "Env": ["PATH=/usr/local/sbin:...", "NGINX_VERSION=1.27"],
      "ExposedPorts": { "80/tcp": {} },
      "Cmd": ["nginx", "-g", "daemon off;"]
    }
  }
]
```

**三个关键字段，记住它们：**

| 字段 | 含义 |
|---|---|
| `RootFS.Layers` | **这个镜像由哪些层组成**（从下到上），每个是一个 sha256 |
| `Config.Env` | 镜像默认的环境变量 |
| `Config.Cmd` | 容器启动时的默认命令（第 04 章讲 CMD 时会再遇到） |
| `Architecture` / `Os` | 镜像面向什么架构/系统（`amd64`、`arm64`） |

**`docker inspect` 是个万能命令**——不仅能看镜像，还能看容器、网络、卷。它输出 JSON，所以可以配合格式模板提取单个字段：

```bash
# 只看镜像由哪些层组成
docker image inspect --format '{{json .RootFS.Layers}}' nginx
```

```text
["sha256:a1b2c3d4...","sha256:b2c3d4e5...","sha256:c3d4e5f6..."]
```

> 一句话记住它：**`image ls` 看列表，`image inspect` 看详情。`RootFS.Layers` 告诉你一个镜像由哪些层组成；inspect 是万能命令，镜像/容器/网络/卷都能看。**

## 02.7 镜像名与 tag 的完整规矩

第 01 章给了镜像名的形状，这一节把它讲全，尤其是**你容易踩的两个坑**。

**完整结构：**

```text
[registry/][命名空间/]仓库名[:tag][@digest]
```

逐段拆开：

| 段 | 必填？ | 默认值 | 例子 |
|---|---|---|---|
| registry | 否 | `docker.io` | `gcr.io`、`mcr.microsoft.com` |
| 命名空间（用户名/组织） | 否 | 官方镜像用 `library` | `你的用户名`、`library` |
| 仓库名 | 是 | 无 | `nginx`、`myapp` |
| tag | 否 | `latest` | `1.27`、`22-alpine` |
| digest | 否 | 无 | `@sha256:6139...` |

**坑一：`latest` 不是"最新版"。** 它是"没写 tag 时的默认值"。`nginx:latest` 指向哪个版本，取决于维护者把哪个版本打上了 `latest` 标签。它甚至可能指向一个很旧的版本，因为"打标签"是人为动作，不是自动的。**生产永远写明确 tag。**

**坑二：tag 和 digest 可以同时用，但 tag 可被移动，digest 焊死。** 看这两种写法：

```bash
docker pull nginx:1.27                          # 用 tag：1.27 这个标签可以被人重新指向别的镜像
docker pull nginx@sha256:6139a7d6b26f...        # 用 digest：焊死这个内容，永不变
```

同一个 tag（比如 `1.27`）理论上可以被"重新打"到另一个镜像上（虽然正规仓库不会这么干 `1.27` 这种版本号，但 `latest` 一定会被移动）。而 digest 是内容指纹，内容变了 digest 就变，所以用 digest 引用是**绝对精确**的。

**实战建议：**

| 场景 | 推荐写法 |
|---|---|
| 本地开发 | `nginx:latest` 随便用 |
| 生产部署 | `nginx:1.27`（明确版本） |
| 极严格的生产（审计/合规） | `nginx@sha256:6139...`（焊死内容） |

**自建私有仓库时的写法**（第 08 章会讲，这里先认形状）：

```text
registry.mycompany.com/team/app:1.2.3
   ↑ registry         ↑ 命名空间  ↑ 仓库  ↑ tag
```

> 一句话记住它：**镜像名 = `[registry/][命名空间/]仓库名[:tag][@digest]`。`latest` 是默认 tag 不是最新；digest 焊死内容，比 tag 精确。**

## 02.8 层缓存：为什么第二次 build 快那么多

**先说结论**：`docker build` 是一条指令一条指令地执行，每条指令生成一层。如果某条指令的"输入"没变（指令内容 + 上一层 digest 都没变），Docker 就**直接用缓存层**，不重新执行。这就是"第二次 build 快"的原因。

**看一次真实的两次构建对比**（简化示意，完整演示见配套脚本）：

```text
第一次构建（全部 RUN）：
  [RUN ] FROM node:22
  [RUN ] COPY package.json .
  [RUN ] RUN npm install
  [RUN ] COPY . .

第二次构建（只改了源码）：
  [CACHED] FROM node:22
  [CACHED] COPY package.json .
  [CACHED] RUN npm install        ← 前 3 层命中缓存
  [RUN ] COPY . .                 ← 源码变了，从这层开始全部重跑
```

**`CACHED` 意味着什么？** 意味着这一层直接复用上次的结果，`npm install` 这种最贵的操作**根本没再执行**。

**缓存失效的规则，一句话**：**从"第一条变化的指令"开始，它和它后面的所有层都要重建；它前面的层继续命中缓存。**

这引出第 04 章最重要的一个优化原则——**"把最贵的、最不容易变的指令放在最前面"**：

```dockerfile
# ✅ 好：先 COPY 依赖清单，再 npm install
COPY package*.json ./
RUN npm install

# ❌ 差：先 COPY 所有源码，再 npm install
# 这样每次改源码，npm install 都要重跑（因为 COPY . . 这层变了）
COPY . .
RUN npm install
```

为什么？因为 `COPY package*.json ./` 这层只有在 `package.json` 变化时才失效；而 `COPY . .` 这层在任何源码文件变化时都会失效。把 `npm install` 放在 `COPY . .` 之后，就等于"每次改代码都要重装依赖"——慢得离谱。

**配套脚本里跑一次层缓存：**

```bash
node examples/docker/02-镜像分层.mjs
```

```text
==================== 3. 层缓存（build 缓存失效） ====================
第一次构建（全部 RUN）：
  [RUN ] 13664a77c295  FROM node:22
  [RUN ] cb7b10b4eacd  COPY package.json .
  [RUN ] d5c6eb382277  RUN npm install
  [RUN ] 4a363c45de7e  COPY . .
第二次构建（改了源码，前 3 层命中缓存）：
  [CACHED] 13664a77c295  FROM node:22
  [CACHED] cb7b10b4eacd  COPY package.json .
  [CACHED] d5c6eb382277  RUN npm install
  [RUN ] 4a363c45de7e  COPY . .
```

> 一句话记住它：**缓存 = 每条指令一层；指令输入没变就 CACHED，从第一条变化的指令起往后全部重建。所以最贵最不易变的指令要排最前。**

## 02.9 一个真实的"分层"观察

如果你装了 Docker，可以亲眼验证前面讲的一切。这一节用三个命令，让你"看见"分层。

**第一步：看一个镜像有几层。**

```bash
docker image inspect nginx --format '{{range .RootFS.Layers}}{{println .}}{{end}}'
```

会打印出每一层的 sha256，层数 = 行数。

**第二步：看"历史"——每层是怎么来的。** `docker history` 把"每条构建指令对应一层"展示出来：

```bash
docker history nginx
```

```text
IMAGE          CREATED        CREATED BY                                      SIZE
6139a7d6b26f   2 weeks ago    CMD ["nginx" "-g" "daemon off;"]               0B
<missing>      2 weeks ago    EXPOSE map[80/tcp:{}]                           0B
<missing>      2 weeks ago    ENV NGINX_VERSION=1.27                          0B
<missing>      2 weeks ago    RUN /bin/sh -c apt-get install nginx            xxMB
<missing>      2 weeks ago    /bin/sh -c #(nop) ADD file:... in /               xxMB
```

**注意两点：**

1. **`CREATED BY` 那一列**，能看到每层对应的指令：`RUN`、`ENV`、`EXPOSE`、`CMD`……这和第 04 章 Dockerfile 的指令一一对应。
2. **`SIZE` 那一列**，能看到每层占多大。像 `CMD`、`EXPOSE`、`ENV` 这种"只改元数据不写文件"的指令，SIZE 是 `0B`——它们不产生文件变化，只改镜像配置。

**第三步：删镜像时，看"层"怎么被共享。** 当你删一个镜像，如果它的某些层还被别的镜像用着，Docker 只删"没人用"的层：

```bash
docker image rm nginx
```

```text
Untagged: nginx:latest
Deleted: sha256:6139a7d6b26f...
Deleted: sha256:a1b2c3d4...    ← 只删了不再被共享的层
```

**`<missing>` 是什么？** 在 `docker history` 里，有些 `IMAGE` 显示 `<missing>`，意思是"这一层的历史信息在本地已经没有了（比如它来自 pull 下来的镜像，本地没有构建记录）"。不影响使用，只是"历史记录不全"的意思，别慌。

> 一句话记住它：**`docker history` 把"层 ↔ 构建指令"一一对应给你看；`docker inspect` 看层的 sha256；`CMD/ENV/EXPOSE` 这类指令的层是 0 字节，只改元数据不写文件。**

## 02.10 多架构镜像：为什么有 arm64 和 amd64

**先说结论**：同一个 `nginx:latest`，在 x86 服务器上和 M 系列 Mac（ARM 芯片）上，拉下来的其实是**不同架构的镜像**。Docker 用**多架构镜像（manifest list）**来解决"一个名字，多套内容"。

你在 `docker image inspect` 里看到的 `Architecture: amd64` 或 `arm64`，就是这回事。

**背景**：CPU 有不同指令集架构，最常见两种：

| 架构 | 简称 | 常见设备 |
|---|---|---|
| x86_64 | `amd64` | 大多数服务器、Intel/AMD 电脑 |
| ARM64 | `arm64` | 苹果 M 系列 Mac、树莓派、云上的 ARM 服务器 |

同一个软件（比如 nginx），要分别编译出 amd64 版和 arm64 版。它们的二进制不通用。

**Docker 的做法**：一个 tag（如 `nginx:latest`）下面挂着一个 **manifest list**，里面列出"这个 tag 有哪几种架构的镜像，各自指向哪个 digest"。你 `docker pull` 时，Docker 根据**你机器的架构**自动选对的那个。

```text
nginx:latest（manifest list）
  ├── amd64 → digest sha256:aaaa...
  └── arm64 → digest sha256:bbbb...
```

**架构不匹配时会报错**（真实原文，比如在一个只发布了 amd64 的镜像上，用 arm 机器去拉）：

```text
no matching manifest for linux/arm64/v8 in the manifest list entries
```

或者反过来（用老 x86 机器拉一个只发了 arm64 的镜像）：

```text
no matching manifest for linux/amd64 in the manifest list entries
```

**这解释了你的一个真实体验**：为什么同一个 `docker pull nginx`，在服务器上拉几百 MB，在 Mac 上拉另一个大小——因为你俩架构不同，拉的是同一 tag 下不同架构的镜像。

**怎么指定架构？** 构建时用 `--platform`：

```bash
# 为 ARM 架构构建（哪怕你现在在 x86 机器上，也能交叉构建）
docker build --platform linux/arm64 -t myapp:arm64 .
```

> 一句话记住它：**一个 tag 下可以挂多架构的 manifest list，Docker 按你机器架构自动选；架构不匹配会报 `no matching manifest for linux/xxx`。**

## 02.11 镜像的导入导出与打标签

**先说结论**：镜像不仅能从 registry 拉，还能打包成文件传输（`save`/`load`），也能改名字（`tag`）。这三个命令在"没有 registry"的场景（内网、离线）里是刚需。

**`docker tag`：给镜像换个名字/打个 tag。** 注意它**不复制镜像**，只是加了个标签（引用）：

```bash
docker tag nginx:1.27 myname/nginx:prod
docker image ls
```

```text
REPOSITORY      TAG       IMAGE ID       CREATED        SIZE
nginx           1.27      6139a7d6b26f   2 weeks ago    192MB
myname/nginx    prod      6139a7d6b26f   2 weeks ago    192MB   ← 同一个 IMAGE ID
```

两个名字指向**同一个 `IMAGE ID`**——因为 `tag` 只是加标签，内容没变。

**`docker save`：把镜像导出成一个 tar 文件。** 用于离线分发：

```bash
docker save -o nginx.tar nginx:1.27
ls -lh nginx.tar
```

```text
-rw-r--r-- 1 user user 190M ... nginx.tar
```

**`docker load`：从 tar 文件导入镜像。** 离线机器上：

```bash
docker load -i nginx.tar
```

```text
Loaded image: nginx:1.27
```

**`save`/`load` 的典型场景**：服务器在内网、不能连 Docker Hub，你在能联网的机器上 `save` 出 tar，拷进去 `load`，就能用了。

**一个容易混的点**：`save` 和 `export` 不是一回事。

| 命令 | 作用对象 | 导出什么 |
|---|---|---|
| `docker save` | **镜像** | 完整的镜像（含所有层和元数据），能 `load` 回一个镜像 |
| `docker export` | **容器** | 一个运行中容器的**文件系统快照**，丢层结构，只能 `import` 成镜像 |

新手常搞混。记住：**save 是镜像的，export 是容器的**。日常离线分发用 `save`/`load` 就对了。

> 一句话记住它：**`tag` 加标签（不复制内容），`save`/`load` 离线搬运镜像，`export`/`import` 搬运容器文件系统。save 是镜像的，export 是容器的。**

## 02.13 本章常见坑速查

| 坑 | 现象 | 原因 | 正确做法 |
|---|---|---|---|
| 把镜像当成一个大文件 | 理解不了"为什么 pull 有 Already exists" | 镜像是分层存储，不是单文件 | 用"图层"模型理解镜像 |
| 用 `latest` 部署 | 上线跑的是不确定版本 | `latest` 只是默认 tag | 生产写死 `nginx:1.27` |
| 以为 `latest` 会自动是最新 | 拉下来发现是旧版 | tag 是人为打的，不会自动更新 | 显式指定版本号 |
| 看不懂 `docker history` 的 `<missing>` | 以为镜像坏了 | 只是本地没有构建历史记录 | 正常现象，不影响使用 |
| 改一次代码却重新 `npm install` | build 每次都很慢 | `COPY . .` 放在了 `RUN npm install` 之前 | 先 `COPY package*.json` 再 `RUN npm install` |
| 用 `docker image ls` 找层信息 | 只有 SIZE 没有层列表 | `ls` 是列表视图 | 用 `docker image inspect` 或 `docker history` |
| 删镜像报 `is being used by stopped container` | 删不掉 | 有停止的容器还引用它 | 先 `docker rm` 容器再删镜像 |
| 拉镜像报 `manifest unknown` | 找不到这个 tag | tag 不存在 | 检查 tag 拼写，用 `docker search` 确认存在 |

## 02.14 本章小结

- **镜像是分层存储的**：一串只读层从下往上叠，不是一个大文件。
- **分层的意义是复用**：层之间共享，下载省、存储省、构建快。
- **UnionFS / OverlayFS**：把多只读层 + 一个可写层叠成一个视图；读自上而下，写进最上层可写层。
- **内容寻址**：层的身份是 sha256(内容)，内容一样 digest 一样，可复用、可校验、可缓存。
- **`docker pull` 分层下载**：`Already exists` = 该层已有、跳过；`Digest:` 是整个镜像的内容指纹。
- **看镜像**：`image ls` 看列表，`image inspect` 看详情（`RootFS.Layers` 是层列表），`history` 看"层 ↔ 指令"。
- **镜像名**：`[registry/][命名空间/]仓库名[:tag][@digest]`；`latest` 是默认 tag 不是最新；digest 焊死内容。
- **层缓存**：指令输入没变就 CACHED，从第一条变化指令起往后全重建；贵且不易变的指令排最前。

## 02.15 动手练习

**1. `docker pull nginx` 时，输出里 `Pull complete` 和 `Already exists` 分别是什么意思？**

<details><summary>参考答案</summary>

- `Pull complete`：这一层刚下载完成。
- `Already exists`：这一层本地已经有了（可能来自其它镜像的共享），直接复用，不重复下载。

这是分层 + 内容寻址带来的"复用"在下载阶段的体现。

</details>

---

**2. 镜像 A 和镜像 B 共享同一个 Debian 底层，本地已经拉过 A。现在拉 B，那个共享底层会重新下载吗？为什么？**

<details><summary>参考答案</summary>

不会。因为层靠内容寻址（sha256）认亲，本地已经有这个 digest 的层了，`docker pull B` 时该层会显示 `Already exists`，直接跳过。

</details>

---

**3. 为什么"改一行源码"会导致 `docker build` 里 `npm install` 重新执行？怎么避免？**

<details><summary>参考答案</summary>

因为 Dockerfile 写成了 `COPY . .` 在前、`RUN npm install` 在后。`COPY . .` 在源码变化时失效，它后面的 `npm install` 也跟着失效重跑。

避免办法：先 `COPY package*.json ./`，再 `RUN npm install`，最后才 `COPY . .`。这样只有 `package.json` 变化时才重装依赖。

</details>

---

**4. `docker image ls` 里两个不同 tag 的镜像，`IMAGE ID` 却相同，说明什么？**

<details><summary>参考答案</summary>

说明这两个 tag 指向的是**同一个镜像内容**（比如 `nginx:latest` 和 `nginx:1.27` 恰好内容一样）。因为 `IMAGE ID` 是内容摘要，内容相同 ID 就相同。

</details>

---

**5. `latest` 标签代表什么？生产环境该不该用？为什么？**

<details><summary>参考答案</summary>

`latest` 只是"没写 tag 时的默认值"，**不代表最新版本**。它指向哪个镜像取决于维护者给谁打了 `latest` 标签，且会被移动。

生产不该用，因为版本不确定、不可复现。应写死明确版本号（`nginx:1.27`），甚至用 digest 焊死内容。

</details>

---

**6. 用一条命令看一个镜像由哪些层组成，怎么写？**

<details><summary>参考答案</summary>

```bash
docker image inspect nginx --format '{{json .RootFS.Layers}}'
```

或直接 `docker image inspect nginx` 看完整 JSON 里的 `RootFS.Layers` 字段。想看"层 ↔ 构建指令"的对应关系，用 `docker history nginx`。

</details>
