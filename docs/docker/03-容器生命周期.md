# 第 03 章 · 容器生命周期：从 create 到 rm 的完整状态机

> 第 02 章讲了镜像怎么"存"，这一章讲容器怎么"活"——它的创建、启动、停止、删除，以及这一生中会经历哪些状态。
>
> 本章你需要记住的就一件事：**容器是一个状态机，状态只在 `created → running → exited → removed` 之间迁移；`docker run` 是一步到位的快捷方式，而 `create/start/stop/rm` 是拆开的分步操作。**

---

## 03.1 容器的一生：状态机

**先说结论**：一个容器从出生到消亡，只会处于这几种状态之一，并且状态之间只能按固定的路径迁移。

```text
                 docker start              docker stop
   created ───────────────────▶ running ──────────────▶ exited
     ▲                            │  ▲                     │
     │                            │  └───── docker start ──┘
     │                       docker kill                    │
     │                            ▼                         │
     └────────────────────────── killed ────────────────────┘
                          （所有状态最终都能 rm → removed）
```

**四种核心状态：**

| 状态 | 含义 | 怎么进入 |
|---|---|---|
| `created` | 容器创建了，但**还没启动**（进程没跑） | `docker create` |
| `running` | 容器正在运行（主进程活着） | `docker start` |
| `exited` | 容器停了（主进程结束，可能是正常退出也可能是崩了） | `docker stop`、进程自己退出 |
| `removed` | 容器被删除，彻底消失 | `docker rm` |

**两个关键认知，先记住：**

**认知一：`exited` 的容器还在，只是"停了"。** 它占用磁盘（保留了可写层），只是进程不跑了。所以你会看到很多人机器上积压了一堆 `exited` 容器——那是"用完没删"的后果。

**认知二：`stopped` 不是独立状态。** 你经常听人说"停止容器"，但 `docker ps -a` 的 `STATUS` 列里，停掉的容器显示的是 `Exited (0)` 或 `Exited (137)`——`Exited` 后面的数字是**退出码**：

| 退出码 | 含义 |
|---|---|
| `0` | 正常退出 |
| `1` | 一般错误 |
| `137` | 被 `kill -9`（SIGKILL）杀死，常见于内存超限被 OOM 杀掉 |
| `143` | 收到 SIGTERM 优雅退出（`docker stop` 的默认信号） |

**这个状态机，用配套脚本能直接跑出来：**

```bash
node examples/docker/03-容器生命周期.mjs
```

```text
==================== 1. 容器状态机 ====================
  web(nginx:latest): created --start--> running
  web(nginx:latest): running --stop--> exited
  web(nginx:latest): exited --start--> running
  web(nginx:latest): running --kill--> killed
  web(nginx:latest): killed --rm--> removed
最终状态: removed
```

注意那条 `exited --start--> running`：**停掉的容器可以再次启动**，这是状态机里"复活"的路径。

> 一句话记住它：**容器状态：created → running → exited → removed（中间可 kill）。exited 是"停了但还在"，removed 才彻底消失。退出码 0 正常、137 被强杀、143 优雅退出。**

## 03.2 docker run = create + start + attach

**先说结论**：`docker run` 是"一步到位"的快捷方式，等价于 `docker create` + `docker start` + `docker attach` 三步。

**分步拆开看：**

```bash
# 第一步：创建容器（状态 created，进程没跑）
docker create --name web nginx
# 输出：容器 id

# 第二步：启动容器（状态 running）
docker start web

# 第三步：附着（把终端连到容器，前台看输出）—— 这步其实由 run 自动做了
docker attach web
```

**为什么需要知道这个拆解？** 两个实际场景：

**场景一：你想"先准备好，再启动"。** `docker create` 允许你先创建容器（配好端口、卷、环境变量），过会儿再 `start`。虽然日常少用，但理解它你才知道 `run` 背后发生了什么。

**场景二：你想改启动参数。** `docker run` 的参数在创建时就定死了。如果你 `docker run` 时漏了某个参数，不能"改"，只能删掉重建（或 `create` 一个新的）。理解"创建和启动是两件事"，你才不会疑惑"为什么不能给已启动的容器加端口"。

**`docker run` 的完整参数模型**（第 01 章见过，这里完整化）：

```text
docker run [OPTIONS] IMAGE [COMMAND] [ARG...]
```

末尾的 `[COMMAND] [ARG...]` 可以**覆盖镜像里默认的启动命令**（镜像的 CMD，第 04 章会讲）。例如：

```bash
# 覆盖 nginx 默认命令，改成打印一句话后退出
docker run nginx echo "覆盖了默认命令"
```

```text
覆盖了默认命令
```

这个容器打印完就退出了（因为 `echo` 执行完就结束）——这正好演示了"容器主进程退出 = 容器 exited"的规则（03.9 展开）。

> 一句话记住它：**`run` = `create` + `start` + `attach`。run 的参数在创建时定死，不能改，只能重建。末尾 `[COMMAND]` 能覆盖镜像默认命令。**

## 03.3 前台 vs 后台：-d 到底改了什么

**先说结论**：`-d`（detach）让容器在后台运行，`docker run` 命令立即返回，不把终端"绑"在容器上。

**不加 `-d`（前台运行）：**

```bash
docker run nginx
```

终端被占住，一直刷 nginx 日志，直到 `Ctrl+C`。**而且 `Ctrl+C` 会直接停掉容器**（因为前台模式下，信号直接传给容器主进程）。

**加 `-d`（后台运行）：**

```bash
docker run -d --name web nginx
```

```text
a1b2c3d4e5f6   ← 打印容器 id 后立即返回，容器在后台跑
```

之后你要看它、管它，用 `docker ps`、`docker logs`。

**一个高频困惑：`-d` 之后看不到日志了，怎么知道它活着？**

```bash
docker ps                 # 看它是否 running
docker logs web           # 看它的输出
```

**什么容器适合 `-d`，什么不适合？**

| 类型 | 用法 | 例子 |
|---|---|---|
| 长期运行的服务（Web、数据库） | `-d` 后台跑 | `docker run -d nginx` |
| 一次性任务（算完就走） | 前台跑（或 `--rm`） | `docker run --rm node -e "console.log(1)"` |
| 需要交互调试 | `-it`（03.4） | `docker run -it node` |

> 一句话记住它：**`-d` = 后台运行、命令秒回；前台运行时 `Ctrl+C` 会直接停容器；后台跑的服务靠 `ps` 看状态、`logs` 看输出。**

## 03.4 交互模式：-it 到底是什么

**先说结论**：`-it` 其实是两个参数 `-i` + `-t`，合起来让容器"像一台能交互的终端"。很多人一直 `-it` 一起用，但不知道它俩各管一半。

| 参数 | 全称 | 作用 |
|---|---|---|
| `-i` | `--interactive` | 保持 **stdin 打开**，让你能**输入** |
| `-t` | `--tty` | 分配一个**伪终端（TTY）**，让输出**有交互格式**（彩色、光标、提示符） |

**分开理解：**

- 只有 `-i` 没有 `-t`：能输入，但输出没终端格式（比如看不到 bash 的提示符 `#`）。
- 只有 `-t` 没有 `-i`：有终端格式，但你**没法输入**（stdin 关着）。

**为什么 bash 必须 `-it`？** 因为 bash 是一个"交互式 shell"，它需要 stdin 读你的命令（`-i`），也需要一个 TTY 来显示提示符和光标（`-t`）。少一个都不像样：

```bash
# 进一个交互式 Node REPL
docker run -it node
```

```text
Welcome to Node.js v22.0.0.
Type ".help" for more information.
> 1 + 1
2
> .exit
```

看到 `>` 提示符、能输入 `1 + 1` 得到 `2`——这就是 `-i`（能输入）+ `-t`（有提示符）共同的作用。

**一个真实报错**：在非终端环境（比如 CI 脚本、管道里）用 `-t`，会报：

```text
the input device is not a TTY
```

因为 `-t` 要分配一个 TTY，但环境里没有。CI 里跑命令应该用 `-i` 或者干脆不带 `-it`。

**什么时候用 `-it`，什么时候不用？**

| 场景 | 参数 |
|---|---|
| 进 bash/REPL 交互 | `-it` |
| CI 里跑命令、脚本里跑命令 | 不带（或只带 `-i`） |
| 后台服务 | `-d`（和 `-it` 互斥，一般不同时用） |

> 一句话记住它：**`-i` 开 stdin（能输入）、`-t` 开伪终端（有提示符），合起来才能交互。非终端环境用 `-t` 会报 `the input device is not a TTY`。**

## 03.5 docker ps 读透

**先说结论**：`docker ps` 是"看容器"的入口，但它的默认行为（只看运行中的）坑过很多人。这一节把它读透。

**基本用法：**

```bash
docker ps           # 只看运行中的
docker ps -a        # 看所有状态（含 exited）
docker ps -q        # 只输出容器 id（脚本里常用）
```

**`docker ps` 的列，逐个吃透：**

```text
CONTAINER ID   IMAGE          COMMAND                  CREATED          STATUS                    PORTS                  NAMES
a1b2c3d4e5f6   nginx:latest   "/docker-entrypoint.…"   5 minutes ago    Up 5 minutes              0.0.0.0:8080->80/tcp   web
```

| 列 | 含义 | 易混点 |
|---|---|---|
| `CONTAINER ID` | 容器唯一 id（前 12 位） | 和镜像 `IMAGE ID` 不是一回事 |
| `IMAGE` | 用的哪个镜像 | 可能带 tag |
| `COMMAND` | 启动时执行的命令 | 被截断显示，完整用 `docker inspect` |
| `CREATED` | 创建时间（相对） | 不是"启动时间" |
| `STATUS` | 当前状态 | `Up X` = 运行中；`Exited (码)` = 停了 |
| `PORTS` | 端口映射 | `宿主:容器`，第 05 章 |
| `NAMES` | 容器名 | 不指定就随机生成 |

**`STATUS` 列是重点，几种常见形态：**

| STATUS 显示 | 含义 |
|---|---|
| `Up 5 minutes` | 运行中，跑了 5 分钟 |
| `Up 5 minutes (Paused)` | 运行中但被暂停了 |
| `Exited (0) 2 minutes ago` | 2 分钟前正常退出 |
| `Exited (137) 1 hour ago` | 1 小时前被强杀（OOM 或 kill -9） |
| `Created` | 创建了但没启动 |
| `Restarting (1) 10 seconds ago` | 正在重启循环中（异常，03.10） |

**`-a` 的坑**：新手 `docker ps` 看不到容器就慌了（第 01 章讲过），本质就是没加 `-a`。

**过滤容器**：`--filter` 能按状态、名字等筛选：

```bash
docker ps -a --filter "status=exited"          # 只看已停止的
docker ps --filter "name=web"                   # 按名字
```

**只看 id（脚本/清理常用）：**

```bash
docker ps -q
```

```text
a1b2c3d4e5f6
b2c3d4e5f6a1
```

> 一句话记住它：**`ps` 只看运行中，`-a` 看全部，`-q` 只要 id；`STATUS` 列是关键——`Up` 在跑、`Exited (码)` 停了，`137` 是强杀。**

## 03.6 看日志：docker logs

**先说结论**：后台容器的输出去哪了？进了容器的日志，用 `docker logs` 读。

```bash
docker run -d --name web nginx
docker logs web
```

```text
/docker-entrypoint.sh: /docker-entrypoint.d/ is not empty, will attempt to perform configuration
...
2024/01/01 12:00:00 [notice] 1#1: using the "epoll" event method
```

**常用选项：**

| 选项 | 作用 |
|---|---|
| `-f` / `--follow` | 持续跟踪日志（类似 `tail -f`） |
| `--tail N` | 只看最后 N 行 |
| `-t` / `--timestamps` | 每条日志带时间戳 |

```bash
docker logs -f --tail 100 web    # 实时跟踪，从最后 100 行开始
```

**一个必须知道的机制**：`docker logs` 读的是容器的**标准输出（stdout）和标准错误（stderr）**。所以你的程序**要写到 stdout/stderr**，日志才看得见；写到文件里，`docker logs` 看不到。

这也是"容器化应用的正确姿势"——**别往文件写日志，往 stdout 打**，让 Docker 的日志系统统一收集。

**日志去哪了？** 默认驱动是 `json-file`，日志存在宿主机的 JSON 文件里（`docker info` 里 `Logging Driver: json-file`）。可以换驱动（如 fluentd、journald），这是第 08 章的进阶内容。

> 一句话记住它：**`docker logs` 读的是容器 stdout/stderr；`-f` 跟踪、`--tail` 截尾、`-t` 加时间戳。程序要往 stdout 打日志，别写文件。**

## 03.7 进入正在运行的容器：docker exec

**先说结论**：容器后台跑着，你想"进去看看"（看文件、跑命令、调试），用 `docker exec`。它是在**运行中的容器里再启动一个新进程**。

```bash
docker exec -it web bash        # 在 web 容器里开一个 bash
```

```text
root@a1b2c3d4e5f6:/#            # 现在你在容器"里面"了
```

进去之后，你看到的文件系统就是那个容器的（OverlayFS 合并视图，第 02 章）。`ls`、`cat` 随便跑：

```bash
root@a1b2c3d4e5f6:/# ls
bin  boot  dev  etc  home  ...
root@a1b2c3d4e5f6:/# exit      # 退出（注意：exit 只退出 exec 的 bash，不影响容器本身）
```

**关键点：`exit` 不会停掉容器。** 因为你 `exec` 进去的是一个"额外进程"，`exit` 只是结束这个进程。容器的主进程（nginx）还在跑，所以容器继续 `Up`。

**不交互、只跑一条命令：**

```bash
docker exec web ls /app        # 在容器里跑一条命令，输出完就返回
```

```text
node_modules  server.js  package.json
```

**`exec` 和 `run` 的区别，务必分清：**

| 命令 | 作用 | 对象 |
|---|---|---|
| `docker run` | **新建并启动**一个容器 | 基于镜像，造一个新容器 |
| `docker exec` | 在**已运行**的容器里跑命令 | 作用于现有容器 |

新手常见错误：想"进去看看"，结果敲了 `docker run -it nginx bash`——这是**又起了一个新容器**，不是进原来那个。

**进容器看什么？** 三个高频用途：

1. 看文件：`docker exec web ls -la /app`
2. 看环境变量：`docker exec web env`
3. 调试网络：`docker exec web curl localhost:80`（容器里 curl 自己的服务）

> 一句话记住它：**`docker exec -it 容器 bash` 进入运行中的容器；`exit` 只退 exec 不影响容器；`run` 造新容器，`exec` 进现有容器，别混。**

## 03.8 停止：stop vs kill

**先说结论**：`docker stop` 是"**温柔地劝退**"（发 SIGTERM，给进程时间收尾），`docker kill` 是"**一枪崩了**"（发 SIGKILL，立即死）。

| 命令 | 发的信号 | 行为 |
|---|---|---|
| `docker stop 容器` | SIGTERM（可配置） | 给进程 10 秒优雅退出，超时才强杀 |
| `docker kill 容器` | SIGKILL（默认） | 立即杀死，不给收尾机会 |

**为什么 stop 要"温柔"？** 因为很多程序需要在退出前收尾：保存状态、关闭数据库连接、flush 日志。直接 SIGKILL，这些收尾都做不了，可能丢数据。

**一个进程对两种信号的反应：**

```text
SIGTERM → 程序可以捕获，做清理，然后退出   → 退出码通常是 143
SIGKILL → 程序无法捕获，立刻死            → 退出码通常是 137
```

**所以 `docker ps -a` 里 `Exited (143)` 和 `Exited (137)` 是有含义的**（03.1 表里提过）：143 = 被 SIGTERM 优雅停止，137 = 被 SIGKILL 强杀。

**什么时候用 kill？** 程序卡死、不响应 SIGTERM 时。`docker stop` 默认等 10 秒（可用 `-t` 改），超时自动转成强杀。

```bash
docker stop web            # 优雅停止
docker kill web            # 立刻杀死（慎用）
docker stop -t 30 web      # 给 30 秒优雅退出时间
```

> 一句话记住它：**`stop` 发 SIGTERM 优雅退出（退出码 143），`kill` 发 SIGKILL 立即死（退出码 137）。能 stop 就别 kill，给程序收尾的机会。**

## 03.9 删除：rm 与 --rm

**先说结论**：`docker rm` 删除容器；运行中的容器默认删不掉；`--rm` 让容器"用完自动删"。

**基本删除：**

```bash
docker stop web
docker rm web
```

**删运行中的容器会报错**（真实原文）：

```bash
docker rm web        # 假设 web 还在 running
```

```text
Error response from daemon: You cannot remove a running container a1b2c3d4e5f6. Stop the container before attempting removal or force remove.
```

**两个解决方式：**

```bash
# 方式一：先停再删
docker stop web && docker rm web

# 方式二：强制删（运行中也删）
docker rm -f web
```

`-f` 等于"先 kill 再 rm"，省一步，但粗暴。

**`--rm`：一次性容器。** 有些容器就是"跑完即弃"的（比如一个编译任务、一个数据迁移脚本），用完让它自动删：

```bash
docker run --rm node -e "console.log('跑完就删')"
```

```text
跑完就删
```

这个容器跑完（进程退出）后**自动删除**，`docker ps -a` 里找不到它。避免了"exited 容器越积越多"的问题。

**清理积压的 exited 容器**（新手迟早要用）：

```bash
# 删除所有已停止的容器
docker container prune
```

```text
WARNING! This will remove all stopped containers.
Are you sure you want to continue? [y/N] y
Deleted Containers:
a1b2c3d4...
```

> 一句话记住它：**删运行中容器要 `-f` 或先 stop；`--rm` 让容器跑完自动删；清理积压用 `docker container prune`。**

## 03.10 重启：restart 与 restart 策略

**先说结论**：`docker restart` 手动重启一个容器；`--restart` 策略让容器在**意外退出时自动重启**（生产必备）。

**手动重启：**

```bash
docker restart web        # = stop + start，但更快
```

**自动重启策略**（`--restart` 参数，在 `docker run` 时指定）：

| 策略 | 行为 |
|---|---|
| `no` | 默认，不自动重启 |
| `on-failure[:N]` | 只在**异常退出**（非 0 退出码）时重启，可限定最多 N 次 |
| `always` | 无论怎么退出都重启（含手动 stop） |
| `unless-stopped` | 类似 always，但**手动 stop 后不重启**（推荐） |

**生产最常用的是 `unless-stopped`：**

```bash
docker run -d --restart unless-stopped --name web nginx
```

为什么推荐 `unless-stopped` 而不是 `always`？因为 `always` 会在你**手动 `docker stop` 后也自动重启**（等于你想停都停不掉，得先改策略）；`unless-stopped` 尊重你的手动停止。

**`on-failure` 的用途**：程序有 bug、崩溃退出，让它自动拉起来，但限制次数防止"崩溃循环"：

```bash
docker run -d --restart on-failure:5 --name app myapp
```

**一个真实现象**：如果容器因为配置错误（比如端口冲突、挂载路径不存在）**起不来**，`--restart always` 会让它陷入无限重启。`docker ps` 里 `STATUS` 会显示：

```text
Restarting (1) 10 seconds ago
```

这时先看 `docker logs` 找原因，别让它一直空转。

> 一句话记住它：**`restart` 手动重启；`--restart` 策略自动重启。生产用 `unless-stopped`（手动停不重启），崩溃循环用 `on-failure:N` 限次数。**

## 03.11 状态迁移的完整地图

把前面所有命令汇总成一张"容器生命周期全地图"。这张图是本章的**总纲**，建议你照着它把每个命令都敲一遍。

```text
                        ┌───────────┐
      docker create ───▶│  created  │
                        └─────┬─────┘
                       docker start
                              ▼
                        ┌───────────┐     docker stop(SIGTERM)   ┌──────────┐
                        │  running  │ ────────────────────────▶ │  exited  │
                        └─────┬─────┘                           └────┬─────┘
                              │  docker kill(SIGKILL)  ▲             │
                              └───────────────────────►│  docker start│
                                              ┌───────┴──────┐       │
                                              │    killed     │       │
                                              └──────┬───────┘       │
                                                     │                │
                                      （所有状态） docker rm ──────────┘
                                                     ▼
                                               ┌───────────┐
                                               │  removed  │
                                               └───────────┘
```

**每条命令对应的一句话：**

| 命令 | 状态迁移 | 一句话 |
|---|---|---|
| `docker create` | — → created | 只创建不启动 |
| `docker start` | created/exited → running | 启动 |
| `docker run` | — → running | create + start + attach |
| `docker stop` | running → exited | 优雅停止（SIGTERM） |
| `docker kill` | running → killed | 强杀（SIGKILL） |
| `docker restart` | running → running | 快速 stop + start |
| `docker rm` | 任意 → removed | 删除 |
| `docker rm -f` | running → removed | 强删（kill + rm） |

**配套脚本的完整状态机演示**（本章开头已引用，这里补全命令对照）：

```bash
node examples/docker/03-容器生命周期.mjs
```

```text
（对照 docker 命令：）
  docker create 镜像      → 只创建容器，状态 created（不运行）
  docker start 容器       → created → running
  docker run 镜像         → create + start 一步到位
  docker stop 容器        → running → exited（发 SIGTERM，优雅退出）
  docker rm 容器          → 删除容器（数据随容器一起没）
  docker ps               → 只列出 running 的容器
  docker ps -a            → 列出所有状态（含 exited）的容器
```

> 一句话记住它：**所有命令都是状态机的一次迁移；run 是捷径，create/start/stop/rm 是分步。理解这张图，就理解了"容器生命周期"的全部。**

## 03.12 本章常见坑速查

| 坑 | 现象 | 原因 | 正确做法 |
|---|---|---|---|
| `docker ps` 看不到容器 | 以为容器丢了 | `ps` 只看运行中的 | `docker ps -a` |
| 想"进"容器却跑了新容器 | 多出一个容器 | `docker run` 是新建，不是进入 | 进入用 `docker exec -it` |
| `docker rm` 删不掉 | `You cannot remove a running container` | 容器在运行 | 先 `stop`，或 `rm -f` |
| `exit` 之后容器停了 | 以为退出会停容器 | 其实没停，是 exec 的 bash 退了 | 用 `docker ps` 确认，容器还在 Up |
| 用 `-t` 在 CI 里报错 | `the input device is not a TTY` | `-t` 要 TTY，CI 没有 | CI 里不带 `-t`（或只带 `-i`） |
| 日志写文件导致 logs 看不到 | `docker logs` 空 | 程序把日志写文件了，不是 stdout | 程序往 stdout 打日志 |
| `docker stop` 很慢 | 等了 10 秒才停 | 进程不响应 SIGTERM，等超时才强杀 | 检查程序是否处理了 SIGTERM |
| 容器名冲突 | `Conflict. The container name "/web" is already in use` | 同名容器已存在 | 换名字，或先删旧的 |
| exited 容器堆积 | `docker ps -a` 一大堆 | 用完没删 | `--rm` 或 `docker container prune` |
| 容器无限重启 | `Restarting (1)` | `--restart always` + 起不来的容器 | 看 `logs` 找根因，改 `on-failure:N` |

**补一条真实报错**（容器名冲突的完整原文，照抄）：

```text
docker: Error response from daemon: Conflict. The container name "/web" is already in use by container "a1b2c3d4e5f6". You have to remove (or rename) that container to be able to reuse that name.
```

> 一句话记住它：**容器生命周期里的坑，一半是"没加 -a"，一半是"run 和 exec 没分清"，剩下是"没设 --rm / --restart"。**

## 03.13 本章小结

- **容器是状态机**：`created → running → exited → removed`，中间可 `kill`。
- **`docker run` = create + start + attach**；参数创建时定死，不能改，只能重建。
- **`-d` 后台运行**：命令秒回，靠 `ps`/`logs` 管理；前台 `Ctrl+C` 会停容器。
- **`-it` = `-i`（stdin）+ `-t`（TTY）**：交互必带；非终端环境用 `-t` 报 `the input device is not a TTY`。
- **`docker ps`**：只看运行中，`-a` 看全部，`-q` 只要 id；`STATUS` 列是关键。
- **`docker logs`**：读 stdout/stderr；`-f` 跟踪、`--tail` 截尾。
- **`docker exec -it 容器 bash`**：进入运行中容器；`exit` 不影响容器；`run` 新建、`exec` 进入。
- **`stop` vs `kill`**：SIGTERM 优雅（143）vs SIGKILL 强杀（137）。
- **`rm` vs `--rm`**：手动删 vs 自动删；删运行中要 `-f` 或先 stop。
- **`--restart`**：`unless-stopped` 生产推荐；`on-failure:N` 防崩溃循环。

## 03.14 动手练习

**1. `docker run -d nginx` 和 `docker run nginx` 有什么区别？**

<details><summary>参考答案</summary>

- `-d`：后台运行，命令立即返回容器 id，终端不被占用。
- 不加 `-d`：前台运行，终端被占住刷日志，`Ctrl+C` 会直接停掉容器。

</details>

---

**2. 你想在正在运行的容器 `web` 里看看 `/app` 下有什么文件，用哪条命令？用 `docker run` 对吗？**

<details><summary>参考答案</summary>

```bash
docker exec web ls /app
```

**不对用 `docker run`**——`docker run` 会基于镜像**新建一个容器**，不是进现有的 `web`。进入现有容器用 `docker exec`。

</details>

---

**3. `docker ps -a` 里看到 `Exited (137)`，这说明什么？**

<details><summary>参考答案</summary>

退出码 137 = 被 SIGKILL 强杀（`docker kill`、`kill -9`、或 OOM 被内核杀）。常见于内存超限。对比：143 是 SIGTERM 优雅退出，0 是正常退出。

</details>

---

**4. 一个容器运行中，你直接 `docker rm web` 报错了，原文是什么？怎么解决？**

<details><summary>参考答案</summary>

报错原文：

```text
Error response from daemon: You cannot remove a running container a1b2c3d4e5f6. Stop the container before attempting removal or force remove.
```

解决：先 `docker stop web` 再 `docker rm web`；或者 `docker rm -f web` 强删。

</details>

---

**5. 你的程序日志写到了 `/var/log/app.log` 文件里，`docker logs` 却看不到任何输出，为什么？怎么改？**

<details><summary>参考答案</summary>

`docker logs` 读的是容器的 **stdout/stderr**，不读文件。

改法：程序把日志打到 stdout（`console.log` / `print`），让 Docker 的日志系统统一收集。这是容器化应用的规范做法。

</details>

---

**6. `docker exec -it web bash` 进去后敲 `exit`，容器 `web` 会停吗？为什么？**

<details><summary>参考答案</summary>

不会。`exec` 是在运行中的容器里**额外启动一个 bash 进程**，`exit` 只是结束这个 bash，容器的主进程（如 nginx）还在跑，所以容器继续 `Up`。

</details>
