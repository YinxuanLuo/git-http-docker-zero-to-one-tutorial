# 第 08 章 · 工程化：多阶段构建、镜像瘦身与安全

> 前面你会写 Dockerfile、会编排 compose 了，这一章把它们打磨到"能上生产"：镜像更小、构建更快、更安全。
>
> 本章你需要记住的就一件事：**工程化的三条主线——多阶段构建（构建工具不进镜像）、镜像瘦身（alpine + .dockerignore + 合并层）、安全（非 root 运行 + 最小权限）。**

---

## 08.1 工程化的目标：小、快、安全

**先说结论**：一个"能跑"的 Dockerfile 和"能上生产"的 Dockerfile，差别就在三个词：**小**（镜像体积）、**快**（构建速度）、**安全**（攻击面）。

**为什么这三者重要？**

| 目标 | 为什么重要 |
|---|---|
| **小** | 镜像小 → 拉取快、部署快、磁盘省。1GB 的镜像拉一次要几分钟，100MB 的秒级。 |
| **快** | 构建快 → 迭代快。改一行代码等 10 分钟 build，和等 30 秒，开发体验天差地别。 |
| **安全** | 攻击面小 → 漏洞少。镜像里没有编译器、没有 dev 依赖，能被攻击利用的东西就少。 |

**一个惊人的对比**：同一个 Node 应用，不同写法，镜像能差 10 倍：

```text
naive 写法：node:22 完整版 + 所有依赖 + 源码 = ~1GB
工程化写法：多阶段 + alpine + 只留产物 = ~100MB
```

**这一章就是教你从 1GB 到 100MB 的完整路径。**

> 一句话记住它：**工程化 = 让镜像小、构建快、攻击面小。多阶段构建、镜像瘦身、安全实践，是三条并行的主线。**

---

## 08.2 多阶段构建：构建工具不进最终镜像

**先说结论**：很多应用"构建时"需要的工具（编译器、打包器、dev 依赖），和"运行时"需要的完全不同。多阶段构建让"构建"和"运行"分开：**在第一个阶段里构建，只把产物复制到第二个"运行阶段"**，工具链不进最终镜像。

**单阶段的问题**（一个典型 Node + 构建的例子）：

```dockerfile
FROM node:22
WORKDIR /app
COPY . .
RUN npm install              # 装了所有依赖，含 dev（测试框架、编译器等）
RUN npm run build            # 构建产物 dist/
CMD ["node", "dist/server.js"]
```

问题：**构建用的工具（webpack、typescript、jest、所有 devDependencies）全部留在最终镜像里**，但你运行 `node dist/server.js` 根本用不到它们。结果镜像又大、攻击面又广。

**多阶段构建的写法：**

```dockerfile
# ---------- 阶段一：构建（起别名 builder） ----------
FROM node:22 AS builder
WORKDIR /app
COPY package*.json ./
RUN npm install              # 这里可以装 dev 依赖（构建需要）
COPY . .
RUN npm run build            # 产出 dist/

# ---------- 阶段二：运行（最终镜像从这里开始） ----------
FROM node:22-alpine
WORKDIR /app
COPY --from=builder /app/dist ./dist      # 只复制产物
ENV NODE_ENV=production
CMD ["node", "dist/server.js"]
```

**关键点：**

1. **每个 `FROM` 开启一个新阶段**，最终镜像是"最后一个 `FROM` 之后的层"。
2. **`COPY --from=builder`** 从上一个阶段复制文件。
3. **第一个阶段可以起别名**（`AS builder`），用别名引用；不写别名也能 `--from=0` 用序号引用。

**体积对比（配套脚本实测的逻辑）：**

```bash
node examples/docker/08-多阶段构建.mjs
```

```text
==================== 3. 对比 ====================
  单阶段最终镜像 : 622 MB
  多阶段最终镜像 : 157 MB
  省下           : 465 MB（75%）
  同时：攻击面更小（没有编译器、没有 dev 依赖可被利用）。
```

**多阶段构建的通用模式：**

```text
阶段一（build）：FROM 完整版 → 装齐工具 → 构建出产物
阶段二（run）：FROM 精简版 → COPY --from=阶段一 产物 → 运行
```

> 一句话记住它：**多阶段构建 = 阶段一构建、阶段二只拷产物运行；工具链（编译器/dev 依赖）不进最终镜像，体积和攻击面都大幅下降。每个 FROM 开一个阶段，COPY --from 跨阶段复制。**

## 08.3 镜像瘦身三板斧

**先说结论**：镜像瘦身有三个最有效的招，按性价比排序：**换 alpine 基础镜像 → 用多阶段构建 → 写 .dockerignore**。

**第一板斧：换 alpine 基础镜像。** 同样的应用，基础镜像换一下，体积立减一个量级：

| 基础镜像 | 大约体积 |
|---|---|
| `node:22`（完整 Debian） | ~1GB |
| `node:22-slim`（Debian 精简） | ~200MB |
| `node:22-alpine`（Alpine） | ~130MB |

改这一行 `FROM node:22` → `FROM node:22-alpine`，镜像就能小 80%。**这是性价比最高的一步。**

**alpine 的代价**（第 04 章提过，这里强调）：

1. 用 `musl` 而非 `glibc`，少数依赖 glibc 的程序不兼容；
2. 包管理器是 `apk` 不是 `apt`；
3. 缺一些常见的编译工具，构建时可能要额外装。

遇到兼容问题，退回到 `-slim`。

**第二板斧：多阶段构建。** 08.2 已讲，这里补一句：它和 alpine 是**叠加**的——多阶段构建的"运行阶段"通常也选 alpine，两个优化一起上，效果最好。

**第三板斧：`.dockerignore`。** 严格说它不减小最终镜像，但**大幅减小构建上下文**，让 build 变快。08.4 专讲。

**一个额外的细节**：注意 `RUN` 合并（第 04 章 04.4 讲过），装完就清理：

```dockerfile
# ❌ 装了又删，但垃圾固在中间层
RUN apt-get install -y curl
RUN rm -rf /var/lib/apt/lists/*

# ✅ 一条命令，装完立刻清，垃圾不留层
RUN apt-get update && apt-get install -y curl && rm -rf /var/lib/apt/lists/*
```

> 一句话记住它：**瘦身三板斧：换 alpine（立减 80%）、多阶段构建（工具链不进镜像）、.dockerignore（减小构建上下文）。三者叠加，镜像从 1GB 降到 100MB 级。**

## 08.4 .dockerignore

**先说结论**：`.dockerignore` 像 `.gitignore`，告诉 Docker"构建时**别把这些文件放进构建上下文**"。它不直接影响最终镜像大小，但**大幅减小构建上下文、加快 build**。

**一个常见场景**：在项目根目录 `docker build .`，而目录里有：

```text
node_modules/     （几百 MB）
.git/             （历史可能很大）
*.log             （日志）
.env              （敏感信息！）
dist/             （如果你在镜像里重新构建的话）
```

这些**全都会被打包进构建上下文**，发给 daemon——即使 Dockerfile 根本 `COPY` 它们。结果 build 卡在"上传上下文"这一步。

**写一个 .dockerignore：**

```dockerignore
node_modules
.git
.gitignore
.env
*.log
npm-debug.log
Dockerfile
docker-compose.yml
.dockerignore
```

**`.dockerignore` 的两个关键作用：**

**作用一：加速构建。** 排除 node_modules（几百 MB）后，上下文从几百 MB 降到几 MB，上传和打包都快。

**作用二：防止敏感信息泄漏。** `.env` 里可能有密码、密钥，如果不 ignore，它会被打进构建上下文——甚至可能被 `COPY . .` 复制进镜像。**这是真实的安全事故来源。**

**一个必须知道的坑**：`.dockerignore` 的语法和 `.gitignore` **几乎一样，但不完全一样**（比如 `.dockerignore` 没有 `.gitignore` 的 `!` 取反规则的历史包袱）。别假设两者 100% 等价。

**看构建上下文有多大：**

```bash
docker build . 2>&1 | head    # 看 Sending build context 那行
```

```text
Sending build context to Docker daemon  523.5MB   ← 没写 .dockerignore，巨大
Sending build context to Docker daemon  2.1MB     ← 写了之后，正常
```

> 一句话记住它：**`.dockerignore` 排除 node_modules/.git/.env 等，减小构建上下文、加快 build、防止敏感信息进镜像。作用类似 .gitignore 但不完全等价。**

## 08.5 基础镜像的选择策略

**先说结论**：选基础镜像不是"随便挑个名字"，而是一个有明确取舍的决策。这一节给一套决策框架。

**决策顺序：**

**第一步：有没有官方的？** 优先用**官方镜像**（Docker Hub 上 `library/` 命名空间下的），它们有维护、有安全更新、有版本管理。自己从零搭基础镜像，99% 是重复造轮子还容易出问题。

**第二步：选哪个 tag？** 官方镜像通常提供多种 tag：

| tag 模式 | 说明 | 例子 |
|---|---|---|
| 具体版本 | 最稳，生产推荐 | `node:22.11.0` |
| 主版本 | 较稳 | `node:22` |
| `-alpine` | 小，生产推荐 | `node:22-alpine` |
| `-slim` | 精简 Debian，折中 | `node:22-slim` |
| `latest` | 别用，会漂移 | `node:latest` |

**第三步：考虑架构。** 第 02 章讲过，镜像有 amd64/arm64 之分。确保基础镜像支持你的目标架构（`docker build --platform`）。

**一个决策表：**

| 你的需求 | 选 |
|---|---|
| 生产，追求最小 | `-alpine` + 具体版本 |
| 生产，alpine 有兼容问题 | `-slim` + 具体版本 |
| 快速验证/开发 | 完整版 `latest` 随便 |
| 要跑 glibc 依赖的程序 | `-slim` 或完整版（别用 alpine） |
| Go/Rust 编译的纯静态二进制 | `scratch`（0 体积） |

**`scratch` 是什么？** 一个**空的**基础镜像（0 字节），用于"程序是单个静态二进制"的场景（Go、Rust 静态编译）。从 `scratch` 构建的镜像，只有一个可执行文件，体积=文件大小：

```dockerfile
FROM scratch
COPY myapp /myapp
ENTRYPOINT ["/myapp"]
```

> 一句话记住它：**基础镜像优先官方 + 具体版本 + `-alpine`（小）；glibc 不兼容换 `-slim`；纯静态二进制（Go/Rust）用 `scratch` 压到极限。别用 `latest`。**

## 08.6 层数优化：层越少越好吗

**先说结论**：层数**不是越少越好，也不是越多越好**——要在"缓存友好"和"层数精简"之间权衡。真正要避免的是"**垃圾固在中间层**"。

**为什么层数会影响性能？** 每层有元数据开销，层太多会让 pull/build 变慢一点。但现代 Docker（overlay2）下，几十层的镜像性能影响很小。所以**别为了"少层"去疯狂合并所有 RUN**——那会破坏缓存（第 04 章 04.13）。

**正确的权衡原则：**

1. **同一件"装东西 + 清理"的事，合并成一条 RUN**（避免垃圾固中间层，第 04 章 04.4）。
2. **不同性质的指令别乱合并**：`COPY package.json` 和 `RUN npm install` 分开，才能缓存 install。
3. **声明类指令（ENV/EXPOSE/CMD）产生的层是 0 字节**，多少都无所谓。

**一个坏例子（过度合并，破坏缓存）：**

```dockerfile
# ❌ 把 COPY 和 RUN 全合并了，源码一变，依赖也重装
RUN cp -r /src/* /app/ && cd /app && npm install
```

**一个好处多的分层：**

```dockerfile
# ✅ 依赖清单独立 COPY，缓存 install；声明类指令放最后
COPY package*.json ./
RUN npm install
COPY . .
ENV NODE_ENV=production
EXPOSE 3000
CMD ["node", "server.js"]
```

**结论一句话**：**层数的原则是"该分则分（为了缓存）、该合则合（为了不留垃圾）"，而不是追求绝对的最小层数。**

> 一句话记住它：**层数不是越少越好；该分则分（缓存依赖安装）、该合则合（装完即清理）。别为了少层破坏缓存，垃圾固中间层才是真问题。**

## 08.7 以非 root 运行

**先说结论**：容器默认以 **root** 运行，这是安全上的一大隐患。生产镜像应该**显式切到非 root 用户**运行。

**为什么默认是 root？** Dockerfile 不指定用户时，容器主进程以 root 跑。而 root 在容器里，权限很大（即使有 namespace 隔离，root 仍能做一些危险操作）。

**为什么危险？** 假设你的应用有漏洞被攻破（比如命令注入），攻击者拿到的是**容器里的 root 权限**，能干的事更多。如果应用以非 root 跑，攻击者拿到的权限就小得多。这叫**最小权限原则**。

**怎么改非 root？** 两种方式：

**方式一：用基础镜像自带的非 root 用户。** 很多官方镜像有 `USER` 指令可切换：

```dockerfile
FROM node:22-alpine
# node 镜像自带一个叫 node 的用户
USER node
WORKDIR /home/node/app
COPY --chown=node:node . .
CMD ["node", "server.js"]
```

**方式二：自己建一个用户。** 需要 root 权限做的事（装依赖）做完后，再切用户：

```dockerfile
FROM node:22-alpine
WORKDIR /app
COPY package*.json ./
RUN npm install          # 这里还是 root（要写文件）

COPY . .
RUN addgroup -S app && adduser -S app -G app   # 建用户
USER app                 # 切到非 root 用户运行
CMD ["node", "server.js"]
```

**注意一个坑**：切换 USER 后，后续的 `COPY`/`RUN` 都以非 root 跑，可能**权限不足**（比如要写 root 拥有的目录）。所以通常**先 root 做完安装，最后再 `USER` 切过去**。

**验证容器以谁运行：**

```bash
docker exec 容器 whoami
```

```text
app        ← 非 root，正确
```

> 一句话记住它：**容器默认 root 运行，不安全；生产镜像先 root 装依赖，最后 `USER` 切到非 root 用户运行。最小权限原则：进程能用多小的权限，就给多小。**

## 08.8 安全：最小权限、镜像扫描、镜像源

**先说结论**：Docker 安全是个大话题，但日常工程化里，抓住三条就够了：**最小权限**、**镜像扫描**、**可信镜像源**。

**第一条：最小权限（08.7 已展开）。** 非 root 运行、只暴露必要端口、只挂必要卷、只给必要能力。

**第二条：镜像扫描。** 镜像里的基础系统、依赖可能有已知漏洞。用扫描工具找出漏洞：

```bash
docker scout quickview nginx:1.27     # Docker 官方的扫描工具
```

```text
Target: nginx:1.27
  ✓ No vulnerable packages detected      ← 或列出漏洞清单
```

把扫描放进 CI，阻止"有高危漏洞的镜像"上线。

**第三条：可信镜像源。** 只用官方镜像 + 官方/可信来源的基础镜像。别随便 `docker pull` 一个来历不明的镜像——恶意镜像可以内置后门、挖矿程序。

**额外的几条安全实践：**

| 实践 | 说明 |
|---|---|
| 固定版本（别用 latest） | 版本漂移 = 引入了不可控的依赖 |
| 用 digest 引用 | 焊死内容，防篡改 |
| 别把密钥 build 进镜像 | 密钥用运行时注入（环境变量/secret 管理） |
| 定期更新基础镜像 | 打安全补丁 |
| 限制容器资源 | `--memory`、`--cpus` 防单个容器吃光资源 |

**一个容易忽略的坑**：**别把密钥 build 进镜像**。有人图省事，把 API key、数据库密码写进 Dockerfile 的 `ENV` 或 `COPY` 进镜像——一旦镜像被推出去/泄漏，密钥就暴露了。正确做法是运行时通过环境变量、secret 管理工具注入。

> 一句话记住它：**安全三件事：最小权限（非 root、少端口）、镜像扫描（scout/trivy）、可信源（官方 + 固定版本）。别把密钥 build 进镜像。**

## 08.9 日志与信号处理

**先说结论**：容器化的应用要遵守两条"正确姿势"：**日志往 stdout 打**、**正确处理 SIGTERM 信号**。这两条没做好，日志收集和优雅停机都会出问题。

**日志：往 stdout 打。** 第 03 章 03.6 讲过 `docker logs` 读 stdout/stderr。这里补一句工程化的理由：日志系统（ELK、Loki、云日志）都是通过收集容器的 stdout 来工作的。你写文件，日志系统就收不到。

**信号：正确处理 SIGTERM。** `docker stop` 会给主进程发 SIGTERM，期望它优雅退出（保存状态、关闭连接）。但有个经典问题：**如果 CMD 用 shell 形式，主进程是 sh，不是你的程序**：

```dockerfile
# ❌ shell 形式：主进程是 sh，SIGTERM 发给 sh，sh 不转发给 node
CMD node server.js

# ✅ exec 形式：主进程是 node，SIGTERM 直达 node
CMD ["node", "server.js"]
```

用 shell 形式时，`docker stop` 发 SIGTERM 给 sh，sh 默认**不会转发**给子进程 node，导致 node 收不到信号、无法优雅退出，最后被超时强杀（10 秒后 SIGKILL）。这就是为什么**CMD 一律用 exec 形式**（第 04 章 04.9 也强调过）。

**应用层面，Node 里处理 SIGTERM：**

```js
process.on('SIGTERM', () => {
  console.log('收到 SIGTERM，开始优雅退出');
  server.close(() => process.exit(0));   // 关闭连接后再退出
});
```

**验证优雅退出**：`docker stop` 一个处理了 SIGTERM 的容器，日志里能看到"优雅退出"，退出码是 143（SIGTERM）；没处理的，10 秒后被强杀，退出码 137。

> 一句话记住它：**日志往 stdout 打（日志系统靠它收集）；CMD 用 exec 形式让 SIGTERM 直达主进程；应用里处理 SIGTERM 做优雅退出。否则会被超时强杀（137）。**

## 08.10 完整最佳实践清单

**先说结论**：把本章所有点收进一份"上线前自检清单"，一条条过。

```dockerfile
# ✅ 一份"工程化达标"的 Dockerfile 长这样
FROM node:22-alpine AS builder          # 官方镜像 + alpine + 具体版本
WORKDIR /app
COPY package*.json ./                    # 依赖清单先 COPY（缓存）
RUN npm install                          # 构建阶段装 dev 依赖
COPY . .
RUN npm run build                        # 构建产物

FROM node:22-alpine                      # 运行阶段：重新 FROM，最精简
WORKDIR /app
COPY --from=builder /app/dist ./dist     # 多阶段：只拷产物
ENV NODE_ENV=production
USER node                                # 非 root 运行
EXPOSE 3000
CMD ["node", "dist/server.js"]           # exec 形式
```

**上线前自检清单：**

| 项 | 检查点 |
|---|---|
| 基础镜像 | 官方？alpine/slim？具体版本（非 latest）？ |
| 多阶段 | 构建工具没进最终镜像？ |
| 缓存 | 依赖清单先 COPY？install 能缓存？ |
| 层 | 垃圾固在中间层了吗？RUN 合并了吗？ |
| .dockerignore | node_modules/.git/.env 排除了？ |
| 用户 | 切到非 root 了吗？ |
| 信号 | CMD exec 形式？应用处理 SIGTERM？ |
| 日志 | 往 stdout 打？ |
| 密钥 | 没 build 进镜像？ |
| 扫描 | 镜像扫描过漏洞？ |

**配套的示例文件**（见 `examples/docker/08-多阶段构建.Dockerfile`）：

```dockerfile
# ---------- 阶段一：构建（起别名 builder） ----------
FROM node:22 AS builder
WORKDIR /app
COPY package*.json ./
RUN npm install
COPY . .
RUN npm run build

# ---------- 阶段二：运行（最终镜像从这里开始） ----------
FROM node:22-alpine
WORKDIR /app
COPY --from=builder /app/dist ./dist
COPY --from=builder /app/package*.json ./
RUN npm install --omit=dev
ENV NODE_ENV=production
EXPOSE 3000
CMD ["node", "dist/server.js"]
```

> 一句话记住它：**工程化达标 = 官方 alpine 基础镜像 + 多阶段构建 + 缓存友好分层 + .dockerignore + 非 root + exec 形式 CMD + 密钥不进镜像 + 漏洞扫描。这份清单，上线前逐条过。**

## 08.11 本章常见坑速查

| 坑 | 现象 | 原因 | 正确做法 |
|---|---|---|---|
| 镜像 1GB+ | 部署慢、磁盘爆 | 用完整版基础镜像 + dev 依赖全留 | alpine + 多阶段构建 |
| 构建工具进镜像 | 镜像大、攻击面广 | 没做多阶段构建 | 阶段一构建、阶段二只拷产物 |
| 改代码 build 很慢 | 每次 npm install 重跑 | COPY . . 在 install 前 | 依赖清单先 COPY |
| 上下文几百 MB | build 卡在 Sending context | 没写 .dockerignore | 排除 node_modules/.git/.env |
| 容器默认 root | 被攻破后权限大 | 没指定 USER | 最后 USER 切非 root |
| `docker stop` 等 10 秒 | 退出码 137 | shell 形式 CMD，信号不直达 | exec 形式 CMD |
| alpine 程序跑不起来 | 找不到动态库 | 程序依赖 glibc，alpine 是 musl | 换 `-slim` |
| 密钥 build 进镜像 | 密钥泄漏 | 图省事写进 Dockerfile | 运行时注入 |
| 用 latest 上线 | 版本漂移 | latest 会动 | 固定版本 + digest |

## 08.12 本章小结

- **工程化三目标**：小（体积）、快（构建）、安全（攻击面）。
- **多阶段构建**：阶段一构建、阶段二只拷产物；`COPY --from` 跨阶段复制；工具链不进最终镜像。
- **瘦身三板斧**：alpine 基础镜像、多阶段构建、.dockerignore。
- **.dockerignore**：排除 node_modules/.git/.env，减小上下文、防敏感信息泄漏。
- **基础镜像选择**：官方 + 具体版本 + alpine；glibc 不兼容换 slim；静态二进制用 scratch。
- **层数**：该分则分（缓存）、该合则合（不留垃圾），不追求绝对最少。
- **非 root**：最后 `USER` 切非 root，最小权限。
- **安全三件事**：最小权限、镜像扫描（scout）、可信源（固定版本 + digest）。
- **日志与信号**：日志往 stdout；CMD exec 形式让 SIGTERM 直达；应用处理 SIGTERM 优雅退出。

## 08.13 动手练习

**1. 一个 Node 应用的镜像有 1GB，主要可能是什么原因？给出至少两条优化。**

<details><summary>参考答案</summary>

可能原因：用 `node:22` 完整版基础镜像（~1GB）、dev 依赖全装进镜像、没做多阶段构建。

优化：

1. 换 `node:22-alpine`（~130MB）；
2. 多阶段构建，只把 `dist/` 产物和 `--omit=dev` 的生产依赖拷进运行阶段。

</details>

---

**2. 什么是多阶段构建？它解决了什么问题？`COPY --from` 是干什么的？**

<details><summary>参考答案</summary>

多阶段构建：Dockerfile 里写多个 `FROM`，每个 `FROM` 开启一个新阶段；最终镜像只包含最后一个阶段。构建工具（编译器、dev 依赖）只在第一个阶段存在，不进入最终镜像。

它解决"构建工具和运行时依赖不分"导致的镜像臃肿 + 攻击面大。

`COPY --from=builder` 从名为 builder 的**上一个阶段**复制文件到当前阶段。

</details>

---

**3. 为什么容器默认 root 运行不安全？怎么改成非 root？**

<details><summary>参考答案</summary>

root 权限大，应用一旦被攻破（如命令注入），攻击者拿到的是容器里的 root 权限，危害更大。最小权限原则要求用尽可能小的权限运行。

改法：先 root 做完安装，最后 `USER` 切到非 root：

```dockerfile
RUN addgroup -S app && adduser -S app -G app
USER app
CMD ["node", "server.js"]
```

</details>

---

**4. `docker stop` 一个容器要等 10 秒才停，退出码是 137，为什么？怎么改？**

<details><summary>参考答案</summary>

因为 CMD 用了 **shell 形式**（`CMD node server.js`），主进程是 `sh` 不是 node。`docker stop` 发的 SIGTERM 被 sh 接收，sh 不转发给 node，node 没机会优雅退出，10 秒超时后被 SIGKILL 强杀（退出码 137）。

改法：CMD 用 **exec 形式** `CMD ["node", "server.js"]`，让 node 直接是主进程，SIGTERM 直达；应用里再 `process.on('SIGTERM', ...)` 做优雅退出。

</details>

---

**5. 为什么 `.env` 要写进 `.dockerignore`？**

<details><summary>参考答案</summary>

`.env` 里可能有密码、密钥等敏感信息。如果不 ignore，它会被打进构建上下文，甚至被 `COPY . .` 复制进镜像——一旦镜像被推出去或泄漏，密钥就暴露了。这是真实的安全事故来源。

正确做法：`.env` 写进 `.dockerignore`，密钥通过运行时环境变量/secret 管理注入。

</details>

---

**6. 列出"工程化达标"的 Dockerfile 至少 5 条特征。**

<details><summary>参考答案</summary>

任选 5 条：

1. 官方 + alpine/slim + 具体版本（非 latest）基础镜像；
2. 多阶段构建，工具链不进最终镜像；
3. 依赖清单先 COPY，install 可缓存；
4. RUN 合并、装完即清理，垃圾不留中间层；
5. 有 .dockerignore；
6. USER 切非 root；
7. CMD 用 exec 形式；
8. 密钥不 build 进镜像。

</details>
