# 第 00 章 · 设计哲学：把"代码 + 环境"打包成不可变的镜像

> 本章**一个命令都不教你**（`docker run` 都没有）。
> 但读完它，后面每一章"为什么非得这么用"你都能自己想出来。
>
> 本章你需要记住的就一件事：**Docker 解决的从不是"打包代码"，而是"环境不一致"——它把"代码 + 运行它需要的一切"焊死成一个不可变的镜像，做到"我这儿能跑，你那儿就一定能跑"。**

---

## 0.1 先问你一个问题

假设你是一个前端，写好了一个 Node.js 应用。本地跑得好好的，你 `npm run build`、`node server.js`，一切正常。

你把代码打包，交给运维同事，让他部署到服务器。结果对方回你一句：

**"在我这跑不起来，报错。"**

你一看错误截图：

```text
Error: Cannot find module 'some-lib'
    at Module._resolveFilename (...)
```

你心里第一反应是："怎么可能？我 `npm install` 过了啊。" 然后你回他："你 `npm install` 一下试试。" 他照做，跑起来了。

**问题解决了吗？表面上解决了。但你有没有想过——为什么"在你机器上能跑，换台机器就要重新折腾一遍"这件事，几十年来一直存在？**

根源一句话：

> **你的程序从来不是"只依赖你的代码"，它依赖一整套环境：Node 版本、npm 包的版本、系统库、环境变量、甚至操作系统的发行版和它的 glibc 版本。**

而这些"隐形的依赖"，**从来没有被一起打包过**。你交付的只是代码，环境是"对方机器上碰巧有"或"碰巧没有"的东西。

这就是著名的"**在我机器上能跑**（works on my machine）"诅咒。

## 0.2 历史：部署是怎么一步步变难的

要理解 Docker 为什么被创造出来，得先看它之前的人是怎么"部署"的：

| 时代 | 做法 | 痛点 |
|---|---|---|
| 早期 | 直接登服务器，手敲命令装环境、跑程序 | 换台机器重来一遍；几个人部署出几种结果 |
| 虚拟化 | 用 VMware 等装**虚拟机**，每个应用一个完整的"假电脑" | 能隔离了，但**每台虚拟机都要跑一个完整的操作系统**，重、慢、费内存 |
| 配置管理 | Chef / Puppet / Ansible 写脚本自动化装环境 | 解决了"重复劳动"，但**没解决"环境漂移"**——脚本跑两次，环境可能不一样（依赖版本变了） |

你会发现一个规律：**大家一直在"更快地复制环境"，但从没解决"环境本身的一致性问题"。**

- 虚拟机：隔离了，但太重（每个虚机一个完整 OS）。
- 自动化脚本：快了，但不一致（装的时候库的最新版可能已经变了）。

直到 2013 年，一家叫 dotCloud 的公司开源了一个内部工具，它换了个思路。这个工具后来改名叫 **Docker**，那家公司也改名叫 **Docker Inc.**。

## 0.3 Docker 的核心洞察：镜像 = 不可变的构建产物

Docker 的思路，一句话：

> **别在"运行的时候"去装环境了，改成在"构建的时候"就把"代码 + 环境"打包成一个固化的、不可变的产物，叫镜像（image）。运行的时候，只是把这个镜像"点亮"成一个进程。**

这个思路其实一点都不新——**它跟"编译"是一个道理。**

你写 Node 代码，源码是"给人看、给人改"的，但你部署的是 `npm run build` 之后那堆 dist 文件，是"固化"的。你不会在服务器上现改 dist。

Docker 做的，就是把"构建产物"这个概念从"代码"推广到"**整个运行环境**"：

| 类比 | 源码/构建产物 | Docker |
|---|---|---|
| 开发时 | 你写 `src/*.js` | 你写 `Dockerfile`（描述怎么装环境） |
| 构建 | `npm run build` → dist | `docker build` → **镜像** |
| 运行 | `node dist/server.js` | `docker run 镜像` → **容器** |

所以 Docker 有两个最核心的名词，你现在就要分清楚（后面每一章都离不开它俩）：

| 名词 | 是什么 | 类比 | 关键性质 |
|---|---|---|---|
| **镜像（image）** | 构建出来的、只读的、固化的环境 + 代码 | 一个**装好系统的"安装包"** | **不可变**，构建完就不改了 |
| **容器（container）** | 镜像"运行起来"的一个实例 | 安装包**安装后正在运行的那个进程** | 可创建、可销毁，跑的是镜像的一份副本 |

> 一句话记住它：镜像是"类"，容器是"实例"。镜像只读、构建一次到处用；容器是镜像运行出来的、可随时销毁重建的进程。

## 0.4 "不可变"为什么这么重要

Docker 的精髓，全在那个词——**不可变（immutable）**。

**因为镜像不可变，所以"在我机器上能跑"第一次变成了"在任何地方都能跑"：**

- 你 `docker build` 出来的镜像，和你同事 `docker build` 出来的镜像，**只要 Dockerfile 一样，内容就一样**。不再有"你装的是 Node 18，他装的是 Node 20"这种事。
- 你本地 `docker run` 跑通的容器，推到服务器上 `docker run` 同一个镜像，**环境一字不差**。因为环境不是"现场装的"，是"早就焊死在镜像里"的。
- 出了 bug，你不需要"复现对方的环境"——**镜像本身就是环境**。拉下来一跑，bug 原样复现。

"不可变"还带来一个工程上的巨大好处：**回滚变得简单到可怕**。

传统部署，你升级依赖升坏了，要回滚得"把旧版本一个个装回去"。Docker 里，你只需要：

```
把容器指回上一个版本的镜像 → 完成回滚
```

因为旧镜像是**不可变的**，它还在那儿，原封不动，指回去就回去了。

> 一句话记住它：不可变，是"环境一致"和"秒级回滚"的共同前提。镜像一旦构建，就再也不会被"现场修改"污染。

## 0.5 容器 vs 虚拟机：Docker 凭什么更轻

你可能听说过"Docker 也是虚拟化"。对，但它和虚拟机有本质区别，这个区别决定了它为什么快：

```
虚拟机：每个虚机里跑一整个操作系统（Guest OS）
┌──────────────┬──────────────┐
│  App A       │  App B       │
│  Guest OS A  │  Guest OS B  │   ← 每个都带一个完整 OS，重
├──────────────┴──────────────┤
│   Hypervisor（虚拟化软件）    │
├─────────────────────────────┤
│  宿主操作系统（Host OS）      │
└─────────────────────────────┘

容器：共享宿主内核，只隔离"用户空间"
┌──────────────┬──────────────┐
│  App A       │  App B       │
│  + 它的依赖   │  + 它的依赖   │   ← 没有各自的操作系统，轻
├──────────────┴──────────────┤
│  Docker 引擎                  │
├─────────────────────────────┤
│  宿主操作系统（共享同一个内核） │
└─────────────────────────────┘
```

**关键区别**：虚拟机是"硬件级"隔离（每个虚机模拟出一整台电脑），容器是"进程级"隔离（复用宿主的内核，只给每个容器划一块独立的空间）。

所以：

- 容器**秒级启动**（它本质就是启动一个进程），虚拟机要几十秒（要启动一个 OS）。
- 一个宿主能跑**成百上千个容器**，但跑几十个虚拟机就吃力了。
- 容器镜像通常**几十 MB 到几百 MB**，虚拟机镜像动辄几个 GB。

代价也摆在明面上：**容器共享宿主内核，所以隔离性不如虚拟机强**，而且容器里的"系统"必须是和宿主内核兼容的（Linux 容器跑在 Linux 宿主上）。

> 一句话记住它：虚拟机隔离的是"整台电脑"，容器隔离的是"一个进程"。Docker 用"共享内核 + 隔离用户空间"换来了轻和快。

## 0.6 Docker 明确不负责什么

最后讲清楚 Docker **不是**什么，省得拿它当万能药：

| 它不是 | 原因 | 该用什么 |
|---|---|---|
| **虚拟机** | 它共享宿主内核，隔离性弱于虚拟机；也不是"把一台真机完整虚拟出来" | 要强隔离、要跑不同内核，用虚拟机 |
| **性能加速器** | 容器本身不让你代码跑更快，有时还有轻微开销 | 性能优化是代码层的事 |
| **云平台** | Docker 只负责"打包和跑"，不负责"在哪跑、怎么编排几千个容器" | 大规模编排用 Kubernetes / Docker Swarm |
| **数据持久化方案** | 容器默认是"用完即丢"的，数据不特别处理会随容器销毁 | 用卷（volume）或外部数据库 |
| **万能打包工具** | 它最擅长"跑服务/应用"；图形界面、需要内核模块的程序不一定适合容器化 | 先评估你的应用是否适合 |

**Docker 真正负责的只有一件事：把"代码 + 环境"打包成不可变镜像，并在任何有 Docker 的地方一致地运行它。**

它不是万能的，但这一件事，恰好治好了"在我机器上能跑"这个几十年的老毛病。
